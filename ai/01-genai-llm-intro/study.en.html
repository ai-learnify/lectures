Why AI: where if/else ends

Part 1 · What can't if / else do?

Slide 8

Before reading on, try to answer yourself: what kind of problem can't you write in regular C# code, no matter how many conditions you add?

The problem: customers write in plain language

Slide 9

Three realistic messages from the restaurant chat:

  • Nino: “Something light, no meat, for two, under 40 GEL”
  • Giorgi: “Four of us tomorrow at 8, with a kid, by the window if possible”
  • Luka: “I want that thing with the red sauce I got last week, but less spicy”

Try it: how would you turn each one into a call to our API? For Nino the filters isVegetarian=true, maxPrice=40 would still work, but what is “light” — calories? portion size? For Giorgi, “tomorrow at 8” has to become a date and time, and “with a kid” — an extra chair? For Luka we'd have to search past orders and match the “red sauce” to a dish description.

You can't write this with keyword search (Contains("no meat")): the same idea is said in a thousand ways, with typos, slang, in two languages. Regular code expects exact input — human language isn't exact.

✅ Check yourself think first, then open the answer
Why can't we handle natural language with if/else?
The same idea can be phrased in countless ways; the number of rules is endless and they break on every new phrasing.

Regular code vs a language model

Slide 10
C# code LLM
Input exact, structured (dishId, date) any text
Rules we write them the model “learned” them from text
Result deterministic: one input → always the same result probabilistic: one question can get different answers
Error a bug — we find and fix it a convincingly stated falsehood (we'll name it in part 2)

The key idea: an LLM doesn't replace regular code. Adding to the cart, calculating the price, saving a reservation stay in C# — that's where we need precision. We use an LLM where human language has to be “understood” or produced. This whole module is about connecting these two worlds.

📘 Terms
deterministic
the same input always produces the same result
probabilistic
the result contains randomness; one input can produce different results

AI → ML → Deep Learning → GenAI → LLM

These terms are often used as synonyms, but they are actually circles nested inside each other: each one is part of the previous.

Term What it is Example
AI — artificial intelligence The broadest concept: any program that performs a “smart” task. It can be written with ordinary rules (if/else) a chess program, a navigation route
Machine Learning The programmer doesn't write the rules: the program finds them itself from examples a spam filter that has “seen” thousands of labelled emails
Deep Learning ML that uses a multi-layer neural network. That's how it learns complex things: images, sound, language face unlock, speech recognition
GenAI — generative AI Models that don't just recognise things but create new ones images from a description, music, text, code
LLM — large language model GenAI for text: text in → text out. “Large” — billions of parameters and an enormous training text ChatGPT, Gemini, Claude

ChatGPT is all three — AI, Machine Learning and an LLM at once, because the LLM sits inside all the other circles. But not every AI is an LLM: an old chess program is AI but not ML.

In this course we are users of LLMs, not their creators: we don't train models, we call a ready model through an API and connect it to our system. That is how most of the AI engineering profession works.

📘 Terms
AI (artificial intelligence)
any program that performs a “smart” task
Machine Learning
the program finds the rules itself from examples
Deep Learning
Machine Learning with a multi-layer neural network
GenAI
AI that creates new content

For us an LLM = just another HTTP API

Slide 11

For a backend developer an LLM is nothing magical: it's an external service we send an HTTP request to — just like a weather or payment API. Almost all providers use the same format (the so-called OpenAI-compatible API). Above is Gemini's OpenAI-compatible address; a request to OpenAI, Groq or a local Ollama looks almost identical.

Request:

  • model — which model we're asking
  • messages — a list of messages, each with its own role (user, assistant, system — in detail in lecture 2)
  • temperature, max_tokens — parameters, in part 3

Response:

  • choices[0].message.content — the text of the answer
  • finish_reason — why it stopped writing (stop — it finished by itself, length — it hit the limit)
  • usage — how many tokens were spent. This is what we pay for.

We won't write this JSON by hand — in C# a .NET library will do it — we write code in the next lectures. But it's good to know what goes on “under the hood”.

How an LLM works

🎯 After this you can explain what a token is, how the model writes an answer, why it makes things up and why it doesn't remember the previous conversation.

Part 2 · How does an LLM “think”?

Slide 12

First we'll see the big picture — what happens from pressing “Send” to the answer — and then break down, piece by piece, three ideas we'll need throughout the course: the token (what the model “reads”), next-token prediction (how it writes the answer) and the context window (how much it “sees” at once).

The big picture: what happens after “Send”?

Slide 13

Before we go into the details, here's how a language model works in simple terms.

Once, in advance — training. The model “read” trillions of words (books, web pages, code) and learned which word follows which. Companies do this (Google, OpenAI…). We use a ready model.

On every request — 4 steps:

  1. The text is cut into pieces — “Book a table for” → Book · a · table · for. These pieces are called tokens.
  2. The model calculates which piece comes next — it gives every possible piece a probability: two 62%, four 21%, pizza 0.1%…
  3. It picks one and appends it to the text — “Book a table for two”. How “boldly” it picks is decided by Temperature (part 3).
  4. It repeats — what comes after “Book a table for two”? And so on, piece by piece, until it finishes the answer. That's why you see the answer in a chat appear gradually, word by word.

Analogy: a phone keyboard that suggests the next word — only one that has read almost the entire internet.

On the next slides we break down each step: what a token is, how the next token is chosen, why the model makes mistakes and what it sees in one request.

What is a token?

Slide 14

First try to answer yourself: does the model read text by letters, by words, or some other way?

Answer: neither — by tokens. A token is a piece of text: a common word is one token, a rare one splits into several parts, sometimes even into single letters. Each token has its own number (ID), and the model actually sees these numbers.

For the backend a token is the unit of measurement: price, limit (context window) and speed are all counted in tokens.

📘 Terms
token
a piece of text the model reads and writes in
tokenizer
a program that splits text into tokens (and IDs) and back

One idea in two languages — real tokens

Slide 15

Below is the real split by the GPT-4o tokenizer (o200k_base), with real IDs:

Text Tokens Count
Book a table for two Book · a · table · for · two 5
დაჯავშნე მაგიდა ორისთვის (Georgian) დ · აჯ · ავშ · ნ · ე · მაგ · იდა · ო · რის · თვის 10

Notice: a token often includes the leading space (table). The English word is a single token, while Georgian splits into parts — the tokenizer “learned” on the text that is most common on the internet, and there is little Georgian there.

What it means for us: Georgian text is more tokens → more expensive, slower, and less of it fits into the context.

💡

Different models have different tokenizers (Gemini has its own), so the numbers vary from model to model — but the trend is the same. You'll see this yourself in Tiktokenizer.

The model sees only numbers

This is how text reaches the model:

  1. Text — e.g. Book a table for two.
  2. Pieces — the tokenizer cuts the text into tokens: Book · a · table · for · two. A token often includes the leading space.
  3. Vocabulary — the tokenizer has a table where each piece has its own number (ID). GPT-4o's vocabulary has ~200 000 pieces; table = 3293.
  4. Only numbers go into the model — [6904, 261, 3293, 395, 1920]. The model also returns its answer as numbers, and the tokenizer turns them back into text.

How does the model “know” what 3293 means? Inside the model each number maps to a vector — hundreds of numbers that, during training, “arranged themselves” so that tokens with similar meanings are close together. We'll come back to this idea in lecture 9 (embeddings) — RAG is built on it.

📘 Terms
tokenizer
a program that cuts text into tokens and turns them into numbers (and back)
vocabulary
the tokenizer's table: piece → number (ID)

Next-token prediction — the whole secret of an LLM

Slide 17

An LLM does one thing: it knows which token comes next. More precisely, based on the text it calculates a probability for every possible token.

The loop looks like this:

  1. Input — the model receives a sequence of tokens: Book a table for
  2. Probabilities — it calculates which token comes next: two — 62%, four — 21%, tonight — 9%, pizza — 0.1%… (illustrative numbers)
  3. Choice — it picks one (how — that's decided by Temperature, part 3)
  4. Repeat — it appends the chosen token to the text and runs the whole loop again: Book a table for two → next token → …
  5. End — when the model picks a special “end” token, or hits the limit (max_tokens)

That's all. Chat, writing code, translation — everything happens through this one loop. The model's “thinking” and “knowledge” are “written” into these probabilities: while training on an enormous text it learned what follows what.

Backend takeaway: every token is one full run of the model. That's why a 500-token answer is noticeably slower and more expensive than a 50-token one. It's also why the answer in ChatGPT “appears gradually” — that's streaming (lecture 6).

📘 Terms
next-token prediction
predicting the next token: the core mechanism of an LLM
probability distribution
the list of all possible tokens with their probabilities; they add up to 100%

🎮 Try it yourself · Be the LLM

Slide 18

The sentence: “Tomorrow evening I'd like a table ___”

First write one word yourself, then ask 3–4 friends the same. The result is almost always like this: most write “for two”, some “for four” or “by the window”, and nobody writes “banana”.

That is exactly a probability distribution. While training on text, the model saw that a sentence like this is most often followed by “for two”, so its probability is high. “Banana” is grammatically possible but almost never occurs — its probability is close to zero.

An important detail: not everyone writes the same thing, yet every answer is “normal”. The model is the same: one question has several valid continuations, and which one it picks is decided by Temperature.

Where the model “knows” things from — and when it lies

Slide 19

A model is created in two stages:

  1. Pre-training — on an enormous text (internet, books, code) it learns to guess the next token. The result: a model that “convincingly continues” any text, but isn't an assistant yet — it might “continue” a question with ten more questions.
  2. Fine-tuning (and RLHF) — extra training on dialogues and human ratings: it learns to follow instructions and behave like an assistant. That's how it becomes a “chat” model.

Knowledge cutoff — the training data goes up to a certain date. The model doesn't know what happened after it. And most importantly: our restaurant's menu, prices and free tables it has never seen.

Hallucination — when the model doesn't know the answer, it still writes the most “likely” text. “Khinkali 1.20 ₾” sounds convincing because there are many such sentences on the internet — but it's not our price. The model isn't lying on purpose: its goal is likely text, not true text.

The fix (the main theme of the course): we don't make the model answer from memory, we give it our data — with a tool (lecture 4: the model calls our GetMenu() method) or with RAG (lecture 11: we find the relevant document and put it in the prompt).

⚠️

A rule that applies throughout the course: prices, stock, reservations, money — never from the model's memory. Such data always comes from our database.

📘 Terms
pre-training
the main training on a large text: guessing the next token
fine-tuning
additional training for a specific behaviour (e.g. assistant dialogue)
knowledge cutoff
the date up to which the model's training data reaches
hallucination
convincingly stated but wrong or made-up information

Context window — what the model “sees” in one request

Slide 20

The context window is the maximum number of tokens the model processes in one request — input and output together. With modern models this ranges from tens of thousands of tokens to a million (the exact number is in the model's documentation).

What goes into it (the bar on the slide):

  • System — instructions for the model (“You are a restaurant assistant…”)
  • Chat history — previous questions and answers
  • Data — the menu, documents, tool results
  • Question — the user's latest message
  • Answer — what the model will write

The model has no memory (stateless). This is the most common misunderstanding. In ChatGPT it looks as if the model “remembers” the conversation — in reality, on every new message the app sends the whole history again. We'll have to do the same: if we don't send the history, the model doesn't know what we were talking about. We'll see this in code in lecture 2, and learn to store the history in PostgreSQL in lecture 7.

Backend takeaways:

  • a long history = more tokens on every request = more money
  • the history will eventually hit the limit — managing it (compressing, selecting) is our job
  • the model sees only what we put into this request
📘 Terms
context window
the maximum number of tokens in one request (input + output)
stateless
a system that doesn't remember previous requests; every request is independent

Why is the same text more expensive in Georgian than in English?

The model named the price of our dish. Why don't we trust it?

Parameters: Temperature, Top-P, Max Tokens

🎯 After this you'll choose parameters for the task and know when a reasoning model is needed.

Part 3 · Which token will it pick?

Slide 22

We know that at every step the model gets a list of probabilities. Now we'll see which parameters control the choice and the length of the answer — they appear in every API request.

🎛️ Temperature and Top-P — live

Slide 23

This slide uses the real formula: the model gives each token a “score” (logit), and the probabilities are calculated like this — each score is divided by Temperature and then turned into a probability with softmax.

  • Temperature ↓ (towards 0) → the distribution gets sharper: the most likely option wins (“for two”). At 0 — almost always the same.
  • Temperature ↑ (towards 2) → the distribution gets flatter: weak options (“banana”) also get a chance.
  • Top-P — in the list sorted by probability, it keeps the most likely options until their sum reaches P; it cuts the rest (shown in grey).

🎲 Pick 10 times — picks exactly like the model does: randomly, with these probabilities. Try Temperature 0, 0.7 and 2.

When to use what: one correct answer (extracting a date, classification) → 0; chat → ~0.7; creative text → 1+. We usually don't change Top-P and Temperature together.

💡

The starting probabilities are illustrative; the formula is real.

📘 Terms
logit
the model's “score” for each token before it becomes a probability
softmax
the formula that turns scores into probabilities (adding up to 100%)

Max Tokens — where to stop

Slide 24

Max Tokens (max_tokens, max_output_tokens, in C# MaxOutputTokens) limits how many tokens the model may write in the answer. When it reaches the limit, writing simply stops — even mid-word or mid-sentence.

Why we need it:

  • 💸 Cost limit — output tokens are the most expensive; the limit guarantees one request won't “grow out of control”.
  • ⏱️ Time limit — a short answer arrives quickly.
  • 🐛 Protection from odd behaviour — sometimes a model repeats the same thing endlessly; the limit stops it.

How do we know whether it was cut off? The response has finish_reason:

Value Means
stop the model finished by itself — the normal case
length it hit Max Tokens — the answer is cut off
⚠️

If the limit is too low, the user gets a cut-off sentence. That's why the backend should always check finish_reason == length (log it, or raise the limit). We'll see this in code in lecture 2.

One project — different parameters

Slide 25

In RestaurantApi the LLM will do several different jobs, and each needs its own parameters:

Task Temperature Max Tokens Why
Detecting the message type (order / reservation / question) 0 ~10 one correct answer; one word
“Four of us tomorrow at 8” → date, time, party size 0 ~100 exact data extraction (lecture 3: structured output)
Chat with a customer, recommendations 0.5–0.8 ~300 natural tone, but no fantasy
Description of a new dish for the menu 0.9–1.2 ~200 creative text

The numbers are a guide, not a law — the right values are found by experiment (lectures 12 and 20: evaluation/evals).

The key point: a parameter belongs to an individual request. The same model is called with 0 in one endpoint and with 0.8 in another.

💡

An exception — reasoning models. The table is about regular models. Gemini 3 “thinks” before answering, and Google recommends leaving Temperature at the default (1.0) — at low values quality may drop. We use Gemini, so in code (lecture 2) we mostly don't change Temperature. An exact shape (e.g. JSON) is protected not by Temperature but by structured output (lecture 3).

Reasoning models — they think first, then answer

A regular model starts writing the answer right away. A reasoning model first writes an internal “thought” — step-by-step reasoning (so-called reasoning or thinking tokens) — and only then the final answer. It's still next-token prediction; the model is simply trained to “think out loud” before answering.

When it's worth it: multi-step tasks — “8 guests, 2 children, the terrace is taken, which tables should we combine?”, calculations, combining complex rules, planning an agent's actions.

What it costs:

  • 💸 Money — reasoning tokens are billed (usually as output tokens), even if you don't show them to the user; some providers don't show them at all, only the count in usage.
  • 🐢 Time — several seconds or more may pass before the answer.
  • 🎛️ Parameters — some reasoning models don't accept Temperature, but have a “how much to think” parameter instead (e.g. reasoning effort).

Rule: for a simple question (“How much is khinkali?”, “Open on Sunday?”) a reasoning model is wasted money. Real systems often use two models: a fast, cheap one for most requests, and a reasoning one only for the hard ones.

❓ Check yourself · part 3

✅ Check yourself think first, then open the answer
We extract the date and party size from a customer's message. Which Temperature would you set?
On a regular model — 0 (or very low): there is one correct answer and we want the same result every time. On Gemini 3 (reasoning) — the default 1.0; the shape is protected by structured output (lecture 3).
The answer stops mid-word. What happened and where do you see it?
The model hit the Max Tokens limit. The response has finish_reason = length (in C# ChatFinishReason.Length).
Would you use a reasoning model for the menu FAQ bot (“Open on Sunday?”)?
No. The question is simple; a reasoning model is slow and we pay for thinking tokens too. A fast, cheap model is entirely enough.
How is Top-P different from Temperature?
Temperature changes the shape of the distribution (sharp ↔ flat), while Top-P cuts weak tokens: it keeps the most likely ones until their sum reaches P.

Part 4 · Who, where and how much?

Slide 26

The model has to run on someone's server — in the provider's cloud or on our own computer. The choice affects price, speed, quality and data security.

Providers — whose model, whose server

Slide 27
Provider Models What stands out
OpenAI GPT, reasoning models The most widely used API. Others adopted its request/response format (“OpenAI-compatible”)
Anthropic Claude Strong at code, long documents, agentic tasks
Google Gemini Large context window, text + images + audio; has a free tier
Groq Open models (Llama, Qwen, etc.) Custom chips, very fast answers; free tier for learning
Ollama Open models, on your computer Free, offline, data never leaves the computer
Others Azure OpenAI, Mistral, DeepSeek… Most offer an OpenAI-compatible endpoint

An open (open-weight) model means the model's “weights” (learned parameters) are public: anyone can download it and run it on their own server or computer. A closed model (GPT, Claude, Gemini) can only be called through the provider's API.

💡

Specific model versions and names change month by month, so we don't memorise them in this lecture. We always check the current list in the provider's documentation.

Cloud API or a local model?

☁️ Cloud 💻 Local (Ollama)

Price — we pay per token, and not equally

Slide 28

Providers list prices per 1 million tokens (sometimes per 1000), and count three things separately:

  • 📥 Input — everything we send: system instructions, chat history, data, the question. Relatively cheap.
  • 📤 Output — what the model writes. Usually several times more expensive than input, because each output token is a separate run of the model. A reasoning model's “thinking” tokens are billed as output too.
  • ♻️ Cached input — if many requests share the same beginning (e.g. a long system prompt), some providers bill its repetition cheaply.

Google Gemini prices (November 2026, per 1M tokens):

Model Input / 1M Output / 1M
⚡ Gemini 3.8 Flash — our model, fast and cheap $0.75 $3.75
🧠 Gemini 3.1 Pro — strong, for complex tasks $2.00 $12.00

The Flash price is an introductory one until December 31, 2026; from January 1, 2027 — $1.50 / $7.50. Even within one provider prices differ several times, and between providers — tenfold or more. That's why “the smartest model for everything” is often a bad decision.

⚠️

Prices change often. For a real cost estimate always open the provider's pricing page — you'll do this in the homework.

🎮 What will an AI assistant cost the restaurant?

Slide 29

Given: 300 conversations a day; 2 000 input and 300 output tokens each; 30 days. Prices per 1M tokens (Google, November 2026): ⚡ Gemini 3.8 Flash — $0.75 / $3.75, 🧠 Gemini 3.1 Pro — $2 / $12.

First calculate it yourself, then check with the calculator on the slide (it's public — use it at home too).

Solution:

  1. input: 300 × 2 000 × 30 = 18M tokens; output: 300 × 300 × 30 = 2.7M
  2. ⚡ Gemini 3.8 Flash: 18 × 0.75 + 2.7 × 3.75 = ≈ $23.6 per month (from 2027, at $1.50 / $7.50 — ≈ $47.3)
  3. 🧠 Gemini 3.1 Pro: 18 × 2 + 2.7 × 12 = ≈ $68.4 per month — almost 3 times more

Something to think about: because of Georgian, tokens ×1.5 → cost ×1.5 too. The chat history is sent again with every new message (stateless!) — input grows fast (lecture 7). A reasoning model increases output with thinking tokens.

All terms of the lecture

Terms

deterministic
the same input always produces the same result
probabilistic
the result contains randomness; one input can produce different results
AI (artificial intelligence)
any program that performs a “smart” task
Machine Learning
the program finds the rules itself from examples
Deep Learning
Machine Learning with a multi-layer neural network
GenAI
AI that creates new content
LLM
large language model: text in, text out
token
a piece of text the model reads and writes in
tokenizer
a program that splits text into tokens (and IDs) and back
vocabulary
the tokenizer's table: piece → number (ID)
next-token prediction
predicting the next token: the core mechanism of an LLM
probability distribution
the list of all possible tokens with their probabilities; they add up to 100%
pre-training
the main training on a large text: guessing the next token
fine-tuning
additional training for a specific behaviour (e.g. assistant dialogue)
knowledge cutoff
the date up to which the model's training data reaches
hallucination
convincingly stated but wrong or made-up information
context window
the maximum number of tokens in one request (input + output)
stateless
a system that doesn't remember previous requests; every request is independent
logit
the model's “score” for each token before it becomes a probability
softmax
the formula that turns scores into probabilities (adding up to 100%)
