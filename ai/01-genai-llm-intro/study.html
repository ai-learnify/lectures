შესავალი Generative AI-სა და LLM API-ებში

🎯 ამ ლექციის შემდეგ შეძლებ

  • ახსნა, რას ააწყობ მოდულში, რას შეძლებ მის ბოლოს და ვინ გახდები
  • ახსნა, როგორ ქმნის LLM ტექსტს: ტოკენები, next-token prediction, context window
  • Temperature-ის, Top-P-ის და Max Tokens-ის შერჩევა ამოცანის მიხედვით
  • პროვაიდერის არჩევა და თვის ხარჯის დათვლა ტოკენებით

⚡ მთავარი

  1. მოდულის ბოლოს შენს API-ში იქნება აგენტი: მოდელი წყვეტს, რა გააკეთოს, აკეთებს კი შენი C# კოდი.
  2. მოდელი ტექსტს ტოკენებად კითხულობს. ტოკენებით ითვლება ფასი, ლიმიტი და სიჩქარე. ქართული ტექსტი მეტ ტოკენს იკავებს.
  3. მოდელი წერს ყველაზე სავარაუდოს და არა ჭეშმარიტს. ფასი, მარაგი და ჯავშანი მხოლოდ ბაზიდან მოდის.
  4. მოდელს წინა მოთხოვნა არ ახსოვს: ისტორიას ყოველ ჯერზე ჩვენ ვუგზავნით, და მასშიც ვიხდით.
  5. Temperature-ს, Max Tokens-ს და მოდელს ამოცანის მიხედვით ვირჩევთ, ხარჯს კი წინასწარ ვითვლით.

📍 ლექცია გააცდინე?

  1. ნახე პრეზენტაცია: სლაიდები ლექციის მთელ გზას აჩვენებს
  2. წაიკითხე თემები: ~4 წთ, თითოს ბოლოს „შეამოწმე თავი“
  3. გაიარე ტესტი: 8 კითხვა
  4. გააკეთე დავალებები

1

რას ააწყობ ამ მოდულში

▶ სლაიდები 1–7

აქამდე AI-ს იყენებდი. ამ მოდულში მას საკუთარ სისტემაში ჩააშენებ: შენი API-დან გამოიძახებ, შენს მონაცემს მიაწვდი და შენს C# მეთოდებს გამოაძახებინებ.

მოდულის ბოლოს RestaurantApi-ში კლიენტი წერს: „რამე მსუბუქი, ხორცის გარეშე, ორისთვის. და ხვალ 8-ზე მაგიდა“. აგენტი მენიუს ბაზაში ეძებს, მაგიდას შენი მეთოდით ჯავშნის, ოპერაციამდე თანხმობას ეკითხება და თავს იცავს მოტყუებისგან.

ეტაპი რას შეძლებ
ლექციები 1–3 მოდელთან საუბარი C#-იდან, პასუხი C# ობიექტად
ლექციები 4–8 მოდელი შენს C# კოდს იძახებს; streaming, ისტორია, ხარჯი
ლექციები 9–12 პასუხი შენი მონაცემით (embeddings, pgvector, RAG)
ლექციები 13–18 აგენტები, MCP, რამდენიმე აგენტი ერთად
ლექციები 19–24 დაცვა, შეფასება და საფინალო პროექტი
✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
ვინ ასრულებს მოქმედებას (ჯავშანს, კალათაში დამატებას), მოდელი თუ ჩვენი კოდი?
ჩვენი C# კოდი. მოდელი მხოლოდ წყვეტს და ითხოვს, რომელი მეთოდი გამოიძახოს.
2

სად მთავრდება if / else

▶ სლაიდები 8–11

კლიენტები ჩვეულებრივი ენით წერენ: „ხვალ 8-ზე ოთხნი ვიქნებით, ბავშვიც გვყავს, ფანჯარასთან თუ შეიძლება“. ასეთ ტექსტს if-ებით ვერ დაამუშავებ: ერთსა და იმავეს ადამიანები ათასნაირად წერენ.

C# კოდი LLM
შეყვანა ზუსტი (dishId, date) ნებისმიერი ტექსტი
შედეგი ერთი შეყვანა → ყოველთვის ერთი შედეგი ერთ კითხვაზე შეიძლება სხვადასხვა პასუხი მოვიდეს
შეცდომა bug, რომელსაც ვასწორებთ დამაჯერებლად ნათქვამი სიცრუე

LLM ჩვეულებრივ კოდს არ ცვლის. ფასის დათვლა და ჯავშნის შენახვა C#-ში რჩება. LLM ადამიანის ენას „იგებს“, და ამ ორს ვაერთებთ.

ჩვენთვის LLM კიდევ ერთი HTTP API-ა: POST-ით ვაგზავნით messages-ს და ვიღებთ პასუხის ტექსტს, finish_reason-ს და usage-ს (რამდენი ტოკენი დაიხარჯა).

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
რომელი ამოცანა სჯობს დარჩეს C#-ში და რომელი გადავცეთ LLM-ს: ფასდაკლების დათვლა თუ კლიენტის შეტყობინების გაგება?
ფასდაკლება C#-ში, რადგან სიზუსტე გვჭირდება. შეტყობინების გაგება LLM-ს, რადგან ეს ადამიანის ენაა.

ტოკენები

▶ სლაიდები 12–16

მოდელი ტექსტს არც ასოებად კითხულობს და არც სიტყვებად, არამედ ტოკენებად: ტექსტის ნაჭრებად, რომლებსაც ნომერი აქვს. ხშირი სიტყვა ერთი ტოკენია, იშვიათი რამდენიმე ნაწილად იშლება.

როგორ წერს პასუხს

▶ სლაიდები 17–20

მოდელი ერთ საქმეს აკეთებს: გამოიცნობს შემდეგ ტოკენს. ითვლის ალბათობებს (two 62%, four 21%, pizza 0.1%…), ირჩევს ერთს, უმატებს ტექსტს და იმეორებს, სანამ არ დაასრულებს.

აქედან ორი მთავარი დასკვნა:

  1. Hallucination. მოდელი წერს სავარაუდოს და არა ჭეშმარიტს. ჩვენი მენიუ და ფასები მას არასდროს უნახავს, ამიტომ შეიძლება დამაჯერებლად მოიგონოს. ფაქტებს მას ჩვენ ვაწვდით ბაზიდან.
  2. Stateless. მოდელს წინა მოთხოვნა არ ახსოვს. ChatGPT-ში ჩანს, რომ „ახსოვს“, მაგრამ სინამდვილეში აპლიკაცია ყოველ ჯერზე მთელ ისტორიას თავიდან უგზავნის.

Context window არის ტოკენების მაქსიმუმი ერთ მოთხოვნაში: ინსტრუქცია + ისტორია + მონაცემები + კითხვა + პასუხი. რაც აქ არ ჩავსვით, მოდელი ვერ „ხედავს“.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
პირველ მოთხოვნაში დავწერეთ „ჩემი სახელია ნინო“, მეორე ცალკე მოთხოვნაში „რა მქვია?“. რას უპასუხებს?
არ იცის, რადგან მოდელი stateless-ია. უნდა გავუგზავნოთ წინა შეტყობინებებიც.
მოდელმა თქვა: „ხინკალი ჩვენთან 1.20 ₾ ღირს“. რატომ არ ვენდობით?
ჩვენი მენიუ არ უნახავს და სავარაუდო რიცხვი დაწერა (hallucination). ფასი ყოველთვის ბაზიდან.
📘 ტერმინები
hallucination
დამაჯერებლად დაწერილი, მაგრამ არასწორი ინფორმაცია
context window
ტოკენების მაქსიმუმი ერთ მოთხოვნაში (შემავალი + გამომავალი)
stateless
წინა მოთხოვნები არ ახსოვს; ყოველი მოთხოვნა დამოუკიდებელია

Temperature და Max Tokens

▶ სლაიდები 22–25
  • Temperature წყვეტს, რამდენად „გაბედულად“ ირჩევს მოდელი ტოკენს. 0-ზე თითქმის ყოველთვის ყველაზე სავარაუდოს ირჩევს, 2-ზე სუსტ ვარიანტებსაც („ბანანი“).
  • Top-P სუსტ ვარიანტებს საერთოდ ჭრის.
  • Max Tokens პასუხის სიგრძეს ზღუდავს. ლიმიტზე პასუხი მოიჭრება და finish_reason იქნება length.
ამოცანა Temperature
ტექსტიდან მონაცემის ამოღება (თარიღი, სტუმრები) ~0
ჩატი კლიენტთან ~0.7
კერძის აღწერა რეკლამისთვის ~1+

პარამეტრი ცალკეულ მოთხოვნას ეკუთვნის: ერთ endpoint-ში 0, მეორეში 0.7.

💡

Gemini 3 პასუხამდე „ფიქრობს“ (reasoning მოდელია), და Google ურჩევს, Temperature ნაგულისხმევზე (1.0) დავტოვოთ. ამიტომ ლექცია 2-დან მას ძირითადად არ ვცვლით.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
finish_reason: "length". რას ნიშნავს?
პასუხი Max Tokens-ის ლიმიტზე მოიჭრა და დაუმთავრებელია.
