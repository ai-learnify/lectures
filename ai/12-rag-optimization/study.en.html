RAG Optimization and Evaluation

🎯 After this lecture you can

  • You'll explain where RAG fails (retrieval vs generation), put together a golden set and calculate hit@3 and MRR with /evaluation/retrieval
  • You'll build hybrid search: the vector + PostgreSQL full-text (tsvector, 'english'), merged with RRF, and prove the improvement with a number
  • You'll add metadata filtering in SQL and explain why it's also a security matter
  • You'll compare chunking strategies and reranking, and evaluate the answer's groundedness with GroundednessEvaluator

⚡ Key points

  1. RAG fails in two places: retrieval (most often) and the answer. We do not check a change "by eye"; we measure it.
  2. Golden set = questions plus a phrase that must be found. hit@3 and MRR tell us how good retrieval is.
  3. Hybrid search = vector (meaning) + full-text (exact words), combined with RRF.
  4. Filters (category, branch, permissions) live in SQL, before the model. It is a security matter.
  5. Groundedness checks whether the answer relies on the sources (LLM-as-judge). We check the judge too.

Measuring

▶ Slides 6–9

"Sometimes it finds the wrong thing" is not a number. We reduced the chunk size from 800 to 400: did it get better? To know, we have to measure.

Golden set: questions for which we know what must be found. We mark the right chunk with a phrase, not an Id, because Ids change when chunking changes.

  • hit@3: the share of questions where the right chunk is in the top three
  • MRR: how high it ranks: 1st place = 1, 2nd = ½, 3rd = ⅓, not found = 0, averaged
golden.json
[  { "question": "How do I cancel a booking?",   "mustContain": "24 hours before" },  { "question": "I'm allergic to nuts",         "mustContain": "walnut" },  { "question": "Can I bring a dog?",           "mustContain": "terrace" },  { "question": "Where is hall B-2?",           "mustContain": "B-2" },  { "question": "Can I bring my own cake?",     "mustContain": "15 GEL" },  { "question": "Service charge for 6 people?", "mustContain": "12%" }]

[HttpPost("retrieval")]public async Task<IActionResult> Retrieval(bool hybrid = true, CancellationToken ct = default){    string json = await System.IO.File.ReadAllTextAsync("golden.json", ct);   // ControllerBase.File is something else    List<GoldenItem> golden = JsonSerializer.Deserialize<List<GoldenItem>>(json, JsonSerializerOptions.Web)!;     int hits = 0;    double reciprocalRanks = 0;    List<string> misses = [];     foreach (GoldenItem item in golden)    {        List<ChunkMatch> found = hybrid            ? await _search.SearchAsync(item.Question, null, ct)            : await _search.VectorSearchAsync(item.Question, ct);           // lecture 11's search         int rank = found.FindIndex(c => c.Content.Contains(item.MustContain)) + 1;   // 1, 2, 3… or 0         if (rank is >= 1 and <= 3) hits++;        else misses.Add(item.Question);         if (rank > 0) reciprocalRanks += 1.0 / rank;    }     return Ok(new RetrievalReport(        HitAt3: (double)hits / golden.Count,        Mrr: reciprocalRanks / golden.Count,        Misses: misses));}
💡

/evaluation/retrieval does not call the LLM, only the embedding model. It is cheap and fast, so run it after every change.

Better retrieval

▶ Slides 10–13

A vector finds meaning ("without meat" → lobio) but struggles with exact words: "B-2", "15 GEL", "12%". PostgreSQL's full-text search looks for exact words. We use both and merge the results with RRF (by rank, because the scores are on different scales).

PostgreSQL computes the full-text column itself:

Ai/Documents/DocumentSearch.cs · OrQuery
private static string OrQuery(string query){    var words = Regex.Matches(query, @"[\p{L}\p{N}]+(?:-[\p{L}\p{N}]+)*").Select(m => m.Value);    return string.Join(" | ", words);   // "Where is hall B-2?" → "Where | is | hall | B-2"}
Ai/Documents/DocumentSearch.cs · SearchAsync (hybrid)
// hybrid: by meaning + by words, merged with RRFpublic async Task<List<ChunkMatch>> SearchAsync(string query, string? category, CancellationToken ct){    var queryVector = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingInput.Query(query), cancellationToken: ct));    var words = EF.Functions.ToTsQuery("english", OrQuery(query));     // metadata filtering — always in SQL, before the search    IQueryable<Chunk> chunks = _db.Chunks;    if (category is not null)        chunks = chunks.Where(c => c.Document.Category == category);     List<int> byMeaning = await chunks                                 // by vector, with a threshold        .Where(c => 1 - c.Embedding!.CosineDistance(queryVector) >= _minScore)        .OrderBy(c => c.Embedding!.CosineDistance(queryVector))        .Select(c => c.Id)        .Take(20)        .ToListAsync(ct);     List<int> byWords = await chunks                                   // by words        .Where(c => c.SearchVector.Matches(words))        .OrderByDescending(c => c.SearchVector.Rank(words))        .Select(c => c.Id)        .Take(20)        .ToListAsync(ct);     List<int> top = Rrf(byMeaning, byWords).Take(5).ToList();     var found = await _db.Chunks        .Where(c => top.Contains(c.Id))        .Select(c => new { c.Id, c.Document.FileName, c.Page, c.Content })        .ToDictionaryAsync(c => c.Id, ct);     return top        .Select((id, i) => new ChunkMatch(found[id].FileName, found[id].Page, found[id].Content,            Score: 1.0 / (i + 1)))                                     // Score — here simply by rank        .ToList();} private static IEnumerable<int> Rrf(params List<int>[] lists) => lists    .SelectMany(list => list.Select((id, i) => (id, score: 1.0 / (60 + i + 1))))    .GroupBy(x => x.id)    .OrderByDescending(g => g.Sum(x => x.score))    .Select(g => g.Key);

Chunking and the answer

▶ Slides 15–18

Chunking. By size (simplest), by paragraph/heading (the topic is not cut), recursively or by meaning. Most often, cutting by heading and attaching the heading to the chunk helps. Only measurement tells which is better: 300 characters is not "more precise"; it often loses context.

Reranking. Search is fast but coarse: it scores the question and the chunk separately. A reranker reads the candidates (e.g. 20) together with the question and ranks them precisely. It is slow, so it only sees the candidates.

Groundedness. The chunk is right, but did the model make something up? A second model (the judge) checks whether the answer relies on the sources:

Controllers/EvaluationController.cs · Groundedness
using Microsoft.Extensions.AI.Evaluation;using Microsoft.Extensions.AI.Evaluation.Quality; IEvaluator evaluator = new GroundednessEvaluator(); EvaluationResult result = await evaluator.EvaluateAsync(    [new ChatMessage(ChatRole.User, request.Question)],      // what was asked    response,                                                // what our RAG answered (ChatResponse)    new ChatConfiguration(_judge),                           // the judge — an IChatClient    [new GroundednessEvaluatorContext(context)],             // the sources the model received    ct); NumericMetric score = result.Get<NumericMetric>(GroundednessEvaluator.GroundednessMetricName);// score.Value — from 1 to 5; score.Reason — the judge's explanation
✅ Check yourself think first, then open the answer
Why don't we fully trust the judge?
It is a model too and can be wrong. We check its scores on a few known good and bad answers.
📘 Terms
reranker (cross-encoder)
a model that scores the question and the chunk together; precise but slow
groundedness
how far the answer relies only on the given sources
LLM-as-judge
a model that evaluates another model's answer
