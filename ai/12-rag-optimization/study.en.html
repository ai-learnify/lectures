✅ Check yourself think first, then open the answer
Why don't we put the whole PDF into the context, and why don't we train the model (fine-tuning)?
The whole PDF — thousands of tokens on every question, slow, a large document doesn't fit, “lost in the middle” · fine-tuning — expensive, again on every change, it memorizes facts badly and can't name the source
What are RAG's two pipelines, and when does each one run?
ingestion — once, on upload: PDF → text → parts → vectors → database · query — on every question: vector → top 5 → prompt → an answer with a source
Why do we cut a document into parts, and what do we need the overlap for?
The vector of a whole document is the “average” of everything — blurry; a part = one idea, a precise vector and a cheap context · the overlap — the last sentence in the next part too, so an idea isn't cut at the boundary
Why do we need a threshold in RAG's search?
A search always finds something · without a threshold, for “a borscht recipe” the model would get 5 meaningless parts and might make something up · with a threshold — 0 parts and “I don't have information”
Why do we store the original question in the chat history and not the message with the sources (augmented)?
The sources are only for this request — others will be found next time · storing them in the history would inflate every message with 5 parts (the budget, lecture 7)

Measuring RAG: golden set, hit@k, MRR

🎯 After this You'll put together a golden set and measure the quality of the search with a number.

Part 1 · A number instead of “I think”

Slide 6

First we see where RAG can make a mistake. Then — the golden set and two numbers that measure the quality of the search. Finally we calculate these numbers in code.

The problem: “sometimes” isn't a number

Slide 7

In lecture 11's homework we made a table: “6 out of 8 are correct”. That's already a number — and that's exactly what we need, systematically. RAG fails in two places:

Where What happens Example
Retrieval (search) the right part didn't make it into the top 5 “Hall B-2?” — the vector found parts about “halls” in general, but not B-2's page
Generation (answer) the part is right, but the model added something in the source: “cake — 15 GEL”; in the answer: “cake — 15 GEL, candles are free”

In practice retrieval errors are the most common: if the right part wasn't found, even the best model can't answer. That's why we measure the search first.

Why don't we check “by eye”? We change the chunk size from 800 to 400. It got better on two questions, worse on one. On eight questions? On forty? A change — a prompt, the chunk size, the search method — always improves something and breaks something. Only a number tells us what happened overall. Real teams work this way too: first we measure, then we change, then we measure again.

📘 Terms
Retrieval
the search part: finding the parts relevant to a question
Generation
the answer part: the model writes the answer with the found parts
Evaluation (evals)
measuring a system's quality on examples prepared in advance

The golden set and two numbers: hit@k and MRR

Slide 8

A golden set — a set of questions for which we know what should be found. We put it together by hand, once, and run it after every change. A good golden set resembles real questions: ordinary ones, with a synonym, with an exact number/name, with the answer in two places, and also something that isn't in the document. Lecture 11's homework table is its first version.

For each question we write a phrase that must appear in the right part (“24 hours before”, “B-2”). Why a phrase and not the chunk's Id? When we change the chunking, the parts are cut again and the Ids change — but the golden set must stay. A phrase works with any chunking strategy.

hit@k — on what share of the questions the right part was in the first k. In the table: on 4 out of 6 it's in the top three → hit@3 = 0.67. For RAG this is the main number: if the right part didn't get into the context, the model can't answer.

MRR (Mean Reciprocal Rank) — the average of 1 / rank (0 if not found). In first place — 1, second — ½, third — ⅓. It measures how high the right part is:

(1 + 1 + ½ + 0 + ⅓ + ⅕) / 6 = 3.03 / 6 ≈ 0.51

Your number depends on your data. Two systems can have the same hit@3 but a different MRR: in one the right part is always first, in the other — third.

📘 Terms
Golden set
a set of questions with a known right answer; for measuring quality
hit@k
on what share of the questions the right result landed in the first k
MRR (Mean Reciprocal Rank)
the average of 1/rank of the right result; how high the right one is

Slide 9

The golden set — a JSON file in the project (golden.json, “Copy to Output Directory” or in the project folder):

golden.json
[  { "question": "How do I cancel a booking?",   "mustContain": "24 hours before" },  { "question": "I'm allergic to nuts",         "mustContain": "walnut" },  { "question": "Can I bring a dog?",           "mustContain": "terrace" },  { "question": "Where is hall B-2?",           "mustContain": "B-2" },  { "question": "Can I bring my own cake?",     "mustContain": "15 GEL" },  { "question": "Service charge for 6 people?", "mustContain": "12%" }]
Controllers/AiLabController.cs · EvalRag
public record GoldenItem(string Question, string MustContain); [HttpPost("rag/eval")]public async Task<IActionResult> EvalRag(CancellationToken ct){    string json = await System.IO.File.ReadAllTextAsync("golden.json", ct);   // ControllerBase.File is something else    var golden = JsonSerializer.Deserialize<List<GoldenItem>>(json, JsonSerializerOptions.Web)!;     int hits = 0; double rr = 0; List<string> misses = [];    foreach (GoldenItem item in golden)    {        List<FoundChunk> found = await SearchChunksAsync(item.Question, ct);         // lecture 11's search        int rank = found.FindIndex(c => c.Content.Contains(item.MustContain)) + 1;   // 1, 2, 3… or 0         if (rank is >= 1 and <= 3) hits++; else misses.Add(item.Question);        if (rank > 0) rr += 1.0 / rank;    }     return Ok(new { HitAt3 = (double)hits / golden.Count,                    Mrr = rr / golden.Count, Misses = misses });}
  • System.IO.File — in a controller File(...) is the method for returning a file, so the full namespace.
  • JsonSerializerOptions.Web — camelCase and case-insensitive (question ↔ Question).
  • FindIndex(...) + 1 — the rank from 1; if not found, -1 + 1 = 0.
  • misses — on which questions it didn't find it. This matters more than the number: the misses show what needs fixing.

In our example both misses are exact words: “B-2” and “12%”. The vector looks for meaning — “hall”, “service” — and “doesn't see” a code or a number. That's part 2's topic.

💡

/rag/eval doesn't call the LLM — only the embedding (the question's vector). It's cheap and fast: you can run it on every change. In lecture 22 the same evaluation becomes a test: if hit@3 drops below a threshold, the build fails.

Hybrid search and metadata filtering

🎯 After this You'll add full-text to the vector, merge them with RRF and filter the search by metadata.

Part 2 · Meaning + the exact word

Slide 10

Exact words are hard for a vector. PostgreSQL has full-text search, which looks exactly for words. We merge the two lists with RRF — this is hybrid search. Then — metadata filtering: searching only in the documents that this question is about.

Hybrid search: vector + full-text

Slide 11

The vector finds meaning: “without meat” → lobio. But exact words — codes, numbers, names (“B-2”, “12%”, “SKU-1234”) — “dissolve” in a vector: an embedding stores the idea, not the exact letters. Search by words works the other way round: it finds “B-2” exactly, but not “without meat”. In lecture 9 we said: “we don't throw LIKE away — we complement it”. Hybrid search runs both searches together and merges the results.

PostgreSQL's full-text search — much stronger than LIKE:

  • tsvector — the text, split into words (lexemes): to_tsvector('english', 'Hall B-2 seats 20+ guests') → 'hall' 'b-2' 'b' '2' 'seat' '20' 'guest'.
  • tsquery — the query: 'b-2' | 'hall' (| — or, & — and).
  • @@ — whether it matches; ts_rank — how well (how many words, how many times).
  • The GIN index — a fast search by words.

The configuration: 'english'. Our documents are in English, and PostgreSQL has a dictionary and a stemmer for English: 'english' turns “guests” into “guest”, “rooms” into “room”, and throws away stop words (is, the, where…). The query must be processed with the same configuration (ToTsQuery("english", …)), otherwise “guests” ≠ “guest”. For Georgian there's no such dictionary — Georgian text uses 'simple': a word is stored as it is, and the vector covers the grammatical forms (“დარბაზი” / “დარბაზში” — hall / in the hall).

RRF (Reciprocal Rank Fusion) — merging two lists by rank:

score(chunk) = Σ 1 / (60 + rank) — in each list where the part was found.

A part that's high in both lists comes first. Why the rank and not the scores? The vector's score (0.3–0.8) and ts_rank (0.01–0.1) are in different “units” — adding them up makes no sense. The rank is the same everywhere: 1, 2, 3. 60 is the standard constant (from the original RRF study): it softens the difference between the top places.

📘 Terms
Hybrid search
searching by meaning (vector) and by words (full-text) together, merging the results
tsvector / tsquery
PostgreSQL's full-text: the text as words / a query with words
'english' / 'simple'
a full-text configuration: with the English dictionary and stemmer / without a dictionary (a word as it is)
RRF (Reciprocal Rank Fusion)
merging several lists by rank: Σ 1/(60 + rank)

Hybrid search in code

Slide 12

1. The full-text column. DocumentChunk gets a tsvector column that PostgreSQL calculates by itself from Content (a generated column), and a GIN index:

Data/DocumentChunk.cs
using NpgsqlTypes;// ...public NpgsqlTsVector SearchVector { get; set; } = null!;
Data/AppDbContext.cs · OnModelCreating
modelBuilder.Entity<DocumentChunk>()    .HasGeneratedTsVectorColumn(c => c.SearchVector, "english", c => new { c.Content })    .HasIndex(c => c.SearchVector)    .HasMethod("GIN");

After the migration the old parts get a SearchVector too — a generated column is calculated on every row. We don't need to upload again.

2. The query with words. plainto_tsquery joins the words with “and”: “Where is hall B-2” would only find the part that has all the words — on a natural question often 0 results. We join them with “or”, and ts_rank puts the one with more matches higher:

Controllers/AiLabController.cs · OrQuery
private static string OrQuery(string q){    var words = Regex.Matches(q, @"[\p{L}\p{N}]+(?:-[\p{L}\p{N}]+)*").Select(m => m.Value);    return string.Join(" | ", words);   // "Where is hall B-2?" → "Where | is | hall | B-2"}

The regex takes words and numbers, keeps hyphenated ones together (“B-2”), and throws away punctuation (otherwise to_tsquery would return a syntax error).

3. Two lists and RRF:

Controllers/AiLabController.cs · HybridSearchAsync
private async Task<List<FoundChunk>> HybridSearchAsync(string q, CancellationToken ct){    float minScore = _config.GetValue<float>("Rag:MinScore");    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));    var words = EF.Functions.ToTsQuery("english", OrQuery(q));     List<int> byMeaning = await _db.DocumentChunks                    // by vector, with a threshold        .Where(c => 1 - c.Embedding!.CosineDistance(query) >= minScore)        .OrderBy(c => c.Embedding!.CosineDistance(query))        .Select(c => c.Id).Take(20).ToListAsync(ct);     List<int> byWords = await _db.DocumentChunks                      // by words        .Where(c => c.SearchVector.Matches(words))        .OrderByDescending(c => c.SearchVector.Rank(words))        .Select(c => c.Id).Take(20).ToListAsync(ct);     List<int> top = Rrf(byMeaning, byWords).Take(5).ToList();     var chunks = await _db.DocumentChunks        .Where(c => top.Contains(c.Id))        .Select(c => new { c.Id, c.Document.FileName, c.Page, c.Content })        .ToDictionaryAsync(c => c.Id, ct);    return top.Select((id, i) => new FoundChunk(chunks[id].FileName, chunks[id].Page,        chunks[id].Content, Score: 1.0 / (i + 1))).ToList();        // Score — here simply by rank} private static IEnumerable<int> Rrf(params List<int>[] lists) => lists    .SelectMany(l => l.Select((id, i) => (id, s: 1.0 / (60 + i + 1))))    .GroupBy(x => x.id)    .OrderByDescending(g => g.Sum(x => x.s))    .Select(g => g.Key);
  • The threshold is only on the vector list: a full-text match is “evidence” in itself (the word really is written there). Both empty → 0 parts → “I don't have information”, as in lecture 11.
  • 20 + 20 → 5. We take more candidates from each list, and after RRF — 5 for the context.
  • The last query loads the parts by Id; we keep top's order (WHERE IN doesn't preserve order).
  • In /chat and /rag/eval, HybridSearchAsync instead of SearchChunksAsync. Measure again.

The result (sample): hit@3 0.67 → 0.83, MRR 0.51 → 0.72. “B-2” got fixed. “Service charge for 6 people?” — still a miss: the document says “for 5+ people — 12%”. Neither the word (“6”) nor the meaning matches exactly — this is the limit of search. For a question like this, reranking or a tool that calculates the rule in code is better.

📘 Terms
Generated column
a column that PostgreSQL calculates by itself from other columns
GIN index
PostgreSQL's index for words (and for arrays, jsonb)

Metadata filtering: searching only in the documents we need

Slide 13

Metadata — information about a document, not in its text: the category, the branch, the language, the date it's valid from, who can see it. Document gets a column (e.g. Category), filled in on upload, and the search filters first, then searches:

Data/Document.cs
public string Category { get; set; } = "rules";   // "rules" / "menu" / "events"
Controllers/AiLabController.cs · HybridSearchAsync(q, category)
IQueryable<DocumentChunk> chunks = _db.DocumentChunks;if (category is not null)    chunks = chunks.Where(c => c.Document.Category == category); // byMeaning and byWords — from chunks:List<int> byMeaning = await chunks    .Where(c => 1 - c.Embedding!.CosineDistance(query) >= minScore)    // ... as before

Lecture 10's homework “filter + meaning in one SQL query” — this is exactly it.

Two reasons:

  1. Quality. “Prices” — are written both in the old menu PDF and in the event prices. If the question is about an event, the other category is just noise.
  2. Security. In a system that holds the documents of many clients (tenants), a filter by TenantId is mandatory. “Don't show someone else's document” in the prompt isn't enough — the model doesn't always obey the prompt, and if someone else's part got into the context, it has already “leaked”. The filter is always in SQL, before the model.

Where does the category come from? Simply — from the user interface (the chat's “topic”) or an endpoint parameter. Cleverly — the model classifies the question (structured output, lecture 2) or an agent chooses (lecture 15).

⚠️

Lecture 10's 🔬: HNSW + WHERE on a large table can return fewer results through “overfiltering”. In pgvector 0.8+: SET hnsw.iterative_scan = relaxed_order;. At our scale the planner picks a seq scan and you don't see it.

📘 Terms
Metadata
data about a document (category, tenant, language, date, permissions), not its text
Metadata filtering
filtering the parts by metadata before the search
Tenant
one client (company) in a system used by many clients

Chunking, reranking and groundedness

🎯 After this You'll compare chunking strategies, explain reranking and evaluate the answer's groundedness.

Part 3 · Cutting and the answer

Slide 15

Four chunking strategies and how to choose (by measuring). Reranking — a second, precise layer of the search. And evaluating the answer: groundedness — whether the model relied only on the sources.

Chunking strategies

Slide 16
Strategy How Plus Minus
By size (fixed) every N characters/tokens, with an overlap the simplest cuts a sentence and an idea in the middle
By sentences / recursive first by paragraph, then by sentence, then by word — until it fits the size natural boundaries; our lecture 11 version doesn't see the boundary of a topic
By headings (heading-aware / structure-aware) a part = a section; the heading is attached to the part topics don't get mixed; the heading is strong context needs structure (Word styles, Markdown); recognizing a heading in a PDF is hard
By meaning (semantic) compares the vectors of consecutive sentences and cuts where the similarity drops finds the topic boundary by itself an embedding for every sentence — expensive; studies show it isn't always better than the simple one

The heading in the prefix. Lecture 9's document format: title: … | text: …. In lecture 11 we wrote the file name as the title. When cutting by headings — the section's heading: title: Cancelling a booking | text: …. The part's vector now “knows” the topic too, even if the word “booking” isn't written in the text. This is one of the cheapest and most effective improvements.

How to choose — only by measuring. A change → upload the documents again (vectors on the new parts) → /rag/eval. On the sample: by headings 0.92; 300-character parts — worse (0.75): the parts are too small and lose context. “Smaller = more precise” doesn't always work — that's why we measure.

The golden set survives a change in chunking, because it checks by a phrase (“24 hours before”), not by Id — part 1's decision pays off here.

📘 Terms
Recursive chunking
first by a big boundary (paragraph), then a smaller one (sentence, word), until the part fits the size
Heading-aware chunking
cutting by the document's sections; the heading is attached to the part
Semantic chunking
cutting where the meaning of consecutive sentences changes

Reranking: a second, precise layer of the search

Slide 17

Our search (vector and full-text) is fast but “rough”: the embedding model sees the question and the part separately. The part's vector was calculated at ingestion — it knew nothing about the question. A model like this is called a bi-encoder.

A reranker (usually a cross-encoder) reads the question and the part together and returns one number: how well this part answers this question. This is much more precise — “service charge for 6 people?” ↔ “for 5+ people — 12%” is an obvious pair for a reranker. But you can't calculate anything in advance: on every question every pair needs a separate computation.

So, two layers: the fast search picks 20–50 candidates → the reranker sorts them precisely and 5 go into the context. You can't run a reranker on a million parts — but you can on 20.

What options there are:

How Cost
A rerank API — Cohere Rerank, Voyage, Jina HTTP: a question + 20 texts → 20 scores a separate key and account; a price per request; +100–300 ms
An LLM as the reranker we ask Gemini: “sort these 20 parts by relevance” — structured output (lecture 2) the chat model's price — expensive; slow (seconds)
A local cross-encoder an open model (e.g. bge-reranker) on your own server GPU/CPU, infrastructure

The Gemini API has no separate rerank model. We're on Gemini, so in the lecture we explain reranking, and the code is in the ⭐ (LLM-rerank). In real systems reranking often gives the biggest jump in hit@3 — at the price of cost and latency. And again: measure whether it's worth it.

📘 Terms
Bi-encoder
a model that turns the question and the document into vectors separately (embedding)
Cross-encoder (reranker)
a model that reads the question and the document together and returns a relevance number
Reranking
re-sorting the search candidates precisely

Groundedness: does the answer rely on the sources?

Slide 18

In part 1 we measured the search. The second place where RAG fails is the answer: the part is right, but the model added something. Groundedness — how much the answer relies only on the given sources.

You can't measure this with Contains: “15 GEL” could also be “fifteen lari”. So — LLM-as-judge: we give another (or the same) model the question, the sources and the answer, and ask: “is everything written in the answer from the sources?”

Microsoft.Extensions.AI.Evaluation.Quality — ready-made evaluators on Microsoft.Extensions.AI: GroundednessEvaluator, RelevanceEvaluator, CompletenessEvaluator, RetrievalEvaluator and others. The judge is any IChatClient (Gemini for us):

Controllers/AiLabController.cs · CheckGroundedness
using Microsoft.Extensions.AI.Evaluation;using Microsoft.Extensions.AI.Evaluation.Quality; IEvaluator evaluator = new GroundednessEvaluator(); EvaluationResult result = await evaluator.EvaluateAsync(    [new ChatMessage(ChatRole.User, question)],                       // what was asked    response,                                                          // what our RAG answered (ChatResponse)    new ChatConfiguration(_judge),                                     // the judge — an IChatClient    [new GroundednessEvaluatorContext(BuildContext(sources))],         // the sources the model received    ct); NumericMetric g = result.Get<NumericMetric>(GroundednessEvaluator.GroundednessMetricName);// g.Value — from 1 to 5; g.Reason — the judge's explanation
  • _judge — an IChatClient for the judge. The judge doesn't need the chat pipeline's client with tools and middleware (lectures 4–5, 8) — a separate, simple client (a keyed service, lecture 8's ⭐) or a stronger model is better.
  • The number 1–5: 5 — everything is in the source; 1 — the answer doesn't rely on the sources. In Reason the judge writes what the model added.

We check the judge too. An LLM-as-judge is a model itself: it can be wrong, and it sometimes rates its “own” answers (the same model) more softly. So: (1) as the judge — the same or a stronger model; (2) we look at the number over many examples, not one; (3) from time to time we compare the judge's rating with a manual one.

The cost. Every evaluation is one LLM call. hit@k (part 1) is free and runs on every change; groundedness — on the golden set's answers, from time to time.

In which two places does RAG fail, and which one is more common?
retrieval — the right part didn't get into the top k (the most common; then even the best model can't answer) · generation — the part is right, but the model added something that isn't in the source
What are hit@3 and MRR? Why do we write a phrase in the golden set and not the chunk's Id?
hit@3 — on what share of the questions the right part was in the top three · MRR — the average 1/rank, how high it is · when the chunking changes the Ids change, the phrase doesn't
Why do we need hybrid search, and why do we merge the lists by rank (RRF) and not by scores?
the vector finds exact words (a code, a number, a name) badly, full-text finds them exactly · the scores are in different “units”, the rank is the same everywhere: Σ 1/(60 + rank)
Why must metadata filtering be in SQL and not in the prompt?
the model doesn't always obey the prompt; if someone else's part got into the context, it has already leaked · a tenant/permissions filter is security, before the model
What is groundedness and how do we measure it? Why don't we trust the judge completely?
does the answer rely only on the sources? · LLM-as-judge: GroundednessEvaluator, 1–5 and an explanation · the judge is a model too — it makes mistakes and rates its own answers softly; on many examples and manually from time to time

Summary

Slide 21
  • RAG fails in two places: in the search (the right part wasn't found — the most common) and in the answer (the model added something). We can't tell “by eye” whether it improved — we measure.
  • Golden set — questions with a phrase that must appear in the right part (not by Id — it survives the chunking). hit@3 — on what share the right one was in the top three; MRR — the average 1/rank; misses — what to fix. /rag/eval doesn't call the LLM — it's cheap.
  • Hybrid search: the vector (meaning) + PostgreSQL full-text (tsvector, 'english' — a stemmer and stop words; exact words, codes, numbers), merged with RRF: Σ 1/(60 + rank).
  • Metadata filtering: the category, tenant, language, date, permissions — in SQL, before the model. Both quality and security.
  • Chunking: by size / by sentences / by headings / by meaning. The heading in the prefix — cheap and effective. A smaller part isn't always better — measure.
  • Reranking: a fast search picks 20 candidates, a cross-encoder sorts them precisely and 5 go into the context. The cost and the latency — measure whether it's worth it.
  • Groundedness: GroundednessEvaluator (Microsoft.Extensions.AI.Evaluation.Quality) — LLM-as-judge, 1–5 and an explanation. We check the judge too.

All terms of the lecture

Terms

Retrieval
the search part: finding the parts relevant to a question
Generation
the answer part: the model writes the answer with the found parts
Evaluation (evals)
measuring a system's quality on examples prepared in advance
Golden set
a set of questions with a known right answer; for measuring quality
hit@k
on what share of the questions the right result landed in the first k
MRR (Mean Reciprocal Rank)
the average of 1/rank of the right result; how high the right one is
Hybrid search
searching by meaning (vector) and by words (full-text) together, merging the results
tsvector / tsquery
PostgreSQL's full-text: the text as words / a query with words
'english' / 'simple'
a full-text configuration: with the English dictionary and stemmer / without a dictionary (a word as it is)
RRF (Reciprocal Rank Fusion)
merging several lists by rank: Σ 1/(60 + rank)
Generated column
a column that PostgreSQL calculates by itself from other columns
GIN index
PostgreSQL's index for words (and for arrays, jsonb)
Metadata
data about a document (category, tenant, language, date, permissions), not its text
Metadata filtering
filtering the parts by metadata before the search
Tenant
one client (company) in a system used by many clients
Recursive chunking
first by a big boundary (paragraph), then a smaller one (sentence, word), until the part fits the size
Heading-aware chunking
cutting by the document's sections; the heading is attached to the part
Semantic chunking
cutting where the meaning of consecutive sentences changes
Bi-encoder
a model that turns the question and the document into vectors separately (embedding)
Cross-encoder (reranker)
a model that reads the question and the document together and returns a relevance number
Reranking
re-sorting the search candidates precisely
Groundedness
how much the answer relies only on the given sources
LLM-as-judge
a model that evaluates another model's answer
Microsoft.Extensions.AI.Evaluation
.NET libraries for evaluating the quality of AI answers
