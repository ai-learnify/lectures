Let's recall: Text Embeddings: Vectorizing Text

1Why doesn't LIKE find the lobio for “without meat”, and what does an embedding do differently?LIKE looks for words, and those words aren't in the description · an embedding turns the text into a vector where a similar meaning is close — regardless of language and words
2How is an embedding model different from a chat model? Which one do we use and at what size?It doesn't write text — it returns one vector, and only the input is charged · IEmbeddingGenerator · gemini-embedding-2, 768 dimensions
3Why can't we “just” change the model if vectors are already stored?Every model (and size) has its own “map” — vectors from different models can't be compared · changing the model = calculating every vector again
4What is a task prefix, and why do the question and the document have different ones?Asymmetric search: a short “wish” ↔ long “facts” · task: search result | query: … and title: … | text: … · always by the same rule
5What does cosine similarity measure, and how do we read the number?The angle between two vectors: 1 — the same direction, 0 — nothing in common · the number depends on the model — we compare and sort, we don't judge it on its own

Today's topic

PostgreSQL pgvector and EF Core

🤔Why you need this

Lecture 9's vectors are in memory: they disappear on restart, and the search compares every dish one by one. In a real system vectors are stored in the database and the search runs with an index. Today we teach PostgreSQL to “understand” vectors with pgvector, store and search them with EF Core, and create an HNSW index. This is the storage for RAG (lecture 11).

03
⚡ Exact vs approximate search

HNSW: a floor-by-floor path to the closest

📖
Without an indexEvery row, every vector — exact, but O(n)
🛗
HNSW = a graph with floorsAt the top — few points, long jumps. At the bottom — all of them, short steps
🎯
Approximate (ANN)Very fast, but it can occasionally miss a correct one
🙋 Is a 1% error acceptablein a restaurant menu? In bank transactions?
💡 In a restaurant — yes: the second-best dish is a good answer too. In a bank — no: ANN isn't used there
🧑‍💻 We write · the HNSW index and EXPLAIN

The index with one migration

Data/DataContext.cs · OnModelCreatingmodelBuilder.Entity<Product>()    .HasIndex(p => p.Embedding)    .HasMethod("hnsw")    .HasOperators("vector_cosine_ops");
SET enable_seqscan = off; -- only for the test EXPLAIN SELECT "Name" FROM "Products" ORDER BY "Embedding" <=> '[0.02, …]' LIMIT 3; Limit -> Index Scan using "IX_Products_Embedding" Order By: ("Embedding" <=> '…')
⚠️
Operator = search functionvector_cosine_ops ↔ CosineDistance. With another function the index isn't used
🙋 On 20 dishes PostgreSQL does not use the index. Why?
🧮
The planner calculatesReading 20 rows is cheaper than the index. The index pays off on thousands of rows

5 questions

1What three problems do vectors kept in memory have?They disappear on restart — everything is calculated again · the search compares everything one by one (O(n)) · the data is in two places — the description changes, the vector stays old
2What does <=> measure, and why do we sort ascending?cosine distance = 1 − similarity · 0 — the same direction · a small distance = close, so ORDER BY distance ASC · score 0.71 → distance 0.29
3Why does Product also store EmbeddingModel?One model — one map · when the model changes we know which vectors need recalculating · indexing calculates only those (and the nulls)
4What does it mean that HNSW is approximate? What is recall?ANN — it doesn't compare everything, it searches a graph by “floors”; very fast, but it can occasionally miss a correct one · recall — what share of the exact search results it found
5You created an HNSW index, but EXPLAIN shows a Seq Scan. Two possible reasons?The operator doesn't match the search (vector_l2_ops vs CosineDistance) · the table is small — a seq scan is cheaper for the planner, that's normal
