PostgreSQL pgvector და EF Core

ლექციის სრული მასალა თავებად, ~16 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. pgvector PostgreSQL-ს vector(768) სვეტს და მანძილის ოპერატორებს უმატებს; Docker-ში pgvector/pgvector იმავე ვერსიით.
  2. <=> — cosine distance = 1 − similarity: პატარა = ახლოს, ORDER BY distance ზრდადობით.
  3. EF Core: Pgvector.EntityFrameworkCore, UseVector(), HasPostgresExtension("vector"), Vector? Embedding + EmbeddingModel, migration.
  4. ინდექსაცია მხოლოდ გადასათვლელს ითვლის; ძებნა: OrderBy(CosineDistance).Take(3) — დალაგება ბაზაში ხდება.
  5. HNSW — მიახლოებითი (ANN), სწრაფი ინდექსი; ოპერატორი (vector_cosine_ops) ძებნის ფუნქციას უნდა ემთხვეოდეს; EXPLAIN-ით მოწმდება. ერთ PostgreSQL-ში — EF Core, ცალკე store-ზე — VectorData.

პრობლემა: ვექტორები მეხსიერებაში

სლაიდი 7

ლექცია 9-ში ვექტორები MenuIndex Singleton-ში ინახებოდა. ამას სამი პრობლემა აქვს:

  1. რესტარტზე ქრება. ყოველ deploy-ზე მთელი მენიუ თავიდან უნდა გაიგზავნოს embedding მოდელთან — ფული და დრო.
  2. ყველას სათითაოდ ვადარებთ. 200 კერძზე ეს მილიწამებია. მილიონ დოკუმენტზე ყოველი შეკითხვა წამებს წაიღებს, და ყველა ვექტორი მეხსიერებაში უნდა ეტეოდეს.
  3. ორი ადგილი, ერთი მონაცემი. კერძი ბაზაშია, მისი ვექტორი — მეხსიერებაში. თუ აღწერა შეიცვალა, ვექტორი ძველი რჩება, და ამას არავინ ამჩნევს.

ვექტორული ბაზა (vector database) ინახავს ვექტორებს და სწრაფად პოულობს მოცემულ ვექტორთან ყველაზე ახლოს მყოფებს. არსებობს ცალკე ვექტორული ბაზები (Qdrant, Pinecone, Weaviate, Milvus), მაგრამ ჩვენ უკვე გვაქვს PostgreSQL. მისი გაფართოება pgvector ჩვეულებრივ ცხრილს ვექტორის სვეტს უმატებს: კერძი და მისი ვექტორი ერთ ხაზზე, ერთ ტრანზაქციაში, ერთი backup-ით.

Docker-ში ცვლილება ერთი ხაზია: PostgreSQL-ის image-ის ნაცვლად ვიღებთ იმავე ვერსიის image-ს, რომელშიც pgvector უკვე დაყენებულია:

docker-compose.yml

PostgreSQL-ის გაფართოება: vector ტიპი, მანძილის ოპერატორები და ვექტორული ინდექსები

pgvector: vector ტიპი და მანძილის ოპერატორები

სლაიდი 8

pgvector PostgreSQL-ს ორ რამეს უმატებს:

1. სვეტის ტიპი vector(n) — n რიცხვის (float4) მასივი. ჩვენი ვექტორი 768 რიცხვია, ამიტომ vector(768). ზომა სვეტშივე იწერება: 3072-იან ვექტორს ბაზა არ ჩაწერს — შეცდომას დააბრუნებს. ეს კარგია: ლექცია 9-ის „ერთი მოდელი, ერთი რუკა“ ბაზის დონეზე მოწმდება.

sql
CREATE EXTENSION IF NOT EXISTS vector;ALTER TABLE "Products" ADD COLUMN "Embedding" vector(768);

2. მანძილის ოპერატორები:

ოპერატორი რას ზომავს როდის
<=> cosine distance = 1 − cosine similarity ტექსტის embedding-ები — ჩვენი
<-> L2 (ევკლიდური) — „სწორი ხაზით“ მანძილი ნორმალიზებულ ვექტორებზე იგივე რიგს იძლევა
<#> უარყოფითი dot product ნორმალიზებულ ვექტორებზე ყველაზე სწრაფი

ყურადღება: distance, არა similarity. ლექცია 9-ში ვზომავდით მსგავსებას (1 — ძალიან მსგავსი). pgvector ზომავს მანძილს (0 — ერთი და იგივე). კავშირი მარტივია: distance = 1 − similarity. score 0.71 → distance 0.29. ამიტომ ძებნაში ORDER BY distance ზრდადობით — პატარა მანძილი პირველია.

ძებნა SQL-ში — უბრალოდ დალაგება მანძილით და პირველი სამი:

sql
SELECT "Name", "Embedding" <=> @q AS distanceFROM "Products"ORDER BY distanceLIMIT 3;

@q — შეკითხვის ვექტორი, რომელსაც C#-ში ვითვლით (ლექცია 9-ის EmbeddingText.Query) და პარამეტრად ვაგზავნით.

[HttpGet("menu/search")]public async Task<IActionResult> SearchMenu(string q, CancellationToken ct){    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));     var top = await _db.Products        .Where(p => p.Embedding != null)        .OrderBy(p => p.Embedding!.CosineDistance(query))       // → ORDER BY "Embedding" <=> @query        .Select(p => new { p.Name, Distance = p.Embedding!.CosineDistance(query) })        .Take(3)                                                  // → LIMIT 3        .ToListAsync(ct);     return Ok(top.Select(x => new { x.Name, Score = 1 - x.Distance }));   // distance → similarity}
  • CosineDistance(query) — Pgvector.EntityFrameworkCore-ის ფუნქცია; SQL-ში <=> ხდება. დალაგება და LIMIT ბაზაში სრულდება — C#-ში მხოლოდ 3 ხაზი მოდის.
  • Score = 1 - Distance — ლექცია 9-ის score-ს ვაბრუნებთ, რომ საშინაოს ზღვარი (MinScore) არ შეიცვალოს.

ლოგში (Microsoft.EntityFrameworkCore.Database.Command) ნახავ SQL-ს: ORDER BY p."Embedding" <=> @query LIMIT @p.

HNSW ინდექსი და VectorData

🎯 ამის შემდეგ: HNSW ინდექსს შექმნი, EXPLAIN-ით შეამოწმებ და აირჩევ EF Core-სა და VectorData-ს შორის.

ნაწილი 3 · ვექტორული ინდექსი

სლაიდი 13

ინდექსის გარეშე ბაზა ძებნისას ყველა ხაზს კითხულობს. ვნახავთ, როგორ მუშაობს მიახლოებითი ძებნა (HNSW), როგორ შევქმნათ ინდექსი EF Core-ით და როგორ შევამოწმოთ EXPLAIN-ით. ბოლოს ვპასუხობთ ლექცია 9-ის კითხვას: გვჭირდება თუ არა Microsoft.Extensions.VectorData.

ზუსტი vs მიახლოებითი ძებნა: HNSW

სლაიდი 14

ინდექსის გარეშე ბაზა ORDER BY distance-ზე ყველა ხაზს კითხულობს და ყველა ვექტორთან მანძილს ითვლის (sequential scan). შედეგი ზუსტია, მაგრამ დრო ხაზების რაოდენობის პროპორციულია: O(n). B-tree ინდექსი აქ ვერ შველის — ის „ტოლობას“ და „მეტ/ნაკლებს“ ეძებს, არა „ყველაზე ახლოს მყოფს“ 768-განზომილებიან სივრცეში.

ვექტორული ინდექსი ამიტომ მიახლოებითია — ANN (approximate nearest neighbor): ძალიან სწრაფად პოულობს „თითქმის ყოველთვის“ სწორ მეზობლებს. pgvector-ს ორი ასეთი ინდექსი აქვს: HNSW და IVFFlat. ჩვენ HNSW-ს ვიყენებთ — უფრო ზუსტი და სწრაფია, და ცარიელ ცხრილზეც შეიძლება შეიქმნას.

HNSW (Hierarchical Navigable Small World) — „სართულიანი გრაფი“:

  • ყველა ვექტორი სართულ 0-ზეა, დაკავშირებული უახლოეს მეზობლებთან (გრაფი).
  • ზედა სართულებზე ცოტა ვექტორია, შორი კავშირებით — „ექსპრეს ხაზი“.
  • ძებნა იწყება ზემოდან: დიდი ნახტომებით სწორ „უბანში“ მივდივართ, მერე ქვედა სართულზე ვეშვებით და მოკლე ნაბიჯებით უახლოესს ვპოულობთ.

ანალოგია: ქალაქის მისამართის ძებნა — ჯერ მაგისტრალი (სწორი რაიონი), მერე ქუჩა, მერე სახლი. ყველა სახლის შემოვლა არ გვჭირდება.

ფასი — recall. ANN-მა იშვიათად შეიძლება ერთი სწორი მეზობელი გამოტოვოს. recall — რა წილი იპოვა ზუსტი ძებნის შედეგებიდან (მაგ. 0.98 = 100-დან 98). ძებნის ხარისხს hnsw.ef_search პარამეტრი არეგულირებს (ნაგულისხმევად 40): მეტი — ზუსტი, მაგრამ ნელი. ტექსტის ძებნაში და RAG-ში ეს ნორმალურია: „მეორე საუკეთესო“ კერძიც კარგი პასუხია. სადაც ზუსტი შედეგია აუცილებელი (ფინანსები, აუდიტი), ANN არ გამოიყენება.
