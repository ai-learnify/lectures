A vector in the database: pgvector

🎯 After this You'll explain what a vector database is, and use pgvector's type and operators in SQL.

Part 1 · A vector in the database

Slide 6

First we see what problem vectors kept in memory have. Then the idea of a vector database and pgvector: how a vector is stored in a PostgreSQL column and how we search with SQL.

The problem: vectors in memory

Slide 7

In lecture 9 the vectors were kept in the MenuIndex Singleton. This has three problems:

  1. It disappears on restart. On every deploy the whole menu has to be sent to the embedding model again — money and time.
  2. We compare everything one by one. On 200 dishes this is milliseconds. On a million documents every question takes seconds, and every vector has to fit in memory.
  3. Two places, one piece of data. The dish is in the database, its vector is in memory. If the description changes, the vector stays old, and nobody notices.

A vector database stores vectors and quickly finds the ones closest to a given vector. There are dedicated vector databases (Qdrant, Pinecone, Weaviate, Milvus), but we already have PostgreSQL. Its extension pgvector adds a vector column to an ordinary table: the dish and its vector on one row, in one transaction, with one backup.

In Docker the change is one line: instead of the PostgreSQL image we take the image of the same version that already has pgvector installed:

docker-compose.yml
services:  db:    image: pgvector/pgvector:pg17   # before: postgres:17 — keep the same version!
⚠️

The version (pg17, pg16…) must match your old image. An image of a different major version can't read the old volume's data.

📘 Terms
Vector database
a database that stores vectors and quickly finds the ones closest to each other
pgvector
a PostgreSQL extension: the vector type, distance operators and vector indexes

pgvector: the vector type and the distance operators

Slide 8

pgvector adds two things to PostgreSQL:

1. The column type vector(n) — an array of n numbers (float4). Our vector is 768 numbers, so vector(768). The size is written in the column itself: the database won't store a 3072-long vector — it returns an error. That's good: lecture 9's “one model, one map” is checked at the database level.

sql
CREATE EXTENSION IF NOT EXISTS vector;ALTER TABLE "Products" ADD COLUMN "Embedding" vector(768);

2. The distance operators:

Operator What it measures When
<=> cosine distance = 1 − cosine similarity text embeddings — ours
<-> L2 (Euclidean) — the “straight line” distance gives the same order on normalized vectors
<#> negative dot product the fastest on normalized vectors

Careful: distance, not similarity. In lecture 9 we measured similarity (1 — very similar). pgvector measures distance (0 — the same thing). The link is simple: distance = 1 − similarity. Score 0.71 → distance 0.29. So in the search ORDER BY distance is ascending — the smallest distance comes first.

A search in SQL — just sorting by distance and taking the first three:

sql
SELECT "Name", "Embedding" <=> @q AS distanceFROM "Products"ORDER BY distanceLIMIT 3;

@q — the question's vector, which we calculate in C# (lecture 9's EmbeddingText.Query) and send as a parameter.

📘 Terms
vector(n)
pgvector's column type: a vector of n numbers
Cosine distance
1 − cosine similarity; 0 — the same direction. In pgvector: <=>
L2 distance
the Euclidean, “straight line” distance. In pgvector: <->

Part 2 · EF Core and the vector

Slide 9

We don't need to write SQL by hand: EF Core has a pgvector package. We add a vector column to Product, create a migration, indexing writes the vectors to the database, and the search is written in LINQ.

EF Core: configuration and the migration

Slide 10

1. NuGet: Pgvector.EntityFrameworkCore — pgvector's types and functions for EF Core (on Npgsql).

2. Registration — we add UseVector() to UseNpgsql, so that Npgsql knows the vector type:

Program.cs
builder.Services.AddDbContext<AppDbContext>(o =>    o.UseNpgsql(connectionString, npgsql => npgsql.UseVector()));

3. The extension — the migration should create CREATE EXTENSION vector by itself:

Data/AppDbContext.cs · OnModelCreating
modelBuilder.HasPostgresExtension("vector");

4. Two new columns in Product:

Data/Product.cs
using Pgvector; public class Product{    // ... Id, Name, Description, Price — as in the API course     [Column(TypeName = "vector(768)")]    public Vector? Embedding { get; set; }        // the vector; null — not calculated yet     public string? EmbeddingModel { get; set; }   // which model: "gemini-embedding-2"}
  • Vector — pgvector's C# type (an array of floats). Vector? — nullable, because old dishes don't have a vector yet.
  • vector(768) — the size is in the column type. The database won't accept a vector of another size.
  • EmbeddingModel — lecture 9's “one model — one map”: if we change the model, we know exactly which vectors are old and need recalculating.

5. The migration:

bash
dotnet ef migrations add ProductEmbeddingdotnet ef database update

In the migration you'll see the vector(768) column and the extension annotation. In the database: \d "Products" — Embedding | vector(768).

Indexing and search on the database

Slide 11

Indexing — lecture 9's IndexMenu, but now the vector is written into Product:

Controllers/AiLabController.cs · menu/index
[HttpPost("menu/index")]public async Task<IActionResult> IndexMenu(CancellationToken ct){    string model = _config["Gemini:EmbeddingModel"]!;     // only the dishes that have no vector, or have one from another model    List<Product> products = await _db.Products        .Where(p => p.Embedding == null || p.EmbeddingModel != model)        .ToListAsync(ct);     foreach (Product[] batch in products.Chunk(100))          // Gemini: up to 100 per request    {        var vectors = await _embeddings.GenerateAsync(            batch.Select(p => EmbeddingText.Document(p.Name, p.Description)),            cancellationToken: ct);         for (int i = 0; i < batch.Length; i++)        {            batch[i].Embedding = new Vector(vectors[i].Vector);  // ReadOnlyMemory<float> → Vector            batch[i].EmbeddingModel = model;        }    }     await _db.SaveChangesAsync(ct);    return Ok(new { Indexed = products.Count });}
  • Where(Embedding == null || EmbeddingModel != model) — only what needs recalculating. The second call returns Indexed: 0: the vectors are already in the database, no more money is spent.
  • Chunk(100) — Gemini takes up to 100 texts in one batch request (lecture 9's 💡).
  • new Vector(...) — the result of GenerateAsync (ReadOnlyMemory<float>) as pgvector's type.

Search — LINQ that is translated to SQL:

Controllers/AiLabController.cs · menu/search
[HttpGet("menu/search")]public async Task<IActionResult> SearchMenu(string q, CancellationToken ct){    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));     var top = await _db.Products        .Where(p => p.Embedding != null)        .OrderBy(p => p.Embedding!.CosineDistance(query))       // → ORDER BY "Embedding" <=> @query        .Select(p => new { p.Name, Distance = p.Embedding!.CosineDistance(query) })        .Take(3)                                                  // → LIMIT 3        .ToListAsync(ct);     return Ok(top.Select(x => new { x.Name, Score = 1 - x.Distance }));   // distance → similarity}
  • CosineDistance(query) — a Pgvector.EntityFrameworkCore function; in SQL it becomes <=>. The sorting and the LIMIT run in the database — only 3 rows come to C#.
  • Score = 1 - Distance — we return lecture 9's score, so that the homework threshold (MinScore) doesn't change.

In the log (Microsoft.EntityFrameworkCore.Database.Command) you'll see the SQL: ORDER BY p."Embedding" <=> @query LIMIT @p.

The restart test: restart the app and go straight to /menu/search without /menu/index — the result is the same. The vectors are in the database.

💡

When do we calculate the vector in a real system? When a dish is created or its description changes: Embedding = null — and the next indexing recalculates it. Our /menu/index does exactly that: only the “empty” ones and the ones calculated with an “old model”. In large systems a background worker does this.

The HNSW index and VectorData

🎯 After this You'll create an HNSW index, check it with EXPLAIN and choose between EF Core and VectorData.

Part 3 · The vector index

Slide 13

Without an index the database reads every row when it searches. We see how approximate search works (HNSW), how to create the index with EF Core and how to check it with EXPLAIN. At the end we answer lecture 9's question: do we need Microsoft.Extensions.VectorData or not.

Exact vs approximate search: HNSW

Slide 14

Without an index, for ORDER BY distance the database reads every row and calculates the distance to every vector (a sequential scan). The result is exact, but the time is proportional to the number of rows: O(n). A B-tree index doesn't help here — it looks for “equal” and “greater/less”, not for “the closest one” in a 768-dimensional space.

That's why a vector index is approximate — ANN (approximate nearest neighbor): it finds the “almost always” correct neighbours very fast. pgvector has two such indexes: HNSW and IVFFlat. We use HNSW — it's more accurate and faster, and it can be created on an empty table too.

HNSW (Hierarchical Navigable Small World) — a “graph with floors”:

  • Every vector is on floor 0, linked to its closest neighbours (a graph).
  • The upper floors hold few vectors, with long links — an “express line”.
  • The search starts at the top: with big jumps we get to the right “neighbourhood”, then go down a floor and find the closest one with short steps.

An analogy: finding an address in a city — first the highway (the right district), then the street, then the house. We don't need to walk past every house.

The price — recall. ANN can occasionally miss one correct neighbour. Recall — what share of the exact search results it found (e.g. 0.98 = 98 out of 100). The search quality is controlled by the hnsw.ef_search parameter (40 by default): more — more accurate, but slower. In text search and RAG this is normal: the “second best” dish is a good answer too. Where an exact result is required (finance, auditing), ANN isn't used.

📘 Terms
Sequential scan
reading every row of a table; exact, but O(n)
ANN (approximate nearest neighbor)
an approximate nearest-neighbour search: fast, occasionally misses
HNSW
a multi-floor graph index for vectors; pgvector's main index
Recall
what share of the exact search results the index found

The HNSW index with EF Core and EXPLAIN

Slide 15

The index is written in OnModelCreating and created by a migration:

Data/AppDbContext.cs · OnModelCreating
modelBuilder.Entity<Product>()    .HasIndex(p => p.Embedding)    .HasMethod("hnsw")                       // the index type    .HasOperators("vector_cosine_ops");      // for which distance
bash
dotnet ef migrations add ProductEmbeddingIndexdotnet ef database update

In SQL this is: CREATE INDEX ... ON "Products" USING hnsw ("Embedding" vector_cosine_ops);

The most common mistake: the operator. An index is created for one specific distance:

Index operator Search function (EF) SQL
vector_cosine_ops CosineDistance <=>
vector_l2_ops L2Distance <->
vector_ip_ops MaxInnerProduct <#>

If the index uses vector_l2_ops and the search uses CosineDistance — the index is not used, and there's no error either: it's just slow.

How to check — EXPLAIN. In psql or pgAdmin:

sql
SET enable_seqscan = off;   -- only for the test: we forbid the planner a seq scanEXPLAIN SELECT "Name" FROM "Products"ORDER BY "Embedding" <=> (SELECT "Embedding" FROM "Products" WHERE "Name" = 'Lobio in a clay pot')LIMIT 3;-- Limit -> Index Scan using "IX_Products_Embedding" on "Products"

Why doesn't it use it on 20 dishes? PostgreSQL's planner calculates what's cheaper. Reading 20 rows is cheaper than walking through an index — so it picks a Seq Scan. That's the correct behaviour. The index starts to pay off on thousands of rows and more. enable_seqscan = off is only for seeing that the index can be used — it isn't turned on in production.

📘 Terms
EXPLAIN
a PostgreSQL command that shows how the database will run a query (seq scan or index)
vector_cosine_ops
the HNSW index operator class for cosine distance

A decision: EF Core directly or Microsoft.Extensions.VectorData

Slide 16

In lecture 9 we said: “in lecture 10 we'll see whether we need Microsoft.Extensions.VectorData”. The answer:

EF Core + pgvector Microsoft.Extensions.VectorData
What it is a vector column in an ordinary table an abstraction over vector stores (like IChatClient for models)
Where it's stored in the same table, next to the dish in a separate “collection”: PostgreSQL, Qdrant, Azure AI Search, in-memory…
Filters, JOINs, transactions ordinary SQL / LINQ with the store's capabilities
When the database is PostgreSQL and stays that way the vectors are in a separate store, or the store may change

Our choice — EF Core directly. The reason: the data is already in PostgreSQL. The vector stands next to the dish, and “without meat, up to 20 lari” is one query: WHERE "Price" <= 20 ORDER BY "Embedding" <=> @q. One AppDbContext, one migration, one transaction.

If the vectors were in a separate database (Qdrant), the same question would need a “join” between two systems: either we copy the price into Qdrant too, or two queries and merging the results in C#. Exactly in a case like that VectorData gives one API for every store.

The idea of Microsoft.Extensions.VectorData (to try in the ⭐):

csharp
public class MenuRecord{    [VectorStoreKey] public int Id { get; set; }    [VectorStoreData] public string Name { get; set; } = "";    [VectorStoreVector(768, DistanceFunction = DistanceFunction.CosineDistance)]    public ReadOnlyMemory<float> Embedding { get; set; }}// collection.SearchAsync(queryVector, top: 3) — the same way on any store

Microsoft.Extensions.VectorData
an abstraction over vector stores in .NET: one API for PostgreSQL, Qdrant, Azure AI Search and others
Vector store
the place where vectors are stored and searched

Slide 19

All terms of the lecture

Terms

Vector database
a database that stores vectors and quickly finds the ones closest to each other
pgvector
a PostgreSQL extension: the vector type, distance operators and vector indexes
vector(n)
pgvector's column type: a vector of n numbers
Cosine distance
1 − cosine similarity; 0 — the same direction. In pgvector: <=>
L2 distance
the Euclidean, “straight line” distance. In pgvector: <->
Pgvector.EntityFrameworkCore
a NuGet package: pgvector's types and functions in EF Core
UseVector()
the Npgsql option that turns on the vector type
Vector
pgvector's C# type for a vector
CosineDistance
a Pgvector.EntityFrameworkCore function that is translated to the <=> operator in SQL
Chunk(n)
LINQ: a list in parts of n elements
Sequential scan
reading every row of a table; exact, but O(n)
ANN (approximate nearest neighbor)
an approximate nearest-neighbour search: fast, occasionally misses
HNSW
a multi-floor graph index for vectors; pgvector's main index
Recall
what share of the exact search results the index found
EXPLAIN
a PostgreSQL command that shows how the database will run a query (seq scan or index)
vector_cosine_ops
the HNSW index operator class for cosine distance
Microsoft.Extensions.VectorData
an abstraction over vector stores in .NET: one API for PostgreSQL, Qdrant, Azure AI Search and others
Vector store
the place where vectors are stored and searched
