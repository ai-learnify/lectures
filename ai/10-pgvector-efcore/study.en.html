PostgreSQL pgvector and EF Core

🎯 After this lecture you can

  • You'll explain what a vector database is and why we use PostgreSQL with pgvector instead of a separate vector database
  • You'll add a vector(768) column with EF Core (Pgvector.EntityFrameworkCore, UseVector, a migration) and write vectors to the database
  • You'll write a semantic search in LINQ (CosineDistance) and explain why distance = 1 − similarity
  • You'll create an HNSW index, check it with EXPLAIN and explain what approximate search and recall mean

⚡ Key points

  1. pgvector adds a vector(768) column type and distance operators to PostgreSQL. In Docker: pgvector/pgvector, same version.
  2. <=> is cosine distance = 1 − similarity. Smaller = closer, so ORDER BY ascending.
  3. EF Core: UseVector(), HasPostgresExtension("vector"), Vector? Embedding and EmbeddingModel.
  4. Search: OrderBy(p => p.Embedding!.CosineDistance(q)).Take(3); the sorting happens in the database.
  5. An HNSW index is approximate and fast. The operator = the search function. On a small table a seq scan is normal.

Vectors in the database

▶ Slides 6–8

In lecture 9 the vectors lived in memory. That has three problems: they disappear on restart, search compares every vector one by one, and the data is in two places (the dish in the database, the vector in memory).

Instead of a separate vector database we add the pgvector extension to PostgreSQL. In Docker the image changes:

docker-compose.yml
services:  db:    image: pgvector/pgvector:pg17   # before: postgres:17 — keep the same version!
⚠️

The version (pg17, pg16…) must match your old image, otherwise it cannot read the old data.

A vector is an ordinary column, and search is ORDER BY + LIMIT:

sql
CREATE EXTENSION IF NOT EXISTS vector;ALTER TABLE "Products" ADD COLUMN "Embedding" vector(768);
sql
SELECT "Name", "Embedding" <=> @q AS distanceFROM "Products"ORDER BY distanceLIMIT 3;

EF Core

▶ Slides 9–11

The Pgvector.EntityFrameworkCore NuGet package, and UseVector() in the registration:

Program.cs
builder.Services.AddDbContext<DataContext>(o =>    o.UseNpgsql(connectionString, npgsql => npgsql.UseVector()));
Data/DataContext.cs · OnModelCreating
modelBuilder.HasPostgresExtension("vector");

We add two fields to Product: the vector and the model name (so we know what to recompute when the model changes):

Data/Product.cs
using Pgvector; public class Product{    // ... Id, Name, Description, Price — as in the API course     [Column(TypeName = "vector(768)")]    public Vector? Embedding { get; set; }        // the vector; null — not calculated yet     public string? EmbeddingModel { get; set; }   // which model: "gemini-embedding-2"}
bash
dotnet ef migrations add ProductEmbeddingdotnet ef database update

Indexing: only the dishes that have no vector or have one from another model:

Controllers/AiLabController.cs · menu/index
[HttpPost("menu/index")]public async Task<IActionResult> IndexMenu(CancellationToken ct){    string model = _config["Gemini:EmbeddingModel"]!;     // only the dishes that have no vector, or have one from another model    List<Product> products = await _db.Products        .Where(p => p.Embedding == null || p.EmbeddingModel != model)        .ToListAsync(ct);     foreach (Product[] batch in products.Chunk(100))          // Gemini: up to 100 per request    {        var vectors = await _embeddings.GenerateAsync(            batch.Select(p => EmbeddingText.Document(p.Name, p.Description)),            cancellationToken: ct);         for (int i = 0; i < batch.Length; i++)        {            batch[i].Embedding = new Vector(vectors[i].Vector);  // ReadOnlyMemory<float> → Vector            batch[i].EmbeddingModel = model;        }    }     await _db.SaveChangesAsync(ct);    return Ok(new { Indexed = products.Count });}

Search: CosineDistance translates to the <=> operator in SQL, and the sorting happens in the database:

Controllers/AiLabController.cs · menu/search
[HttpGet("menu/search")]public async Task<IActionResult> SearchMenu(string q, CancellationToken ct){    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));     var top = await _db.Products        .Where(p => p.Embedding != null)        .OrderBy(p => p.Embedding!.CosineDistance(query))       // → ORDER BY "Embedding" <=> @query        .Select(p => new { p.Name, Distance = p.Embedding!.CosineDistance(query) })        .Take(3)                                                  // → LIMIT 3        .ToListAsync(ct);     return Ok(top.Select(x => new { x.Name, Score = 1 - x.Distance }));   // distance → similarity}

A vector index

▶ Slides 13–16

Without an index the database reads every row (sequential scan): exact, but slow on a million records. An HNSW index searches approximately: fast, but it may occasionally miss one close neighbour.

Data/DataContext.cs · OnModelCreating
modelBuilder.Entity<Product>()    .HasIndex(p => p.Embedding)    .HasMethod("hnsw")                       // the index type    .HasOperators("vector_cosine_ops");      // for which distance
bash
dotnet ef migrations add ProductEmbeddingIndexdotnet ef database update

EXPLAIN shows what the database will execute:

sql
SET enable_seqscan = off;   -- only for the test: we forbid the planner a seq scanEXPLAIN SELECT "Name" FROM "Products"ORDER BY "Embedding" <=> (SELECT "Embedding" FROM "Products" WHERE "Name" = 'Lobio in a clay pot')LIMIT 3;-- Limit -> Index Scan using "IX_Products_Embedding" on "Products"
💡

On a small table EXPLAIN shows a Seq Scan: that is cheaper for the database. It is normal.

⚠️

The operator (vector_cosine_ops) must match the search function (CosineDistance), otherwise the index is not used.

💡 If you get stuck

  • type "vector" does not exist → the image is still the old one (docker compose up -d --force-recreate) or HasPostgresExtension("vector") is missing
  • The container doesn't start → the version doesn't match the old one (pg16 vs pg17): go back to the same version
  • Can't find Vector → using Pgvector;; can't find CosineDistance → using Pgvector.EntityFrameworkCore;
