Context Engineering: კონტექსტისა და მეხსიერების მართვა

ლექციის სრული მასალა თავებად, ~18 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. მოდელი stateless-ია: „მეხსიერება“ ისტორიაა, რომელსაც ყოველ მოთხოვნაში ჩვენ ვუგზავნით.
  2. კონტექსტი = System + tool-ების აღწერები + ისტორია + tool-ების შედეგები + შეკითხვა. Context engineering — რა ჩავდოთ, რა დავტოვოთ, რა რიგით.
  3. ისტორია PostgreSQL-შია: ერთი ხაზი = ერთი ChatMessage, ConversationId-ით, მთელი შეტყობინება jsonb-ში, tool-ების ჩათვლით. System prompt — არა.
  4. /chat: ჩატვირთე → [SystemPrompt(), .. history, question] → შეინახე [question, .. response.Messages].
  5. ბაზაში ყველაფერი, კონტექსტში ნაწილი: MessageCountingChatReducer ბოლო N-ს ტოვებს და tool-ის შეტყობინებებს ამოყრის.

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~18 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“
  2. გაიარე ტესტი — 10 კითხვა, ქულით
  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

🎯 ამის შემდეგ: ახსნი, რატომ არ ახსოვს მოდელს წინა შეკითხვა და რა შედის ერთ მოთხოვნაში.

ნაწილი 1 · კონტექსტი

სლაიდი 6

ჯერ ვნახავთ პრობლემას ცოცხლად: მეორე შეკითხვას მოდელი ვერ იგებს. მერე ვალაგებთ, რა მიდის მოდელთან ერთ მოთხოვნაში და რატომ არის ეს ჩვენი, დეველოპერების, გადასაწყვეტი.

პრობლემა: მოდელს წინა შეკითხვა არ ახსოვს

სლაიდი 7

ჩვენი /chat ყოველ მოთხოვნაზე ახალ messages სიას ქმნის: System + მომხმარებლის ერთი შეკითხვა. ორი მოთხოვნა ერთმანეთზე არაფერი იცის:

მოთხოვნა რას ხედავს მოდელი პასუხი
1 System + „ხვალ 20:00-ზე ოთხნი ვართ, ადგილი გაქვთ?“ „დიახ, ორი მაგიდაა“ (check_availability)
2 System + „და 21:00-ზე?“ „რა გაინტერესებთ 21:00-ზე?“

მეორე მოთხოვნაში პირველი შეკითხვა საერთოდ არ არის. ლექცია 1-დან ვიცით: მოდელი stateless-ია, ის მხოლოდ იმას ხედავს, რაც ამ მოთხოვნაში გავუგზავნეთ. „მეხსიერება“ ChatGPT-შიც ასე მუშაობს: ყოველ ახალ შეტყობინებასთან ერთად სერვერი მოდელს მთელ საუბარს უგზავნის.

ესე იგი, მეხსიერება მოდელში კი არა, ჩვენს კოდშია: ისტორიას ჩვენ ვინახავთ და ჩვენ ვუგზავნით. ლექცია 2-ის ⭐-ში ეს ხელით ვცადეთ List<ChatMessage>-ით. დღეს ამას სწორად ვაკეთებთ: ბაზაში.

კონტექსტი: რას ხედავს მოდელი ერთ მოთხოვნაში

სლაიდი 8

კონტექსტი ყველაფერია, რაც მოდელამდე ერთ მოთხოვნაში მიდის. ჩვენს ჩატში ის ხუთი ნაწილისგან შედგება:

ნაწილი საიდან ნიმუში (ტოკენი)
System ჩვენი ინსტრუქცია (ლექცია 2) ~180
Tools tool-ების სახელები, აღწერები, პარამეტრების JSON Schema (ლექცია 4) ~310
ისტორია წინა შეკითხვები და პასუხები ~460
tool შედეგები რაც tool-ებმა დააბრუნა, მაგ. მთელი მენიუ ~1 780
ახალი შეკითხვა მომხმარებელი ~25

ციფრები ნიმუშია, მაგრამ სურათი ტიპურია: ყველაზე დიდი ნაწილი ხშირად tool-ების შედეგებია, და არა ის, რაც მომხმარებელმა დაწერა. get_menu მთელ მენიუს აბრუნებს, და თუ ის ისტორიაში დარჩა, ყოველ შემდეგ მოთხოვნაში თავიდან მიდის.

ყველაფერი ეს ერთ context window-ში უნდა ჩაეტიოს (ლექცია 1), და ყველაფერში ვიხდით: input ტოკენი ფასიანია, დიდი კონტექსტი ნელია.

Prompt engineering vs context engineering:

  • Prompt engineering (ლექცია 2) — როგორ დავწეროთ ინსტრუქცია: როლი, წესები, მაგალითები.
  • Context engineering — რა ჩავდოთ ფანჯარაში ყოველ მოთხოვნაზე: რომელი ისტორია, რომელი tool-ები, რომელი შედეგები, რა რიგით, და რა დარჩეს გარეთ. Prompt ამ ფანჯრის ერთი ნაწილია.

აგენტებთან (ლექცია 13+) ეს მთავარი უნარი ხდება: აგენტი ათობით tool-ს იძახებს, და კონტექსტი ძალიან სწრაფად ივსება.

რატომ jsonb და არა სვეტები? ChatMessage-ს Text კი არა, Contents აქვს: სხვადასხვა ტიპის ნაწილების სია. ტექსტი (TextContent), tool-ის გამოძახება (FunctionCallContent), tool-ის შედეგი (FunctionResultContent), Gemini-ს ფიქრის ხელმოწერა (TextReasoningContent, ლექცია 4). ყოველი ტიპისთვის სვეტები რომ გავაკეთოთ, ცხრილი ჩიხი გახდება. ამიტომ მთელ შეტყობინებას JSON-ად ვინახავთ ერთ jsonb სვეტში: PostgreSQL მას JSON-ად ინახავს და შიგნით ძებნაც შეუძლია.

სერიალიზაცია. AIJsonUtilities.DefaultOptions — Microsoft.Extensions.AI-ის მზა პარამეტრები, რომლებმაც AIContent-ის ყველა ტიპი იციან. JSON-ში ყოველ ნაწილს "$type" ეწერება ("text", "functionCall"…), რომ უკან წაკითხვისას სწორი ტიპი შეიქმნას:

public class ChatHistoryStore{    // jsonb key-ებს ალაგებს — "$type" აღარ არის პირველი    private static readonly JsonSerializerOptions Json =        new(AIJsonUtilities.DefaultOptions) { AllowOutOfOrderMetadataProperties = true };     private readonly AppDbContext _db;    public ChatHistoryStore(AppDbContext db) { _db = db; }     public async Task<List<ChatMessage>> LoadAsync(Guid conversationId, CancellationToken ct)    {        List<string> rows = await _db.ChatMessages            .Where(m => m.ConversationId == conversationId)            .OrderBy(m => m.Position)            .Select(m => m.Json)            .ToListAsync(ct);         return rows.Select(j => JsonSerializer.Deserialize<ChatMessage>(j, Json)!).ToList();    }     public async Task AppendAsync(Guid conversationId, IEnumerable<ChatMessage> messages, CancellationToken ct)    {        int position = await _db.ChatMessages.CountAsync(m => m.ConversationId == conversationId, ct);        foreach (ChatMessage message in messages)        {            _db.ChatMessages.Add(new ChatMessageRecord            {                Id = Guid.NewGuid(),                ConversationId = conversationId,                Position = position++,                Role = message.Role.Value,                Json = JsonSerializer.Serialize(message, Json),                CreatedAt = DateTime.UtcNow            });        }        await _db.SaveChangesAsync(ct);    }}

ნაბიჯ-ნაბიჯ:

  1. ConversationId ?? Guid.NewGuid() — პირველ შეკითხვაზე კლიენტს id არ აქვს, ამიტომ ახალ საუბარს ვიწყებთ. id-ს პასუხში ვაბრუნებთ, და კლიენტი მას ყოველ შემდეგ მოთხოვნაში აგზავნის.
