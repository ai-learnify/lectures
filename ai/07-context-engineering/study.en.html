Chapter 1 · ~3 min read

Context: what the model sees

🎯 After this You'll explain why the model doesn't remember the previous question and what goes into one request.

Part 1 · Context

Slide 6

First we see the problem live: the model doesn't understand the second question. Then we lay out what goes to the model in one request and why it's for us, the developers, to decide.

The problem: the model doesn't remember the previous question

Slide 7

Our /chat creates a new messages list on every request: System + one question from the user. Two requests know nothing about each other:

Request What the model sees Answer
1 System + “Four of us tomorrow at 20:00, do you have room?” “Yes, two tables are free” (check_availability)
2 System + “And at 21:00?” “What would you like to know about 21:00?”

The first question isn't in the second request at all. We know from lecture 1: the model is stateless, it only sees what we sent in this request. “Memory” works the same way in ChatGPT: with every new message the server sends the model the whole conversation.

So memory isn't in the model, it's in our code: we store the history and we send it. In lecture 2's ⭐ we tried this by hand with a List<ChatMessage>. Today we do it properly: in the database.

Context: what the model sees in one request

Slide 8

Context is everything that reaches the model in one request. In our chat it has five parts:

Part Where from Sample (tokens)
System our instruction (lecture 2) ~180
Tools the tool names, descriptions, parameters' JSON Schema (lecture 4) ~310
History the previous questions and answers ~460
Tool results what the tools returned, e.g. the whole menu ~1,780
New question the user ~25

The numbers are a sample, but the picture is typical: the biggest part is often the tool results, not what the user wrote. get_menu returns the whole menu, and if it stays in the history, it goes again in every later request.

All of this has to fit in one context window (lecture 1), and we pay for all of it: input tokens cost money, and a large context is slow.

Prompt engineering vs context engineering:

  • Prompt engineering (lecture 2) — how to write the instruction: the role, the rules, the examples.
  • Context engineering — what to put in the window on every request: which history, which tools, which results, in what order, and what stays out. The prompt is one part of that window.

With agents (lecture 13+) this becomes the key skill: an agent calls dozens of tools, and the context fills up very fast.

📘 Terms
Context
everything the model sees in one request: the instruction, the tools, the history, the tool results, the question
Context engineering
deciding what to put in the context on every request, in what order, and what to leave out

History in PostgreSQL

🎯 After this You'll store the conversation in the database with jsonb and write /chat with a history.

Part 2 · History in the database

Slide 9

The history has to be stored somewhere. We choose the place, create a table in PostgreSQL, and teach /chat to load the history first on every request and save the new messages at the end.

Where to store the history

Slide 10
Option What happens Problem
The client sends it the frontend sends the whole conversation in every request the client can change the history (e.g. write that the assistant “promised” a 50% discount); the traffic grows every time
Server memory a Dictionary<Guid, List<ChatMessage>> in a Singleton service everything disappears when the app restarts; with two servers, one user's requests end up in different memories
PostgreSQL ✓ a table where one row is one message, by ConversationId —

In the database the history stays, every server sees the same one, and we can analyse it: what people ask often, where the assistant makes mistakes.

What do we store? Everything, the tool calls and results included. Real systems work this way too: the database has the full record, while what we send to the model is a separate decision (part 3). “Stored in the database” and “goes into the context” are two different things.

The table and storing: ChatMessageRecord and ChatHistoryStore

Slide 11

The table. One row is one message:

Data/ChatMessageRecord.cs
public class ChatMessageRecord{    public Guid Id { get; set; }    public Guid ConversationId { get; set; }   // which conversation it belongs to    public int Position { get; set; }          // order in the conversation: 0, 1, 2…    public string Role { get; set; } = "";     // user / assistant / tool — for looking at the DB     [Column(TypeName = "jsonb")]    public string Json { get; set; } = "";     // the whole ChatMessage     public DateTime CreatedAt { get; set; }}

In DataContext: public DbSet<ChatMessageRecord> ChatMessages => Set<ChatMessageRecord>();, then a migration (Add-Migration ChatHistory, Update-Database).

Why jsonb and not columns? A ChatMessage doesn't have a Text, it has Contents: a list of parts of different types. Text (TextContent), a tool call (FunctionCallContent), a tool result (FunctionResultContent), Gemini's thought signature (TextReasoningContent, lecture 4). If we made columns for every type, the table would become a dead end. So we store the whole message as JSON in one jsonb column: PostgreSQL stores it as JSON and can search inside it.

Serialization. AIJsonUtilities.DefaultOptions — Microsoft.Extensions.AI's ready-made settings that know every AIContent type. In the JSON every part gets a "$type" ("text", "functionCall"…), so that the right type is created when reading it back:

Ai/ChatHistoryStore.cs
public class ChatHistoryStore{    // jsonb reorders keys — "$type" is no longer first    private static readonly JsonSerializerOptions Json =        new(AIJsonUtilities.DefaultOptions) { AllowOutOfOrderMetadataProperties = true };     private readonly DataContext _db;    public ChatHistoryStore(DataContext db) { _db = db; }     public async Task<List<ChatMessage>> LoadAsync(Guid conversationId, CancellationToken ct)    {        List<string> rows = await _db.ChatMessages            .Where(m => m.ConversationId == conversationId)            .OrderBy(m => m.Position)            .Select(m => m.Json)            .ToListAsync(ct);         return rows.Select(j => JsonSerializer.Deserialize<ChatMessage>(j, Json)!).ToList();    }     public async Task AppendAsync(Guid conversationId, IEnumerable<ChatMessage> messages, CancellationToken ct)    {        int position = await _db.ChatMessages.CountAsync(m => m.ConversationId == conversationId, ct);        foreach (ChatMessage message in messages)        {            _db.ChatMessages.Add(new ChatMessageRecord            {                Id = Guid.NewGuid(),                ConversationId = conversationId,                Position = position++,                Role = message.Role.Value,                Json = JsonSerializer.Serialize(message, Json),                CreatedAt = DateTime.UtcNow            });        }        await _db.SaveChangesAsync(ct);    }}

In Program.cs: builder.Services.AddScoped<ChatHistoryStore>(); (Scoped, because it uses DataContext).

⚠️

AllowOutOfOrderMetadataProperties = true is required. System.Text.Json expects "$type" to be first in the object. But jsonb orders keys its own way (shorter ones first), and "text" ends up before "$type". Without this setting reading it back throws an exception.

📘 Terms
jsonb
PostgreSQL's type for JSON: stores it in a processed form and can search inside it
AIJsonUtilities.DefaultOptions
Microsoft.Extensions.AI's JSON settings that know ChatMessage and every AIContent type
$type
a field in the JSON that says which C# type to create (text, functionCall, functionResult…)

/chat with history: load → send → save

Slide 12
Controllers/AiLabController.cs · Chat
public record ChatRequest(Guid? ConversationId, string Prompt); [HttpPost("chat")]public async Task<IActionResult> Chat(ChatRequest request, CancellationToken ct){    Guid conversationId = request.ConversationId ?? Guid.NewGuid();     List<ChatMessage> history = await _history.LoadAsync(conversationId, ct);    ChatMessage question = new(ChatRole.User, request.Prompt);     List<ChatMessage> messages = [SystemPrompt(), .. history, question];    ChatResponse response =        await _chat.GetResponseAsync(messages, ChatToolOptions(), ct);     await _history.AppendAsync(conversationId, [question, .. response.Messages], ct);     return Ok(new { conversationId, response.Text, response.Usage?.InputTokenCount });}

ChatHistoryStore comes to the Controller through the constructor (_history), like RestaurantTools.

Step by step:

  1. ConversationId ?? Guid.NewGuid() — on the first question the client has no id, so we start a new conversation. We return the id in the response, and the client sends it in every later request.
  2. LoadAsync — the previous messages from the database, in order.
  3. [SystemPrompt(), .. history, question] — a collection expression: System first, then the history (.. “spreads” the list), and the new question last. SystemPrompt() is the same System prompt as in lecture 6, moved into its own method, like ChatToolOptions().
  4. AppendAsync(conversationId, [question, .. response.Messages]) — we store the question and everything the model added. In the tool loop response.Messages is more than one message: the tool request, the result and the final answer.

The System prompt isn't stored in the database. It's ours, not part of the conversation: it has today's date in it, and if we change a rule tomorrow, old conversations should get the new rule too. So we build it again on every request and put it at the top of the list.

Checking it in Swagger: the first request without a conversationId → a new id in the response. The second request with the same id: “And at 21:00?” → the model sees the first question and calls check_availability with 21:00. InputTokenCount is bigger on the second request: the history goes too.

What the database shows after two questions

Slide 13

SELECT "Position", "Role", "Json" FROM "ChatMessages" WHERE "ConversationId" = '…' ORDER BY "Position";

Position Role Json (short)
0 user {"text": "Four of us tomorrow at 20:00…", "$type": "text"}
1 assistant functionCall: check_availability, {"at": "…T20:00", "guests": 4} + the thought signature
2 tool functionResult: {"available": true, "freeTables": 2}
3 assistant {"text": "Yes, two tables are free.", "$type": "text"}
4 user “And at 21:00?”
5–7 … functionCall (21:00) → functionResult → “One table is free at 21:00”

One question gives four rows, because the tool loop (lecture 4) works through messages: the model asks for a call (assistant), our code returns the result (tool), the model writes the answer (assistant). All of them are in response.Messages, and we store all of them.

Why do we store the thought signature too? Gemini 3 requires us to send its thought blocks back exactly as it sent them. Since we store the whole ChatMessage, this happens by itself.

In jsonb the keys are in a different order ("text" before "$type"): that's exactly why we need AllowOutOfOrderMetadataProperties.

The token budget and the reducer

🎯 After this You'll explain why the context grows, and send the model only the last N messages.

Part 3 · The token budget

Slide 15

The history works, but every question sends the whole conversation, and it keeps growing. We see how fast, what strategies exist, and how we send the model only part of the history while everything stays in the database.

Growth: every question sends the whole history

Slide 16

The InputTokenCount of each question in one conversation (sample):

Question What happened InputTokenCount
1 “Hello” ~620 (System + tools)
2 “Four of us at 20:00?” → check_availability ~1,450
3 “What do you have under 15 GEL?” → get_menu ~3,300
4 “Is the lobio spicy?” ~3,900
5 “What vegetarian dishes do you have?” → get_menu again ~5,600
6 “OK, I'll book” ~7,100

The biggest jump comes after get_menu: the whole menu stays in the history as a functionResult and goes along with every later question. Twice, at that.

Why this is a problem:

  • 💸 Cost and speed. Input tokens cost money. On the 50th question tens of thousands of tokens go every time, and the model processes a large context more slowly.
  • 🧱 The limit. The context window is big, but not infinite. A long conversation fills it sooner or later.
  • 🕰️ Stale data. In the tool result left in the history the lobio costs 12 GEL, but in the database it's already 14. The model may not call the tool again and quote the old price.
  • 🎯 Attention. The more there is in the context, the more things “get in the way” of the main one. In a long context the model more often “misses” the middle part.

Three strategies: selection, compression, order

Slide 17
Strategy What it means In our project
🎯 Selection only what this question needs goes into the context a tool instead of the whole menu (lecture 4: the model asks for what it needs) · the last N messages of the history · RAG in lecture 11: only the relevant parts of documents
🗜️ Compression the old part in a smaller form truncation: we drop the old messages · summarization: the model sums up the old part briefly and the summary goes in its place
📐 Order where things stand in the context System always first · the new question last · important information at the start or the end, not in the middle

The main idea: everything stays in the database, only part of it goes into the context. On every request our code decides what goes out of the database. This decision is ours, not the model's: that's exactly what context engineering is.

Truncation vs summarization. Truncation is simple and cheap, but an old detail (e.g. “four of us”) disappears. Summarization keeps the detail, but costs one extra call, and the summary may leave something out. Today we do truncation; summarization is in the ⭐.

IChatReducer: the last 10 messages to the model

Slide 18

Microsoft.Extensions.AI has IChatReducer: an interface that takes a list of messages and returns a smaller one. The ready-made MessageCountingChatReducer keeps only the last N messages:

Controllers/AiLabController.cs · Chat
#pragma warning disable MEAI001   // reducers are still experimentalprivate static readonly IChatReducer Reducer = new MessageCountingChatReducer(10);#pragma warning restore MEAI001 // inside Chat:List<ChatMessage> history = await _history.LoadAsync(conversationId, ct);IEnumerable<ChatMessage> recent = await Reducer.ReduceAsync(history, ct); ChatMessage question = new(ChatRole.User, request.Prompt);List<ChatMessage> messages = [SystemPrompt(), .. recent, question];// ... GetResponseAsync, AppendAsync — unchanged

What MessageCountingChatReducer(10) does:

  • It keeps the last 10 messages (besides System). The older ones no longer go into the context.
  • It drops the tool messages (functionCall, functionResult). So the menu no longer goes along with old questions: the biggest part disappears.
  • It doesn't touch the database. AppendAsync still stores everything. Only what goes in this request changes.

And the price? The menu is no longer in the context, so if the user asks about a price, the model calls get_menu again and gets the new price. This is even better: an old price no longer “gets stuck” in the history.

Why not just history.TakeLast(10)? It might cut in the middle of a list: a functionCall stays but its functionResult doesn't. On such a history the provider returns an error. The reducer removes the tool messages entirely and sidesteps this problem.

⚠️

MEAI001. Reducers in Microsoft.Extensions.AI are still marked experimental: the API may change. The compiler shows an error until we write #pragma warning disable MEAI001 (or <NoWarn>MEAI001</NoWarn> in the .csproj).

📘 Terms
IChatReducer
an interface that shrinks the list of messages before it's sent to the model
MessageCountingChatReducer
a ready-made reducer: keeps the last N messages and drops the tool messages
Truncation
dropping old messages from the context

Context

Context engineering
deciding what to put in the context on every request, in what order, and what to leave out
