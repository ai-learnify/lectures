Tools and Function Calling

The whole lecture in chapters, ~23 minutes of reading. Your progress is saved in the browser. This page follows the presentation: when the slide changes, the matching part is highlighted.

⚡ In 5 minutes

If this is all you remember, you know the core of the lecture:

  1. The model can't see our database — it either makes things up or refuses. Putting the whole database in the prompt is expensive and goes stale.
  2. Function calling: we send the question + the list of tools → the model asks for a call → our code runs the method → the result goes to the model → a text answer.
  3. A tool = name + description ([Description]) + the parameters' JSON Schema. AIFunctionFactory.Create(method, name: "...") creates it from a C# method, ChatOptions.Tools sends it with the request.
  4. .UseFunctionInvocation() in Program.cs runs the loop automatically. response.Messages shows which tool was called.
  5. A good tool: name = verb + what, a description, typed parameters, one job. Today only read tools — writing needs confirmation.

Chapter 1 · ~5 min read

The model and our database: the function-calling loop

🎯 After this You'll explain why the model can't see our database and how it asks for our method to be called, in four steps.

Part 1 · The model and our database

Slide 6

The model only “sees” what we sent in the request (lecture 1: stateless, knowledge up to its training date). Our database, today's bookings and the menu prices are not part of its knowledge. In this part we'll see how function calling gives the model access to this data while only our code talks to the database.

The model can't see our database

Slide 7

A user writes: “There are four of us, tomorrow at 8 — do you have a table?”. On lecture 2's /ask the model doesn't have our database, so it does one of two things:

Answer Problem
“Yes, of course! We're expecting you” It made it up (hallucination): it hasn't seen the bookings but answers confidently. The user comes and the table is taken
“I don't have access to bookings” Honest, but it doesn't help the user at all

Idea 1: the whole database in the prompt? All tables and all bookings as text. That's a bad idea:

  • Many tokens. Thousands of input tokens on every question, even on “hello” (cost, lecture 1).
  • It goes stale. The prompt is a snapshot from the moment it was sent, while bookings change every minute.
  • Unneeded. “How much is khinkali?” doesn't need the bookings at all.

Idea 2 (the right one): the model itself asks us for the data it needs, and only when it needs it. This is called function calling (or tool calling).

Function calling: the loop in four steps

Slide 8

The main idea: the model can't call our method. It runs on Google's servers, while our database is with us. The model only asks; our code runs the method.

  1. We → the model: we send the question and the list of tools. For each tool: a name (check_availability), a description (“checks for a free table”) and parameters (at, guests).
  2. The model → us: the model realises it needs data for the answer and, instead of text, returns a call request: “call check_availability, at = tomorrow 20:00, guests = 4”. It filled in the parameters from the user's text by itself.
  3. We → the model: our code calls the real C# method, the method reads the database, and we send the result ({ available: true, freeTables: 2 }) to the model. This is the second request to Gemini, and it carries the whole history: the question, the request and the result.
  4. The model → us: based on the result, the model writes an ordinary text answer.

We made two requests to Gemini (steps 1 and 3). If the model needs several tools, the loop repeats, so there can be more requests.

💡

The model never connects to our database. Our code decides which methods exist, what they do and what they return. The model only chooses which tool to call and with which parameters.

📘 Terms
Tool
our function described for the model: name, description, parameters. The model can ask for it to be called
Function calling (tool calling)
instead of text, the model returns a request to call a tool; we run it and send back the result

What goes over the wire

Slide 9

Above is Gemini's format, simplified. We don't write it by hand — Microsoft.Extensions.AI builds it. But it helps to know what happens inside:

  1. The tool description goes with the request: name, description and parameters. parameters is a JSON Schema, just like the one created from BookingRequest in lecture 3. The schema is created automatically from the C# method's parameters: DateTime at → "type": "string", "format": "date-time", int guests → "type": "integer".
  2. The model's answer is not text but a functionCall: the tool name and the arguments (args), filled in according to the schema.
  3. Our result goes back as a functionResponse. The object the method returned is turned into JSON.

Who runs the method? Our server. Gemini only writes the name and the arguments, just as it filled in the BookingRequest fields in lecture 3.

👉

This shows why the description matters so much: the model can't see the tool's code. It learns what the tool does and when to call it only from the name and the description.

Chapter 2 · ~4 min read

The first tool: the menu from the database

🎯 After this You'll turn a C# method into a tool, switch on UseFunctionInvocation and see in Swagger that the answer comes from your database.

Part 2 · The first tool: the menu

Slide 10

We start with the simplest tool, one without parameters: the menu from the database. There are three steps: a C# method with a description, turning it into a tool, and one line in Program.cs that runs the four-step loop for us.

RestaurantTools: the methods the model will call

Slide 11

A tool is an ordinary C# method. We create a separate class where all the tools will live:

Ai/RestaurantTools.cs
using System.ComponentModel;using Microsoft.EntityFrameworkCore; public record MenuItemInfo(string Name, decimal Price); public class RestaurantTools{    private readonly AppDbContext _db;     public RestaurantTools(AppDbContext db)    {        _db = db;    }     [Description("Returns the restaurant menu: dish name and price in GEL")]    public async Task<List<MenuItemInfo>> GetMenu()    {        return await _db.Products            .Select(p => new MenuItemInfo(p.Name, p.Price))            .ToListAsync();    }}

And the registration in Program.cs:

Program.cs
builder.Services.AddScoped<RestaurantTools>();
  • AppDbContext through the constructor. Exactly as in the API course services. RestaurantTools is Scoped because DbContext is Scoped too: one request, one DbContext.
  • [Description(...)] on the method. This description goes to the model as the tool's description. The model can't see the code, so this is the only place it learns what the tool does.
  • MenuItemInfo. We don't return the entity to the model, only the fields it needs. Fewer fields mean fewer tokens and less unneeded information (e.g. internal ids).
  • Ordinary LINQ inside. There's nothing AI-related in the tool. It's our ordinary code.
💡

_db.Products, p.Name, p.Price are RestaurantApi names. In your project use your own entities and fields. If you already read the menu through a service (from the API course), take that service through the constructor instead of AppDbContext.

The Controller: the list of tools and UseFunctionInvocation

Slide 12

The Controller receives RestaurantTools through its constructor, next to IChatClient:

Controllers/AiLabController.cs
private readonly IChatClient _chat;private readonly RestaurantTools _tools; public AiLabController(IChatClient chat, RestaurantTools tools){    _chat = chat;    _tools = tools;}

A new endpoint /chat:

Controllers/AiLabController.cs · Chat
[HttpPost("chat")]public async Task<IActionResult> Chat(AskRequest request){    List<ChatMessage> messages =    [        new(ChatRole.System, """            You are a restaurant assistant. Answer briefly.            Take menu data only from the tool, don't make anything up.            """),        new(ChatRole.User, request.Prompt)    ];     ChatOptions options = new()    {        Tools = [AIFunctionFactory.Create(_tools.GetMenu, name: "get_menu")]    };     ChatResponse response = await _chat.GetResponseAsync(messages, options);     List<string> toolCalls = response.Messages        .SelectMany(m => m.Contents)        .OfType<FunctionCallContent>()        .Select(c => c.Name)        .ToList();     return Ok(new { response.Text, ToolCalls = toolCalls });}
  • AIFunctionFactory.Create(_tools.GetMenu, name: "get_menu") — creates a tool from a C# method: a name (get_menu), a description (from [Description]) and the JSON Schema of the parameters. We pass the method without parentheses: we give the method itself, not the result of calling it.
  • ChatOptions.Tools — the list of tools sent with this request.
  • response.Messages — the whole history created during this request: the call request (FunctionCallContent), the result (FunctionResultContent) and the final answer. In toolCalls we collect which tools the model called, so we can see it in Swagger.

One line is added to Program.cs:

Program.cs
builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .UseFunctionInvocation();

Without .UseFunctionInvocation(), GetResponseAsync would stop at step 2: the answer would contain a call request instead of text, and we'd have to write the tool call and the second request ourselves. This line runs the loop for us: it sees the request, calls the method, sends the result and returns only the final answer. What this line really is, we'll see in lecture 5.

⚠️

The second line in the System prompt (“take it only from the tool”) matters: without it the model may make the menu up from its own “knowledge” and not call the tool.

📘 Terms
AIFunctionFactory.Create
creates a tool (AIFunction) from a C# method: name, description, JSON Schema of the parameters
UseFunctionInvocation
runs the function-calling loop automatically: request → method call → result to the model → final answer

The result: /ask vs /chat

Slide 13

The same question on two endpoints: “What dishes do you have under 15 GEL?”

endpoint Answer Why
/ask (lecture 2) “We have khachapuri, khinkali, mtsvadi…” The model made up a “typical Georgian restaurant” menu. It doesn't know our menu
/chat (today) “Under 15 GEL: lobio in a clay pot (12 ₾) and mchadi (4 ₾)”, toolCalls: ["get_menu"] The model called get_menu, got the whole menu and filtered it to under 15 GEL itself

We didn't need a separate tool for the filter: the model received the whole menu and picked the right items for the question. For a small menu that's fine. With 500 dishes it's better for the tool to have a parameter (e.g. maxPrice), so we don't feed the whole list to the model.

On “Hello!” toolCalls is empty: the model decided it doesn't need the menu. Whether to call a tool and which one is the model's decision, based on the name and the description.

💡

The exact text will differ for you: your database has other dishes and the model works with probabilities. What matters is seeing get_menu in toolCalls and the prices coming from your database.

Parameters and a good tool

🎯 After this You'll write a tool with parameters that the model fills in from the text, and tell a good tool from a bad one.

Part 3 · Parameters and a good tool

Slide 15

get_menu had no parameters. Now we add a tool whose parameters the model fills in from the user's text: checking for a free table by date and number of guests. Then we'll see what separates a good tool from a bad one.

CheckAvailability: a tool with parameters

Slide 16
Ai/RestaurantTools.cs · CheckAvailability
public record AvailabilityInfo(bool Available, int FreeTables); [Description("Checks whether a table is free at the given time")]public async Task<AvailabilityInfo> CheckAvailability(    [Description("Booking date and time")] DateTime at,    [Description("Number of guests")] int guests){    var busyTableIds = await _db.Bookings        .Where(b => b.At > at.AddHours(-2) && b.At < at.AddHours(2))        .Select(b => b.TableId)        .ToListAsync();     int free = await _db.Tables        .CountAsync(t => t.Seats >= guests && !busyTableIds.Contains(t.Id));     return new AvailabilityInfo(free > 0, free);}
  • [Description] on the parameters. They go into the schema as each parameter's description, exactly like on the BookingRequest fields in lecture 3. The [property: ...] form isn't needed here, because this is a method parameter, not a record one.
  • The logic is ours. A table counts as busy if it has a booking within ±2 hours, and it must seat guests people. It's a simple rule. In your project use your own booking rule.
  • The result is AvailabilityInfo. A short object the model uses to build its answer.

In the Controller a second tool is added to the list, and today's date to the System prompt, like in lecture 3:

Controllers/AiLabController.cs · Chat
new(ChatRole.System, $"""    You are a restaurant assistant. Answer briefly.    Take menu and free-table data only from the tools, don't make anything up.    Today is {DateTime.Now:yyyy-MM-dd, dddd}.    """),// ...ChatOptions options = new(){    Tools =    [        AIFunctionFactory.Create(_tools.GetMenu, name: "get_menu"),        AIFunctionFactory.Create(_tools.CheckAvailability, name: "check_availability")    ]};

Why the date? “Tomorrow at 8” → at = 2026-11-26T20:00. Without today's date the model can't work out “tomorrow” (lecture 3).

👉

If you also want to see the parameters in toolCalls, write .Select(c => $"{c.Name}({string.Join(", ", c.Arguments ?? new Dictionary<string, object?>())})") instead of .Select(c => c.Name). Swagger will show check_availability([at, 2026-11-26T20:00:00], [guests, 4]).

Which tool will it call?

Slide 17

Four texts on /chat. Guess first, then check in Swagger:

Text What it calls What to notice
“There are four of us, tomorrow at 8 — do you have a table?” check_availability(at: …T20:00, guests: 4) Parameters from the text. “8” → 20:00 or 08:00: still the model's guess (lecture 3)
“How much is lobio?” get_menu() The price comes from the database
“Hi, until what time are you open?” none We have no opening-hours tool. The right answer is “I don't have that information” (that's why the System prompt says “don't make anything up”)
“Two of us are coming on Saturday at 7. What vegetarian dishes do you have?” check_availability and get_menu Two tools for one question. UseFunctionInvocation runs both

The model chooses: no tool, one, or several. And it fills in the parameters from the text itself.

What if data is missing? “There are four of us, do you have a table?”: no day is given. A good model will ask a question first (“Which day and what time?”) and won't call the tool. In a bad case it picks a day itself. That's why a C# check inside the tool is still needed (e.g. at is in the past → the result says “the date is in the past”).

💡

The exact result may differ for you: the model chooses with probabilities. If the model doesn't call a tool when it should, improve the description first (next slide).

A good tool: 4 rules

Slide 18

The model knows a tool only by its name, its description and the schema of its parameters. It can't see the code. So these three decide the tool's quality.

Rule Bad Good
Name = verb + what Check, Func1, Data check_availability, get_menu
Description: what it does, what it returns, and when to use it if needed missing “Checks whether a table is free at the given time”
Typed parameters with descriptions string data (“2026-11-26 20:00 4”?) DateTime at, int guests, or an enum if the values come from a list
One tool, one job DoEverything(string action, string data) separate get_menu and check_availability

Why typed parameters? With string data the model has to guess the format, and we have to parse that string. DateTime and int go into the schema as exact types, and AIFunctionFactory converts the model's JSON into C# types by itself.

Why only reading today (read-only)? If we give the model create_booking, the model decides the booking by itself: it may take “8” for 8 in the morning and create the booking without asking the user. A tool that writes to the database needs the user's confirmation (“Shall I book tomorrow at 20:00 for 4?”). This is called human-in-the-loop, and we'll see it in lecture 15.

👉

If the model calls a tool at the wrong time or doesn't call it at all, don't change the code. Improve the description first: often one sentence is enough (“use it when the user asks about a price or a dish”).

Your project or RestaurantApi · with code · in Swagger

Steps

Summary

Slide 21
