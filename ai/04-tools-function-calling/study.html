Tools და Function Calling

ლექციის სრული მასალა თავებად, ~17 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. მოდელი ჩვენს ბაზას ვერ ხედავს — ან იგონებს, ან უარს ამბობს. მთელი ბაზის prompt-ში ჩაწერა ძვირია და ძველდება.
  2. Function calling: ჩვენ ვაგზავნით შეკითხვას + tool-ების სიას → მოდელი ითხოვს გამოძახებას → ჩვენი კოდი ასრულებს მეთოდს → შედეგი მოდელს → ტექსტური პასუხი.
  3. Tool = სახელი + აღწერა ([Description]) + პარამეტრების JSON Schema. AIFunctionFactory.Create(method, name: "...") C# მეთოდიდან ქმნის, ChatOptions.Tools მოთხოვნასთან აგზავნის.
  4. .UseFunctionInvocation() Program.cs-ში ციკლს ავტომატურად ატრიალებს. response.Messages-ში ჩანს, რომელი tool გამოიძახა.
  5. კარგი tool: სახელი = ზმნა + რა, აღწერა, ტიპიზებული პარამეტრები, ერთი საქმე. დღეს მხოლოდ კითხვის tool-ები — ჩანაწერს დადასტურება სჭირდება.

მოდელი და ჩვენი ბაზა: function calling-ის ციკლი

🎯 ამის შემდეგ: ახსნი, რატომ ვერ ხედავს მოდელი ჩვენს ბაზას და როგორ ითხოვს ის ჩვენი მეთოდის გამოძახებას ოთხ ნაბიჯად.

ნაწილი 1 · მოდელი და ჩვენი ბაზა

სლაიდი 6

მოდელი მხოლოდ იმას „ხედავს“, რაც მოთხოვნაში გავუგზავნეთ (ლექცია 1: stateless, ცოდნა ვარჯიშის თარიღამდე). ჩვენი ბაზა, დღევანდელი ჯავშნები და მენიუს ფასები მის ცოდნაში არ არის. ამ ნაწილში ვნახავთ, როგორ აძლევს function calling მოდელს წვდომას ამ მონაცემებზე ისე, რომ ბაზასთან კავშირი მაინც მხოლოდ ჩვენს კოდს აქვს.

მოდელი ჩვენს ბაზას ვერ ხედავს

სლაიდი 7

მომხმარებელი წერს: „ხვალ 8-ზე ოთხნი ვართ, ადგილი გაქვთ?“. ლექცია 2-ის /ask-ზე მოდელს ჩვენი ბაზა არ აქვს, ამიტომ ორიდან ერთს აკეთებს:

პასუხი პრობლემა
„დიახ, რა თქმა უნდა! გელოდებით“ მოიგონა (hallucination): ჯავშნები არ უნახავს, მაგრამ დამაჯერებლად პასუხობს. მომხმარებელი მოვა და მაგიდა დაკავებული იქნება
„ჯავშნებზე წვდომა არ მაქვს“ პატიოსანია, მაგრამ მომხმარებელს არაფერში ეხმარება

იდეა 1: მთელი ბაზა prompt-ში? ყველა მაგიდა და ყველა ჯავშანი ტექსტად. ეს ცუდი იდეაა:

  • ბევრი ტოკენი. ყოველ კითხვაზე, თუნდაც „გამარჯობა“-ზე, ათასობით ტოკენი input-ში (ფასი, ლექცია 1).
  • ძველდება. prompt გაგზავნის მომენტის ასლია, ჯავშნები კი წუთში იცვლება.
  • ზედმეტი. „ხინკალი რა ღირს?“-ზე ჯავშნები საერთოდ არ სჭირდება.

იდეა 2 (სწორი): მოდელმა თვითონ გვთხოვოს ის მონაცემი, რომელიც სჭირდება, და მხოლოდ მაშინ, როცა სჭირდება. ამას ჰქვია function calling (ან tool calling).

Function calling: ციკლი ოთხ ნაბიჯად

სლაიდი 8

მთავარი იდეა: მოდელი ჩვენს მეთოდს ვერ იძახებს. ის Google-ის სერვერზეა, ჩვენი ბაზა კი ჩვენთან. მოდელი მხოლოდ ითხოვს, ჩვენი კოდი ასრულებს.

  1. ჩვენ → მოდელი: ვაგზავნით შეკითხვას და tool-ების სიას. თითო tool-ზე: სახელი (check_availability), აღწერა („ამოწმებს თავისუფალ მაგიდას“) და პარამეტრები (at, guests).
  2. მოდელი → ჩვენ: მოდელი ხვდება, რომ პასუხისთვის მონაცემი სჭირდება, და ტექსტის ნაცვლად გამოძახების თხოვნას აბრუნებს: „გამოიძახე check_availability, at = ხვალ 20:00, guests = 4“. პარამეტრები მომხმარებლის ტექსტიდან თვითონ შეავსო.
  3. ჩვენ → მოდელი: ჩვენი კოდი იძახებს ნამდვილ C# მეთოდს, მეთოდი ბაზას კითხულობს, და შედეგს ({ available: true, freeTables: 2 }) მოდელს ვუგზავნით. ეს მეორე მოთხოვნაა Gemini-სთან, და მასში მთელი ისტორიაა: შეკითხვა, თხოვნა და შედეგი.
  4. მოდელი → ჩვენ: შედეგის საფუძველზე მოდელი ჩვეულებრივ ტექსტურ პასუხს წერს.

Gemini-სთან ორი მოთხოვნა გვქონდა (ნაბიჯი 1 და 3). თუ მოდელს რამდენიმე tool სჭირდება, ციკლი მეორდება, ასე რომ მოთხოვნა შეიძლება მეტიც იყოს.
