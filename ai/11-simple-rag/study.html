Simple RAG: პასუხი დოკუმენტებიდან

ლექციის სრული მასალა თავებად, ~14 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. RAG = retrieve → augment → generate: მოდელი პასუხობს ჩვენი დოკუმენტების ნაპოვნი ნაწილებით და წყაროს ასახელებს.
  2. Ingestion (ერთხელ): PDF → ტექსტი გვერდებით (PdfPig, ContentOrderTextExtractor) → გაწმენდა → chunks → ვექტორები → DocumentChunk.
  3. Chunking: ~800 სიმბოლო, წინადადებებით, overlap ერთი წინადადება, გვერდ-გვერდ — ზუსტი წყაროსთვის.
  4. Query: top 5 + ზღვარი → [1] (ფაილი, გვ. N) → წესები: მხოლოდ წყაროებიდან, ნომრით, „ამ საკითხზე ინფორმაცია არ მაქვს“.
  5. ჩატში: ისტორიაში — ორიგინალი შეკითხვა; წყაროები — მხოლოდ ამ მოთხოვნაში; response-ში sources.

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~14 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“
  2. გაიარე ტესტი — 10 კითხვა, ქულით
  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

სლაიდი 6

ჯერ ვხედავთ, რატომ არ გამოდგება „მთელი PDF კონტექსტში“ და fine-tuning. მერე — RAG-ის სრული სურათი: რა ხდება ერთხელ (ingestion) და რა ხდება ყოველ შეკითხვაზე (query).

პრობლემა: პასუხი დოკუმენტშია

სლაიდი 7

რესტორანს აქვს წესების PDF — 18 გვერდი: ჯავშნის გაუქმება, ალერგენები, ცხოველები, ღონისძიებები. მომხმარებლის ბევრი შეკითხვის პასუხი იქაა, არა მენიუში. მოდელმა ეს დოკუმენტი არ იცის — მისი ცოდნა ვარჯიშის მონაცემებიდანაა (ლექცია 1), ჩვენი რესტორნის წესები იქ არ ყოფილა.

რა გზები გვაქვს:

გზა პრობლემა
მთელი PDF კონტექსტში ყოველ შეკითხვაზე 18 გვერდი = ათასობით input ტოკენი (ლექცია 7–8): ფული და ნელი პასუხი. 500-გვერდიან დოკუმენტებზე context window-შიც არ ეტევა. და რაც მეტია კონტექსტში, მით უფრო „იკარგება“ მთავარი (lost in the middle)
Fine-tuning (მოდელის დამატებითი ვარჯიში) ძვირი და ნელი; წესი შეიცვლება — ისევ ვარჯიში. მოდელი ფაქტებს ცუდად „იმახსოვრებს“ და წყაროს ვერ ასახელებს
RAG — ვიპოვოთ მხოლოდ საჭირო ნაწილები ყოველ შეკითხვაზე 3–5 ნაწილი; დოკუმენტი შეიცვალა — თავიდან ვტვირთავთ; პასუხს წყარო ახლავს

RAG ლექცია 7-ის შერჩევის სტრატეგიაა: კონტექსტში მხოლოდ ის, რაც ამ შეკითხვას სჭირდება. და ლექცია 9–10-ის ძებნა მნიშვნელობით ზუსტად ამ ნაწილების პოვნას აკეთებს.

📘 ტერმინები
Fine-tuning
არსებული მოდელის დამატებითი ვარჯიში საკუთარ მონაცემზე; სტილისა და ფორმატისთვის კარგია, ფაქტებისთვის — ნაკლებად
Lost in the middle
გრძელ კონტექსტში მოდელი შუა ნაწილის ინფორმაციას უფრო ხშირად „ვერ ამჩნევს“

RAG: ორი pipeline

სლაიდი 8

RAG — Retrieval-Augmented Generation: „გენერაცია, გაძლიერებული ძებნით“. სამი სიტყვა — სამი ნაბიჯი:

  • Retrieve — შეკითხვაზე ვპოულობთ დოკუმენტების ყველაზე რელევანტურ ნაწილებს (ლექცია 9–10-ის ძებნა);
  • Augment — ამ ნაწილებს ვამატებთ prompt-ს;
  • Generate — მოდელი პასუხს წერს მათზე დაყრდნობით და წყაროს ასახელებს.

ამისთვის ორი ცალკე pipeline გვჭირდება:

Ingestion Query
როდის ერთხელ — დოკუმენტის ატვირთვისას (ან შეცვლისას) ყოველ შეკითხვაზე
ნაბიჯები PDF → ტექსტი → ნაწილები (chunks) → ვექტორები → ბაზა შეკითხვის ვექტორი → top 5 ნაწილი → prompt → პასუხი
ლექცია 9 (ვექტორები), 10 (ბაზა), დღეს — PDF და chunking 9–10 (ძებნა), 7 (ჩატი), დღეს — augment და წყაროები

ანალოგია — გამოცდა ღია წიგნით. მოდელი ჭკვიანი სტუდენტია, რომელმაც ჩვენი რესტორნის წესები არ იცის. RAG-ით გამოცდაზე წიგნი აქვს: შეკითხვას კითხულობს, წიგნში სწორ გვერდს პოულობს (ჩვენ ვპოულობთ მისთვის) და პასუხს წერს, გვერდის მითითებით. დახურული წიგნით (RAG-ის გარეშე) — „იხსენებს“ ან იგონებს (hallucination, ლექცია 1).

PDF → ტექსტი: PdfPig

სლაიდი 10

PDF ტექსტური ფაილი არ არის. მასში წერია ასოები და მათი კოორდინატები გვერდზე — „ასო ‚ჯ‘, x=72, y=540, შრიფტი…“. სიტყვა, ხაზი, აბზაცი ან სვეტი ფაილში არ არსებობს: ტექსტის ამოღება ნიშნავს ასოებიდან სიტყვების და ხაზების „აწყობას“.

PdfPig (NuGet PdfPig, ლიცენზია Apache-2.0) — .NET-ის ბიბლიოთეკა PDF-ის წასაკითხად:

Ai/PdfText.cs
using System.Text.RegularExpressions;using UglyToad.PdfPig;using UglyToad.PdfPig.DocumentLayoutAnalysis.TextExtractor; public static class PdfText{    public static List<(int Page, string Text)> ReadPages(byte[] pdf)    {        using PdfDocument doc = PdfDocument.Open(pdf);        return doc.GetPages()            .Select(p => (p.Number, Clean(ContentOrderTextExtractor.GetText(p))))            .Where(p => p.Item2.Length > 0)          // skip empty pages            .ToList();    }     private static string Clean(string text) =>        Regex.Replace(text, @"\s+", " ").Trim();     // extra spaces and line breaks}
  • ContentOrderTextExtractor.GetText(page) — ასოებს კითხვის რიგით აწყობს (ხაზები, სვეტები). მარტივი page.Text ასოებს ფაილის რიგით აბრუნებს და ხშირად სიტყვებს აწებებს ან ურევს.
  • გვერდის ნომერი (p.Number) რჩება — ის წყაროს მითითებისთვის გვჭირდება ("rules.pdf, p. 3").
  • გაწმენდა — ჰარების და ხაზების ნორმალიზაცია. რეალურ დოკუმენტებში ამას ემატება განმეორებადი header/footer-ის (გვერდის ნომერი, კომპანიის სახელი) ამოღება.
⚠️

სკანირებული PDF (ფოტოები) ტექსტს საერთოდ არ შეიცავს — GetText ცარიელს დააბრუნებს. ასეთ ფაილს OCR სჭირდება (ტექსტის ამოცნობა სურათიდან). ცხრილები და სვეტები PdfPig-ით ხშირად „ირევა“ — რთული დოკუმენტებისთვის არსებობს layout-ის ანალიზის სერვისები (Azure Document Intelligence, Docling).

Chunking: ტექსტი ნაწილებად

სლაიდი 11

რატომ არა მთელი დოკუმენტი ერთ ვექტორად? ვექტორი ტექსტის „საშუალო მნიშვნელობაა“. 18 გვერდის ვექტორი ჯავშნის, ალერგენების, ცხოველების და ღონისძიებების ნაზავია — "cancelling a booking" მას ცუდად ედრება. ამას ემატება: embedding მოდელს შეყვანის ლიმიტი აქვს (gemini-embedding-2 — 8 192 ტოკენი), და ნაპოვნი ტექსტი კონტექსტში უნდა ჩავდოთ — 18 გვერდი ისევ ძვირია.

Chunk (ნაწილი) — დოკუმენტის მონაკვეთი, რომელიც ერთ აზრს ფარავს. თითოეული ცალკე ვექტორად ინახება და ცალკე იძებნება.

ზომა — კომპრომისი:

ზომა პლიუსი მინუსი
ძალიან პატარა (1 წინადადება) ვექტორი ზუსტია კონტექსტი იკარგება: "this rule applies to 8+ people" — რომელი წესი?
ძალიან დიდი (გვერდები) კონტექსტი სრულია ვექტორი ბუნდოვანია, კონტექსტში ძვირია
საშუალო (~500–1000 სიმბოლო) ერთი აზრი + მისი კონტექსტი — ჩვენი არჩევანი: 800

Overlap (გადაფარვა). ნაწილის ბოლო წინადადება შემდეგი ნაწილის დასაწყისშიც მეორდება. თუ აზრი ორ ნაწილს შორის გაიყო ("cancellation 24 hours before" + "If cancelled late, the money isn't returned"), ორივე ნაწილს აქვს „ხიდი“.

ჩვენი chunker — წინადადებებით:

Ai/TextChunker.cs
public static class TextChunker{    public static List<string> Split(string text, int maxChars = 800, int overlap = 1)    {        string[] sentences = Regex.Split(text, @"(?<=[.!?])\s+");        List<string> chunks = [];        List<string> current = [];         foreach (string sentence in sentences)        {            if (current.Count > 0 && current.Sum(s => s.Length) + sentence.Length > maxChars)            {                chunks.Add(string.Join(" ", current));                current = current.TakeLast(overlap).ToList();   // overlap: the last sentence stays            }            current.Add(sentence);        }        if (current.Count > 0)            chunks.Add(string.Join(" ", current));        return chunks;    }}
  • ტექსტს წინადადებებად ვყოფთ (., !, ?-ის შემდეგ) — ნაწილი წინადადების შუაში არ იჭრება.
  • წინადადებებს ვაგროვებთ, სანამ ~800 სიმბოლოს არ გადააჭარბებს; მერე ნაწილი იხურება და ბოლო წინადადება შემდეგში გადადის.
  • ვჭრით გვერდ-გვერდ — ასე ყოველ ნაწილს ზუსტი გვერდის ნომერი აქვს.

ეს ერთ-ერთი სტრატეგიაა. ლექცია 12-ში სხვებს შევადარებთ (სათაურებით, მნიშვნელობით) — და გავზომავთ, რომელი სჯობს.

[HttpPost("documents")]public async Task<IActionResult> UploadDocument(IFormFile file, CancellationToken ct){    using var ms = new MemoryStream();    await file.CopyToAsync(ms, ct);     // 1–2: PDF → pages → parts    var doc = new Document { FileName = file.FileName, UploadedAt = DateTime.UtcNow };    foreach (var (page, text) in PdfText.ReadPages(ms.ToArray()))        foreach (string chunk in TextChunker.Split(text))            doc.Chunks.Add(new DocumentChunk { Page = page, Content = chunk });     // 3: vectors, in batches of 100    string model = _config["Gemini:EmbeddingModel"]!;    foreach (DocumentChunk[] batch in doc.Chunks.Chunk(100))    {        var vectors = await _embeddings.GenerateAsync(            batch.Select(c => EmbeddingText.Document(doc.FileName, c.Content)),            cancellationToken: ct);        for (int i = 0; i < batch.Length; i++)        {            batch[i].Embedding = new Vector(vectors[i].Vector);            batch[i].EmbeddingModel = model;        }    }     // 4: into the database — the document and all its parts together    _db.Documents.Add(doc);    await _db.SaveChangesAsync(ct);    return Ok(new { doc.Id, Chunks = doc.Chunks.Count });}

ლექცია 10-თან შედარებით ახალი მხოლოდ ორი რამაა: PDF-ის წაკითხვა და chunking. ვექტორი, prefix (EmbeddingText.Document — სათაურად ფაილის სახელი), Chunk(100), vector(768) — ყველაფერი ნაცნობია.

public record FoundChunk(string File, int Page, string Content, double Score); private async Task<List<FoundChunk>> SearchChunksAsync(string q, CancellationToken ct){    float minScore = _config.GetValue<float>("Rag:MinScore");   // by testing — like lecture 9's homework    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));     List<FoundChunk> top = await _db.DocumentChunks        .Where(c => c.Embedding != null)        .OrderBy(c => c.Embedding!.CosineDistance(query))        .Select(c => new FoundChunk(c.Document.FileName, c.Page, c.Content,            1 - c.Embedding!.CosineDistance(query)))        .Take(5)        .ToListAsync(ct);     return top.Where(c => c.Score >= minScore).ToList();}

სამი მნიშვნელოვანი დეტალი:

  1. ისტორიაში ორიგინალი შეკითხვა ინახება (question), არა augmented. წყაროები მხოლოდ ამ მოთხოვნისთვისაა: შემდეგ შეკითხვაზე სხვა წყაროები მოიძებნება. თუ წყაროებს ისტორიაში შევინახავდით, ყოველი შეტყობინება ხუთი ნაწილით „გაიბერებოდა“ (ლექცია 7-ის ბიუჯეტი).
  2. „ინფორმაცია არ მაქვს“ — ზუსტი ფრაზა: ასე კოდშიც შეგვიძლია ამოვიცნოთ (ლოგი, სტატისტიკა: რა შეკითხვებზე არ ვიცით პასუხი — რომელი დოკუმენტი აკლია).
  3. წყაროები response-ში — UI-ს შეუძლია [1]-ზე ბმული აჩვენოს: "rules.pdf, p. 3".

„ყოველთვის ვეძებთ“ vs tool. ჩვენი ჩატი ძებნას ყოველ შეკითხვაზე აკეთებს — „გამარჯობა“-ზეც (ზღვარი 0 ნაწილს დააბრუნებს, მაგრამ embedding-ის გამოძახება მაინც ხდება). ლექცია 9-ის ⭐-ში search_menu tool იყო: მოდელი თვითონ წყვეტს, როდის მოძებნოს. ორივე რეალური გზაა:

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
რატომ არ ვდებთ მთელ PDF-ს კონტექსტში და რატომ არ ვავარჯიშებთ მოდელს (fine-tuning)?
მთელი PDF — ყოველ შეკითხვაზე ათასობით ტოკენი, ნელი, დიდი დოკუმენტი არ ეტევა, „lost in the middle“ · fine-tuning — ძვირი, ყოველ ცვლილებაზე თავიდან, ფაქტებს ცუდად იმახსოვრებს და წყაროს ვერ ასახელებს
რა არის RAG-ის ორი pipeline და როდის სრულდება თითოეული?
ingestion — ერთხელ, ატვირთვისას: PDF → ტექსტი → ნაწილები → ვექტორები → ბაზა · query — ყოველ შეკითხვაზე: ვექტორი → top 5 → prompt → პასუხი წყაროთი
რატომ ვჭრით დოკუმენტს ნაწილებად და რისთვის გვჭირდება overlap?
მთელი დოკუმენტის ვექტორი ყველაფრის „საშუალოა“ — ბუნდოვანი; ნაწილი = ერთი აზრი, ზუსტი ვექტორი და იაფი კონტექსტი · overlap — ბოლო წინადადება შემდეგშიც, რომ აზრი საზღვარზე არ გაწყდეს
რატომ გვჭირდება ზღვარი RAG-ის ძებნაში?
ძებნა ყოველთვის რაღაცას პოულობს · ზღვრის გარეშე „ბორშის რეცეპტი“-ზე მოდელი 5 უაზრო ნაწილს მიიღებდა და შეიძლება რამე მოეგონა · ზღვრით — 0 ნაწილი და „ინფორმაცია არ მაქვს“
ჩატის ისტორიაში რატომ ვინახავთ ორიგინალ შეკითხვას და არა წყაროებიან (augmented) შეტყობინებას?
წყაროები მხოლოდ ამ მოთხოვნისთვისაა — შემდეგზე სხვა მოიძებნება · ისტორიაში შენახვა ყოველ შეტყობინებას 5 ნაწილით გაბერავდა (ბიუჯეტი, ლექცია 7)

შეჯამება

სლაიდი 19
  • RAG (Retrieval-Augmented Generation) — მოდელი პასუხობს ჩვენი დოკუმენტებიდან: retrieve (რელევანტური ნაწილები) → augment (prompt-ში) → generate (პასუხი წყაროთი). მთელ დოკუმენტზე იაფია, fine-tuning-ზე მარტივი და წყაროს ასახელებს.
  • Ingestion (ერთხელ): PDF → ტექსტი გვერდებით (PdfPig, ContentOrderTextExtractor) → გაწმენდა → chunks → ვექტორები → DocumentChunk ცხრილი (ლექცია 10-ის გზით). სკანირებულ PDF-ს OCR სჭირდება.
  • Chunking: ~800 სიმბოლო, წინადადების საზღვარზე, overlap ერთი წინადადება; გვერდ-გვერდ — ზუსტი წყაროსთვის. ზომა — კომპრომისი სიზუსტესა და კონტექსტს შორის.
  • Query: top 5 ნაწილი + ზღვარი → გადანომრილი წყაროები [1] (file, p. N) → წესები system prompt-ში: მხოლოდ წყაროებიდან, ნომრით, "I don't have information on this".
  • ჩატში: ისტორიაში ორიგინალი შეკითხვა, წყაროები — მხოლოდ ამ მოთხოვნაში; response-ში — sources.

შემდეგ ლექციაზე

RAG მუშაობს, მაგრამ ზოგჯერ არასწორ ნაწილს პოულობს — განსაკუთრებით ზუსტ სიტყვებზე (სახელები, რიცხვები). „ზოგჯერ“ რამდენჯერ ნიშნავს? chunk-ის ზომის შეცვლამ გააუმჯობესა თუ გააუარესა? ლექცია 12-ზე: RAG-ის გაზომვა და გაუმჯობესება — golden set, hit@k, hybrid search (full-text + ვექტორი), metadata filtering, chunking-ის სტრატეგიები და პასუხის groundedness.

PdfPig

Chunking
