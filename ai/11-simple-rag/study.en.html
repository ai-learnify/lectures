Simple RAG: Answers from Documents

The whole lecture in chapters, ~19 minutes of reading. Your progress is saved in the browser. This page follows the presentation: when the slide changes, the matching part is highlighted.

⚡ In 5 minutes

If this is all you remember, you know the core of the lecture:

  1. RAG = retrieve → augment → generate: the model answers with the found parts of our documents and names the source.
  2. Ingestion (once): PDF → text page by page (PdfPig, ContentOrderTextExtractor) → cleaning → chunks → vectors → DocumentChunk.
  3. Chunking: ~800 characters, by sentences, an overlap of one sentence, page by page — for an exact source.
  4. Query: top 5 + a threshold → [1] (file, p. N) → rules: only from the sources, with the number, “I don't have information on this”.
  5. In the chat: the original question in the history; the sources — only in this request; sources in the response.

The idea of RAG

🎯 After this You'll explain what RAG is, why it beats the whole document and fine-tuning, and what ingestion and query are.

Part 1 · The idea of RAG

Slide 6

First we see why “the whole PDF in the context” and fine-tuning don't work. Then the full picture of RAG: what happens once (ingestion) and what happens on every question (query).

The problem: the answer is in a document

Slide 7

The restaurant has a rules PDF — 18 pages: cancelling a booking, allergens, pets, events. The answers to many of the users' questions are there, not in the menu. The model doesn't know this document — its knowledge comes from its training data (lecture 1), and our restaurant's rules weren't in it.

What options do we have:

Option The problem
The whole PDF in the context 18 pages on every question = thousands of input tokens (lectures 7–8): money and a slow answer. With 500-page documents it doesn't even fit in the context window. And the more there is in the context, the more the important part “gets lost” (lost in the middle)
Fine-tuning (extra training of the model) Expensive and slow; a rule changes — training again. The model “memorizes” facts badly and can't name the source
RAG — find only the parts we need 3–5 parts per question; the document changed — we upload it again; the answer comes with a source

RAG is lecture 7's selection strategy: only what this question needs goes into the context. And lectures 9–10's search by meaning does exactly the finding of these parts.

📘 Terms
Fine-tuning
extra training of an existing model on your own data; good for style and format, less so for facts
Lost in the middle
in a long context the model more often “misses” information in the middle part

RAG: two pipelines

Slide 8

RAG — Retrieval-Augmented Generation: “generation, augmented by search”. Three words — three steps:

  • Retrieve — for the question we find the most relevant parts of the documents (lectures 9–10's search);
  • Augment — we add these parts to the prompt;
  • Generate — the model writes the answer based on them and names the source.

For this we need two separate pipelines:

Ingestion Query
When once — when a document is uploaded (or changed) on every question
Steps PDF → text → parts (chunks) → vectors → database the question's vector → top 5 parts → prompt → answer
Lecture 9 (vectors), 10 (database), today — PDF and chunking 9–10 (search), 7 (chat), today — augment and sources

An analogy — an open-book exam. The model is a smart student who doesn't know our restaurant's rules. With RAG it has the book at the exam: it reads the question, finds the right page in the book (we find it for it) and writes the answer, citing the page. With a closed book (without RAG) — it “remembers” or makes things up (hallucination, lecture 1).

📘 Terms
RAG (Retrieval-Augmented Generation)
a model answer that relies on our documents found by search
Ingestion
preparing a document for search: text → parts → vectors → database
Chunk
a part of a document that is stored and searched as a separate vector

Ingestion: PDF → parts → database

🎯 After this You'll extract text from a PDF, cut it into parts and store them with vectors.

Part 2 · Ingestion: the document in the database

Slide 9

We take the text out of the PDF page by page, clean it, cut it into parts (chunks) and store each part with its vector in the database — the lecture 10 way.

PDF → text: PdfPig

Slide 10

A PDF isn't a text file. It contains letters and their coordinates on the page — “letter ‘ჯ’, x=72, y=540, font…”. A word, a line, a paragraph or a column doesn't exist in the file: extracting the text means “assembling” words and lines from the letters.

PdfPig (NuGet PdfPig, Apache-2.0 licence) — a .NET library for reading PDFs:

Ai/PdfText.cs
using System.Text.RegularExpressions;using UglyToad.PdfPig;using UglyToad.PdfPig.DocumentLayoutAnalysis.TextExtractor; public static class PdfText{    public static List<(int Page, string Text)> ReadPages(byte[] pdf)    {        using PdfDocument doc = PdfDocument.Open(pdf);        return doc.GetPages()            .Select(p => (p.Number, Clean(ContentOrderTextExtractor.GetText(p))))            .Where(p => p.Item2.Length > 0)          // skip empty pages            .ToList();    }     private static string Clean(string text) =>        Regex.Replace(text, @"\s+", " ").Trim();     // extra spaces and line breaks}
  • ContentOrderTextExtractor.GetText(page) — assembles the letters in reading order (lines, columns). The simple page.Text returns the letters in file order and often glues or mixes up words.
  • The page number (p.Number) stays — we need it for citing the source (“rules.pdf, p. 3”).
  • Cleaning — normalizing spaces and line breaks. In real documents this also includes removing a repeated header/footer (the page number, the company name).
⚠️

A scanned PDF (photos) contains no text at all — GetText returns nothing. Such a file needs OCR (recognizing text in an image). Tables and columns often get “mixed up” with PdfPig — for complex documents there are layout analysis services (Azure Document Intelligence, Docling).

📘 Terms
PdfPig
a .NET library for reading text and content from PDFs (Apache-2.0)
OCR
recognizing text in an image; a scanned PDF needs it

Chunking: text into parts

Slide 11

Why not the whole document as one vector? A vector is the “average meaning” of a text. The vector of 18 pages is a mix of bookings, allergens, pets and events — “cancelling a booking” compares badly with it. On top of that: the embedding model has an input limit (gemini-embedding-2 — 8,192 tokens), and the text we find has to go into the context — 18 pages are expensive again.

A chunk (a part) — a section of the document that covers one idea. Each one is stored as a separate vector and searched separately.

The size — a compromise:

Size Plus Minus
very small (1 sentence) the vector is precise the context is lost: “this rule applies to 8+ people” — which rule?
very large (pages) the context is complete the vector is blurry, expensive in the context
medium (~500–1000 characters) one idea + its context — our choice: 800

Overlap. The last sentence of a part is repeated at the start of the next part too. If an idea is split between two parts (“cancelling 24 hours before” + “if cancelled late the money isn't returned”), both parts have a “bridge”.

Our chunker — by sentences:

Ai/TextChunker.cs
public static class TextChunker{    public static List<string> Split(string text, int maxChars = 800, int overlap = 1)    {        string[] sentences = Regex.Split(text, @"(?<=[.!?])\s+");        List<string> chunks = [];        List<string> current = [];         foreach (string sentence in sentences)        {            if (current.Count > 0 && current.Sum(s => s.Length) + sentence.Length > maxChars)            {                chunks.Add(string.Join(" ", current));                current = current.TakeLast(overlap).ToList();   // overlap: the last sentence stays            }            current.Add(sentence);        }        if (current.Count > 0)            chunks.Add(string.Join(" ", current));        return chunks;    }}
  • We split the text into sentences (after ., !, ?) — a part is never cut in the middle of a sentence.
  • We collect sentences until they exceed ~800 characters; then the part is closed and the last sentence moves to the next one.
  • We cut page by page — so every part has an exact page number.

This is one strategy. In lecture 12 we compare others (by headings, by meaning) — and measure which one is better.

📘 Terms
Chunking
cutting a document into parts for search
Overlap
the overlap between parts: the last text is repeated in the next part too

Controllers/AiLabController.cs · UploadDocument
[HttpPost("documents")]public async Task<IActionResult> UploadDocument(IFormFile file, CancellationToken ct){    using var ms = new MemoryStream();    await file.CopyToAsync(ms, ct);     // 1–2: PDF → pages → parts    var doc = new Document { FileName = file.FileName, UploadedAt = DateTime.UtcNow };    foreach (var (page, text) in PdfText.ReadPages(ms.ToArray()))        foreach (string chunk in TextChunker.Split(text))            doc.Chunks.Add(new DocumentChunk { Page = page, Content = chunk });     // 3: vectors, in batches of 100    string model = _config["Gemini:EmbeddingModel"]!;    foreach (DocumentChunk[] batch in doc.Chunks.Chunk(100))    {        var vectors = await _embeddings.GenerateAsync(            batch.Select(c => EmbeddingText.Document(doc.FileName, c.Content)),            cancellationToken: ct);        for (int i = 0; i < batch.Length; i++)        {            batch[i].Embedding = new Vector(vectors[i].Vector);            batch[i].EmbeddingModel = model;        }    }     // 4: into the database — the document and all its parts together    _db.Documents.Add(doc);    await _db.SaveChangesAsync(ct);    return Ok(new { doc.Id, Chunks = doc.Chunks.Count });}

Compared with lecture 10, only two things are new: reading the PDF and chunking. The vector, the prefix (EmbeddingText.Document — the file name as the title), Chunk(100), vector(768) — all familiar.

💡

This endpoint does everything inside the request — a few seconds for 18 pages. For a 500-page document an HTTP request can't wait that long: in real systems the file is stored and the ingestion runs in a background worker (with a status: “processing…”). In the ⭐ — re-uploading a document (deleting the old parts).

Part 3 · Query: an answer with a source

Slide 14

For the question we find the 5 closest parts, put them into the prompt as numbered sources and write the rules: “only from the sources, with the number, if it isn't written — say so”. Finally all of this joins lecture 7's chat.

Retrieve and augment

Slide 15

Retrieve — lecture 10's search, but on parts and with 5 results:

Controllers/AiLabController.cs · SearchChunksAsync
public record FoundChunk(string File, int Page, string Content, double Score); private async Task<List<FoundChunk>> SearchChunksAsync(string q, CancellationToken ct){    float minScore = _config.GetValue<float>("Rag:MinScore");   // by testing — like lecture 9's homework    var query = new Vector(await _embeddings.GenerateVectorAsync(        EmbeddingText.Query(q), cancellationToken: ct));     List<FoundChunk> top = await _db.DocumentChunks        .Where(c => c.Embedding != null)        .OrderBy(c => c.Embedding!.CosineDistance(query))        .Select(c => new FoundChunk(c.Document.FileName, c.Page, c.Content,            1 - c.Embedding!.CosineDistance(query)))        .Take(5)        .ToListAsync(ct);     return top.Where(c => c.Score >= minScore).ToList();}
  • top 5 — several parts: the answer may be in two places. More — the context gets expensive and the “noise” grows.
  • The threshold — lecture 9's lesson: a search always finds something. “A borscht recipe” would still return the five “closest” parts of the restaurant's rules — and the model would “answer” something based on them. In such a case the threshold returns 0 parts.

Augment — we put the parts into the prompt as numbered sources:

Controllers/AiLabController.cs · BuildContext
private static string BuildContext(List<FoundChunk> chunks) =>    chunks.Count == 0        ? "(No relevant information was found in the sources)"        : string.Join("\n\n", chunks.Select((c, i) => $"[{i + 1}] ({c.File}, p. {c.Page})\n{c.Content}"));

Why numbers and the page: the model can write [1] in the answer — and we know which file and page it means. The user checks the source themselves, and we see where the answer came from (and with a wrong answer — which part was bad).

📘 Terms
Retrieve
finding the parts relevant to the question
Augment
putting the found parts into the prompt
Citation
a source number in the answer that points to a file and a page

RAG in the chat: history + sources + question

Slide 16

Lecture 7's /chat gets one more step — the search and an augmented message:

Controllers/AiLabController.cs · Chat
List<ChatMessage> history = await _history.LoadAsync(conversationId, ct);IEnumerable<ChatMessage> recent = await Reducer.ReduceAsync(history, ct); List<FoundChunk> sources = await SearchChunksAsync(request.Prompt, ct);   // retrieveChatMessage question = new(ChatRole.User, request.Prompt);ChatMessage augmented = new(ChatRole.User, $"""    Sources:    {BuildContext(sources)}     Question: {request.Prompt}    """);                                                                  // augment List<ChatMessage> messages = [SystemPrompt(), .. recent, augmented];ChatResponse response = await _chat.GetResponseAsync(messages, ChatToolOptions(), ct);   // generate await _history.AppendAsync(conversationId, [question, .. response.Messages], ct);return Ok(new { conversationId, response.Text,    Sources = sources.Select((s, i) => new { N = i + 1, s.File, s.Page }) });

The rules in SystemPrompt() (with lecture 2's techniques):

text
Answer about the restaurant's rules, allergens and policy only from the given sourcesand give the source number for every fact: [1], [2].If the answer isn't in the sources, say: “I don't have information on this” — and make nothing up.Data on the menu, prices and free tables — only from the tools (as before).

Three important details:

  1. The original question is stored in the history (question), not augmented. The sources are only for this request: on the next question other sources will be found. If we stored the sources in the history, every message would be “inflated” with five parts (lecture 7's budget).
  2. “I don't have information” — an exact phrase: this way we can also recognize it in code (logs, statistics: which questions we can't answer — which document is missing).
  3. The sources in the response — the UI can show a link on [1]: “rules.pdf, p. 3”.

“We always search” vs a tool. Our chat searches on every question — on “hello” too (the threshold returns 0 parts, but the embedding call still happens). In lecture 9's ⭐ there was a search_menu tool: the model decides by itself when to search. Both are real approaches:

We always search (today) Search as a tool (lecture 15)
Plus simple, predictable, the model can't “forget” to search search only when needed; the model refines the question by itself
Minus extra searches; the question “and for children?” is searched without the previous context the model may not search when it's needed

Slide 18

These questions will also be asked at the start of the next lecture.

✅ Check yourself think first, then open the answer
Why don't we put the whole PDF into the context, and why don't we train the model (fine-tuning)?
The whole PDF — thousands of tokens on every question, slow, a large document doesn't fit, “lost in the middle” · fine-tuning — expensive, again on every change, it memorizes facts badly and can't name the source
What are RAG's two pipelines, and when does each one run?
ingestion — once, on upload: PDF → text → parts → vectors → database · query — on every question: vector → top 5 → prompt → an answer with a source
Why do we cut a document into parts, and what do we need the overlap for?
The vector of a whole document is the “average” of everything — blurry; a part = one idea, a precise vector and a cheap context · the overlap — the last sentence in the next part too, so an idea isn't cut at the boundary
Why do we need a threshold in RAG's search?
A search always finds something · without a threshold, for “a borscht recipe” the model would get 5 meaningless parts and might make something up · with a threshold — 0 parts and “I don't have information”
Why do we store the original question in the chat history and not the message with the sources (augmented)?
The sources are only for this request — others will be found next time · storing them in the history would inflate every message with 5 parts (the budget, lecture 7)

Summary

Slide 19
  • RAG (Retrieval-Augmented Generation) — the model answers from our documents: retrieve (the relevant parts) → augment (into the prompt) → generate (an answer with a source). It's cheaper than the whole document, simpler than fine-tuning, and it names the source.
  • Ingestion (once): PDF → text page by page (PdfPig, ContentOrderTextExtractor) → cleaning → chunks → vectors → the DocumentChunk table (the lecture 10 way). A scanned PDF needs OCR.
  • Chunking: ~800 characters, on a sentence boundary, an overlap of one sentence; page by page — for an exact source. The size is a compromise between precision and context.
  • Query: top 5 parts + a threshold → numbered sources [1] (file, p. N) → rules in the system prompt: only from the sources, with the number, “I don't have information on this”.
  • In the chat: the original question goes into the history, the sources — only into this request; sources in the response.

All terms of the lecture

Terms

Fine-tuning
extra training of an existing model on your own data; good for style and format, less so for facts
Lost in the middle
in a long context the model more often “misses” information in the middle part
RAG (Retrieval-Augmented Generation)
a model answer that relies on our documents found by search
Ingestion
preparing a document for search: text → parts → vectors → database
Chunk
a part of a document that is stored and searched as a separate vector
PdfPig
a .NET library for reading text and content from PDFs (Apache-2.0)
OCR
recognizing text in an image; a scanned PDF needs it
Chunking
cutting a document into parts for search
Overlap
the overlap between parts: the last text is repeated in the next part too
IFormFile
ASP.NET Core's type for an uploaded file (multipart/form-data)
Retrieve
finding the parts relevant to the question
Augment
putting the found parts into the prompt
Citation
a source number in the answer that points to a file and a page
Augmented message
the user's question with the found sources attached; sent only in this request
