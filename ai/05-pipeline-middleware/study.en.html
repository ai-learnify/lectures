Chat Client Pipeline and Middleware

The whole lecture in chapters, ~17 minutes of reading. Your progress is saved in the browser. This page follows the presentation: when the slide changes, the matching part is highlighted.

⚡ In 5 minutes

If this is all you remember, you know the core of the lecture:

  1. AddChatClient returns a ChatClientBuilder. Every .Use…() adds one layer (middleware) to the IChatClient — just like app.Use…() in ASP.NET Core.
  2. A layer = an IChatClient around another IChatClient. The request goes in, the response comes back. The first .Use…() is the outer layer (close to the Controller). The Controller knows nothing about the layers.
  3. UseLogging — shows how many requests went to Gemini (Debug); Trace writes the full text — development only.
  4. UseDistributedCache — doesn't call Gemini for exactly the same request. Only for answers that don't change; not in a chat with tools.
  5. DelegatingChatClient — your own layer: before base the request, after base the response; without base — a stop (short-circuit).

Does the model call our C# method itself? Describe the loop step by step.
No · 1) us: the question + the list of tools · 2) the model: a call request (name + arguments) · 3) our code runs the method and sends the result · 4) the model: a text answer · at least 2 requests to Gemini
The model can't see a tool's code. How does it learn what the tool does and when to call it?

The pipeline: layers around the client

🎯 After this You'll explain what .UseFunctionInvocation() is and how a request passes through the layers from the Controller to Gemini.

Part 1 · The pipeline

Slide 6

We barely write code in this part. We find out what lecture 4's “magic” line was, and why the idea is familiar from the API course.

.UseFunctionInvocation() — what is it

Slide 7

In lecture 4 this one line ran the whole tool loop. Where have we seen a similar .Use…()? In the API course's Program.cs:

Program.cs · API course
app.UseExceptionHandler();app.UseAuthentication();app.UseAuthorization();app.MapControllers();

That's ASP.NET Core middleware: an HTTP request passes through layers before it reaches the Controller, and each layer does its own job (errors, authentication, authorization).

Microsoft.Extensions.AI has the same idea, just in another place: from the Controller to Gemini. AddChatClient(...) returns a ChatClientBuilder (we mentioned it in lecture 3), and every .Use…() adds one layer to the client. .UseFunctionInvocation() was the first such layer.

📘 Terms
Middleware (layer)
code that sits between the request and the response: it can look at them, change them or stop them
ChatClientBuilder
the object AddChatClient returns; its .Use…() methods add layers to the IChatClient

The pipeline: layers around the client

Slide 8

Each layer is itself an IChatClient that holds another IChatClient inside (this is called the decorator pattern). The Controller calls the outer layer, it calls the inner one, and so on down to the Gemini client:

plain
Controller → FunctionInvocation → Logging → Gemini client → Google           ←                    ←         ←               ←
  • The request goes from left to right, the response comes back. Every layer sees both: it can change the request, look at the response, or stop the request altogether.
  • FunctionInvocation works like this: it lets the request in, sees a tool request in the response, calls the method and sends the request in again. That's why two requests reach Gemini, while the Controller gets one response.
  • Order: the first .Use…() in Program.cs is closest to the Controller (the outer layer), and the last one is closest to Gemini.
Program.cs
builder.Services.AddChatClient(gemini)   // inside: the Gemini client    .UseFunctionInvocation()             // 1 — outer layer (close to the Controller)    .UseLogging();                       // 2 — inner layer (close to Gemini)

The Controller knows nothing about the layers: it gets an IChatClient through the constructor. Adding or removing a layer happens only in Program.cs. It's the same benefit as with lecture 3's DI: the Controller's code doesn't change.

📘 Terms
Pipeline
a chain of layers from the Controller to Gemini; the request goes in, the response comes back

Ready-made layers: logging and caching

🎯 After this You'll switch on logging and caching, see the two requests of the tool loop and understand when caching is dangerous.

Part 2 · Ready-made layers

Slide 9

Microsoft.Extensions.AI has several ready-made layers. We try two: logging, which shows what happens between the Controller and Gemini, and caching, which doesn't call Gemini again for the same question. Each is one line in Program.cs.

UseLogging: what happens between the Controller and Gemini

Slide 10
Program.cs
builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .UseFunctionInvocation()    .UseLogging();

UseLogging() takes the logger from DI by itself (ILoggerFactory), just like your services in the API course. It writes at the Debug level, so in appsettings.Development.json we have to lower the level for Microsoft.Extensions.AI:

appsettings.Development.json
{  "Logging": {    "LogLevel": {      "Default": "Information",      "Microsoft.Extensions.AI": "Debug"    }  }}

What we'll see on /chat (“How much is lobio?”): in the application console, two requests to Gemini (GetResponseAsync invoked / completed) with the get_menu call between them. That's lecture 4's loop, now in the log. The exact text depends on the library version.

Why do both requests show up? UseLogging is the inner layer (we added it last), closest to Gemini. Every request of the FunctionInvocation loop passes through it.

⚠️

At the Trace level ("Microsoft.Extensions.AI": "Trace") the log also contains the full text of the request and the response: users' questions, tool results. It's handy for debugging, but in production it's a leak of personal data. Trace only in appsettings.Development.json.

UseDistributedCache: the same question without Gemini

Slide 11
Program.cs
builder.Services.AddDistributedMemoryCache(); builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .UseDistributedCache()    .UseFunctionInvocation()    .UseLogging();
  • AddDistributedMemoryCache() — the cache store, in the application's memory (IDistributedCache). UseDistributedCache() takes it from DI. On a real server this could be Redis, and the code wouldn't change.
  • The key — the messages + the options (ChatOptions). If exactly the same request comes in, the response comes from memory and no request goes to Gemini.

We try it on /ask, with the same question twice:

Time In the log (LoggingChatClient)
1st ~2 seconds invoked / completed — a request to Gemini
2nd a few milliseconds nothing — it never reached Gemini

The log is empty because the cache is the outer layer (the first .Use…()) and logging is an inner one. The cache returned the response itself and the request never went down to the inner layers.

💡

Usage shows the same tokens on the second response too: it's a copy of the stored response. No tokens were actually spent the second time. The log and the time prove it.

When is caching dangerous? “There are four of us, tomorrow at 8 — do you have a table?” — the question's text is the same, but the answer depends on the database. In ten minutes the table may get booked, while the cache would still return “it's free”. A cache is good when the answer to the same question doesn't change: FAQ, translation, classifying the same text.

In our RestaurantApi /chat works with tools and availability changes, so we remove UseDistributedCache and AddDistributedMemoryCache. That's another advantage of the pipeline: removing a layer is deleting one line.

📘 Terms
UseDistributedCache
a layer that returns a stored response for exactly the same request, without calling Gemini

Our own layer: DelegatingChatClient

🎯 After this You'll write a layer that counts tokens and a layer that doesn't let a long question reach Gemini.

Part 3 · Our own layer

Slide 13

Ready-made layers can't do everything. We want, for example, to count tokens on every request, or to stop a too-long question before it reaches Gemini (money!). For that we write our own layer: a class that inherits from DelegatingChatClient.

TokenCounterChatClient: our first layer

Slide 14
Ai/TokenCounterChatClient.cs
using Microsoft.Extensions.AI; public class TokenCounterChatClient : DelegatingChatClient{    private readonly ILogger<TokenCounterChatClient> _logger;     public TokenCounterChatClient(IChatClient inner,        ILogger<TokenCounterChatClient> logger) : base(inner)    {        _logger = logger;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages,        ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        // ↓ here is the request — it hasn't reached Gemini yet        ChatResponse response =            await base.GetResponseAsync(messages, options, cancellationToken);        // ↑ here is the response — Gemini has already answered         _logger.LogInformation("🔢 in: {In}, out: {Out}, total: {Total}",            response.Usage?.InputTokenCount,            response.Usage?.OutputTokenCount,            response.Usage?.TotalTokenCount);         return response;    }}
  • DelegatingChatClient — Microsoft.Extensions.AI's base class for layers. It passes every IChatClient method on to the inner client. We change (override) only what we need, here GetResponseAsync.
  • inner — the next layer in the pipeline. We pass it to base(inner) in the constructor.
  • base.GetResponseAsync(...) — passing the request inward, to the next layer. It's exactly the analogue of ASP.NET Core middleware's await next(context):
  • code written before base sees the request (before Gemini),
  • code written after base sees the response (after Gemini).
  • response.Usage — the tokens (lecture 2). We write them to the log at the Information level.
📘 Terms
DelegatingChatClient
a base class for a layer: it passes every request to the inner client; we override only what we need

Registration and order

Slide 15

We add our layer with .Use(...). We need ILogger from DI, so we use the version that also gives us the IServiceProvider (sp):

Program.cs
builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .UseFunctionInvocation()    .Use((inner, sp) => new TokenCounterChatClient(        inner, sp.GetRequiredService<ILogger<TokenCounterChatClient>>()))    .UseLogging();

Order changes the result. /chat “How much is lobio?” — with the tool loop there are two requests to Gemini:

Where the counter sits In the log What it counts
A — before UseFunctionInvocation (outside) 1 line the total for one Controller request: FunctionInvocation adds up both requests' tokens and returns them as one response
B — after UseFunctionInvocation (inside) 2 lines every Gemini request separately: you can see the second request is more expensive (history + menu)

Both are correct; they just answer different questions: “what did one user question cost?” (A) or “what did each Gemini request cost?” (B). In RestaurantApi we keep B.

The numbers are a sample; yours will differ. What matters is the number of lines.

InputGuardChatClient: a layer that stops

Slide 16

TokenCounter only looks at the response. A layer can also stop the request: if we don't call base, the request doesn't go any further in.

Ai/InputGuardChatClient.cs
public class InputGuardChatClient : DelegatingChatClient{    private const int MaxLength = 1000;     public InputGuardChatClient(IChatClient inner) : base(inner) { }     public override Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages,        ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        string? question = messages.LastOrDefault(m => m.Role == ChatRole.User)?.Text;         if (question is not null && question.Length > MaxLength)        {            ChatMessage answer = new(ChatRole.Assistant,                $"The question is too long — {MaxLength} characters at most.");            return Task.FromResult(new ChatResponse(answer));        }         return base.GetResponseAsync(messages, options, cancellationToken);    }}
  • messages.LastOrDefault(m => m.Role == ChatRole.User) — the user's last question (we don't check the System prompt, it's ours).
  • Too long? We create the response ourselves and return it. base isn't called → no request goes to Gemini: 0 tokens, 0 GEL. This is called a short-circuit. ASP.NET Core middleware returns, say, a 401 the same way.
  • We don't need async here: we don't await anything, so we return Task.FromResult or base's Task directly.

The full pipeline in RestaurantApi:

Program.cs
builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .Use(inner => new InputGuardChatClient(inner))          // 1 — stops earliest    .UseFunctionInvocation()                                // 2 — the tool loop    .Use((inner, sp) => new TokenCounterChatClient(         // 3 — every Gemini request        inner, sp.GetRequiredService<ILogger<TokenCounterChatClient>>()))    .UseLogging();                                          // 4 — closest to Gemini

Why is the guard first? The earlier we stop, the less work: a blocked request reaches neither the tool loop, nor the counter, nor the log.

⚠️

A stopped request returns text. If an endpoint calls GetResponseAsync<T> (lecture 3, parse-booking), that text isn't JSON and .Result will throw an exception. Use TryGetResult there (lecture 3's ⭐), or guard at the endpoint itself, with a 400.

📘 Terms
Short-circuit
a layer doesn't pass the request to the next layer and returns a response itself

Classwork: Your layer — in your project

Slide 17

Your project or RestaurantApi · with code · Swagger + console

Steps

  • 1 · Logging — .UseLogging() in Program.cs, "Microsoft.Extensions.AI": "Debug" in appsettings.Development.json. One tool question on /chat → count the Gemini requests in the console
  • 2 · Your layer — Ai/<Name>ChatClient.cs : DelegatingChatClient, override GetResponseAsync. Pick one:
  • stops — by your rule (e.g. forbidden words, off-topic, an empty question) it returns a response itself, without base
  • watches — measures with a Stopwatch how long base took and writes it to the log
  • 3 · Registration — .Use(...) in Program.cs. Where does it go? Stops → first; watches → think: every request of the loop, or the total?
  • 4 · Check — 2 questions in Swagger: one your layer acts on, one ordinary

✓ Done when

The console shows the Gemini requests and your layer's line; in the “stops” variant the LoggingChatClient lines do not appear for a stopped question (it never reached Gemini); the Controller's code didn't change

⭐ Bonus

  • Write both variants and put them in the right order in Program.cs
  • An extension method: public static ChatClientBuilder UseInputGuard(this ChatClientBuilder b) => b.Use(inner => new InputGuardChatClient(inner)); → .UseInputGuard() in Program.cs
  • Have the layer append “answer in Georgian” to the user's question — changing the request before base

💡 If you're stuck

  • Ideas: library — stops a question containing “password” or “key” · shop — stops an empty question or one shorter than 3 characters · anything — a Stopwatch and LogInformation("⏱ {Ms} ms", sw.ElapsedMilliseconds)
  • Nothing in the console? Check the level in appsettings.Development.json and the launch profile (Development)
  • Can't find DelegatingChatClient? using Microsoft.Extensions.AI;
  • Need an ILogger in the layer? .Use((inner, sp) => new MyChatClient(inner, sp.GetRequiredService<ILogger<MyChatClient>>()))
  • /parse-booking throws when stopped? The stop text isn't JSON — use TryGetResult on a structured endpoint (lecture 3)

Summary

Slide 19
  • ChatClientBuilder — what AddChatClient returns. Every .Use…() adds one layer (middleware) to the IChatClient. .UseFunctionInvocation() is one such layer.
  • A layer = an IChatClient around another IChatClient. The request goes in, the response comes back, and every layer sees both. The Controller knows nothing about the layers.
