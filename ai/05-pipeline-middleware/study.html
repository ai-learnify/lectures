Chat Client Pipeline და Middleware

ლექციის სრული მასალა თავებად, ~14 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. AddChatClient აბრუნებს ChatClientBuilder-ს. ყოველი .Use…() IChatClient-ს ერთ ფენას (middleware) ამატებს — ისევე, როგორც app.Use…() ASP.NET Core-ში.
  2. ფენა = IChatClient სხვა IChatClient-ის გარშემო. მოთხოვნა შიგნით მიდის, პასუხი უკან ბრუნდება. პირველი .Use…() გარე ფენაა (Controller-თან ახლოს). Controller ფენებზე არაფერს იცის.
  3. UseLogging — ჩანს, რამდენი მოთხოვნა წავიდა Gemini-სთან (Debug); Trace მთელ ტექსტს წერს — მხოლოდ დეველოპმენტში.
  4. UseDistributedCache — ზუსტად იგივე მოთხოვნაზე Gemini-ს არ მიმართავს. მხოლოდ უცვლელ პასუხებზე; tool-იან ჩატში — არა.
  5. DelegatingChatClient — საკუთარი ფენა: base-მდე მოთხოვნა, base-ის შემდეგ პასუხი; base-ის გარეშე — შეჩერება (short-circuit).

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~14 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“
  2. გაიარე ტესტი — 11 კითხვა, ქულით
  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

სლაიდი 8

ყოველი ფენა თვითონაც IChatClient-ია, რომელსაც შიგნით სხვა IChatClient აქვს (ამას decorator ნიმუშს ეძახიან). Controller იძახებს გარე ფენას, ის შიდას, და ასე Gemini-ს client-მდე:

plain
Controller → FunctionInvocation → Logging → Gemini client → Google           ←                    ←         ←               ←
  • მოთხოვნა მარცხნიდან მარჯვნივ მიდის, პასუხი უკან ბრუნდება. ყოველი ფენა ორივეს ხედავს: შეუძლია მოთხოვნა შეცვალოს, პასუხს შეხედოს ან მოთხოვნა საერთოდ შეაჩეროს.
  • FunctionInvocation ასე მუშაობს: მოთხოვნას შიგნით უშვებს, პასუხში tool-ის თხოვნას ხედავს, მეთოდს იძახებს და მოთხოვნას ისევ შიგნით უშვებს. ამიტომ Gemini-მდე ორი მოთხოვნა მიდის, Controller კი ერთ პასუხს იღებს.
  • რიგი: Program.cs-ში პირველი .Use…() Controller-თან ყველაზე ახლოა (გარე ფენა), ბოლო კი Gemini-სთან.

Microsoft.Extensions.AI-ს რამდენიმე მზა ფენა აქვს. ორს ვცდით: ლოგს, რომელიც გვაჩვენებს, რა ხდება Controller-სა და Gemini-ს შორის, და ქეშს, რომელიც იგივე კითხვაზე Gemini-ს აღარ მიმართავს. ორივე ერთი ხაზია Program.cs-ში.

UseLogging: რა ხდება Controller-სა და Gemini-ს შორის

სლაიდი 10
Program.cs
builder.Services.AddChatClient(        new Client(apiKey: apiKey).AsIChatClient(model))    .UseFunctionInvocation()    .UseLogging();

UseLogging() ლოგერს DI-დან თვითონ იღებს (ILoggerFactory), ისევე, როგორც შენი სერვისები API კურსზე. ის ლოგს Debug დონეზე წერს, ამიტომ appsettings.Development.json-ში Microsoft.Extensions.AI-სთვის დონე უნდა დავწიოთ:

appsettings.Development.json
{  "Logging": {    "LogLevel": {      "Default": "Information",      "Microsoft.Extensions.AI": "Debug"    }  }}

რას დავინახავთ /chat-ზე („ლობიო რა ღირს?“): აპლიკაციის კონსოლში Gemini-სთან ორი მოთხოვნა (GetResponseAsync invoked / completed) და მათ შორის get_menu-ს გამოძახება. ეს ლექცია 4-ის ციკლია, ახლა ლოგში. ზუსტი ტექსტი ბიბლიოთეკის ვერსიაზეა დამოკიდებული.

რატომ ჩანს ორივე მოთხოვნა? UseLogging შიდა ფენაა (ბოლოს დავამატეთ), Gemini-სთან ყველაზე ახლოს. FunctionInvocation-ის ციკლის ყოველი მოთხოვნა მასში გადის.

⚠️

Trace დონეზე ("Microsoft.Extensions.AI": "Trace") ლოგში მოთხოვნის და პასუხის მთელი ტექსტიც იწერება: მომხმარებლის შეკითხვები, tool-ების შედეგები. ეს დებაგისთვის მოსახერხებელია, მაგრამ production-ში პირადი მონაცემების გაჟონვაა. Trace მხოლოდ appsettings.Development.json-ში.

  • AddDistributedMemoryCache() — ქეშის საცავი, აპლიკაციის მეხსიერებაში (IDistributedCache). UseDistributedCache() მას DI-დან იღებს. რეალურ სერვერზე აქ Redis შეიძლება იყოს, და კოდი არ შეიცვლება.
  • გასაღები — შეტყობინებები + პარამეტრები (ChatOptions). თუ ზუსტად იგივე მოთხოვნა მოვიდა, პასუხი მეხსიერებიდან ბრუნდება და Gemini-სთან მოთხოვნა არ მიდის.

ვცდით /ask-ზე, ერთი და იგივე კითხვით ორჯერ:

Usage-ში მეორე პასუხზეც იგივე ტოკენები ჩანს: ეს შენახული პასუხის ასლია. რეალურად ტოკენები მეორედ არ დახარჯულა. ამას ლოგი და დრო ამტკიცებს.

როდის არის ქეში სახიფათო? „ხვალ 8-ზე ოთხნი ვართ, ადგილი გაქვთ?“ — ეს კითხვა ტექსტით იგივეა, პასუხი კი ბაზაზეა დამოკიდებული. ათ წუთში მაგიდა შეიძლება დაიჯავშნოს, ქეში კი ისევ „თავისუფალია“-ს დააბრუნებს. ქეში კარგია, როცა ერთსა და იმავე შეკითხვაზე პასუხი არ იცვლება: FAQ, თარგმანი, ერთი და იგივე ტექსტის კლასიფიკაცია.

ჩვენს RestaurantApi-ში /chat tool-ებით მუშაობს და ხელმისაწვდომობა იცვლება, ამიტომ UseDistributedCache-ს და AddDistributedMemoryCache-ს ვაშორებთ. ესეც pipeline-ის უპირატესობაა: ფენის მოშორება ერთი ხაზის წაშლაა.

ჩვენი ფენა: DelegatingChatClient

🎯 ამის შემდეგ: დაწერ ფენას, რომელიც ტოკენებს ითვლის, და ფენას, რომელიც გრძელ შეკითხვას Gemini-მდე არ უშვებს.

ნაწილი 3 · ჩვენი ფენა

სლაიდი 13

მზა ფენები ყველაფერს ვერ აკეთებს. გვინდა, მაგალითად, ყოველ მოთხოვნაზე ტოკენების დათვლა, ან ზედმეტად გრძელი შეკითხვის შეჩერება, სანამ Gemini-მდე მივა (ფული!). ამისთვის საკუთარ ფენას ვწერთ: კლასს, რომელიც DelegatingChatClient-ს მემკვიდრეობს.

using Microsoft.Extensions.AI; public class TokenCounterChatClient : DelegatingChatClient{    private readonly ILogger<TokenCounterChatClient> _logger;     public TokenCounterChatClient(IChatClient inner,        ILogger<TokenCounterChatClient> logger) : base(inner)    {        _logger = logger;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages,        ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        // ↓ აქ მოთხოვნაა — ჯერ Gemini-მდე არ მისულა        ChatResponse response =            await base.GetResponseAsync(messages, options, cancellationToken);        // ↑ აქ პასუხია — Gemini-მ უკვე უპასუხა         _logger.LogInformation("🔢 in: {In}, out: {Out}, total: {Total}",            response.Usage?.InputTokenCount,            response.Usage?.OutputTokenCount,            response.Usage?.TotalTokenCount);         return response;    }}
  • DelegatingChatClient — Microsoft.Extensions.AI-ის საბაზო კლასი ფენებისთვის. ის IChatClient-ის ყველა მეთოდს შიდა client-ს გადასცემს. ჩვენ ვცვლით (override) მხოლოდ იმას, რაც გვჭირდება, აქ GetResponseAsync-ს.
  • inner — შემდეგი ფენა pipeline-ში. constructor-ში base(inner)-ს გადავცემთ.
  • base.GetResponseAsync(...) — მოთხოვნას შიგნით, შემდეგ ფენაზე გადაცემა. ზუსტად ASP.NET Core middleware-ის await next(context)-ის ანალოგი:
  • base-მდე დაწერილი კოდი მოთხოვნას ხედავს (Gemini-მდე),
  • base-ის შემდეგ დაწერილი კოდი პასუხს ხედავს (Gemini-ს მერე).
  • response.Usage — ტოკენები (ლექცია 2). ვწერთ ლოგში Information დონეზე.

რეგისტრაცია და რიგი

სლაიდი 15

ჩვენს ფენას .Use(...)-ით ვამატებთ. ILogger DI-დან გვჭირდება, ამიტომ ვიყენებთ ვერსიას, რომელიც IServiceProvider-საც იძლევა (sp):

რიგი ცვლის შედეგს. /chat „ლობიო რა ღირს?“ — tool-ის ციკლით Gemini-სთან ორი მოთხოვნაა:

სად დგას მთვლელი ლოგში რას ითვლის
A — UseFunctionInvocation-ის წინ (გარეთ) 1 ხაზი Controller-ის ერთი მოთხოვნის ჯამს: FunctionInvocation ორივე მოთხოვნის ტოკენებს აჯამებს და ერთ პასუხად აბრუნებს
B — UseFunctionInvocation-ის შემდეგ (შიგნით) 2 ხაზი Gemini-ს ყოველ მოთხოვნას ცალკე: ჩანს, რომ მეორე მოთხოვნა უფრო ძვირია (ისტორია + მენიუ)

ორივე სწორია, უბრალოდ სხვადასხვა კითხვას პასუხობს: „რა დაჯდა მომხმარებლის ერთი შეკითხვა?“ (A) თუ „რა დაჯდა Gemini-ს თითო მოთხოვნა?“ (B). RestaurantApi-ში B-ს ვტოვებთ.

ციფრები ნიმუშია, შენთან სხვა იქნება. მთავარია ხაზების რაოდენობა.

InputGuardChatClient: ფენა, რომელიც აჩერებს

სლაიდი 16

TokenCounter პასუხს მხოლოდ უყურებს. ფენას მოთხოვნის შეჩერებაც შეუძლია: თუ base-ს არ გამოვიძახებთ, მოთხოვნა შიგნით აღარ მიდის.

Ai/InputGuardChatClient.cs
public class InputGuardChatClient : DelegatingChatClient{    private const int MaxLength = 1000;     public InputGuardChatClient(IChatClient inner) : base(inner) { }     public override Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages,        ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        string? question = messages.LastOrDefault(m => m.Role == ChatRole.User)?.Text;         if (question is not null && question.Length > MaxLength)        {            ChatMessage answer = new(ChatRole.Assistant,                $"შეკითხვა ძალიან გრძელია — მაქსიმუმ {MaxLength} სიმბოლო.");            return Task.FromResult(new ChatResponse(answer));        }         return base.GetResponseAsync(messages, options, cancellationToken);    }}
  • messages.LastOrDefault(m => m.Role == ChatRole.User) — მომხმარებლის ბოლო შეკითხვა (System prompt-ს არ ვამოწმებთ, ის ჩვენია).
  • გრძელია? ვქმნით პასუხს თვითონ და ვაბრუნებთ. base არ გამოიძახება → Gemini-მდე მოთხოვნა არ მიდის: 0 ტოკენი, 0 ლარი. ამას short-circuit ჰქვია. ASP.NET Core-ის middleware-იც ასე აბრუნებს, მაგალითად, 401-ს.
  • async აქ არ გვჭირდება: არაფერს ველოდებით, ამიტომ Task.FromResult-ს ან base-ის Task-ს პირდაპირ ვაბრუნებთ.
