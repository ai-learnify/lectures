Error Handling, Resilience and Cost Control

🎯 After this lecture you can

  • You'll sort an error as transient, permanent or a content error, and explain which ones retry helps with
  • You'll add retry, timeout and a circuit breaker to an HttpClient with AddStandardResilienceHandler, give that client to Google.GenAI and turn off its own retry
  • You'll write a FallbackChatClient that calls a fallback model on a transient error
  • You'll write the tokens of every call to the database (IServiceScopeFactory) and calculate the day's cost

⚡ Key points

  1. Errors fall into three groups: transient (429, 5xx, timeout: retry helps), permanent (400, 401, 403, 404: it does not), content (length, bad JSON: we check in code).
  2. A proper retry: backoff + jitter, Retry-After, a timeout and a circuit breaker.
  3. AddStandardResilienceHandler on the HttpClient. The SDK's own retry is turned off: retry lives in one place.
  4. FallbackChatClient switches to another model only on a transient error and sits innermost.
  5. We write tokens to the database. A Singleton layer gets the Scoped DbContext through IServiceScopeFactory.

What breaks

▶ Slides 6–8

Any day Gemini may return 503 (overloaded) or 429 (limit reached). It is not our bug, and it often goes away by itself shortly.

Group Example What we do
Transient 429, 500, 503, timeout retry, with a pause
Permanent 400, 401 (key), 403, 404 (model) do not retry, fix it
Content length, bad JSON, a tool error check in code
✅ Check yourself think first, then open the answer
What do 5 retries on a 401 give us?
Nothing: the key is the same and so is the error. The user just waits longer.
📘 Terms
transient error
an error that may not repeat on a retry

Retry and timeout

▶ Slides 9–12

"Failed? Retry immediately, 10 times" makes things worse: Gemini is already overloaded. A proper retry has:

  • backoff: the pause grows with each attempt (1 s, 2 s, 4 s)
  • jitter: a random part added to the pause, so all clients do not come back at once
  • Retry-After: if the server says how long to wait, we listen
  • circuit breaker: after many failures we stop trying for a while

Microsoft.Extensions.Http.Resilience adds this to the HttpClient in one line. Google.GenAI has its own retry, so we turn it off so the retries do not nest:

Program.cs
builder.Services.AddHttpClient("gemini")    .AddStandardResilienceHandler(o =>    {        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(40);   // an LLM is slow        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(90);        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(90);    }); builder.Services.AddChatClient(sp =>    {        IHttpClientFactory http = sp.GetRequiredService<IHttpClientFactory>();        Client gemini = new(            apiKey: apiKey,            httpOptions: new HttpOptions { RetryOptions = new HttpRetryOptions { Attempts = 1 } },            clientOptions: new ClientOptions { HttpClientFactory = () => http.CreateClient("gemini") });        return gemini.AsIChatClient(model);    })    .Use(inner => new InputGuardChatClient(inner))    .UseFunctionInvocation()    // ... the other layers — as before

Fallback and cost

▶ Slides 14–16

If the model has been overloaded for 5 minutes, all three retries fail too. Then we switch to another model. A layer catches the error, but only a transient one:

Ai/FallbackChatClient.cs
public class FallbackChatClient : DelegatingChatClient{    private readonly IChatClient _fallback;    private readonly ILogger<FallbackChatClient> _logger;     public FallbackChatClient(IChatClient inner, IChatClient fallback,        ILogger<FallbackChatClient> logger) : base(inner)    {        _fallback = fallback;        _logger = logger;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages, ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        try        {            return await base.GetResponseAsync(messages, options, cancellationToken);        }        catch (Exception ex) when (IsTransient(ex))        {            _logger.LogWarning("🛟 {Error} — fallback model", ex.Message);            return await _fallback.GetResponseAsync(messages, options, cancellationToken);        }    }     private static bool IsTransient(Exception ex) => ex switch    {        ApiException api => api.StatusCode is 429 or >= 500,        HttpRequestException or TimeoutRejectedException => true,        _ => false    };}

✅ Check yourself think first, then open the answer
Why not simply DataContext db in the layer's constructor?
The pipeline is a Singleton and DbContext is Scoped. One DbContext would be shared by every request forever, so we create a scope ourselves.
Why catch … when (IsTransient(ex)) in the fallback and not catch (Exception)?
On a permanent error (e.g. 404) a backup model does not help; it only hides the problem.
📘 Terms
fallback
a backup: if the main service does not answer, the request goes elsewhere
IServiceScopeFactory
creates a scope inside a Singleton so we can get a Scoped service (DbContext)

📝 Classwork

A daily limit — a layer that stops

Your project or RestaurantApi · with code · a layer + Swagger

Steps

  • 1 · The table — AiUsageRecord (Id, At, Model, InputTokens, OutputTokens), DbSet<AiUsageRecord> AiUsage, a migration; TokenCounterChatClient writes to the database (slide 16)
  • 2 · The layer — BudgetGuardChatClient : DelegatingChatClient: IServiceScopeFactory and long dailyLimit in the constructor; in GetResponseAsync — a scope → the sum of today's tokens (At >= DateTime.UtcNow.Date) → if ≥ the limit, an answer without base: “Today's limit is used up”
  • 3 · The pipeline — the limit in appsettings.json ("Ai": { "DailyTokenLimit": 3000 }); the layer as the first .Use(...) — the outermost
  • 4 · Check — several questions in Swagger until you go over the limit → the refusal answer, and the log no longer shows a Gemini request; in the database SELECT SUM("InputTokens" + "OutputTokens") FROM "AiUsage"

✓ Done when

AiUsage gets a new row for every call; after the limit the chat refuses without calling Gemini; the limit can only be changed through appsettings.json

⭐ Bonus

  • A limit per user, not for the whole app: add a ConversationId to AiUsageRecord and count the limit per conversation. What has to be passed to the layer, and how?
  • Instead of refusing, switch to a cheaper model at 80% of the limit
  • What's better in a browser/UI: a 200 with the refusal text, or a 429? Why?

💡 If you're stuck

  • Cannot consume scoped service 'DataContext' from singleton? Don't put DataContext straight into the layer — IServiceScopeFactory → CreateScope() → GetRequiredService<DataContext>()
  • The sum: await db.AiUsage.Where(u => u.At >= today).SumAsync(u => u.InputTokens + u.OutputTokens, cancellationToken)
  • The refusal answer: return new ChatResponse(new ChatMessage(ChatRole.Assistant, "...")); — like lecture 5's InputGuard
  • The limit from configuration: .Use((inner, sp) => new BudgetGuardChatClient(inner, sp.GetRequiredService<IServiceScopeFactory>(), builder.Configuration.GetValue<long>("Ai:DailyTokenLimit")))
  • TokenCounter still writes to the log? Change it first (step 1) — otherwise the sum is always 0
