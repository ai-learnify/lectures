Chapter 1 · ~3 min read

What breaks: the error map

🎯 After this You'll sort an error as transient, permanent or content, and explain which ones retry helps with.

Part 1 · What breaks

Slide 6

First we see what the user sees when Gemini fails. Then we sort the errors into groups: reacting the same way to every error is wrong.

The problem: Gemini sometimes fails

Slide 7

Two typical responses that Gemini will return on any given day:

Code Status What it means
503 UNAVAILABLE “The model is overloaded, please try again later” — too many requests on Google's side
429 RESOURCE_EXHAUSTED our limit ran out: the number of requests or tokens per minute (the limit is small on a free key)

On such a response Google.GenAI throws an exception: ServerError (5xx) or ClientError (4xx). Both are ApiExceptions, with a StatusCode property. We don't catch it, so ASP.NET Core returns a 500 to the user. On top of that, in lecture 7's /chat the AppendAsync comes after the answer, so the question is lost too.

This isn't our bug: an external service sometimes fails, the network drops. It will definitely happen. But the reaction is ours. A person would wait a few seconds and try again: that's exactly what we teach the code.

The error map: three groups

Slide 8
What happened What it means Group What we do
429 A limit: too many requests or tokens per minute transient we wait (if the response says Retry-After — exactly that long) and try again
500 · 503 Gemini is overloaded or has an internal error transient retry; if it doesn't work — a fallback model
timeout The answer takes too long, the network drops transient a time limit and retry
400 · 401 · 403 · 404 A wrong request, key, permission or model name permanent no retry: the same request brings the same error. Log it and fix it
FinishReason = length · bad JSON An answer arrived, but it's cut off or doesn't match the schema content in code: headroom in MaxOutputTokens (lecture 2), TryGetResult (lecture 3)
tool exception Our C# method failed content FunctionInvokingChatClient returns the error to the model, and the model writes the answer anyway

The main rule: retry only on a transient error. On a 401 (wrong key), trying again five times gives five 401s and wastes the user's time. Same with a 400: the request is wrong and will stay wrong.

Content errors don't show at the HTTP level: the status is 200, an answer arrived. Our code checks them: lecture 3's TryGetResult (if the JSON doesn't match the schema, false instead of an exception), checking the FinishReason.

📘 Terms
Transient error
an error that may not repeat on another try: 429, 5xx, timeout, the network
Permanent error
trying again doesn't help: a wrong request, key, permission, model name (4xx, except 429)
ApiException
a Google.GenAI error with a StatusCode: ClientError (4xx) and ServerError (5xx)

Retry and timeout: Microsoft.Extensions.Http.Resilience

🎯 After this You'll add retry, timeout and a circuit breaker to an HttpClient and check it with an artificial 503.

Part 2 · Retry and timeout

Slide 9

Trying again sounds simple, but a wrong retry makes the problem worse. We see how to retry properly, add it with one package and check it live.

Retry done right: backoff, jitter, Retry-After, circuit breaker

Slide 10

A naive retry — “it failed? try again immediately, 10 times” — makes the problem worse: Gemini is overloaded, and we send it even more requests, while a thousand clients do the same in the same second. A proper retry has four parts:

Part What it does
📈 exponential backoff we wait longer before every attempt: ~2 → ~4 → ~8 seconds. The service gets time to “catch its breath”
🎲 jitter a random part is added to the pause (2.3 s, 1.8 s…). A thousand clients no longer retry at the same moment
⏰ Retry-After · timeout on a 429 the server often tells us how long to wait (the Retry-After header). And each attempt has a time limit: if the answer doesn't arrive in 40 seconds, the attempt counts as failed
🔌 circuit breaker if a large share of recent attempts failed, the “breaker” trips: for a few seconds we don't call Gemini at all and return an error right away. The service rests, the user doesn't wait for nothing
📘 Terms
Retry
sending a failed request again on a transient error
Exponential backoff
a growing pause between retries (2, 4, 8… seconds)
Jitter
a random part of the pause, so many clients don't retry at the same time
Circuit breaker
a “breaker”: after many failures it temporarily stops the calls

AddStandardResilienceHandler: retry, timeout and circuit breaker on the HttpClient

Slide 11

dotnet add package Microsoft.Extensions.Http.Resilience — a Microsoft package (built on Polly) that adds a ready-made “resilience pipeline” to an IHttpClientFactory client:

Program.cs
builder.Services.AddHttpClient("gemini")    .AddStandardResilienceHandler(o =>    {        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(40);   // an LLM is slow        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(90);        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(90);    }); builder.Services.AddChatClient(sp =>    {        IHttpClientFactory http = sp.GetRequiredService<IHttpClientFactory>();        Client gemini = new(            apiKey: apiKey,            httpOptions: new HttpOptions { RetryOptions = new HttpRetryOptions { Attempts = 1 } },            clientOptions: new ClientOptions { HttpClientFactory = () => http.CreateClient("gemini") });        return gemini.AsIChatClient(model);    })    .Use(inner => new InputGuardChatClient(inner))    .UseFunctionInvocation()    // ... the other layers — as before

What the “standard” pipeline contains:

Part By default Ours
Retry 3 retries, exponential backoff + jitter, respects Retry-After; on 408, 429, 5xx and network errors unchanged
AttemptTimeout 10 s per attempt 40 s — Gemini thinks and writes long answers
TotalRequestTimeout 30 s for all attempts together 90 s
CircuitBreaker stops for a few seconds on many failures SamplingDuration must be ≥ 2 × AttemptTimeout (validation) → 90

Why do we turn off the SDK's retry? Google.GenAI has its own retry (HttpRetryOptions). If two retries stayed nested, one question would make 4 × 4 = 16 attempts, and the user would wait for minutes. Retry must be in one place. Attempts = 1 means “only the original request, no retries”.

ClientOptions.HttpClientFactory — we tell the SDK to send its HTTP requests with our HttpClient, the one with the resilience pipeline. AddChatClient(sp => …) — the factory version, so we can take IHttpClientFactory from DI.

The Controllers haven't changed. Retry happens at the HTTP level, inside IChatClient. In the tool loop, every Gemini request has its own retry.

📘 Terms
Microsoft.Extensions.Http.Resilience
a package that adds retry, timeout and a circuit breaker to an HttpClient (built on Polly)
AddStandardResilienceHandler
a ready-made pipeline with recommended settings

Checking it: an artificial 503

Slide 12

We can't make Gemini return a 503 on command, so for the test we write our own handler that returns a 503 on the first two of every three requests, without reaching Gemini:

Ai/ChaosHandler.cs · for testing only
public class ChaosHandler : DelegatingHandler{    private int _count;     protected override Task<HttpResponseMessage> SendAsync(        HttpRequestMessage request, CancellationToken ct)    {        // the first two of every 3 → 503        if (Interlocked.Increment(ref _count) % 3 != 0)            return Task.FromResult(                new HttpResponseMessage(HttpStatusCode.ServiceUnavailable));         return base.SendAsync(request, ct);    }}
Program.cs · for testing only
builder.Services.AddTransient<ChaosHandler>();builder.Services.AddHttpClient("gemini")    .AddStandardResilienceHandler(/* ... */)    .AddHttpMessageHandler<ChaosHandler>();   // inside, close to the network

DelegatingHandler — a “layer” of the HttpClient, exactly like DelegatingChatClient (lecture 5), but at the HTTP level. The order: the first one added is outside. Resilience is outside, ChaosHandler inside: the retry sees the 503 and tries again.

The result in the log: two 503s, pauses of ~2 and ~4 seconds, the third attempt — 200. The user waits ~6 seconds but gets an answer instead of a 500.

Testing a permanent error: change the name in appsettings.json under Gemini:Model (e.g. gemini-0) → Gemini returns a 404 → one attempt, no retry. That's the right behaviour.

⚠️

ChaosHandler is only for testing: remove it from Program.cs afterwards (or put it inside if (builder.Environment.IsDevelopment())).

A fallback model and recording the cost

🎯 After this You'll write a FallbackChatClient and write the tokens to the database to calculate the day's cost.

Part 3 · Fallback and cost

Slide 14

Retry doesn't always help: if a Gemini model has been overloaded for 5 minutes, all three attempts will fail. Then we switch to another model. And since one question is several calls (tools, retries, fallback), we write the tokens of every call to the database, so we know what it cost.

FallbackChatClient: retry doesn't help → another model

Slide 15

Lecture 5's DelegatingChatClient — now a layer that catches an error:

Ai/FallbackChatClient.cs
public class FallbackChatClient : DelegatingChatClient{    private readonly IChatClient _fallback;    private readonly ILogger<FallbackChatClient> _logger;     public FallbackChatClient(IChatClient inner, IChatClient fallback,        ILogger<FallbackChatClient> logger) : base(inner)    {        _fallback = fallback;        _logger = logger;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages, ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        try        {            return await base.GetResponseAsync(messages, options, cancellationToken);        }        catch (Exception ex) when (IsTransient(ex))        {            _logger.LogWarning("🛟 {Error} — fallback model", ex.Message);            return await _fallback.GetResponseAsync(messages, options, cancellationToken);        }    }     private static bool IsTransient(Exception ex) => ex switch    {        ApiException api => api.StatusCode is 429 or >= 500,        HttpRequestException or TimeoutRejectedException => true,        _ => false    };}
  • catch … when (IsTransient(ex)) — an exception filter: we catch only a transient error. A permanent one (400, 401, 404) goes up: the fallback uses the same key and the same request and would bring the same error.
  • IsTransient — an ApiException (Google.GenAI, 429 or 5xx), an HttpRequestException (the network) or a TimeoutRejectedException (the resilience timeout, using Polly.Timeout;). The order matters: ApiException is itself an HttpRequestException, so it has to come first. An OperationCanceledException (the user left) doesn't land here — that's right.

Registration: the fallback is the innermost layer, closest to Gemini. This way every request of the tool loop has its own fallback:

Program.cs
IChatClient fallback = new Client(apiKey: apiKey)    .AsIChatClient(builder.Configuration["Gemini:FallbackModel"]!); builder.Services.AddChatClient(sp => /* gemini — as on slide 11 */)    .Use(inner => new InputGuardChatClient(inner))    .UseFunctionInvocation()    .Use((inner, sp) => new TokenCounterChatClient(inner, /* ... */))    .UseLogging()    .Use((inner, sp) => new FallbackChatClient(inner, fallback,        sp.GetRequiredService<ILogger<FallbackChatClient>>()));

In appsettings.json: "Gemini": { "Model": "...", "FallbackModel": "..." } — another, usually lighter model (the current names: Gemini's list of models).

What if Gemini is down entirely? The fallback can be another provider too (OpenAI, Groq…): it's an IChatClient as well (lecture 3: switching the provider = one line). In production this is often how it's done.

📘 Terms
Fallback
a backup option: if the main service doesn't answer, the request goes to another one
Exception filter (catch … when)
a catch that only catches the exception when a condition holds

Recording the cost: tokens in the database

Slide 16

Lecture 5's TokenCounterChatClient wrote the tokens to the log. The log is lost in a few days and is hard to sum up. Now we write to the database: one row = one Gemini call.

Data/AiUsageRecord.cs
public class AiUsageRecord{    public Guid Id { get; set; }    public DateTime At { get; set; }    public string Model { get; set; } = "";    public long InputTokens { get; set; }    public long OutputTokens { get; set; }}
Ai/TokenCounterChatClient.cs
public class TokenCounterChatClient : DelegatingChatClient{    private readonly IServiceScopeFactory _scopes;     public TokenCounterChatClient(IChatClient inner, IServiceScopeFactory scopes) : base(inner)    {        _scopes = scopes;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages, ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        ChatResponse response =            await base.GetResponseAsync(messages, options, cancellationToken);         // a Scoped DbContext in a Singleton layer → its own scope        using IServiceScope scope = _scopes.CreateScope();        AppDbContext db = scope.ServiceProvider.GetRequiredService<AppDbContext>();         db.AiUsage.Add(new AiUsageRecord        {            Id = Guid.NewGuid(),            At = DateTime.UtcNow,            Model = response.ModelId ?? "?",            InputTokens = response.Usage?.InputTokenCount ?? 0,            OutputTokens = (response.Usage?.OutputTokenCount ?? 0)                         + (response.Usage?.ReasoningTokenCount ?? 0)        });        await db.SaveChangesAsync(cancellationToken);         return response;    }}// Program.cs: .Use((inner, sp) => new TokenCounterChatClient(inner,//                 sp.GetRequiredService<IServiceScopeFactory>()))

Why IServiceScopeFactory? AddChatClient registers the client as a Singleton: the pipeline is created once and serves every request. But AppDbContext is Scoped: a new one for every HTTP request. Putting a Scoped service directly into a Singleton is a mistake (a “captive dependency” — one DbContext for every user). So the layer creates its own scope every time and takes the AppDbContext from it.

We add ReasoningTokenCount to the output: Gemini's thinking tokens are counted separately but charged at the output price (lecture 2).

response.ModelId — which model answered. After a fallback this shows the fallback model's name, so the database shows how many times the fallback kicked in.

Today's cost with SQL:

sql
SELECT "Model", SUM("InputTokens") AS input, SUM("OutputTokens") AS outputFROM "AiUsage"WHERE "At" >= CURRENT_DATEGROUP BY "Model";

The cost with lecture 1's formula: input × the input price + output × the output price (the price per 1 million tokens, from Gemini's pricing page).

📘 Terms
IServiceScopeFactory
a DI service with which we create our own scope inside a Singleton and take a Scoped service (DbContext) from it
Captive dependency
a mistake: a Scoped service is “captured” inside a Singleton and every request shares it

Classwork: a daily limit layer

Classwork: A daily limit — a layer that stops

Slide 17

Your project or RestaurantApi · with code · a layer + Swagger

Steps

  • 1 · The table — AiUsageRecord (Id, At, Model, InputTokens, OutputTokens), DbSet<AiUsageRecord> AiUsage, a migration; TokenCounterChatClient writes to the database (slide 16)
  • 2 · The layer — BudgetGuardChatClient : DelegatingChatClient: IServiceScopeFactory and long dailyLimit in the constructor; in GetResponseAsync — a scope → the sum of today's tokens (At >= DateTime.UtcNow.Date) → if ≥ the limit, an answer without base: “Today's limit is used up”
  • 3 · The pipeline — the limit in appsettings.json ("Ai": { "DailyTokenLimit": 3000 }); the layer as the first .Use(...) — the outermost
  • 4 · Check — several questions in Swagger until you go over the limit → the refusal answer, and the log no longer shows a Gemini request; in the database SELECT SUM("InputTokens" + "OutputTokens") FROM "AiUsage"

✓ Done when

AiUsage gets a new row for every call; after the limit the chat refuses without calling Gemini; the limit can only be changed through appsettings.json

⭐ Bonus

  • A limit per user, not for the whole app: add a ConversationId to AiUsageRecord and count the limit per conversation. What has to be passed to the layer, and how?
  • Instead of refusing, switch to a cheaper model at 80% of the limit
  • What's better in a browser/UI: a 200 with the refusal text, or a 429? Why?

💡 If you're stuck

  • Cannot consume scoped service 'AppDbContext' from singleton? Don't put AppDbContext straight into the layer — IServiceScopeFactory → CreateScope() → GetRequiredService<AppDbContext>()
  • The sum: await db.AiUsage.Where(u => u.At >= today).SumAsync(u => u.InputTokens + u.OutputTokens, cancellationToken)
  • The refusal answer: return new ChatResponse(new ChatMessage(ChatRole.Assistant, "...")); — like lecture 5's InputGuard
  • The limit from configuration: .Use((inner, sp) => new BudgetGuardChatClient(inner, sp.GetRequiredService<IServiceScopeFactory>(), builder.Configuration.GetValue<long>("Ai:DailyTokenLimit")))
  • TokenCounter still writes to the log? Change it first (step 1) — otherwise the sum is always 0

Summary

Slide 19
  • The errors of an AI call come in three groups: transient (429, 500/503, timeout — retry helps), permanent (400, 401, 403, 404 — retry doesn't help) and content errors (a cut-off answer, bad JSON, a tool error — we check them in code).
  • A proper retry: exponential backoff, jitter, respecting Retry-After, a timeout per attempt and a circuit breaker on many failures.
  • AddStandardResilienceHandler (Microsoft.Extensions.Http.Resilience) adds this to an HttpClient. For an LLM we raise the timeouts. We give Google.GenAI our HttpClient (ClientOptions.HttpClientFactory) and turn off its own retry: retry in one place.
  • FallbackChatClient — a DelegatingChatClient that calls a fallback model on a transient error. It's the innermost layer of the pipeline.
  • Tokens in the database: TokenCounterChatClient writes every call to AiUsage (IServiceScopeFactory, because the pipeline is a Singleton). ReasoningTokenCount is added to the output.

All terms of the lecture

Terms

Transient error
an error that may not repeat on another try: 429, 5xx, timeout, the network
Permanent error
trying again doesn't help: a wrong request, key, permission, model name (4xx, except 429)
ApiException
a Google.GenAI error with a StatusCode: ClientError (4xx) and ServerError (5xx)
Retry
sending a failed request again on a transient error
Exponential backoff
a growing pause between retries (2, 4, 8… seconds)
Jitter
a random part of the pause, so many clients don't retry at the same time
Circuit breaker
a “breaker”: after many failures it temporarily stops the calls
Microsoft.Extensions.Http.Resilience
a package that adds retry, timeout and a circuit breaker to an HttpClient (built on Polly)
AddStandardResilienceHandler
a ready-made pipeline with recommended settings
Fallback
a backup option: if the main service doesn't answer, the request goes to another one
Exception filter (catch … when)
a catch that only catches the exception when a condition holds
IServiceScopeFactory
a DI service with which we create our own scope inside a Singleton and take a Scoped service (DbContext) from it
Captive dependency
a mistake: a Scoped service is “captured” inside a Singleton and every request shares it
