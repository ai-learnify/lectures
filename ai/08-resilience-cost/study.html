Error Handling, Resilience და ხარჯის კონტროლი

ლექციის სრული მასალა თავებად, ~14 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. შეცდომები: დროებითი (429, 5xx, timeout — retry შველის), მუდმივი (400, 401, 403, 404 — არა), შინაარსის (length, ცუდი JSON, tool-ის შეცდომა — კოდში).
  2. სწორი retry: backoff + jitter, Retry-After, timeout თითო ცდაზე, circuit breaker. AddStandardResilienceHandler — HttpClient-ზე, LLM-ისთვის გაზრდილი დროით.
  3. Google.GenAI ჩვენს HttpClient-ს იყენებს (ClientOptions.HttpClientFactory), მისი retry გამორთულია (Attempts = 1): retry ერთ ადგილას.
  4. FallbackChatClient — დროებით შეცდომაზე სარეზერვო მოდელი; pipeline-ში ყველაზე შიგნით; catch … when.
  5. ტოკენები ბაზაში (AiUsage): IServiceScopeFactory, რადგან pipeline Singleton-ია; ფიქრის ტოკენები output-ს ემატება; ხარჯი = ტოკენები × ფასი.

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~14 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“

  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

თავიდან ცდა მარტივად ჟღერს, მაგრამ არასწორი retry პრობლემას აუარესებს. ვნახავთ, როგორ ცდიან თავიდან სწორად, ვამატებთ ამას ერთი პაკეტით და ცოცხლად ვამოწმებთ.

retry სწორად: backoff, jitter, Retry-After, circuit breaker

სლაიდი 10

გულუბრყვილო retry — „ჩავარდა? მაშინვე თავიდან, 10-ჯერ“ — პრობლემას აუარესებს: Gemini გადატვირთულია, ჩვენ კი მას კიდევ უფრო მეტ მოთხოვნას ვუგზავნით, და ათასი კლიენტი ერთსა და იმავე წამში აკეთებს იგივეს. სწორი retry-ს ოთხი ნაწილი აქვს:

ნაწილი რას აკეთებს
📈 exponential backoff ყოველ ცდამდე მეტს ვიცდით: ~2 → ~4 → ~8 წამი. სერვისს „ამოსუნთქვის“ დრო ეძლევა
🎲 jitter პაუზას შემთხვევითი ნაწილი ემატება (2.3 წმ, 1.8 წმ…). ათასი კლიენტი ერთსა და იმავე მომენტში აღარ ცდის თავიდან
⏰ Retry-After · timeout 429-ზე სერვერი ხშირად გვეუბნება, რამდენი ვიცადოთ (Retry-After header). და თითო ცდას დროის ლიმიტი აქვს: თუ პასუხი 40 წამში არ მოვიდა, ცდა ჩავარდნილად ითვლება
🔌 circuit breaker თუ ბოლო პერიოდში ცდების დიდი ნაწილი ჩავარდა, „ჩამრთველი“ ითიშება: რამდენიმე წამი Gemini-ს საერთოდ არ ვიძახებთ და მაშინვე შეცდომას ვაბრუნებთ. სერვისი ისვენებს, მომხმარებელი ტყუილად არ ელოდება
📘 ტერმინები
Retry
ჩავარდნილი მოთხოვნის თავიდან გაგზავნა დროებით შეცდომაზე
Exponential backoff
retry-ებს შორის მზარდი პაუზა (2, 4, 8… წამი)
Jitter
პაუზის შემთხვევითი ნაწილი, რომ ბევრმა კლიენტმა ერთდროულად არ სცადოს
Circuit breaker
„ჩამრთველი“: ბევრი ჩავარდნის შემდეგ გამოძახებებს დროებით წყვეტს

AddStandardResilienceHandler: retry, timeout და circuit breaker HttpClient-ზე

სლაიდი 11

dotnet add package Microsoft.Extensions.Http.Resilience — Microsoft-ის პაკეტი (Polly-ზე დაფუძნებული), რომელიც IHttpClientFactory-ის client-ს მზა „resilience pipeline“-ს ამატებს:

Program.cs
builder.Services.AddHttpClient("gemini")    .AddStandardResilienceHandler(o =>    {        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(40);   // LLM ნელია        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(90);        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(90);    }); builder.Services.AddChatClient(sp =>    {        IHttpClientFactory http = sp.GetRequiredService<IHttpClientFactory>();        Client gemini = new(            apiKey: apiKey,            httpOptions: new HttpOptions { RetryOptions = new HttpRetryOptions { Attempts = 1 } },            clientOptions: new ClientOptions { HttpClientFactory = () => http.CreateClient("gemini") });        return gemini.AsIChatClient(model);    })    .Use(inner => new InputGuardChatClient(inner))    .UseFunctionInvocation()    // ... დანარჩენი ფენები — როგორც იყო

რას შეიცავს „standard“ pipeline:

ნაწილი ნაგულისხმევად ჩვენთან
Retry 3 retry, exponential backoff + jitter, Retry-After-ს ითვალისწინებს; 408, 429, 5xx და ქსელის შეცდომებზე უცვლელი
AttemptTimeout 10 წმ ერთ ცდაზე 40 წმ — Gemini ფიქრობს და გრძელ პასუხს წერს
TotalRequestTimeout 30 წმ ყველა ცდაზე ერთად 90 წმ
CircuitBreaker ბევრი ჩავარდნისას რამდენიმე წამით წყვეტს SamplingDuration ≥ 2 × AttemptTimeout უნდა იყოს (validation) → 90

რატომ ვთიშავთ SDK-ის retry-ს? Google.GenAI-ს თავისი retry აქვს (HttpRetryOptions). ორი retry ერთმანეთში რომ დარჩეს, ერთ შეკითხვაზე 4 × 4 = 16 ცდა გამოვა, და მომხმარებელი წუთობით დაელოდება. retry ერთ ადგილას უნდა იყოს. Attempts = 1 ნიშნავს „მხოლოდ თავდაპირველი მოთხოვნა, retry-ს გარეშე“.

ClientOptions.HttpClientFactory — SDK-ს ვეუბნებით, რომ HTTP მოთხოვნები ჩვენი HttpClient-ით გააგზავნოს, რომელსაც resilience pipeline აქვს. AddChatClient(sp => …) — factory ვერსია, რომ DI-დან IHttpClientFactory ავიღოთ.

Controller-ები არ შეცვლილა. retry HTTP-ის დონეზე ხდება, IChatClient-ის შიგნით. tool-ის ციკლში Gemini-ს თითოეულ მოთხოვნას თავისი retry აქვს.

ვამოწმებთ: ხელოვნური 503

სლაიდი 12

Gemini-ს 503 ბრძანებით ვერ გამოვიწვევთ, ამიტომ ცდისთვის საკუთარ handler-ს ვწერთ, რომელიც ყოველი სამი მოთხოვნიდან პირველ ორზე 503-ს აბრუნებს, Gemini-მდე მისვლის გარეშე:

Ai/ChaosHandler.cs · მხოლოდ ცდისთვის
public class ChaosHandler : DelegatingHandler{    private int _count;     protected override Task<HttpResponseMessage> SendAsync(        HttpRequestMessage request, CancellationToken ct)    {        // ყოველი 3-დან პირველი ორი → 503        if (Interlocked.Increment(ref _count) % 3 != 0)            return Task.FromResult(                new HttpResponseMessage(HttpStatusCode.ServiceUnavailable));         return base.SendAsync(request, ct);    }}
Program.cs · მხოლოდ ცდისთვის
builder.Services.AddTransient<ChaosHandler>();builder.Services.AddHttpClient("gemini")    .AddStandardResilienceHandler(/* ... */)    .AddHttpMessageHandler<ChaosHandler>();   // შიგნით, ქსელთან ახლოს

DelegatingHandler — HttpClient-ის „ფენა“, ზუსტად ისე, როგორც DelegatingChatClient (ლექცია 5), ოღონდ HTTP-ის დონეზე. რიგი: პირველი დამატებული — გარეთ. resilience გარეთაა, ChaosHandler შიგნით: retry ხედავს 503-ს და თავიდან ცდის.

შედეგი ლოგში: ორი 503, პაუზები ~2 და ~4 წამი, მესამე ცდა — 200. მომხმარებელი ~6 წამს ელოდება, მაგრამ 500-ის ნაცვლად პასუხს იღებს.

მუდმივი შეცდომის ცდა: appsettings.json-ში Gemini:Model-ს შეუცვალე სახელი (მაგ. gemini-0) → Gemini 404-ს აბრუნებს → ერთი ცდა, retry არ ხდება. ესაა სწორი ქცევა.

ნაწილი 3 · fallback და ხარჯი

სლაიდი 14

retry ყოველთვის არ შველის: თუ Gemini-ს მოდელი 5 წუთია გადატვირთულია, სამი ცდაც ჩავარდება. ასეთ დროს სხვა მოდელზე გადავდივართ. და რადგან ერთი შეკითხვა რამდენიმე გამოძახებაა (tool-ები, retry, fallback), ყოველი გამოძახების ტოკენებს ბაზაში ვწერთ, რომ ვიცოდეთ, რა დაჯდა.

FallbackChatClient: retry არ შველის → სხვა მოდელი

სლაიდი 15

ლექცია 5-ის DelegatingChatClient — ახლა ფენა, რომელიც შეცდომას იჭერს:

Ai/FallbackChatClient.cs
public class FallbackChatClient : DelegatingChatClient{    private readonly IChatClient _fallback;    private readonly ILogger<FallbackChatClient> _logger;     public FallbackChatClient(IChatClient inner, IChatClient fallback,        ILogger<FallbackChatClient> logger) : base(inner)    {        _fallback = fallback;        _logger = logger;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages, ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        try        {            return await base.GetResponseAsync(messages, options, cancellationToken);        }        catch (Exception ex) when (IsTransient(ex))        {            _logger.LogWarning("🛟 {Error} — სარეზერვო მოდელი", ex.Message);            return await _fallback.GetResponseAsync(messages, options, cancellationToken);        }    }     private static bool IsTransient(Exception ex) => ex switch    {        ApiException api => api.StatusCode is 429 or >= 500,        HttpRequestException or TimeoutRejectedException => true,        _ => false    };}
  • catch … when (IsTransient(ex)) — exception filter: ვიჭერთ მხოლოდ დროებით შეცდომას. მუდმივი (400, 401, 404) გადის ზევით: fallback-იც იგივე key-ს და იგივე მოთხოვნას იყენებს და იგივე შეცდომას მოიტანს.
  • IsTransient — ApiException (Google.GenAI, 429 ან 5xx), HttpRequestException (ქსელი) ან TimeoutRejectedException (resilience-ის timeout, using Polly.Timeout;). რიგი მნიშვნელოვანია: ApiException თვითონაც HttpRequestException-ია, ამიტომ პირველი უნდა იყოს. OperationCanceledException (მომხმარებელი წავიდა) აქ არ ხვდება — სწორია.

რეგისტრაცია: fallback ყველაზე შიგნითაა, Gemini-სთან ყველაზე ახლოს. ასე tool-ის ციკლის თითოეულ მოთხოვნას თავისი fallback აქვს:

Program.cs
IChatClient fallback = new Client(apiKey: apiKey)    .AsIChatClient(builder.Configuration["Gemini:FallbackModel"]!); builder.Services.AddChatClient(sp => /* gemini — როგორც სლაიდ 11-ზე */)    .Use(inner => new InputGuardChatClient(inner))    .UseFunctionInvocation()    .Use((inner, sp) => new TokenCounterChatClient(inner, /* ... */))    .UseLogging()    .Use((inner, sp) => new FallbackChatClient(inner, fallback,        sp.GetRequiredService<ILogger<FallbackChatClient>>()));

appsettings.json-ში: "Gemini": { "Model": "...", "FallbackModel": "..." } — სხვა, ჩვეულებრივ უფრო მსუბუქი მოდელი (მიმდინარე სახელები: Gemini-ს მოდელების სია).

Gemini მთლიანად რომ იყოს გათიშული? fallback სხვა პროვაიდერიც შეიძლება იყოს (OpenAI, Groq…): ისიც IChatClient-ია (ლექცია 3: პროვაიდერის შეცვლა = ერთი ხაზი). production-ში ხშირად ასე აკეთებენ.

ხარჯის აღრიცხვა: ტოკენები ბაზაში

სლაიდი 16

ლექცია 5-ის TokenCounterChatClient ტოკენებს ლოგში წერდა. ლოგი რამდენიმე დღეში იკარგება და მისი შეჯამება რთულია. ახლა ბაზაში ვწერთ: ერთი ხაზი = Gemini-ს ერთი გამოძახება.

Data/AiUsageRecord.cs
public class AiUsageRecord{    public Guid Id { get; set; }    public DateTime At { get; set; }    public string Model { get; set; } = "";    public long InputTokens { get; set; }    public long OutputTokens { get; set; }}
Ai/TokenCounterChatClient.cs
public class TokenCounterChatClient : DelegatingChatClient{    private readonly IServiceScopeFactory _scopes;     public TokenCounterChatClient(IChatClient inner, IServiceScopeFactory scopes) : base(inner)    {        _scopes = scopes;    }     public override async Task<ChatResponse> GetResponseAsync(        IEnumerable<ChatMessage> messages, ChatOptions? options = null,        CancellationToken cancellationToken = default)    {        ChatResponse response =            await base.GetResponseAsync(messages, options, cancellationToken);         // Singleton ფენაში Scoped DbContext → საკუთარი scope        using IServiceScope scope = _scopes.CreateScope();        AppDbContext db = scope.ServiceProvider.GetRequiredService<AppDbContext>();         db.AiUsage.Add(new AiUsageRecord        {            Id = Guid.NewGuid(),            At = DateTime.UtcNow,            Model = response.ModelId ?? "?",            InputTokens = response.Usage?.InputTokenCount ?? 0,            OutputTokens = (response.Usage?.OutputTokenCount ?? 0)                         + (response.Usage?.ReasoningTokenCount ?? 0)        });        await db.SaveChangesAsync(cancellationToken);         return response;    }}// Program.cs: .Use((inner, sp) => new TokenCounterChatClient(inner,//                 sp.GetRequiredService<IServiceScopeFactory>()))

რატომ IServiceScopeFactory? AddChatClient client-ს Singleton-ად არეგისტრირებს: pipeline ერთხელ იქმნება და ყველა მოთხოვნას ემსახურება. AppDbContext კი Scoped-ია: ყოველ HTTP მოთხოვნაზე ახალი. Singleton-ში Scoped-ის პირდაპირ ჩასმა შეცდომაა („captive dependency“ — ერთი DbContext ყველა მომხმარებელს). ამიტომ ფენა ყოველ ჯერზე საკუთარ scope-ს ქმნის და მისგან იღებს AppDbContext-ს.

ReasoningTokenCount output-ს ვუმატებთ: Gemini-ს ფიქრის ტოკენები ცალკე ითვლება, მაგრამ output-ის ფასით ფასდება (ლექცია 2).

response.ModelId — რომელმა მოდელმა უპასუხა. fallback-ის შემდეგ აქ სარეზერვო მოდელის სახელი ჩანს, ამიტომ ბაზიდან ვხედავთ, რამდენჯერ ჩაერთო fallback.

დღევანდელი ხარჯი SQL-ით:

sql
SELECT "Model", SUM("InputTokens") AS input, SUM("OutputTokens") AS outputFROM "AiUsage"WHERE "At" >= CURRENT_DATEGROUP BY "Model";

ფასი ლექცია 1-ის ფორმულით: input × input-ის ფასი + output × output-ის ფასი (ფასი 1 მილიონ ტოკენზე, Gemini-ს ფასების გვერდიდან).
