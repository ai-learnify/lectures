Text Embeddings: ტექსტის ვექტორიზაცია

ლექციის სრული მასალა თავებად, ~15 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. Embedding: ტექსტი → ვექტორი (რიცხვების სია), სადაც მსგავსი მნიშვნელობა ახლოსაა — ენისა და სიტყვების მიუხედავად.
  2. ვექტორს ცალკე embedding მოდელი აგენერირებს: gemini-embedding-2, 768 განზომილება. ერთი მოდელი = ერთი „რუკა“.
  3. IEmbeddingGenerator: AddEmbeddingGenerator, AsIEmbeddingGenerator(model, defaultModelDimensions), GenerateVectorAsync / GenerateAsync.
  4. Task prefix: შეკითხვა — task: search result | query: …, დოკუმენტი — title: … | text: …; ყოველთვის ერთი წესით.
  5. Cosine similarity — ორი ვექტორის კუთხე (1 — მსგავსი, 0 — არაფერი საერთო); TensorPrimitives.CosineSimilarity. ძებნა: მენიუ ერთხელ → ვექტორები; შეკითხვა → cosine ყველასთან → top 3.

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~15 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“
  2. გაიარე ტესტი — 10 კითხვა, ქულით
  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

ნაწილი 1 · რა არის embedding

სლაიდი 6

ჯერ ვხედავთ, რატომ არ გვყოფნის სიტყვებით ძებნა. მერე — იდეა: ტექსტის „მნიშვნელობის კოორდინატები“. და ბოლოს — რა მოდელი აკეთებს ამას და რამდენი რიცხვია ერთ ვექტორში.

პრობლემა: სიტყვებით ძებნა მნიშვნელობას ვერ ხედავს

სლაიდი 7

მომხმარებელი წერს „რამე მსუბუქი, ხორცის გარეშე“. ჩვეულებრივი ძებნა სიტყვებს ეძებს:

sql
SELECT "Name" FROM "Products" WHERE "Description" ILIKE '%ხორცის გარეშე%';-- 0 შედეგი
კერძი აღწერა LIKE
ლობიო ქოთანში წითელი ლობიო, ხახვი, ქინძი, ცხელი მჭადით ✗
ბადრიჯანი ნიგვზით შემწვარი ბადრიჯანი, ნიგვზის პასტა, ბროწეული ✗
მწვადი ღორის ხორცი შამფურზე, ხახვით ✗
ხინკალი საქონლისა და ღორის ხორცი, ცომში ✗
პომიდვრის სალათი პომიდორი, კიტრი, ნიგოზი ✗

ადამიანი მაშინვე ხედავს, რომ ლობიო, ბადრიჯანი და სალათი შეესაბამება. ხოლო თუ სიტყვა „ხორცი“-ს მოვძებნით, LIKE ზუსტად არასწორ კერძებს იპოვის: მწვადს და ხინკალს. სიტყვა და მნიშვნელობა სხვადასხვა რამეა: „ხორცის გარეშე“, „ვეგეტარიანული“ და „vegetarian“ ერთსა და იმავეს ნიშნავს, ერთი ასოც არ ემთხვევა.

ლექცია 7-ის ენით: გვინდა შერჩევა — კონტექსტში მხოლოდ ის კერძები, რომლებიც შეკითხვას შეესაბამება. ამისთვის მნიშვნელობით ძებნა გვჭირდება.

embedding: ტექსტის „მნიშვნელობის კოორდინატები“

სლაიდი 8

Embedding — ტექსტის გადაქცევა რიცხვების სიად: "ლობიო ქოთანში" → [0.021, -0.047, 0.009, 0.063, …]. ამ სიას ვექტორი ჰქვია. ვექტორი სივრცეში წერტილია: ორ რიცხვს რუკაზე წერტილი შეესაბამება (x, y), 768 რიცხვს — წერტილი 768-განზომილებიან სივრცეში.

მთავარი თვისება: embedding მოდელი ისეა გავარჯიშებული, რომ მსგავსი მნიშვნელობის ტექსტები ახლოს დგანან:

  • „ლობიო ქოთანში“, „ბადრიჯანი ნიგვზით“, „პომიდვრის სალათი“ — ერთ მხარეს (ბოსტნეული, ხორცის გარეშე);
  • „მწვადი“, „ხინკალი“ — მეორე მხარეს (ხორცი);
  • შეკითხვა „ხორცის გარეშე“ პირველ ჯგუფთან ჯდება, და „vegetarian“-იც იქვე: ენა სხვაა, მნიშვნელობა — ერთი.

სლაიდზე ორგანზომილებიანი ნახატია, რომ თვალით დავინახოთ. სინამდვილეში ერთ ვექტორში ასობით ან ათასობით რიცხვია, და თითოეული რიცხვი მნიშვნელობის რაღაც „მიმართულებაა“, რომელიც მოდელმა ვარჯიშისას თვითონ ისწავლა (ადამიანისთვის გასაგები სახელი არც ერთს არ აქვს).

ლექცია 1-ის კითხვაზე „საიდან იცის მოდელმა, რას ნიშნავს ტოკენი 3293?“ — ეს არის პასუხი: მოდელის შიგნით ყოველ ტოკენს ასეთი ვექტორი აქვს.

ფასი input + output მხოლოდ input — ბევრად იაფი

ჩვენი მოდელი: gemini-embedding-2 — Gemini-ს უახლესი embedding მოდელი (Stable). შესაყვანად 8 192 ტოკენამდე იღებს, ვექტორის ზომა 128-დან 3072-მდე შეიძლება იყოს. რეკომენდებული ზომებია 768, 1536 და 3072.

ჩვენ ვიღებთ 768-ს: ხარისხი კარგია, ვექტორი 4-ჯერ პატარაა (ბაზაში ნაკლები ადგილი, ძებნა სწრაფი), და ლექცია 10-ის pgvector ინდექსი ასეთ ზომას თავისუფლად ამუშავებს.

ერთი მოდელი — ერთი „რუკა“. ყველა embedding მოდელი თავის სივრცეს ქმნის. gemini-embedding-2-ის ვექტორს სხვა მოდელის (ან იმავე მოდელის სხვა ზომის) ვექტორს ვერ შევადარებთ — რიცხვები სხვა „რუკაზეა“. ამიტომ მოდელი და ზომა ერთხელ ირჩევა: თუ შევცვლით, ყველა შენახული ვექტორი თავიდან უნდა დავითვალოთ.

task prefix: შეკითხვა და დოკუმენტი სხვადასხვა ფორმატით

სლაიდი 12

შეკითხვა („რამე მსუბუქი?“) და მისი პასუხი (კერძის აღწერა) ერთნაირ ტექსტს არ ჰგავს: შეკითხვა მოკლეა და „სურვილს“ აღწერს, დოკუმენტი — გრძელი და „ფაქტებს“. ასეთ ძებნას ასიმეტრიული ჰქვია. gemini-embedding-2-ისთვის Google ტექსტურ ამოცანებზე გვირჩევს, რომ ტექსტს წინ ამოცანის აღწერა (prefix) მივუწეროთ:

რა ფორმატი
შეკითხვა task: search result \| query: {შეკითხვა}
დოკუმენტი title: {სათაური} \| text: {ტექსტი} (სათაურის გარეშე — title: none)

prefix მოდელს ეუბნება, რომელი ტექსტი რა როლშია, და ძებნის ხარისხი იზრდება. ერთი წესი უცვლელია: ყველა დოკუმენტი ერთი ფორმატით, ყველა შეკითხვა — მეორით. თუ ნახევარს prefix-ით შევინახავთ, ნახევარს — უმისოდ, ვექტორები ერთმანეთს ცუდად შეედრება.

search result-ის ნაცვლად სხვა ამოცანებიც არსებობს (კითხვა-პასუხი, ფაქტის შემოწმება, კოდის ძებნა) — Gemini-ს embeddings გვერდზე.

ნაწილი 3 · მსგავსება და ძებნა

სლაიდი 14

ორი ვექტორი გვაქვს. რამდენად ახლოს არიან? ვსწავლობთ cosine similarity-ს, ვწერთ მას C#-ში და ვაწყობთ მენიუს სემანტიკურ ძებნას.

cosine similarity: ორი ისრის კუთხე

სლაიდი 15

ვექტორი შეგვიძლია ისრად წარმოვიდგინოთ, რომელიც ცენტრიდან რაღაც მიმართულებით იყურება. cosine similarity ზომავს კუთხეს ორ ისარს შორის:

კუთხე cosine რას ნიშნავს
0° — ერთი მიმართულება 1 ძალიან მსგავსი
90° — პერპენდიკულარული 0 არაფერი საერთო
180° — საპირისპირო −1 (ტექსტებზე პრაქტიკულად არ ხდება)

ფორმულა — სკალარული ნამრავლი გაყოფილი სიგრძეების ნამრავლზე:

ხელით — როგორ ითვლება
static float Cosine(ReadOnlySpan<float> a, ReadOnlySpan<float> b){    float dot = 0, na = 0, nb = 0;    for (int i = 0; i < a.Length; i++)    {        dot += a[i] * b[i];   // სკალარული ნამრავლი        na  += a[i] * a[i];   // a-ს სიგრძე²        nb  += b[i] * b[i];   // b-ს სიგრძე²    }    return dot / (MathF.Sqrt(na) * MathF.Sqrt(nb));}

.NET-ში ეს მზაა და სწრაფიც (SIMD — პროცესორი რამდენიმე რიცხვს ერთდროულად ამრავლებს):

csharp
using System.Numerics.Tensors;   // NuGet: System.Numerics.Tensorsfloat score = TensorPrimitives.CosineSimilarity(a.Span, b.Span);

ციფრებს როგორ ვკითხულობთ. ნიმუში: „ხორცის გარეშე“ ↔ ლობიო 0.71, ↔ მწვადი 0.38. აბსოლუტური ციფრი მოდელზეა დამოკიდებული: ზოგ მოდელზე სრულიად უცხო ტექსტებიც 0.4-ს აჩვენებს. ამიტომ ციფრს ცალკე არ ვაფასებთ („0.7 კარგია?“), არამედ ვადარებთ: რომელია უფრო ახლოს. ძებნაში სწორედ ესაა საჭირო — დალაგება.

⚠️

ვექტორები ჯერ მეხსიერებაშია: აპის რესტარტზე ქრება, და ძებნა ყველა ვექტორს სათითაოდ ადარებს. 200 კერძზე ეს მილიწამებია, მილიონ დოკუმენტზე — არა. ლექცია 10-ში ვექტორებს PostgreSQL-ში (pgvector) გადავიტანთ, ინდექსით.
