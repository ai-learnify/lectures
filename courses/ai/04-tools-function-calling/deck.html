## ლექცია 4: Tools და Function Calling ლექცია 3-ზე მოდელმა ტექსტიდან ჯავშანი ამოიღო (`BookingRequest`), მაგრამ ვერ გვითხრა, თავისუფალია თუ არა მაგიდა: ჩვენს ბაზას ის ვერ ხედავს. დღეს მოდელს ვაძლევთ **tool-ებს**: ჩვენს C# მეთოდებს, რომელთა გამოძახებასაც ის თვითონ **ითხოვს**, როცა პასუხისთვის მონაცემი სჭირდება. მეთოდს ჩვენი კოდი ასრულებს, შედეგი მოდელს უბრუნდება, და მოდელი პასუხს ჩვენი ბაზის ნამდვილი მონაცემით წერს.
## Lecture 4: Tools and Function Calling In lecture 3 the model extracted a booking from text (`BookingRequest`), but it couldn't tell us whether a table is free: it can't see our database. Today we give the model **tools**: our C# methods that it **asks** us to call when it needs data for an answer. Our code runs the method, the result goes back to the model, and the model writes its answer with real data from our database.

### The model can't see our database A user writes: “There are four of us, tomorrow at 8 — do you have a table?”. On lecture 2's `/ask` the model doesn't have our database, so it does one of two things: | Answer | Problem | |---|---| | “Yes, of course! We're expecting you” | It **made it up** (hallucination): it hasn't seen the bookings but answers confidently. The user comes and the table is taken | | “I don't have access to bookings” | Honest, but it doesn't help the user at all | **Idea 1: the whole database in the prompt?** All tables and all bookings as text. That's a bad idea: - **Many tokens.** Thousands of input tokens on every question, even on “hello” (cost, lecture 1). - **It goes stale.** The prompt is a snapshot from the moment it was sent, while bookings change every minute. - **Unneeded.** “How much is khinkali?” doesn't need the bookings at all. **Idea 2 (the right one):** the model itself **asks us** for the data it needs, and only when it needs it. This is called **function calling** (or **tool calling**).

### Function calling: ციკლი ოთხ ნაბიჯად მთავარი იდეა: **მოდელი ჩვენს მეთოდს ვერ იძახებს.** ის Google-ის სერვერზეა, ჩვენი ბაზა კი ჩვენთან. მოდელი მხოლოდ **ითხოვს**, ჩვენი კოდი **ასრულებს**. 1. **ჩვენ → მოდელი:** ვაგზავნით შეკითხვას და **tool-ების სიას**. თითო tool-ზე: სახელი (`check_availability`), აღწერა („ამოწმებს თავისუფალ მაგიდას“) და პარამეტრები (`at`, `guests`). 2. **მოდელი → ჩვენ:** მოდელი ხვდება, რომ პასუხისთვის მონაცემი სჭირდება, და ტექსტის ნაცვლად **გამოძახების თხოვნას** აბრუნებს: „გამოიძახე `check_availability`, `at` = ხვალ 20:00, `guests` = 4“. პარამეტრები მომხმარებლის ტექსტიდან თვითონ შეავსო. 3. **ჩვენ → მოდელი:** ჩვენი კოდი იძახებს ნამდვილ C# მეთოდს, მეთოდი ბაზას კითხულობს, და შედეგს (`{ available: true, freeTables: 2 }`) მოდელს ვუგზავნით. ეს **მეორე** მოთხოვნაა Gemini-სთან, და მასში მთელი ისტორიაა: შეკითხვა, თხოვნა და შედეგი. 4. **მოდელი → ჩვენ:** შედეგის საფუძველზე მოდელი ჩვეულებრივ ტექსტურ პასუხს წერს. **Gemini-სთან ორი მოთხოვნა გვქონდა** (ნაბიჯი 1 და 3). თუ მოდელს რამდენიმე tool სჭირდება, ციკლი მეორდება, ასე რომ მოთხოვნა შეიძლება მეტიც იყოს. ```note მოდელი ჩვენს ბაზას **არასდროს** უკავშირდება. რა მეთოდი არსებობს, რას აკეთებს და რა დააბრუნოს, ჩვენი კოდი წყვეტს. მოდელი მხოლოდ ირჩევს, რომელი tool გამოიძახოს და რა პარამეტრებით. ``` ```terms Tool (ხელსაწყო) — მოდელისთვის აღწერილი ჩვენი ფუნქცია: სახელი, აღწერა, პარამეტრები. მოდელს შეუძლია მისი გამოძახება ითხოვოს Function calling (tool calling) — მოდელი ტექსტის ნაცვლად tool-ის გამოძახების თხოვნას აბრუნებს; ჩვენ ვასრულებთ და შედეგს ვუბრუნებთ ```
### Function calling: the loop in four steps The main idea: **the model can't call our method.** It runs on Google's servers, while our database is with us. The model only **asks**; our code **runs** the method. 1. **We → the model:** we send the question and **the list of tools**. For each tool: a name (`check_availability`), a description (“checks for a free table”) and parameters (`at`, `guests`). 2. **The model → us:** the model realises it needs data for the answer and, instead of text, returns **a call request**: “call `check_availability`, `at` = tomorrow 20:00, `guests` = 4”. It filled in the parameters from the user's text by itself. 3. **We → the model:** our code calls the real C# method, the method reads the database, and we send the result (`{ available: true, freeTables: 2 }`) to the model. This is the **second** request to Gemini, and it carries the whole history: the question, the request and the result. 4. **The model → us:** based on the result, the model writes an ordinary text answer. **We made two requests to Gemini** (steps 1 and 3). If the model needs several tools, the loop repeats, so there can be more requests. ```note The model **never** connects to our database. Our code decides which methods exist, what they do and what they return. The model only chooses which tool to call and with which parameters. ``` ```terms Tool — our function described for the model: name, description, parameters. The model can ask for it to be called Function calling (tool calling) — instead of text, the model returns a request to call a tool; we run it and send back the result ```

### რა მიდის ქსელში ზემოთ Gemini-ს ფორმატია, გამარტივებული. ხელით ამას არ ვწერთ, Microsoft.Extensions.AI აწყობს. მაგრამ სასარგებლოა იცოდე, რა ხდება შიგნით: 1. **Tool-ის აღწერა** მოთხოვნასთან მიდის: `name`, `description` და `parameters`. `parameters` **JSON Schema**-ა, ისეთივე, როგორიც ლექცია 3-ზე `BookingRequest`-იდან შეიქმნა. ეს სქემა C# მეთოდის პარამეტრებიდან ავტომატურად იქმნება: `DateTime at` → `"type": "string", "format": "date-time"`, `int guests` → `"type": "integer"`. 2. **მოდელის პასუხი** ტექსტი კი არა, `functionCall`-ია: tool-ის სახელი და არგუმენტები (`args`), შევსებული სქემის მიხედვით. 3. **ჩვენი შედეგი** `functionResponse`-ად ბრუნდება. მეთოდის დაბრუნებული ობიექტი JSON-ად იქცევა. **ვინ ასრულებს მეთოდს?** ჩვენი სერვერი. Gemini მხოლოდ სახელს და არგუმენტებს წერს, ისევე, როგორც ლექცია 3-ზე `BookingRequest`-ის ველებს ავსებდა. ```tip აქედან ჩანს, რატომ არის **აღწერა** ასეთი მნიშვნელოვანი: tool-ის კოდს მოდელი ვერ ხედავს. რას აკეთებს tool და როდის გამოიძახოს, მოდელი მხოლოდ სახელიდან და აღწერიდან იგებს. ```
### What goes over the wire Above is Gemini's format, simplified. We don't write it by hand — Microsoft.Extensions.AI builds it. But it helps to know what happens inside: 1. **The tool description** goes with the request: `name`, `description` and `parameters`. `parameters` is a **JSON Schema**, just like the one created from `BookingRequest` in lecture 3. The schema is created automatically from the C# method's parameters: `DateTime at` → `"type": "string", "format": "date-time"`, `int guests` → `"type": "integer"`. 2. **The model's answer** is not text but a `functionCall`: the tool name and the arguments (`args`), filled in according to the schema. 3. **Our result** goes back as a `functionResponse`. The object the method returned is turned into JSON. **Who runs the method?** Our server. Gemini only writes the name and the arguments, just as it filled in the `BookingRequest` fields in lecture 3. ```tip This shows why the **description** matters so much: the model can't see the tool's code. It learns what the tool does and when to call it only from the name and the description. ```

### The result: `/ask` vs `/chat` The same question on two endpoints: “What dishes do you have under 15 GEL?” | endpoint | Answer | Why | |---|---|---| | `/ask` (lecture 2) | “We have khachapuri, khinkali, mtsvadi…” | The model made up a “typical Georgian restaurant” menu. It doesn't know our menu | | `/chat` (today) | “Under 15 GEL: lobio in a clay pot (12 ₾) and mchadi (4 ₾)”, `toolCalls: ["get_menu"]` | The model called `get_menu`, got the whole menu and filtered it to under 15 GEL **itself** | We didn't need a separate tool for the filter: the model received the whole menu and picked the right items for the question. For a small menu that's fine. With 500 dishes it's better for the tool to have a parameter (e.g. `maxPrice`), so we don't feed the whole list to the model. **On “Hello!”** `toolCalls` is empty: the model decided it doesn't need the menu. **Whether to call a tool and which one** is the model's decision, based on the name and the description. ```note The exact text will differ for you: your database has other dishes and the model works with probabilities. What matters is seeing `get_menu` in `toolCalls` and the prices coming from your database. ```

### `CheckAvailability`: a tool with parameters ```csharp Ai/RestaurantTools.cs · CheckAvailability public record AvailabilityInfo(bool Available, int FreeTables); [Description("Checks whether a table is free at the given time")] public async Task CheckAvailability( [Description("Booking date and time")] DateTime at, [Description("Number of guests")] int guests) { var busyTableIds = await _db.Bookings .Where(b => b.At > at.AddHours(-2) && b.At < at.AddHours(2)) .Select(b => b.TableId) .ToListAsync(); int free = await _db.Tables .CountAsync(t => t.Seats >= guests && !busyTableIds.Contains(t.Id)); return new AvailabilityInfo(free > 0, free); } ``` - **`[Description]` on the parameters.** They go into the schema as each parameter's description, exactly like on the `BookingRequest` fields in lecture 3. ### კარგი tool: 4 წესი მოდელი tool-ს მხოლოდ სახელით, აღწერით და პარამეტრების სქემით იცნობს. კოდს ვერ ხედავს. ამიტომ tool-ის ხარისხს სწორედ ეს სამი წყვეტს. | წესი | ცუდი | კარგი | |---|---|---| | **სახელი** = ზმნა + რა | `Check`, `Func1`, `Data` | `check_availability`, `get_menu` | | **აღწერა**: რას აკეთებს, რას აბრუნებს, საჭიროების შემთხვევაში როდის გამოიყენოს | არ არის | „ამოწმებს, არის თუ არა თავისუფალი მაგიდა მითითებულ დროს“ | | **ტიპიზებული პარამეტრები** აღწერით | `string data` („2026-11-26 20:00 4“?) | `DateTime at`, `int guests`, ან enum, თუ მნიშვნელობები სიიდანაა | | **ერთი tool, ერთი საქმე** | `DoEverything(string action, string data)` | ცალკე `get_menu` და `check_availability` | **რატომ ტიპიზებული პარამეტრები?** `string data`-ში მოდელს ფორმატი თვითონ უნდა გამოიცნოს, ჩვენ კი ეს string უნდა დავპარსოთ. `DateTime` და `int` სქემაში ზუსტ ტიპად მიდის, და `AIFunctionFactory` მოდელის JSON-ს C# ტიპებად თვითონ გარდაქმნის. **რატომ დღეს მხოლოდ კითხვა (read-only)?** თუ მოდელს `create_booking`-ს მივცემთ, ჯავშანს მოდელი **თვითონ გადაწყვეტს**: შეიძლება „8“ დილის 8 ეგონოს და ჯავშანი ისე შექმნას, რომ მომხმარებელს არ ჰკითხოს. ბაზაში ჩამწერ tool-ს მომხმარებლის **დადასტურება** სჭირდება („ვაჯავშნო ხვალ 20:00-ზე 4 კაცზე?“). ამას human-in-the-loop ჰქვია და ლექცია 15-ზე ვნახავთ. ```tip თუ მოდელი tool-ს არასწორ დროს იძახებს ან საერთოდ არ იძახებს, კოდს ნუ შეცვლი. ჯერ **აღწერა** გააუმჯობესე: ხშირად ერთი წინადადება საკმარისია („გამოიყენე, როცა მომხმარებელი ფასს ან კერძს კითხულობს“). ```
### A good tool: 4 rules The model knows a tool only by its name, its description and the schema of its parameters. It can't see the code. So these three decide the tool's quality. | Rule | Bad | Good | |---|---|---| | **Name** = verb + what | `Check`, `Func1`, `Data` | `check_availability`, `get_menu` | | **Description**: what it does, what it returns, and when to use it if needed | missing | “Checks whether a table is free at the given time” | | **Typed parameters** with descriptions | `string data` (“2026-11-26 20:00 4”?) | `DateTime at`, `int guests`, or an enum if the values come from a list | | **One tool, one job** | `DoEverything(string action, string data)` | separate `get_menu` and `check_availability` | **Why typed parameters?** With `string data` the model has to guess the format, and we have to parse that string. `DateTime` and `int` go into the schema as exact types, and `AIFunctionFactory` converts the model's JSON into C# types by itself. **Why only reading today (read-only)?** If we give the model `create_booking`, the model **decides** the booking by itself: it may take “8” for 8 in the morning and create the booking without asking the user. A tool that writes to the database needs the user's **confirmation** (“Shall I book tomorrow at 20:00 for 4?”). This is called human-in-the-loop, and we'll see it in lecture 15. ```tip If the model calls a tool at the wrong time or doesn't call it at all, don't change the code. Improve the **description** first: often one sentence is enough (“use it when the user asks about a price or a dish”). ```

## შეჯამება - **Tool** — ჩვენი C# მეთოდი, რომელიც მოდელს აღწერილი აქვს: სახელი, აღწერა და პარამეტრების JSON Schema. კოდს მოდელი ვერ ხედავს. - **ციკლი:** ჩვენ ვაგზავნით შეკითხვას და tool-ების სიას → მოდელი **ითხოვს** გამოძახებას → **ჩვენი კოდი** ასრულებს მეთოდს → შედეგი მოდელს უბრუნდება → მოდელი ტექსტურ პასუხს წერს. Gemini-სთან მინიმუმ ორი მოთხოვნაა. - **`AIFunctionFactory.Create(method, name: "...")`** — C# მეთოდიდან tool-ს ქმნის. **`ChatOptions.Tools`** — tool-ების სია მოთხოვნისთვის. **`[Description]`** — მეთოდზე და პარამეტრებზე. - **`.UseFunctionInvocation()`** — `Program.cs`-ში ერთი ხაზი, რომელიც ციკლს ავტომატურად ატრიალებს. - **მოდელი ირჩევს**, გამოიძახოს თუ არა tool, რომელი და რამდენი, და **ავსებს** პარამეტრებს ტექსტიდან. - **კარგი tool:** სახელი = ზმნა + რა, აღწერა, ტიპიზებული პარამეტრები, ერთი საქმე. დღეს მხოლოდ კითხვის (read-only) tool-ები. ჩანაწერს დადასტურება სჭირდება. ### შემდეგ ლექციაზე `.UseFunctionInvocation()` ერთი ხაზი იყო, მაგრამ ციკლი მთლიანად შეასრულა. სინამდვილეში ეს client-ის გარშემო **ფენაა** (middleware), ისეთივე, როგორიც ASP.NET Core-ის `app.Use…()`. ლექცია 5-ზე: **Chat Client Pipeline და Middleware**: ლოგირება, ქეში და საკუთარი ფენა, რომელიც ყოველ მოთხოვნაზე ტოკენებს ითვლის.
## Summary - **A tool** is our C# method described to the model: a name, a description and the JSON Schema of its parameters. The model can't see the code. - **The loop:** we send the question and the list of tools → the model **asks** for a call → **our code** runs the method → the result goes back to the model → the model writes a text answer. There are at least two requests to Gemini. - **`AIFunctionFactory.Create(method, name: "...")`** creates a tool from a C# method. **`ChatOptions.Tools`** is the list of tools for a request. **`[Description]`** goes on the method and the parameters. - **`.UseFunctionInvocation()`** — one line in `Program.cs` that runs the loop automatically. - **The model chooses** whether to call a tool, which one and how many, and **fills in** the parameters from the text. - **A good tool:** name = verb + what, a description, typed parameters, one job. Today only read-only tools. Writing needs confirmation. ### Next lecture `.UseFunctionInvocation()` was one line, yet it ran the whole loop. In fact it's a **layer** (middleware) around the client, just like ASP.NET Core's `app.Use…()`.
