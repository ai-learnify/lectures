## 🎯 მიმოხილვა

ლექცია ლექცია 3-ის ბოლო კითხვით იწყება: „მოდელმა ჯავშანი ამოიღო. იცის, მაგიდა თავისუფალია?“. სამი ნაწილია.

**ნაწილი 1 — ციკლი (თეორია, კოდის გარეშე).** მოდელი ჩვენს ბაზას ვერ ხედავს. ის ჩვენს მეთოდს ვერ იძახებს, მხოლოდ **ითხოვს** გამოძახებას. ოთხი ნაბიჯი: სია → თხოვნა → ჩვენ ვასრულებთ → პასუხი. ეს ლექციის მთავარი ცნებაა: თუ ეს გაიგეს, კოდი მარტივია.

**ნაწილი 2 — პირველი tool (`get_menu`).** `RestaurantTools` კლასი, `AIFunctionFactory.Create`, `ChatOptions.Tools`, `.UseFunctionInvocation()`. `/ask` vs `/chat` ერთ კითხვაზე: მოგონილი მენიუ vs ბაზის მენიუ.

**ნაწილი 3 — პარამეტრები და დიზაინი (`check_availability`).** მოდელი პარამეტრებს ტექსტიდან ავსებს. თამაში „რომელ tool-ს გამოიძახებს?“. კარგი tool-ის 4 წესი და რატომ არის დღეს მხოლოდ კითხვა.

### 📌 სტუდენტს აუცილებლად უნდა დარჩეს

1. მოდელი ბაზას ვერ ხედავს და მეთოდს ვერ იძახებს. ის **ითხოვს**, **ჩვენი კოდი** ასრულებს. Gemini-სთან მინიმუმ 2 მოთხოვნაა.
2. Tool = სახელი + აღწერა + პარამეტრების JSON Schema. კოდს მოდელი ვერ ხედავს, ამიტომ **აღწერა** გადამწყვეტია.
3. `AIFunctionFactory.Create(method, name: "...")` → `ChatOptions.Tools` → `GetResponseAsync(messages, options)`.
4. `.UseFunctionInvocation()` ციკლს ჩვენ მაგივრად ატრიალებს. (რა არის ეს — ლექცია 5.)
5. მოდელი **ირჩევს** tool-ს (ან არცერთს) და **ავსებს** პარამეტრებს. დღეს მხოლოდ **კითხვის** tool-ები.

### 📖 ისწავლე: function calling შიგნიდან

#### რა არის tool მოდელისთვის

მოდელისთვის tool მხოლოდ **აღწერაა** — ტექსტი, რომელიც მოთხოვნასთან ერთად მიდის: სახელი, აღწერა და პარამეტრების JSON Schema. მოდელი (Gemini, GPT, Claude) სპეციალურად არის გავარჯიშებული, რომ როცა მოთხოვნაში tool-ები არის და კითხვაზე პასუხისთვის მონაცემი აკლია, ტექსტის ნაცვლად **სტრუქტურირებული თხოვნა** დააბრუნოს: tool-ის სახელი და არგუმენტები სქემის მიხედვით.

ეს ტექნიკურად ძალიან ჰგავს ლექცია 3-ის structured output-ს: იქ მოდელი `BookingRequest`-ის სქემას ავსებდა, აქ — tool-ის პარამეტრების სქემას. განსხვავება: structured output-ში **ჩვენ** ვაიძულებთ ფორმას, აქ კი **მოდელი წყვეტს**, დააბრუნოს ტექსტი თუ tool-ის გამოძახება.

#### ციკლი Gemini-ს API-ში (რეალურად)

1. **მოთხოვნა 1:** `contents` = [user: „ხვალ 8-ზე…“], `tools` = [{ functionDeclarations: [get_menu, check_availability] }].
2. **პასუხი 1:** `parts` = [{ functionCall: { name: "check_availability", args: {...} }, thoughtSignature: "..." }]. ტექსტი არ არის. `finishReason` = STOP.
3. ჩვენი კოდი იძახებს მეთოდს.
4. **მოთხოვნა 2:** `contents` = [user: „ხვალ 8-ზე…“, model: { functionCall … + thoughtSignature }, user: { functionResponse: { name, response: {...} } }], `tools` = იგივე.
5. **პასუხი 2:** `parts` = [{ text: „დიახ, …“ }].

**მნიშვნელოვანი:** მოთხოვნა 2-ში **მთელი ისტორია** მიდის — მოდელი stateless-ია (ლექცია 1). tool-ების აღწერებიც ყოველ მოთხოვნაზე ხელახლა მიდის — ანუ ისინი **input ტოკენებია** ყოველ ჯერზე. 10 tool-ი გრძელი აღწერებით = ასობით ტოკენი ყოველ მოთხოვნაზე. ეს ლექცია 7-ის (context) და 8-ის (ხარჯი) თემაა.

#### Microsoft.Extensions.AI-ში რა ტიპებია

| Gemini | Microsoft.Extensions.AI |
|---|---|
| `functionDeclarations` | `AIFunction` (`ChatOptions.Tools`-ში) |
| `functionCall` | `FunctionCallContent` — `Name`, `Arguments`, `CallId` |
| `functionResponse` | `FunctionResultContent` — `CallId`, `Result` |
| `thoughtSignature` | `TextReasoningContent` (`ProtectedData`-ით) — Google.GenAI-ის adapter-ი ცალკე content-ად აბრუნებს |

`CallId` თხოვნას და შედეგს აკავშირებს — როცა ერთ პასუხში რამდენიმე გამოძახებაა, ასე ვიცით, რომელი შედეგი რომელს ეკუთვნის. (Gemini-ს Developer API-ზე id-ს ზოგჯერ adapter-ი თვითონ აგენერირებს.)

#### Thought signatures (Gemini 3)

Gemini 3 „ფიქრობს“ (ლექცია 2, ფიქრის ტოკენები). როცა tool-ს ითხოვს, პასუხს **დაშიფრულ ხელმოწერას** (thought signature) ურთავს — ფიქრის მდგომარეობის „შენახვას“. მოთხოვნა 2-ში ეს ხელმოწერა **უცვლელად** უნდა დაბრუნდეს, თორემ Gemini 3 `400`-ს აბრუნებს. Google.GenAI-ის `IChatClient` ხელმოწერას `response.Messages`-ში ცალკე content-ად ინახავს, `UseFunctionInvocation` კი მთელ ისტორიას აბრუნებს — ამიტომ ჩვენ არაფერი გვიწევს. **მაგრამ:** თუ ისტორიას ხელით აწყობ და `TextReasoningContent`-ს „ზედმეტად“ ამოჭრი — `400`. ლექცია 7-ზე, ისტორიის შენახვისას, ეს მნიშვნელოვანი იქნება.

#### რატომ არის ეს უსაფრთხო (და სად არის საფრთხე)

- მოდელი ვერ გამოიძახებს იმას, რაც სიაში არ არის. ჩვენ ვწყვეტთ სიას.
- მოდელი ვერ ხედავს connection string-ს, key-ებს, კოდს.
- **საფრთხე — არგუმენტები.** მოდელი არგუმენტებს მომხმარებლის ტექსტიდან ავსებს. მომხმარებელმა შეიძლება მოდელი „დაარწმუნოს“ არასწორი არგუმენტის გადაცემაში (prompt injection — ლექცია 19). ამიტომ tool-ის შიგნით არგუმენტები ისევე უნდა შემოწმდეს, როგორც API-ის ნებისმიერი input. და ამიტომ არ ვაძლევთ ჩამწერ tool-ებს დადასტურების გარეშე.

### 🔬 უფრო ღრმად — თუ ჰკითხავენ

**Parallel function calls.** მოდელს შეუძლია ერთ პასუხში **რამდენიმე** `functionCall` დააბრუნოს (მაგ. `check_availability` და `get_menu` ერთად). `FunctionInvokingChatClient` ყველას ასრულებს და ყველა შედეგს ერთად აგზავნის. ნაგულისხმევად თანმიმდევრულად; `AllowConcurrentInvocation = true` — პარალელურად (ფრთხილად `DbContext`-თან: ის thread-safe არ არის!).

**`ToolMode`.** `ChatOptions.ToolMode`: `Auto` (ნაგულისხმევი — მოდელი წყვეტს), `RequireAny` (აუცილებლად გამოიძახოს რომელიმე), `RequireSpecific("get_menu")`, `None` (tool-ები აღწერილია, მაგრამ არ იძახოს). `RequireAny` სასარგებლოა, როცა ვიცით, რომ პასუხი აუცილებლად ბაზიდან უნდა მოვიდეს.

**OpenAI/Anthropic-ზე იგივეა?** კი — ფორმატი განსხვავდება (`tool_calls`, `tool_use`), მაგრამ `FunctionCallContent`/`FunctionResultContent` ერთნაირია. Microsoft.Extensions.AI-ის მთელი აზრი ესაა: Controller-ის კოდი პროვაიდერზე არ არის დამოკიდებული.

**„Function calling“ vs „tool calling“.** ერთი და იგივე. OpenAI-მ ჯერ „functions“ უწოდა, მერე „tools“ (რადგან tool შეიძლება იყოს არა მხოლოდ ფუნქცია, მაგ. ჩაშენებული Google Search). Gemini-ზე ჩაშენებული tool-ებიც არსებობს (Google Search grounding, code execution) — ისინი Google-ის მხარეს სრულდება, ჩვენი კოდის გარეშე.

### 📖 ისწავლე: AIFunctionFactory, ChatOptions.Tools და UseFunctionInvocation

#### `AIFunctionFactory.Create` — რას აკეთებს

```csharp
AIFunction tool = AIFunctionFactory.Create(_tools.GetMenu, name: "get_menu");
```

- იღებს `Delegate`-ს (მეთოდს) და reflection-ით კითხულობს: მეთოდის `[Description]` → tool-ის `description`; პარამეტრები (სახელი, ტიპი, `[Description]`) → JSON Schema; დაბრუნების ტიპი → შედეგის სერიალიზაციისთვის.
- `name` — თუ არ მიუთითე, მეთოდის სახელიდან იქმნება (`GetMenu`). ჩვენ ცხადად ვწერთ `get_menu` — snake_case მოდელებისთვის ყველაზე ბუნებრივია და Gemini-ს დოკუმენტაციაც ასე წერს. ეს **სტილია**, არა მოთხოვნა.
- **async მეთოდები** (`Task<T>`) — ავტომატურად ელოდება.
- **`CancellationToken` პარამეტრი** — სქემაში **არ** ჯდება; `FunctionInvokingChatClient` მოთხოვნის token-ს თვითონ გადასცემს.
- **დაბრუნებული ობიექტი** JSON-ად სერიალიზდება და მოდელს `functionResponse`-ად მიდის.

**რატომ მეთოდი instance-ზე (`_tools.GetMenu`)?** delegate „იჭერს“ კონკრეტულ ობიექტს — ამ მოთხოვნის `RestaurantTools`-ს, ამ მოთხოვნის `DbContext`-ით. tool ყოველ მოთხოვნაზე ახლიდან იქმნება Controller-ში — ეს იაფია (reflection-ის შედეგი ქეშირდება).

#### რატომ `RestaurantTools` Scoped, `IChatClient` კი Singleton — და რატომ არ არის ეს პრობლემა

API კურსიდან იციან: Singleton-ში Scoped სერვისის ჩასმა (captive dependency) შეცდომაა. აქ ეს **არ** ხდება: tool `IChatClient`-ში არ რეგისტრირდება. ის `ChatOptions.Tools`-ით **ამ მოთხოვნასთან** მიდის და მოთხოვნის დასრულებისას ქრება. Singleton client-ი მას მხოლოდ ამ ერთი `GetResponseAsync`-ის განმავლობაში იყენებს.

#### `ChatOptions.Tools`

`IList<AITool>`. `AIFunction` არის `AITool`-ის ერთ-ერთი სახე (სხვები — ჩაშენებული tool-ები, მაგ. `HostedWebSearchTool`, რომლებსაც პროვაიდერი თვითონ ასრულებს). სია ყოველ მოთხოვნაზე შეიძლება სხვა იყოს — მაგ. ადმინს მეტი tool, სტუმარს ნაკლები.

#### `.UseFunctionInvocation()` — რას აკეთებს (მოკლედ, დეტალურად ლექცია 5)

`AddChatClient(...)` აბრუნებს `ChatClientBuilder`-ს (ლექცია 3-ზე ვახსენეთ). `.UseFunctionInvocation()` Gemini-ს client-ის **გარშემო** ამატებს `FunctionInvokingChatClient`-ს. Controller-ი `IChatClient`-ს იღებს — და ეს უკვე „შეფუთული“ client-ია:

1. Controller → `FunctionInvokingChatClient.GetResponseAsync(messages, options)`
2. ის → Gemini. პასუხში `FunctionCallContent`?
3. კი → `options.Tools`-ში პოულობს `AIFunction`-ს სახელით → `InvokeAsync(arguments)` → `FunctionResultContent` → ისტორიას ამატებს → ისევ Gemini. (მეორდება, სანამ tool-ის თხოვნა აღარ იქნება ან ლიმიტს არ მიაღწევს.)
4. არა → აბრუნებს პასუხს. `response.Messages`-ში **ყველა** შუალედური შეტყობინებაა.

ლიმიტი: `MaximumIterationsPerRequest` — რამდენჯერ შეიძლება ციკლი გაიმეოროს ერთ მოთხოვნაზე (უსასრულო ციკლისგან დაცვა). კონფიგურაცია: `.UseFunctionInvocation(configure: c => c.MaximumIterationsPerRequest = 5)`.

**შეცდომა tool-ში:** exception იჭერება და მოდელს შეტყობინება ეგზავნება, რომ ფუნქცია ვერ შესრულდა; მოდელი მომხმარებელს ამის მიხედვით პასუხობს. exception-ის **ტექსტი** ნაგულისხმევად არ ეგზავნება (`IncludeDetailedErrors = false`) — შეიძლება შიდა ინფორმაცია იყოს.

#### `response.Messages` vs `response.Text`

- `response.Text` — მხოლოდ **ბოლო** ასისტენტის ტექსტი.
- `response.Messages` — ყველაფერი, რაც ამ `GetResponseAsync`-ზე შეიქმნა (ჩვენი input-ის გარეშე): assistant-ის შეტყობინება `FunctionCallContent`-ით (+ Gemini-ს thought signature), tool-ის შეტყობინება `FunctionResultContent`-ით, ბოლო assistant-ის ტექსტი.

`toolCalls`-ს ვაგროვებთ `.OfType<FunctionCallContent>()`-ით — სასწავლო მიზნით. production-ში ამას ლოგი აკეთებს (ლექცია 5).
