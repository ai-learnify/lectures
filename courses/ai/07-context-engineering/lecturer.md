# ლექტორისთვის · ლექცია 7

სტუდენტები ამ გვერდს ვერ ხედავენ. სამი ეტაპი: **📖 ისწავლე** — თემის სრული ახსნა შენთვის; **🎯 მოემზადე** — როგორ ჩაატარო ლექცია: მსვლელობა, კითხვები, შეცდომები; **📋 ლექციაზე** — მოკლე გეგმა კლასში. თუ პრეზენტაცია ამ გვერდიდან გახსენი, მიმდინარე თემა მოინიშნება.

## 🎯 მიმოხილვა

ლექცია ლექცია 6-ის ბოლო კითხვით იწყება: „ხვალ 20:00-ზე ოთხნი ვართ?“ → „და 21:00-ზე?“ — მეორეს მოდელი ვერ იგებს. სამი ნაწილია.

**ნაწილი 1 — კონტექსტი (თეორია, კოდის გარეშე).** stateless-ის პრობლემა ცოცხლად. კონტექსტის „ანატომია“: System, tool-ები, ისტორია, tool-ების შედეგები, შეკითხვა — და ყველაზე დიდი ნაწილი tool-ების შედეგებია. Prompt engineering vs context engineering.

**ნაწილი 2 — ისტორია ბაზაში (ლექციის მთავარი კოდი).** სად ვინახოთ (კლიენტი / მეხსიერება / PostgreSQL). `ChatMessageRecord` jsonb სვეტით, `ChatHistoryStore` (`AIJsonUtilities.DefaultOptions` + `AllowOutOfOrderMetadataProperties`), `/chat` `conversationId`-ით. ბაზაში ვინახავთ **ყველაფერს**, tool-ების შეტყობინებების ჩათვლით — როგორც რეალურ სისტემებში.

**ნაწილი 3 — ბიუჯეტი.** InputTokenCount ყოველ შეკითხვაზე იზრდება (მენიუ ისტორიაში რჩება). სამი სტრატეგია: შერჩევა, შეკუმშვა, რიგი. „ბაზაში ყველაფერი, კონტექსტში ნაწილი“ — `MessageCountingChatReducer`.

**მთავარი იდეა, რომელიც ყველა ნაწილს აკავშირებს:** მეხსიერება მოდელში კი არა, **ჩვენს კოდშია**, და რას ხედავს მოდელი, **ჩვენ** ვწყვეტთ.

### 📌 სტუდენტს აუცილებლად უნდა დარჩეს

1. მოდელი stateless-ია: ისტორიას ყოველ მოთხოვნაში **ჩვენ** ვუგზავნით.
2. კონტექსტი = System + tool-ები + ისტორია + tool შედეგები + შეკითხვა; ყველაფერი ტოკენია (ფასი, ლიმიტი, სიჩქარე).
3. ისტორია ბაზაში: `conversationId`, მთელი `ChatMessage` jsonb-ში, **ყველა** შეტყობინება; System prompt — არა.
4. `/chat`: ჩატვირთე → `[SystemPrompt(), .. history, question]` → შეინახე `[question, .. response.Messages]`.
5. ბაზაში ყველაფერი, კონტექსტში ნაწილი — `MessageCountingChatReducer`.

მოდელი მხოლოდ იმას ხედავს, რაც ამ მოთხოვნაში ჩავდეთ. „მეხსიერებაც“, „ცოდნაც“, „წესებიც“ — ყველაფერი, რაც მოდელს სჭირდება, ჩვენ უნდა ჩავდოთ ფანჯარაში. რა ჩავდოთ — ეს **ჩვენი** საინჟინრო გადაწყვეტილებაა.

### 📖 ისწავლე: კონტექსტი და context engineering

#### stateless — რას ნიშნავს კოდის დონეზე

Gemini-ს REST API (`generateContent`) ყოველ მოთხოვნაზე იღებს `contents` მასივს — ეს ჩვენი `messages` სიაა. სერვერის მხარეს წინა მოთხოვნიდან არაფერი რჩება (ჩვენს რეჟიმში). ამიტომ:

- „მეხსიერება“ = ისტორიის ხელახლა გაგზავნა ყოველ ჯერზე.
- ყოველი ახალი შეკითხვა **ყველა წინა შეტყობინების** input ტოკენებს იხდის.
- ChatGPT, Claude, Gemini-ს აპები ზუსტად ასე მუშაობს: საუბარი სერვერის ბაზაშია და ყოველ შეტყობინებაზე იტვირთება.

ზოგ პროვაიდერს **stateful** რეჟიმიც აქვს (OpenAI Responses API `previous_response_id`/Conversations, Gemini-ს Interactions API): ისტორიას პროვაიდერი ინახავს. Microsoft.Extensions.AI ამას `ChatOptions.ConversationId`-ით ფარავს. ჩვენ მას **არ** ვიყენებთ: ისტორია ჩვენი მონაცემია, ჩვენს ბაზაში, ნებისმიერ პროვაიდერზე გადასატანი.

#### კონტექსტის ხუთი ნაწილი

| ნაწილი | რა არის | როგორ იზრდება |
|---|---|---|
| System | ჩვენი ინსტრუქცია | მუდმივი |
| Tools | tool-ების სახელი, `[Description]`, პარამეტრების JSON Schema — **ყოველ** მოთხოვნაში | tool-ების რაოდენობით |
| ისტორია | წინა User/Assistant შეტყობინებები | ყოველ შეკითხვაზე |
| tool შედეგები | `FunctionResultContent` — რაც tool-მა დააბრუნა | ყოველ გამოძახებაზე, ხშირად ნახტომით |
| შეკითხვა | ახალი User შეტყობინება | — |

**tool-ების აღწერებიც ტოკენებია.** ლექცია 4-ის ⭐-ში ეს ჩანდა: `/ask` vs `/chat` ერთსა და იმავე „გამარჯობაზე“ — `/chat`-ის InputTokenCount მეტია, რადგან tool-ების სქემა მიდის. 20 tool = რამდენიმე ათასი ტოკენი ყოველ მოთხოვნაზე. ამიტომ აგენტებში tool-ების შერჩევაც context engineering-ია (Microsoft.Extensions.AI-ს ამისთვის `IToolReductionStrategy` აქვს — 🔬).

#### prompt engineering vs context engineering

ტერმინი 2025 წელს გავრცელდა, როცა აგენტები პოპულარული გახდა. იდეა: prompt-ის ტექსტი მხოლოდ ერთი ნაწილია; ხარისხს ის წყვეტს, **რა** არის ფანჯარაში ყოველ ნაბიჯზე. აგენტი 30 tool-ს იძახებს, ყოველი შედეგი კონტექსტში ჯდება — და თუ არაფერს ვმართავთ, მე-20 ნაბიჯზე კონტექსტი ნაგვით სავსეა.

სტუდენტებისთვის საკმარისია: **prompt engineering = როგორ დავწეროთ; context engineering = რა ჩავდოთ.**

### 🔬 უფრო ღრმად — თუ ჰკითხავენ

**Context caching.** Gemini-ს (და Anthropic-ის, OpenAI-ის) აქვს prompt/context caching: თუ მოთხოვნის დასაწყისი (System + tools) იგივეა, პროვაიდერი მას იაფად ითვლის. ამიტომ რიგსაც აქვს მნიშვნელობა: უცვლელი ნაწილი — თავში. Gemini-ზე ზოგ მოდელს implicit caching აქვს — პასუხის `Usage`-ში `CachedInputTokenCount` შეიძლება გამოჩნდეს.

**„Lost in the middle“.** კვლევებმა აჩვენა, რომ გრძელ კონტექსტში მოდელი დასაწყისისა და ბოლოს ინფორმაციას უკეთ იყენებს, ვიდრე შუაში მოქცეულს. თანამედროვე მოდელებზე ეფექტი ნაკლებია, მაგრამ წესი რჩება: მნიშვნელოვანი — თავში ან ბოლოს.

**ტოკენების დათვლა გაგზავნამდე.** Gemini-ს `countTokens` endpoint აქვს. პრაქტიკაში ხშირად საკმარისია წინა პასუხის `InputTokenCount` — ის ზუსტად გვეუბნება, რამდენი წავიდა.

`Contents`-ში შეიძლება იყოს: `TextContent`, `FunctionCallContent` (CallId, Name, Arguments), `FunctionResultContent` (CallId, Result), `TextReasoningContent` (Gemini-ს ფიქრი / ხელმოწერა — `ProtectedData`), `UsageContent`, `DataContent` (სურათი/ფაილი) და სხვ.

**რატომ არ ვინახავთ მხოლოდ `Text`-ს:** ასე tool-ის შეტყობინებები (`Text` ცარიელია) და ფიქრის ხელმოწერა იკარგება. Gemini 3 მოითხოვს, რომ ფიქრის ბლოკები ზუსტად ისე დავუბრუნოთ, როგორც მიიღო — თორემ tool-იან ისტორიაზე შეცდომას აბრუნებს. მთელი შეტყობინების სერიალიზაცია ამ ყველაფერს აგვარებს და რეალურ სისტემებშიც ასე ხდება.

#### სერიალიზაცია: `AIJsonUtilities.DefaultOptions`

`AIContent` პოლიმორფულია: JSON-ში ყოველ ნაწილს `"$type"` discriminator ეწერება (`"text"`, `"functionCall"`, `"functionResult"`, `"reasoning"`, `"usage"`…). `AIJsonUtilities.DefaultOptions` ამ ტიპებს იცნობს (camelCase, enum-ები სტრიქონად და ა.შ.). ჩვეულებრივი `JsonSerializerOptions` `ChatMessage`-ს ვერ აღადგენს სწორად.

`RawRepresentation` `[JsonIgnore]`-ია — პროვაიდერის „ნედლი“ ობიექტი არ ინახება, და არც გვჭირდება.

#### jsonb და `$type`-ის რიგი

PostgreSQL-ს ორი JSON ტიპი აქვს:

| | `json` | `jsonb` |
|---|---|---|
| ინახავს | ტექსტს ზუსტად ისე | დამუშავებულ (binary) ფორმას |
| key-ების რიგი | ინარჩუნებს | **ცვლის** (ჯერ მოკლე key-ები) |
| ინდექსი, `@>` ძებნა | არა | კი (GIN) |

jsonb key-ებს თავისებურად ალაგებს: `{"$type":"text","text":"…"}` ბრუნდება როგორც `{"text":"…","$type":"text"}`. System.Text.Json ნაგულისხმევად ელოდება, რომ metadata (`$type`) ობიექტში **პირველი** იყოს, და აგდებს: *The metadata property is either not supported by the type or is not the first property in the deserialized JSON object.* **გამოსავალი:** `AllowOutOfOrderMetadataProperties = true` (.NET 9+). სხვა გამოსავალი `json` ტიპი იქნებოდა, მაგრამ jsonb-ში ძებნა გვინდა (⭐).

`new JsonSerializerOptions(AIJsonUtilities.DefaultOptions) { ... }` — copy constructor: ყველა პარამეტრს (TypeInfoResolver-ის ჩათვლით) იღებს და ჩვენსას ამატებს. `static readonly` — ერთხელ იქმნება (options-ის ყოველ ჯერზე შექმნა ნელია: metadata cache იკარგება).

#### `Position` — რატომ არა `CreatedAt`

ერთ `AppendAsync`-ში 4 შეტყობინება ერთსა და იმავე მილიწამში შეიძლება ჩაიწეროს — `CreatedAt`-ით რიგი არ არის გარანტირებული. `Guid Id` (API კურსის წესი) რიგს არ იძლევა. ამიტომ `Position`: `CountAsync` + ერთით ზრდა. **ერთდროული მოთხოვნები** ერთ საუბარზე (ორი ტაბი) ერთსა და იმავე Position-ს მიიღებს — production-ში `(ConversationId, Position)`-ზე unique index და retry, ან ერთ საუბარზე ერთი მოთხოვნა ერთდროულად. სტუდენტებთან — მხოლოდ თუ ჰკითხავენ.

#### `IChatReducer` და `MessageCountingChatReducer`

```csharp
public interface IChatReducer
{
    Task<IEnumerable<ChatMessage>> ReduceAsync(IEnumerable<ChatMessage> messages, CancellationToken cancellationToken);
}
```

`MessageCountingChatReducer(int targetCount)`:

- ტოვებს ბოლო `targetCount` **არა-System** შეტყობინებას (System-ს, თუ სიაშია, ინარჩუნებს — ჩვენ მას სიაში არ ვატანთ).
- `FunctionCallContent`-ის ან `FunctionResultContent`-ის შემცველ შეტყობინებებს **ამოყრის** — ასე functionCall/functionResult წყვილი არასდროს „იჭრება“ შუაზე.

**რატომ არ ვიყენებთ `TakeLast`:** functionCall ერთ შეტყობინებაშია, functionResult — მეორეში. TakeLast შეიძლება შუაში გაჭრას → პროვაიდერი 400-ს აბრუნებს („function response without call“). reducer ამას თავიდან იცილებს.

**ფიქრის ხელმოწერა reducer-ის შემდეგ:** functionCall-იანი assistant შეტყობინება (სადაც ხელმოწერაა) ამოიყრება მთლიანად, ამიტომ „ნახევრად“ ხელმოწერილი ისტორია არ რჩება. მიმდინარე ბრუნის tool-ის ციკლი `FunctionInvokingChatClient`-ის შიგნით ხდება და reducer მას არ ეხება.

**experimental (MEAI001):** reducer-ები `[Experimental("MEAI001")]`-ითაა მონიშნული. C#-ში experimental API-ს გამოყენება **შეცდომაა** (არა warning), სანამ არ დავთრგუნავთ. ეს ნიშნავს: API შეიძლება შეიცვალოს — კოდი მუშაობს.

**`UseChatReducer` pipeline-ში?** ბიბლიოთეკაში ასეთი ფენა ჩვენთვის საჭირო ფორმით არ გვაქვს, და ჩვენთან ცხადი ვერსია ჯობია: Controller-ში ჩანს, რა მიდის. Agent Framework-ში (ლექცია 14) reducer ისტორიის store-ს ებმება.

public class InMemoryChatHistory

    public Task<List<ChatMessage>> LoadAsync(Guid id, CancellationToken ct) =>
        Task.FromResult(_all.TryGetValue(id, out var list) ? list.ToList() : []);

    {

    }
}

public class LastTurnsReducer(int count) : IChatReducer
{
    public Task<IEnumerable<ChatMessage>> ReduceAsync(
        IEnumerable<ChatMessage> messages, CancellationToken cancellationToken)
    {
        IEnumerable<ChatMessage> textOnly = messages.Where(m =>
            !m.Contents.Any(c => c is FunctionCallContent or FunctionResultContent));
        return Task.FromResult(textOnly.TakeLast(count));
    }
}
