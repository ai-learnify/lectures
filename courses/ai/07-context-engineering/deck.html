## ლექცია 7: Context Engineering — კონტექსტისა და მეხსიერების მართვა ჩვენი ჩატი tool-ებს იძახებს და პასუხს სტრიმავს, მაგრამ ყოველი შეკითხვა ცალკეა. „ხვალ 20:00-ზე ოთხნი ვართ?“ და მერე „და 21:00-ზე?“: მეორე შეკითხვას მოდელი ვერ გაიგებს, რადგან პირველი არ ახსოვს (ლექცია 1: მოდელი stateless-ია). დღეს ვსწავლობთ, **რა** მიდის მოდელთან ყოველ მოთხოვნაზე და **ვინ** წყვეტს ამას: ჩვენ. საუბრის ისტორიას PostgreSQL-ში ვინახავთ, ყოველ მოთხოვნაზე ვტვირთავთ და ვხედავთ, რატომ არ შეიძლება მთელი ისტორიის უსასრულოდ გაგზავნა.
## Lecture 7: Context Engineering — managing context and memory Our chat calls tools and streams the answer, but every question is separate. “Four of us tomorrow at 20:00?” and then “And at 21:00?”: the model won't understand the second question, because it doesn't remember the first (lecture 1: the model is stateless). Today we learn **what** goes to the model on every request and **who** decides it: we do. We store the conversation history in PostgreSQL, load it on every request, and see why we can't keep sending the whole history forever.

### Lecture plan: 3 steps 1. 🪟 **Context.** What goes to the model on every request: our instruction (System), the tool descriptions, the conversation history, the tool results and the new question. Choosing all of this is called **context engineering**. 2. 🗄️ **History in the database.** We store the conversation in PostgreSQL by `conversationId`, every message including the tool ones, and load it on every request. 3. ⚖️ **The budget.** The history grows with every question, and so do the tokens. We decide what to send to the model and what stays only in the database. At the end there's classwork: your chat gets a history.

### პრობლემა: მოდელს წინა შეკითხვა არ ახსოვს ჩვენი `/chat` ყოველ მოთხოვნაზე ახალ `messages` სიას ქმნის: System + მომხმარებლის **ერთი** შეკითხვა. ორი მოთხოვნა ერთმანეთზე არაფერი იცის: | მოთხოვნა | რას ხედავს მოდელი | პასუხი | |---|---|---| | 1 | System + „ხვალ 20:00-ზე ოთხნი ვართ, ადგილი გაქვთ?“ | „დიახ, ორი მაგიდაა“ (`check_availability`) | | 2 | System + „და 21:00-ზე?“ | „რა გაინტერესებთ 21:00-ზე?“ | მეორე მოთხოვნაში პირველი შეკითხვა **საერთოდ არ არის**. ლექცია 1-დან ვიცით: მოდელი **stateless**-ია, ის მხოლოდ იმას ხედავს, რაც ამ მოთხოვნაში გავუგზავნეთ. „მეხსიერება“ ChatGPT-შიც ასე მუშაობს: ყოველ ახალ შეტყობინებასთან ერთად სერვერი მოდელს **მთელ საუბარს** უგზავნის. ესე იგი, მეხსიერება მოდელში კი არა, **ჩვენს კოდშია**: ისტორიას ჩვენ ვინახავთ და ჩვენ ვუგზავნით. ლექცია 2-ის ⭐-ში ეს ხელით ვცადეთ `List`-ით. დღეს ამას სწორად ვაკეთებთ: ბაზაში.
### The problem: the model doesn't remember the previous question Our `/chat` creates a new `messages` list on every request: System + **one** question from the user. Two requests know nothing about each other: | Request | What the model sees | Answer | |---|---|---| | 1 | System + “Four of us tomorrow at 20:00, do you have room?” | “Yes, two tables are free” (`check_availability`) | | 2 | System + “And at 21:00?” | “What would you like to know about 21:00?” | The first question **isn't in** the second request at all. We know from lecture 1: the model is **stateless**, it only sees what we sent in this request. “Memory” works the same way in ChatGPT: with every new message the server sends the model **the whole conversation**. So memory isn't in the model, it's **in our code**: we store the history and we send it. In lecture 2's ⭐ we tried this by hand with a `List`. Today we do it properly: in the database.

### კონტექსტი: რას ხედავს მოდელი ერთ მოთხოვნაში **კონტექსტი** ყველაფერია, რაც მოდელამდე ერთ მოთხოვნაში მიდის. ჩვენს ჩატში ის ხუთი ნაწილისგან შედგება: | ნაწილი | საიდან | ნიმუში (ტოკენი) | |---|---|---| | **System** | ჩვენი ინსტრუქცია (ლექცია 2) | ~180 | | **Tools** | tool-ების სახელები, აღწერები, პარამეტრების JSON Schema (ლექცია 4) | ~310 | | **ისტორია** | წინა შეკითხვები და პასუხები | ~460 | | **tool შედეგები** | რაც tool-ებმა დააბრუნა, მაგ. მთელი მენიუ | ~1 780 | | **ახალი შეკითხვა** | მომხმარებელი | ~25 | ციფრები ნიმუშია, მაგრამ სურათი ტიპურია: **ყველაზე დიდი ნაწილი ხშირად tool-ების შედეგებია**, და არა ის, რაც მომხმარებელმა დაწერა. `get_menu` მთელ მენიუს აბრუნებს, და თუ ის ისტორიაში დარჩა, ყოველ შემდეგ მოთხოვნაში თავიდან მიდის. ყველაფერი ეს ერთ **context window**-ში უნდა ჩაეტიოს (ლექცია 1), და ყველაფერში ვიხდით: input ტოკენი ფასიანია, დიდი კონტექსტი ნელია. **Prompt engineering vs context engineering:** - **Prompt engineering** (ლექცია 2) — **როგორ** დავწეროთ ინსტრუქცია: როლი, წესები, მაგალითები. - **Context engineering** — **რა** ჩავდოთ ფანჯარაში ყოველ მოთხოვნაზე: რომელი ისტორია, რომელი tool-ები, რომელი შედეგები, რა რიგით, და რა დარჩეს გარეთ. Prompt ამ ფანჯრის ერთი ნაწილია. აგენტებთან (ლექცია 13+) ეს მთავარი უნარი ხდება: აგენტი ათობით tool-ს იძახებს, და კონტექსტი ძალიან სწრაფად ივსება. ```terms კონტექსტი (context) — ყველაფერი, რასაც მოდელი ერთ მოთხოვნაში ხედავს: ინსტრუქცია, tool-ები, ისტორია, tool-ების შედეგები, შეკითხვა Context engineering — იმის გადაწყვეტა, რა ჩავდოთ კონტექსტში ყოველ მოთხოვნაზე, რა რიგით და რა დავტოვოთ გარეთ ```
### Context: what the model sees in one request **Context** is everything that reaches the model in one request. In our chat it has five parts: | Part | Where from | Sample (tokens) | |---|---|---| | **System** | our instruction (lecture 2) | ~180 | | **Tools** | the tool names, descriptions, parameters' JSON Schema (lecture 4) | ~310 | | **History** | the previous questions and answers | ~460 | | **Tool results** | what the tools returned, e.g. the whole menu | ~1,780 | | **New question** | the user | ~25 | The numbers are a sample, but the picture is typical: **the biggest part is often the tool results**, not what the user wrote. `get_menu` returns the whole menu, and if it stays in the history, it goes again in every later request. All of this has to fit in one **context window** (lecture 1), and we pay for all of it: input tokens cost money, and a large context is slow. **Prompt engineering vs context engineering:** - **Prompt engineering** (lecture 2) — **how** to write the instruction: the role, the rules, the examples. - **Context engineering** — **what** to put in the window on every request: which history, which tools, which results, in what order, and what stays out. The prompt is one part of that window. With agents (lecture 13+) this becomes the key skill: an agent calls dozens of tools, and the context fills up very fast. ```terms Context — everything the model sees in one request: the instruction, the tools, the history, the tool results, the question Context engineering — deciding what to put in the context on every request, in what order, and what to leave out ```

### სად ვინახოთ ისტორია | ვარიანტი | რა ხდება | პრობლემა | |---|---|---| | **კლიენტი აგზავნის** | frontend ყოველ მოთხოვნაში მთელ საუბარს აგზავნის | კლიენტს შეუძლია ისტორია შეცვალოს (მაგ. ჩაწეროს, რომ ასისტენტმა 50% ფასდაკლება „დაჰპირდა“); ტრაფიკი ყოველ ჯერზე იზრდება | | **სერვერის მეხსიერება** | Singleton სერვისში `Dictionary>` | აპლიკაციის რესტარტზე ყველაფერი ქრება; ორ სერვერზე ერთი მომხმარებლის მოთხოვნები სხვადასხვა მეხსიერებაში ხვდება | | **PostgreSQL** ✓ | ცხრილი, სადაც ერთი ხაზი ერთი შეტყობინებაა, `ConversationId`-ით | — | ბაზაში ისტორია რჩება, ყველა სერვერი ერთსა და იმავეს ხედავს, და შეგვიძლია გავაანალიზოთ: რას კითხულობენ ხშირად, სად ცდება ასისტენტი. **რას ვინახავთ? ყველაფერს**, tool-ების გამოძახებებისა და შედეგების ჩათვლით. ასე მუშაობს რეალური სისტემებიც: ბაზაში სრული ჩანაწერია, ხოლო ის, რასაც **მოდელს ვუგზავნით**, ცალკე გადაწყვეტილებაა (ნაწილი 3). „ბაზაში ინახება“ და „კონტექსტში მიდის“ ორი სხვადასხვა რამეა.
### Where to store the history | Option | What happens | Problem | |---|---|---| | **The client sends it** | the frontend sends the whole conversation in every request | the client can change the history (e.g. write that the assistant “promised” a 50% discount); the traffic grows every time | | **Server memory** | a `Dictionary>` in a Singleton service | everything disappears when the app restarts; with two servers, one user's requests end up in different memories | | **PostgreSQL** ✓ | a table where one row is one message, by `ConversationId` | — | In the database the history stays, every server sees the same one, and we can analyse it: what people ask often, where the assistant makes mistakes. **What do we store? Everything**, the tool calls and results included. Real systems work this way too: the database has the full record, while what we **send to the model** is a separate decision (part 3). “Stored in the database” and “goes into the context” are two different things.

### ცხრილი და შენახვა: `ChatMessageRecord` და `ChatHistoryStore` **ცხრილი.** ერთი ხაზი ერთი შეტყობინებაა: ```csharp Data/ChatMessageRecord.cs public class ChatMessageRecord { public Guid Id { get; set; } public Guid ConversationId { get; set; } // რომელ საუბარს ეკუთვნის public int Position { get; set; } // რიგი საუბარში: 0, 1, 2… public string Role { get; set; } = ""; // user / assistant / tool — ბაზაში სანახავად [Column(TypeName = "jsonb")] public string Json { get; set; } = ""; // მთელი ChatMessage public DateTime CreatedAt { get; set; } } ``` `AppDbContext`-ში: `public DbSet ChatMessages => Set();`, მერე migration (`Add-Migration ChatHistory`, `Update-Database`). **რატომ jsonb და არა სვეტები?** `ChatMessage`-ს `Text` კი არა, **`Contents`** აქვს: სხვადასხვა ტიპის ნაწილების სია. ტექსტი (`TextContent`), tool-ის გამოძახება (`FunctionCallContent`), tool-ის შედეგი (`FunctionResultContent`), Gemini-ს ფიქრის ხელმოწერა (`TextReasoningContent`, ლექცია 4). ყოველი ტიპისთვის სვეტები რომ გავაკეთოთ, ცხრილი ჩიხი გახდება. ამიტომ მთელ შეტყობინებას JSON-ად ვინახავთ ერთ **jsonb** სვეტში: PostgreSQL მას JSON-ად ინახავს და შიგნით ძებნაც შეუძლია. **სერიალიზაცია.** `AIJsonUtilities.DefaultOptions` — Microsoft.Extensions.AI-ის მზა პარამეტრები, რომლებმაც `AIContent`-ის ყველა ტიპი იციან. JSON-ში ყოველ ნაწილს `"$type"` ეწერება (`"text"`, `"functionCall"`…), რომ უკან წაკითხვისას სწორი ტიპი შეიქმნას: ```csharp Ai/ChatHistoryStore.cs public class ChatHistoryStore { // jsonb key-ებს ალაგებს — "$type" აღარ არის პირველი private static readonly JsonSerializerOptions Json = new(AIJsonUtilities.DefaultOptions) { AllowOutOfOrderMetadataProperties = true }; private readonly AppDbContext _db; public ChatHistoryStore(AppDbContext db) { _db = db; } public async Task> LoadAsync(Guid conversationId, CancellationToken ct) { List rows = await _db.ChatMessages .Where(m => m.ConversationId == conversationId) .OrderBy(m => m.Position) .Select(m => m.Json) .ToListAsync(ct); return rows.Select(j => JsonSerializer.Deserialize(j, Json)!).ToList(); } public async Task AppendAsync(Guid conversationId, IEnumerable messages, CancellationToken ct) { int position = await _db.ChatMessages.CountAsync(m => m.ConversationId == conversationId, ct); foreach (ChatMessage message in messages) { _db.ChatMessages.Add(new ChatMessageRecord { Id = Guid.NewGuid(), ConversationId = conversationId, Position = position++, Role = message.Role.Value, Json = JsonSerializer.Serialize(message, Json), CreatedAt = DateTime.UtcNow }); } await _db.SaveChangesAsync(ct); } } ``` `Program.cs`-ში: `builder.Services.AddScoped();` (Scoped, რადგან `AppDbContext`-ს იყენებს). ```warn **`AllowOutOfOrderMetadataProperties = true` აუცილებელია.** System.Text.Json ელოდება, რომ `"$type"` ობიექტში **პირველი** იყოს. jsonb კი key-ებს თავისებურად ალაგებს (ჯერ მოკლეს), და `"text"` `"$type"`-ზე წინ ექცევა. ამ პარამეტრის გარეშე წაკითხვისას exception მოვა. ``` ```terms jsonb — PostgreSQL-ის ტიპი JSON-ისთვის: ინახავს დამუშავებულ ფორმაში, შიგნით ძებნა შეუძლია AIJsonUtilities.DefaultOptions — Microsoft.Extensions.AI-ის JSON პარამეტრები, რომლებმაც ChatMessage და AIContent-ის ყველა ტიპი იციან $type — JSON-ში ველი, რომელიც ამბობს, რომელი C# ტიპი შეიქმნას (text, functionCall, functionResult…) ```
### The table and storing: `ChatMessageRecord` and `ChatHistoryStore` **The table.** One row is one message: ```csharp Data/ChatMessageRecord.cs public class ChatMessageRecord { public Guid Id { get; set; } public Guid ConversationId { get; set; } // which conversation it belongs to public int Position { get; set; } // order in the conversation: 0, 1, 2… public string Role { get; set; } = ""; // user / assistant / tool — for looking at the DB [Column(TypeName = "jsonb")] public string Json { get; set; } = ""; // the whole ChatMessage public DateTime CreatedAt { get; set; } } ``` In `AppDbContext`: `public DbSet ChatMessages => Set();`, then a migration (`Add-Migration ChatHistory`, `Update-Database`). **Why jsonb and not columns?** A `ChatMessage` doesn't have a `Text`, it has **`Contents`**: a list of parts of different types. Text (`TextContent`), a tool call (`FunctionCallContent`), a tool result (`FunctionResultContent`), Gemini's thought signature (`TextReasoningContent`, lecture 4). If we made columns for every type, the table would become a dead end. So we store the whole message as JSON in one **jsonb** column: PostgreSQL stores it as JSON and can search inside it. **Serialization.** `AIJsonUtilities.DefaultOptions` — Microsoft.Extensions.AI's ready-made settings that know every `AIContent` type. In the JSON every part gets a `"$type"` (`"text"`, `"functionCall"`…), so that the right type is created when reading it back: ```csharp Ai/ChatHistoryStore.cs public class ChatHistoryStore { // jsonb reorders keys — "$type" is no longer first private static readonly JsonSerializerOptions Json = new(AIJsonUtilities.DefaultOptions) { AllowOutOfOrderMetadataProperties = true }; private readonly AppDbContext _db; public ChatHistoryStore(AppDbContext db) { _db = db; } public async Task> LoadAsync(Guid conversationId, CancellationToken ct) { List rows = await _db.ChatMessages .Where(m => m.ConversationId == conversationId) .OrderBy(m => m.Position) .Select(m => m.Json) .ToListAsync(ct); return rows.Select(j => JsonSerializer.Deserialize(j, Json)!).ToList(); } public async Task AppendAsync(Guid conversationId, IEnumerable messages, CancellationToken ct) { int position = await _db.ChatMessages.CountAsync(m => m.ConversationId == conversationId, ct); foreach (ChatMessage message in messages) { _db.ChatMessages.Add(new ChatMessageRecord { Id = Guid.NewGuid(), ConversationId = conversationId, Position = position++, Role = message.Role.Value, Json = JsonSerializer.Serialize(message, Json), CreatedAt = DateTime.UtcNow }); } await _db.SaveChangesAsync(ct); } } ``` In `Program.cs`: `builder.Services.AddScoped();` (Scoped, because it uses `AppDbContext`). ```warn **`AllowOutOfOrderMetadataProperties = true` is required.** System.Text.Json expects `"$type"` to be **first** in the object. But jsonb orders keys its own way (shorter ones first), and `"text"` ends up before `"$type"`. Without this setting reading it back throws an exception. ``` ```terms jsonb — PostgreSQL's type for JSON: stores it in a processed form and can search inside it AIJsonUtilities.DefaultOptions — Microsoft.Extensions.AI's JSON settings that know ChatMessage and every AIContent type $type — a field in the JSON that says which C# type to create (text, functionCall, functionResult…) ```

### `/chat` with history: load → send → save ```csharp Controllers/AiLabController.cs · Chat public record ChatRequest(Guid? ConversationId, string Prompt); [HttpPost("chat")] public async Task Chat(ChatRequest request, CancellationToken ct) { Guid conversationId = request.ConversationId ?? Guid.NewGuid(); List history = await _history.LoadAsync(conversationId, ct); ChatMessage question = new(ChatRole.User, request.Prompt); List messages = [SystemPrompt(), .. history, question]; ChatResponse response = await _chat.GetResponseAsync(messages, ChatToolOptions(), ct); await _history.AppendAsync(conversationId, [question, .. response.Messages], ct); return Ok(new { conversationId, response.Text, response.Usage?.InputTokenCount }); } ``` `ChatHistoryStore` comes to the Controller through the constructor (`_history`), like `RestaurantTools`. **Step by step:** 1. **`ConversationId ?? Guid.NewGuid()`** — on the first question the client has no id, so we start a new conversation. We return the id in the response, and the client sends it in every later request. 2. **`LoadAsync`** — the previous messages from the database, in order. 3. **`[SystemPrompt(), .. history, question]`** — a collection expression: System first, then the history (`..` “spreads” the list), and the new question last. `SystemPrompt()` is the same System prompt as in lecture 6, moved into its own method, like `ChatToolOptions()`. 4. **`AppendAsync(conversationId, [question, .. response.Messages])`** — we store the question and **everything** the model added. In the tool loop `response.Messages` is more than one message: the tool request, the result and the final answer. **The System prompt isn't stored in the database.** It's ours, not part of the conversation: it has today's date in it, and if we change a rule tomorrow, old conversations should get the new rule too. So we build it again on every request and put it at the top of the list. **Checking it in Swagger:** the first request without a `conversationId` → a new id in the response. The second request with the same id: “And at 21:00?” → the model sees the first question and calls `check_availability` with 21:00. `InputTokenCount` is bigger on the second request: the history goes too.

### Growth: every question sends the whole history The `InputTokenCount` of each question in one conversation (sample): | Question | What happened | InputTokenCount | |---|---|---| | 1 | “Hello” | ~620 (System + tools) | | 2 | “Four of us at 20:00?” → `check_availability` | ~1,450 | | 3 | “What do you have under 15 GEL?” → **`get_menu`** | ~3,300 | | 4 | “Is the lobio spicy?” | ~3,900 | | 5 | “What vegetarian dishes do you have?” → **`get_menu`** again | ~5,600 | | 6 | “OK, I'll book” | ~7,100 | **The biggest jump comes after `get_menu`**: the whole menu stays in the history as a `functionResult` and goes along with every later question. On the 50th question tens of thousands of tokens go every time, and the model processes a large context more slowly. - 🧱 **The limit.** The context window is big, but not infinite. A long conversation fills it sooner or later. - 🕰️ **Stale data.** In the tool result left in the history the lobio costs 12 GEL, but in the database it's already 14. The model may not call the tool again and quote the old price. - 🎯 **Attention.** The more there is in the context, the more things “get in the way” of the main one. ### Three strategies: selection, compression, order | Strategy | What it means | In our project | |---|---|---| | 🎯 **Selection** | only what this question needs goes into the context | a tool instead of the whole menu (lecture 4: the model asks for what it needs) · the last N messages of the history · RAG in lecture 11: only the relevant parts of documents | | 🗜️ **Compression** | the old part in a smaller form | **truncation**: we drop the old messages · **summarization**: the model sums up the old part briefly and the summary goes in its place | | 📐 **Order** | where things stand in the context | System always first · the new question last · important information at the start or the end, not in the middle | **The main idea: everything stays in the database, only part of it goes into the context.** On every request our code decides what goes out of the database. This decision is ours, not the model's: that's exactly what context engineering is. **Truncation vs summarization.** Truncation is simple and cheap, but an old detail (e.g. “four of us”) disappears. Summarization keeps the detail, but costs one extra call, and the summary may leave something out. Today we do truncation; summarization is in the ⭐.

### `IChatReducer`: the last 10 messages to the model Microsoft.Extensions.AI has **`IChatReducer`**: an interface that takes a list of messages and returns a smaller one. The ready-made **`MessageCountingChatReducer`** keeps only the last N messages: ```csharp Controllers/AiLabController.cs · Chat #pragma warning disable MEAI001 // reducers are still experimental private static readonly IChatReducer Reducer = new MessageCountingChatReducer(10); #pragma warning restore MEAI001 // inside Chat: List history = await _history.LoadAsync(conversationId, ct); IEnumerable recent = await Reducer.ReduceAsync(history, ct); ChatMessage question = new(ChatRole.User, request.Prompt); List messages = [SystemPrompt(), .. recent, question]; // ... GetResponseAsync, AppendAsync — unchanged ``` **What `MessageCountingChatReducer(10)` does:** - It keeps **the last 10** messages (besides System). The older ones no longer go into the context. - It **drops the tool messages** (`functionCall`, `functionResult`). So the menu no longer goes along with old questions: the biggest part disappears. - It **doesn't touch the database.** `AppendAsync` still stores everything. Only what goes in **this** request changes. **And the price?** The menu is no longer in the context, so if the user asks about a price, the model calls `get_menu` **again** and gets the new price. This is even better: an old price no longer “gets stuck” in the history. **Why not just `history.TakeLast(10)`?** It might cut in the middle of a list: a functionCall stays but its functionResult doesn't. On such a history the provider returns an error. The reducer removes the tool messages entirely and sidesteps this problem. ```warn **`MEAI001`.** Reducers in Microsoft.Extensions.AI are still marked **experimental**: the API may change. The compiler shows an error until we write `#pragma warning disable MEAI001` (or `MEAI001` in the `.csproj`). ``` ```terms IChatReducer — an interface that shrinks the list of messages before it's sent to the model MessageCountingChatReducer — a ready-made reducer: keeps the last N messages and drops the tool messages Truncation — dropping old messages from the context ```

## შეჯამება - მოდელი **stateless**-ია. „მეხსიერება“ ისტორიაა, რომელსაც ყოველ მოთხოვნაში **ჩვენ** ვუგზავნით. - **კონტექსტი** ყველაფერია, რასაც მოდელი ერთ მოთხოვნაში ხედავს: System, tool-ების აღწერები, ისტორია, tool-ების შედეგები, ახალი შეკითხვა. ყველაზე დიდი ნაწილი ხშირად tool-ების შედეგებია. - **Context engineering** — იმის გადაწყვეტა, რა ჩავდოთ კონტექსტში, რა დავტოვოთ გარეთ და რა რიგით. სტრატეგიები: **შერჩევა**, **შეკუმშვა** (truncation, summarization), **რიგი**. - ისტორია **PostgreSQL**-შია: ერთი ხაზი = ერთი `ChatMessage`, `ConversationId`-ით, მთელი შეტყობინება **jsonb**-ში (`AIJsonUtilities.DefaultOptions` + `AllowOutOfOrderMetadataProperties`). ვინახავთ **ყველაფერს**, tool-ების ჩათვლით. - **System prompt** ბაზაში არ ინახება: ის ჩვენია და ყოველ მოთხოვნაზე ახლიდან იწყობა. - **ბაზაში ყველაფერი, კონტექსტში ნაწილი.** `MessageCountingChatReducer` ბოლო N შეტყობინებას ტოვებს და tool-ის შეტყობინებებს ამოყრის; მოდელი საჭიროებისას tool-ს თავიდან იძახებს. ### შემდეგ ლექციაზე ჩატს ახლა ახსოვს, მაგრამ ყოველი შეკითხვა Gemini-ს რამდენიმე გამოძახებაა, და Gemini ზოგჯერ ცდება: 429 (ძალიან ბევრი მოთხოვნა), 503 (გადატვირთულია), timeout. ახლა ასეთ დროს მომხმარებელი 500-ს ხედავს. ლექცია 8-ზე: **Error Handling, Resilience და ხარჯის კონტროლი** — retry, timeout, fallback მოდელი და ტოკენების აღრიცხვა ბაზაში.
## Summary - The model is **stateless**. “Memory” is the history that **we** send in every request. - **Context** is everything the model sees in one request: System, the tool descriptions, the history, the tool results, the new question. The biggest part is often the tool results. - **Context engineering** — deciding what to put in the context, what to leave out and in what order. The strategies: **selection**, **compression** (truncation, summarization), **order**. - The history is in **PostgreSQL**: one row = one `ChatMessage`, by `ConversationId`, the whole message in **jsonb** (`AIJsonUtilities.DefaultOptions` + `AllowOutOfOrderMetadataProperties`). We store **everything**, the tool messages included. - The **System prompt** isn't stored in the database: it's ours and gets built again on every request. - **Everything in the database, part of it in the context.** `MessageCountingChatReducer` keeps the last N messages and drops the tool messages; the model calls a tool again when it needs to. ### Next lecture The chat remembers now, but every question is several Gemini calls, and Gemini sometimes fails: 429 (too many requests), 503 (overloaded), a timeout. Right now the user sees a 500 when that happens. In lecture 8: **Error Handling, Resilience and Cost Control** — retry, timeout, a fallback model and recording the tokens in the database.
