## ლექცია 9: Text Embeddings მომხმარებელი წერს: "something light, without meat". მენიუში 200 კერძია. მთელი მენიუს მოდელისთვის გაგზავნა ძვირია (ლექცია 7), ხოლო SQL-ის `LIKE '%without meat%'` ლობიოს ვერ იპოვის, რადგან ეს სიტყვები მის აღწერაში არ წერია. გვჭირდება ძებნა **მნიშვნელობით**, არა სიტყვებით. დღეს ვსწავლობთ **embedding**-ს: ტექსტის გადაქცევას რიცხვების სიად (ვექტორად), სადაც მსგავსი მნიშვნელობის ტექსტები ახლოს არიან. ვაგენერირებთ ვექტორებს Gemini-თი, ვზომავთ მსგავსებას და ვწერთ მენიუს სემანტიკურ ძებნას.
## Lecture 9: Text Embeddings The user writes: “something light, without meat”. The menu has 200 dishes. Sending the whole menu to the model is expensive (lecture 7), and SQL's `LIKE '%without meat%'` won't find the lobio, because those words aren't in its description. We need to search **by meaning**, not by words. Today we learn about **embeddings**: turning text into a list of numbers (a vector), where texts with a similar meaning are close together. We generate vectors with Gemini, measure similarity and write a semantic search for the menu.

### Lecture plan: 3 steps 1. 🧭 **What an embedding is.** Text turns into a list of numbers (a vector), where texts with a similar meaning are close together. We see what “close” means, what a dimension is and why we need a separate model. 2. 🧑‍💻 **A vector in code.** `IEmbeddingGenerator` — Microsoft.Extensions.AI's second interface (next to `IChatClient`). We generate a vector with Gemini's embedding model and see how the format of a question differs from that of a document. 3. 🔎 **Similarity and search.** Cosine similarity — how we measure how close two vectors are; and a semantic search for the menu: we compare the question with every dish and take the three closest. ### The problem: searching by words doesn't see meaning The user writes “something light, without meat”. An ordinary search looks for words: ```sql SELECT "Name" FROM "Products" WHERE "Description" ILIKE '%without meat%'; -- 0 results ``` | Dish | Description | LIKE | |---|---|---| | Lobio in a clay pot | red beans, onion, coriander, with hot mchadi | ✗ | | Aubergine with walnuts | fried aubergine, walnut paste, pomegranate | ✗ | | Mtsvadi | pork on a skewer, with onion | ✗ | | Khinkali | beef and pork, in dough | ✗ | | Tomato salad | tomato, cucumber, walnut | ✗ | A person sees right away that the lobio, the aubergine and the salad match. And if we search for the word “meat”, LIKE finds exactly the **wrong** dishes: the mtsvadi and the khinkali. A word and a meaning are different things: “without meat”, “vegetarian” and “ვეგეტარიანული” mean the same thing, and not a single letter matches. In lecture 7's terms: we want **selection** — only the dishes that match the question go into the context. For that we need to search by meaning.

### embedding: ტექსტის „მნიშვნელობის კოორდინატები“ **Embedding** — ტექსტის გადაქცევა რიცხვების სიად: `"Lobio in a clay pot"` → `[0.021, -0.047, 0.009, 0.063, …]`. ამ სიას **ვექტორი** ჰქვია. ვექტორი სივრცეში წერტილია: ორ რიცხვს რუკაზე წერტილი შეესაბამება (x, y), 768 რიცხვს — წერტილი 768-განზომილებიან სივრცეში. **მთავარი თვისება:** embedding მოდელი ისეა გავარჯიშებული, რომ **მსგავსი მნიშვნელობის ტექსტები ახლოს** დგანან: - "Lobio in a clay pot", "Aubergine with walnuts", "Tomato salad" — ერთ მხარეს (ბოსტნეული, ხორცის გარეშე); - „მწვადი“, „ხინკალი“ — მეორე მხარეს (ხორცი); - შეკითხვა "without meat" პირველ ჯგუფთან ჯდება, და **„vegetarian“-იც იქვე**: ენა სხვაა, მნიშვნელობა — ერთი. სლაიდზე ორგანზომილებიანი ნახატია, რომ თვალით დავინახოთ. სინამდვილეში ერთ ვექტორში ასობით ან ათასობით რიცხვია, და თითოეული რიცხვი მნიშვნელობის რაღაც „მიმართულებაა“, რომელიც მოდელმა ვარჯიშისას თვითონ ისწავლა (ადამიანისთვის გასაგები სახელი არც ერთს არ აქვს). ლექცია 1-ის კითხვაზე „საიდან იცის მოდელმა, რას ნიშნავს ტოკენი 3293?“ — ეს არის პასუხი: მოდელის შიგნით ყოველ ტოკენს ასეთი ვექტორი აქვს. ```terms Embedding — ტექსტის (ან სურათის) გადაქცევა რიცხვების სიად ისე, რომ მსგავსი მნიშვნელობა ახლოს იყოს ვექტორი (vector) — რიცხვების სია; embedding-ის შედეგი; სივრცეში წერტილი განზომილება (dimension) — რამდენი რიცხვია ვექტორში (მაგ. 768) ```
### Embedding: the “coordinates of meaning” of a text **Embedding** — turning a text into a list of numbers: `"Lobio in a clay pot"` → `[0.021, -0.047, 0.009, 0.063, …]`. This list is called a **vector**. A vector is a point in space: two numbers give a point on a map (x, y), 768 numbers give a point in a 768-dimensional space. **The key property:** an embedding model is trained so that **texts with a similar meaning stand close together**: - “Lobio in a clay pot”, “Aubergine with walnuts”, “Tomato salad” — on one side (vegetables, no meat); - “Mtsvadi”, “Khinkali” — on the other side (meat); - the question “without meat” lands next to the first group, and **“ვეგეტარიანული” is right there too**: the language is different, the meaning is the same. The slide shows a two-dimensional picture so we can see it with our eyes. In reality one vector holds hundreds or thousands of numbers, and each number is some “direction” of meaning that the model learned by itself during training (none of them has a name a person would understand). The answer to lecture 1's question “how does the model know what token 3293 means?” is this: inside the model every token has a vector like this. ```terms Embedding — turning a text (or an image) into a list of numbers so that a similar meaning is close together Vector — a list of numbers; the result of an embedding; a point in space Dimension — how many numbers there are in the vector (e.g. 768) ```

### The embedding model: a separate model, a separate interface It isn't the chat model (`gemini-3.8-flash`) that generates the vector, but a **separate embedding model**: | | Chat model | Embedding model | |---|---|---| | In | messages | text | | Out | text (token by token) | one vector (all at once) | | Interface | `IChatClient` | `IEmbeddingGenerator` | | Price | input + output | input only — much cheaper | **Our model: `gemini-embedding-2`** — Gemini's newest embedding model (Stable). It takes up to 8,192 tokens of input, and the vector size can be anywhere from 128 to 3072. The recommended sizes are 768, 1536 and 3072. **We take 768:** the quality is good, the vector is 4 times smaller (less space in the database, faster search), and lecture 10's pgvector index handles this size easily. **One model — one “map”.** Every embedding model creates its own space. A `gemini-embedding-2` vector can't be compared with a vector from another model (or from the same model at another size) — the numbers are on a different “map”. So the model and the size are chosen once: if we change them, every stored vector has to be calculated again. ```terms Embedding model — a model that turns text into a vector; it doesn't write text IEmbeddingGenerator — Microsoft.Extensions.AI's interface for embeddings, like IChatClient ```

### Task prefix: the question and the document in different formats A question (“something light?”) and its answer (a dish's description) don't look like the same kind of text: the question is short and describes a “wish”, the document is long and describes “facts”. One rule never changes: **every document in one format, every question in the other**. If we store half with the prefix and half without, the vectors compare badly. ### cosine similarity: ორი ისრის კუთხე ვექტორი შეგვიძლია ისრად წარმოვიდგინოთ, რომელიც ცენტრიდან რაღაც მიმართულებით იყურება. **cosine similarity** ზომავს **კუთხეს** ორ ისარს შორის: | კუთხე | cosine | რას ნიშნავს | |---|---|---| | 0° — ერთი მიმართულება | 1 | ძალიან მსგავსი | | 90° — პერპენდიკულარული | 0 | არაფერი საერთო | | 180° — საპირისპირო | −1 | (ტექსტებზე პრაქტიკულად არ ხდება) | **ფორმულა** — სკალარული ნამრავლი გაყოფილი სიგრძეების ნამრავლზე: ```csharp ხელით — როგორ ითვლება static float Cosine(ReadOnlySpan a, ReadOnlySpan b) { float dot = 0, na = 0, nb = 0; for (int i = 0; i < a.Length; i++) { dot += a[i] * b[i]; // the dot product na += a[i] * a[i]; // the length of a, squared nb += b[i] * b[i]; // the length of b, squared } return dot / (MathF.Sqrt(na) * MathF.Sqrt(nb)); } ``` .NET-ში ეს მზაა და სწრაფიც (SIMD — პროცესორი რამდენიმე რიცხვს ერთდროულად ამრავლებს): ```csharp using System.Numerics.Tensors; // NuGet: System.Numerics.Tensors float score = TensorPrimitives.CosineSimilarity(a.Span, b.Span); ``` **ციფრებს როგორ ვკითხულობთ.** ნიმუში: "without meat" ↔ ლობიო **0.71**, ↔ მწვადი **0.38**. აბსოლუტური ციფრი მოდელზეა დამოკიდებული: ზოგ მოდელზე სრულიად უცხო ტექსტებიც 0.4-ს აჩვენებს. ამიტომ ციფრს ცალკე არ ვაფასებთ („0.7 კარგია?“), არამედ **ვადარებთ**: რომელია უფრო ახლოს. ძებნაში სწორედ ესაა საჭირო — დალაგება. ```terms Cosine similarity — ორი ვექტორის მსგავსების საზომი მათ შორის კუთხით: 1 — ერთი მიმართულება, 0 — არაფერი საერთო TensorPrimitives — System.Numerics.Tensors-ის კლასი ვექტორული გამოთვლებისთვის (CosineSimilarity, Dot…), SIMD-ით ```
### Cosine similarity: the angle between two arrows We can picture a vector as an arrow pointing from the centre in some direction. **Cosine similarity** measures the **angle** between two arrows: | Angle | cosine | What it means | |---|---|---| | 0° — the same direction | 1 | very similar | | 90° — perpendicular | 0 | nothing in common | | 180° — opposite | −1 | (practically never happens with texts) | **The formula** — the dot product divided by the product of the lengths: ```csharp By hand — how it's calculated static float Cosine(ReadOnlySpan a, ReadOnlySpan b) { float dot = 0, na = 0, nb = 0; for (int i = 0; i < a.Length; i++) { dot += a[i] * b[i]; // the dot product na += a[i] * a[i]; // the length of a, squared nb += b[i] * b[i]; // the length of b, squared } return dot / (MathF.Sqrt(na) * MathF.Sqrt(nb)); } ``` In .NET this is ready-made and fast too (SIMD — the processor multiplies several numbers at once): ```csharp using System.Numerics.Tensors; // NuGet: System.Numerics.Tensors float score = TensorPrimitives.CosineSimilarity(a.Span, b.Span); ``` **How we read the numbers.** A sample: “without meat” ↔ lobio **0.71**, ↔ mtsvadi **0.38**. The absolute number depends on the model: on some models even completely unrelated texts show 0.4. So we don't judge a number on its own (“is 0.7 good?”), we **compare**: which one is closer. That's exactly what a search needs — ordering. ```terms Cosine similarity — a measure of how similar two vectors are, by the angle between them: 1 — the same direction, 0 — nothing in common TensorPrimitives — a System.Numerics.Tensors class for vector computations (CosineSimilarity, Dot…), with SIMD ```

## Summary - An **embedding** turns a text into a vector (a list of numbers) so that **a similar meaning is close together** — even across languages (“without meat” ≈ “ვეგეტარიანული”). This way search happens **by meaning**, not by words. - The vector is generated by a **separate embedding model**: ours is `gemini-embedding-2`, with **768** dimensions. One model — one “map”: vectors from different models can't be compared. - **`IEmbeddingGenerator`** — Microsoft.Extensions.AI's interface (next to `IChatClient`): `AddEmbeddingGenerator`, `AsIEmbeddingGenerator(model, defaultModelDimensions)`, `GenerateVectorAsync` (one) and `GenerateAsync` (many). - **Task prefix:** the question — `task: search result | query: …`, the document — `title: … | text: …`. Always by the same rule. - **Cosine similarity** measures the angle between two vectors (1 — very similar, 0 — nothing in common). We compare the numbers, we don't judge them on their own. In .NET: `TensorPrimitives.CosineSimilarity`. - **Semantic search:** the menu's vectors once (`GenerateAsync`), on a question — only the question's vector, cosine with every dish, top 3. ### Next lecture For now the vectors are in memory: they disappear when the app restarts, and the search compares every vector one by one. On 200 dishes this isn't a problem; on thousands of documents it is. In lecture 10: **PostgreSQL pgvector and EF Core** — vectors in the database, search with SQL and an HNSW index.
