## ლექცია 11: Simple RAG მომხმარებელი კითხულობს: "How do I cancel a booking?" ან "I'm allergic to nuts — what can I eat?". ამის პასუხი მენიუში არ წერია. ის რესტორნის **დოკუმენტებშია**: წესების, ალერგენების და FAQ-ის PDF-ებში. მოდელმა ეს დოკუმენტები არ იცის, მთელი PDF-ის კონტექსტში ჩადება კი ძვირია (ლექცია 7). დღეს ვაწყობთ **RAG**-ს (Retrieval-Augmented Generation): PDF-ს ნაწილებად ვჭრით, ნაწილებს ვექტორებად ვინახავთ (ლექცია 10), შეკითხვაზე რელევანტურ ნაწილებს ვპოულობთ და მოდელს ვაწვდით — ის პასუხობს მხოლოდ მათზე დაყრდნობით და **წყაროს** ასახელებს.
## Lecture 11: Simple RAG The user asks: “How do I cancel a booking?” or “I'm allergic to nuts — what can I eat?”. The answer isn't in the menu. It's in the restaurant's **documents**: the PDFs with the rules, the allergens and the FAQ. The model doesn't know these documents, and putting a whole PDF in the context is expensive (lecture 7). Today we build **RAG** (Retrieval-Augmented Generation): we cut the PDF into parts, store the parts as vectors (lecture 10), find the relevant parts for a question and give them to the model — it answers only from them and names the **source**.

### The problem: the answer is in a document The restaurant has a rules PDF — 18 pages: cancelling a booking, allergens, pets, events. The answers to many of the users' questions are there, not in the menu. The model doesn't know this document — its knowledge comes from its training data (lecture 1), and our restaurant's rules weren't in it. **What options do we have:** | Option | The problem | |---|---| | **The whole PDF in the context** | 18 pages on every question = thousands of input tokens (lectures 7–8): money and a slow answer. With 500-page documents it doesn't even fit in the context window. And the more there is in the context, the more the important part “gets lost” (lost in the middle) | | **Fine-tuning** (extra training of the model) | Expensive and slow; a rule changes — training again. The model “memorizes” facts badly and **can't name the source** | | **RAG** — find only the parts we need | 3–5 parts per question; the document changed — we upload it again; the answer comes with a source | RAG is lecture 7's **selection** strategy: only what this question needs goes into the context. And lectures 9–10's search by meaning does exactly the finding of these parts. ```terms Fine-tuning — extra training of an existing model on your own data; good for style and format, less so for facts Lost in the middle — in a long context the model more often “misses” information in the middle part ```

### RAG: ორი pipeline **RAG — Retrieval-Augmented Generation:** „გენერაცია, გაძლიერებული ძებნით“. სამი სიტყვა — სამი ნაბიჯი: - **Retrieve** — შეკითხვაზე ვპოულობთ დოკუმენტების ყველაზე რელევანტურ ნაწილებს (ლექცია 9–10-ის ძებნა); - **Augment** — ამ ნაწილებს ვამატებთ prompt-ს; - **Generate** — მოდელი პასუხს წერს **მათზე დაყრდნობით** და წყაროს ასახელებს. ამისთვის ორი ცალკე pipeline გვჭირდება: | | Ingestion | Query | |---|---|---| | როდის | ერთხელ — დოკუმენტის ატვირთვისას (ან შეცვლისას) | ყოველ შეკითხვაზე | | ნაბიჯები | PDF → ტექსტი → ნაწილები (chunks) → ვექტორები → ბაზა | შეკითხვის ვექტორი → top 5 ნაწილი → prompt → პასუხი | | ლექცია | 9 (ვექტორები), 10 (ბაზა), დღეს — PDF და chunking | 9–10 (ძებნა), 7 (ჩატი), დღეს — augment და წყაროები | **ანალოგია — გამოცდა ღია წიგნით.** მოდელი ჭკვიანი სტუდენტია, რომელმაც ჩვენი რესტორნის წესები არ იცის. ### RAG: two pipelines **RAG — Retrieval-Augmented Generation:** “generation, augmented by search”. Three words — three steps: - **Retrieve** — for the question we find the most relevant parts of the documents (lectures 9–10's search); - **Augment** — we add these parts to the prompt; - **Generate** — the model writes the answer **based on them** and names the source. For this we need two separate pipelines: | | Ingestion | Query | |---|---|---| | When | once — when a document is uploaded (or changed) | on every question | | Steps | PDF → text → parts (chunks) → vectors → database | the question's vector → top 5 parts → prompt → answer | | Lecture | 9 (vectors), 10 (database), today — PDF and chunking | 9–10 (search), 7 (chat), today — augment and sources | **An analogy — an open-book exam.** The model is a smart student who doesn't know our restaurant's rules. With RAG it has the book at the exam: it reads the question, finds the right page in the book (we find it for it) and writes the answer, citing the page. With a closed book (without RAG) — it “remembers” or makes things up (hallucination, lecture 1). ```terms RAG (Retrieval-Augmented Generation) — a model answer that relies on our documents found by search Ingestion — preparing a document for search: text → parts → vectors → database Chunk — a part of a document that is stored and searched as a separate vector ```

### PDF → ტექსტი: PdfPig PDF ტექსტური ფაილი არ არის. მასში წერია **ასოები და მათი კოორდინატები გვერდზე** — „ასო ‚ჯ‘, x=72, y=540, შრიფტი…“. სიტყვა, ხაზი, აბზაცი ან სვეტი ფაილში არ არსებობს: ტექსტის ამოღება ნიშნავს ასოებიდან სიტყვების და ხაზების „აწყობას“. **PdfPig** (NuGet `PdfPig`, ლიცენზია Apache-2.0) — .NET-ის ბიბლიოთეკა PDF-ის წასაკითხად: ```csharp Ai/PdfText.cs using System.Text.RegularExpressions; using UglyToad.PdfPig; using UglyToad.PdfPig.DocumentLayoutAnalysis.TextExtractor; public static class PdfText { public static List<(int Page, string Text)> ReadPages(byte[] pdf) { using PdfDocument doc = PdfDocument.Open(pdf); return doc.GetPages() .Select(p => (p.Number, Clean(ContentOrderTextExtractor.GetText(p)))) .Where(p => p.Item2.Length > 0) // skip empty pages .ToList(); } private static string Clean(string text) => Regex.Replace(text, @"\s+", " ").Trim(); // extra spaces and line breaks } ``` - **`ContentOrderTextExtractor.GetText(page)`** — ასოებს **კითხვის რიგით** აწყობს (ხაზები, სვეტები). მარტივი `page.Text` ასოებს ფაილის რიგით აბრუნებს და ხშირად სიტყვებს აწებებს ან ურევს. - **გვერდის ნომერი** (`p.Number`) რჩება — ის წყაროს მითითებისთვის გვჭირდება ("rules.pdf, p. 3"). - **გაწმენდა** — ჰარების და ხაზების ნორმალიზაცია. რეალურ დოკუმენტებში ამას ემატება განმეორებადი header/footer-ის (გვერდის ნომერი, კომპანიის სახელი) ამოღება. ```warn **სკანირებული PDF** (ფოტოები) ტექსტს საერთოდ არ შეიცავს — `GetText` ცარიელს დააბრუნებს. ასეთ ფაილს OCR სჭირდება (ტექსტის ამოცნობა სურათიდან). ცხრილები და სვეტები PdfPig-ით ხშირად „ირევა“ — რთული დოკუმენტებისთვის არსებობს layout-ის ანალიზის სერვისები (Azure Document Intelligence, Docling). ``` ```terms PdfPig — .NET ბიბლიოთეკა PDF-დან ტექსტის და შინაარსის წასაკითხად (Apache-2.0) OCR — ტექსტის ამოცნობა სურათიდან; სკანირებულ PDF-ს სჭირდება ```
### PDF → text: PdfPig A PDF isn't a text file. It contains **letters and their coordinates on the page** — “letter ‘ჯ’, x=72, y=540, font…”. A word, a line, a paragraph or a column doesn't exist in the file: extracting the text means “assembling” words and lines from the letters. **PdfPig** (NuGet `PdfPig`, Apache-2.0 licence) — a .NET library for reading PDFs: ```csharp Ai/PdfText.cs using System.Text.RegularExpressions; using UglyToad.PdfPig; using UglyToad.PdfPig.DocumentLayoutAnalysis.TextExtractor; public static class PdfText { public static List<(int Page, string Text)> ReadPages(byte[] pdf) { using PdfDocument doc = PdfDocument.Open(pdf); return doc.GetPages() .Select(p => (p.Number, Clean(ContentOrderTextExtractor.GetText(p)))) .Where(p => p.Item2.Length > 0) // skip empty pages .ToList(); } private static string Clean(string text) => Regex.Replace(text, @"\s+", " ").Trim(); // extra spaces and line breaks } ``` - **`ContentOrderTextExtractor.GetText(page)`** — assembles the letters **in reading order** (lines, columns). The simple `page.Text` returns the letters in file order and often glues or mixes up words. - **The page number** (`p.Number`) stays — we need it for citing the source (“rules.pdf, p. 3”). - **Cleaning** — normalizing spaces and line breaks. In real documents this also includes removing a repeated header/footer (the page number, the company name). ```warn A **scanned PDF** (photos) contains no text at all — `GetText` returns nothing. Such a file needs OCR (recognizing text in an image). Tables and columns often get “mixed up” with PdfPig — for complex documents there are layout analysis services (Azure Document Intelligence, Docling). ``` ```terms PdfPig — a .NET library for reading text and content from PDFs (Apache-2.0) OCR — recognizing text in an image; a scanned PDF needs it ```

### Chunking: text into parts **Why not the whole document as one vector?** A vector is the “average meaning” of a text. The vector of 18 pages is a mix of bookings, allergens, pets and events — “cancelling a booking” compares badly with it. On top of that: the embedding model has an input limit (`gemini-embedding-2` — 8,192 tokens), and the text we find has to go into the context — 18 pages are expensive again. **A chunk (a part)** — a section of the document that covers one idea. Each one is stored as a separate vector and searched separately. **The size — a compromise:** | Size | Plus | Minus | |---|---|---| | very small (1 sentence) | the vector is precise | the context is lost: “this rule applies to 8+ people” — which rule? | | very large (pages) | the context is complete | the vector is blurry, expensive in the context | | **medium (~500–1000 characters)** | one idea + its context | — our choice: 800 | **Overlap.** The last sentence of a part is repeated at the start of the next part too. If an idea is split between two parts (“cancelling 24 hours before” + “if cancelled late the money isn't returned”), both parts have a “bridge”. **Our chunker** — by sentences: ```csharp Ai/TextChunker.cs public static class TextChunker { public static List Split(string text, int maxChars = 800, int overlap = 1) { string[] sentences = Regex.Split(text, @"(?<=[.!?])\s+"); List chunks = []; List current = []; foreach (string sentence in sentences) { if (current.Count > 0 && current.Sum(s => s.Length) + sentence.Length > maxChars) { chunks.Add(string.Join(" ", current)); current = current.TakeLast(overlap).ToList(); // overlap: the last sentence stays } current.Add(sentence); } if (current.Count > 0) chunks.Add(string.Join(" ", current)); return chunks; } } ``` - We split the text into **sentences** (after `.`, `!`, `?`) — a part is never cut in the middle of a sentence. - We collect sentences until they exceed ~800 characters; then the part is closed and the last sentence moves to the next one. - We cut **page by page** — so every part has an exact page number. This is one strategy. In lecture 12 we compare others (by headings, by meaning) — and **measure** which one is better. ```terms Chunking — cutting a document into parts for search Overlap — the overlap between parts: the last text is repeated in the next part too ```

### Retrieve and augment **Retrieve** — lecture 10's search, but on parts and with 5 results: ```csharp Controllers/AiLabController.cs · SearchChunksAsync public record FoundChunk(string File, int Page, string Content, double Score); private async Task> SearchChunksAsync(string q, CancellationToken ct) { float minScore = _config.GetValue("Rag:MinScore"); // by testing — like lecture 9's homework var query = new Vector(await _embeddings.GenerateVectorAsync( EmbeddingText.Query(q), cancellationToken: ct)); List top = await _db.DocumentChunks .Where(c => c.Embedding != null) .OrderBy(c => c.Embedding!.CosineDistance(query)) .Select(c => new FoundChunk(c.Document.FileName, c.Page, c.Content, 1 - c.Embedding!.CosineDistance(query))) .Take(5) .ToListAsync(ct); return top.Where(c => c.Score >= minScore).ToList(); } ``` - **top 5** — several parts: the answer may be in two places. More — the context gets expensive and the “noise” grows. - **The threshold** — lecture 9's lesson: a search **always** finds something. “A borscht recipe” would still return the five “closest” parts of the restaurant's rules — and the model would “answer” something based on them. In such a case the threshold returns 0 parts. **Augment** — we put the parts into the prompt as numbered sources: ```csharp Controllers/AiLabController.cs · BuildContext private static string BuildContext(List chunks) => chunks.Count == 0 ? "(No relevant information was found in the sources)" : string.Join("\n\n", chunks.Select((c, i) => $"[{i + 1}] ({c.File}, p. {c.Page})\n{c.Content}")); ``` Why numbers and the page: the model can write `[1]` in the answer — and we know which file and page it means. The user checks the source themselves, and we see where the answer came from (and with a wrong answer — which part was bad). ```terms Retrieve — finding the parts relevant to the question Augment — putting the found parts into the prompt Citation — a source number in the answer that points to a file and a page ```

### RAG in the chat: history + sources + question Lecture 7's `/chat` gets one more step — the **search** and an **augmented** message: ```csharp Controllers/AiLabController.cs · Chat List history = await _history.LoadAsync(conversationId, ct); IEnumerable recent = await Reducer.ReduceAsync(history, ct); List sources = await SearchChunksAsync(request.Prompt, ct); // retrieve ChatMessage question = new(ChatRole.User, request.Prompt); ChatMessage augmented = new(ChatRole.User, $""" Sources: {BuildContext(sources)} Question: {request.Prompt} """); // augment List messages = [SystemPrompt(), .. recent, augmented]; ChatResponse response = await _chat.GetResponseAsync(messages, ChatToolOptions(), ct); // generate await _history.AppendAsync(conversationId, [question, .. response.Messages], ct); return Ok(new { conversationId, response.Text, Sources = sources.Select((s, i) => new { N = i + 1, s.File, s.Page }) }); ``` **The rules in `SystemPrompt()`** (with lecture 2's techniques): ```text Answer about the restaurant's rules, allergens and policy only from the given sources and give the source number for every fact: [1], [2]. If the answer isn't in the sources, say: “I don't have information on this” — and make nothing up. Data on the menu, prices and free tables — only from the tools (as before). ``` **Three important details:** 1. **The original question is stored in the history** (`question`), not `augmented`. The sources are only for this request: on the next question other sources will be found. If we stored the sources in the history, every message would be “inflated” with five parts (lecture 7's budget). 2. **“I don't have information”** — an exact phrase: this way we can also recognize it in code (logs, statistics: which questions we can't answer — which document is missing). 3. **The sources in the response** — the UI can show a link on `[1]`: “rules.pdf, p. 3”. **“We always search” vs a tool.** Our chat searches on **every** question — on “hello” too (the threshold returns 0 parts, but the embedding call still happens). In lecture 9's ⭐ there was a `search_menu` tool: the model decides by itself when to search. Both are real approaches: | | We always search (today) | Search as a tool (lecture 15) | |---|---|---| | Plus | simple, predictable, the model can't “forget” to search | search only when needed; the model refines the question by itself | | Minus | extra searches; the question “and for children?” is searched without the previous context | the model may not search when it's needed | ```terms Augmented message — the user's question with the found sources attached; sent only in this request ```

## შეჯამება - **RAG** (Retrieval-Augmented Generation) — მოდელი პასუხობს ჩვენი დოკუმენტებიდან: **retrieve** (რელევანტური ნაწილები) → **augment** (prompt-ში) → **generate** (პასუხი წყაროთი). მთელ დოკუმენტზე იაფია, fine-tuning-ზე მარტივი და წყაროს ასახელებს. - **Ingestion** (ერთხელ): PDF → ტექსტი გვერდებით (**PdfPig**, `ContentOrderTextExtractor`) → გაწმენდა → **chunks** → ვექტორები → `DocumentChunk` ცხრილი (ლექცია 10-ის გზით). სკანირებულ PDF-ს OCR სჭირდება. - **Chunking:** ~800 სიმბოლო, წინადადების საზღვარზე, **overlap** ერთი წინადადება; გვერდ-გვერდ — ზუსტი წყაროსთვის. ზომა — კომპრომისი სიზუსტესა და კონტექსტს შორის. - **Query:** top 5 ნაწილი + **ზღვარი** → გადანომრილი წყაროები `[1] (file, p. N)` → წესები system prompt-ში: მხოლოდ წყაროებიდან, ნომრით, "I don't have information on this". - **ჩატში:** ისტორიაში **ორიგინალი** შეკითხვა, წყაროები — მხოლოდ ამ მოთხოვნაში; response-ში — `sources`. ### შემდეგ ლექციაზე RAG მუშაობს, მაგრამ ზოგჯერ არასწორ ნაწილს პოულობს — განსაკუთრებით ზუსტ სიტყვებზე (სახელები, რიცხვები). „ზოგჯერ“ რამდენჯერ ნიშნავს? chunk-ის ზომის შეცვლამ გააუმჯობესა თუ გააუარესა? ლექცია 12-ზე: **RAG-ის გაზომვა და გაუმჯობესება** — golden set, hit@k, hybrid search (full-text + ვექტორი), metadata filtering, chunking-ის სტრატეგიები და პასუხის groundedness.
## Summary - **RAG** (Retrieval-Augmented Generation) — the model answers from our documents: **retrieve** (the relevant parts) → **augment** (into the prompt) → **generate** (an answer with a source). It's cheaper than the whole document, simpler than fine-tuning, and it names the source. - **Ingestion** (once): PDF → text page by page (**PdfPig**, `ContentOrderTextExtractor`) → cleaning → **chunks** → vectors → the `DocumentChunk` table (the lecture 10 way). A scanned PDF needs OCR. - **Chunking:** ~800 characters, on a sentence boundary, an **overlap** of one sentence; page by page — for an exact source. The size is a compromise between precision and context. - **Query:** top 5 parts + a **threshold** → numbered sources `[1] (file, p. N)` → rules in the system prompt: only from the sources, with the number, “I don't have information on this”. - **In the chat:** the **original** question goes into the history, the sources — only into this request; `sources` in the response. ### Next lecture RAG works, but sometimes it finds the wrong part — especially on exact words (names, numbers). How many times is “sometimes”? Did changing the chunk size make it better or worse? In lecture 12: **measuring and improving RAG** — a golden set, hit@k, hybrid search (full-text + vector), metadata filtering, chunking strategies and the answer's groundedness.
