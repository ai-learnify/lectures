### Golden set და ორი ციფრი: hit@k და MRR **Golden set** — შეკითხვების ნაკრები, რომლებზეც **ჩვენ ვიცით**, რა უნდა მოიძებნოს. ხელით ვადგენთ, ერთხელ, და ყოველი ცვლილების შემდეგ ვუშვებთ. კარგი golden set რეალურ შეკითხვებს ჰგავს: ჩვეულებრივი, სინონიმით, ზუსტი რიცხვით/სახელით, ორ ადგილას პასუხით და ისეთიც, რაც დოკუმენტში არ არის. ლექცია 11-ის საშინაოს ცხრილი — მისი პირველი ვერსიაა. თითოეულ შეკითხვაზე ვწერთ **ფრაზას, რომელიც სწორ ნაწილში უნდა წერდეს** ("24 hours before", „B-2“). რატომ ფრაზა და არა chunk-ის Id? როცა chunking-ს შევცვლით, ნაწილები თავიდან იჭრება და Id-ები იცვლება — golden set კი უნდა დარჩეს. ფრაზა chunking-ის ნებისმიერ სტრატეგიაზე მუშაობს. **hit@k** — რა წილ შეკითხვაზე იყო სწორი ნაწილი პირველ k-ში. ცხრილში: 6-დან 4-ზე პირველ სამშია → **hit@3 = 0.67**. RAG-ისთვის ეს მთავარი ციფრია: თუ სწორი ნაწილი კონტექსტში არ მოხვდა, მოდელი ვერ უპასუხებს. **MRR (Mean Reciprocal Rank)** — საშუალო `1 / რიგი` (თუ ვერ იპოვა — 0). პირველ ადგილზე — 1, მეორეზე — ½, მესამეზე — ⅓. ზომავს, რამდენად **მაღლაა** სწორი ნაწილი: (1 + 1 + ½ + 0 + ⅓ + ⅕) / 6 = 3.03 / 6 ≈ **0.51** შენი ციფრი შენს მონაცემზეა დამოკიდებული. ორი სისტემა შეიძლება ერთნაირი hit@3-ით, მაგრამ სხვადასხვა MRR-ით იყოს: ერთში სწორი ყოველთვის პირველია, მეორეში — მესამე. ```terms Golden set — შეკითხვების ნაკრები ცნობილი სწორი პასუხით; ხარისხის გასაზომად hit@k — რა წილ შეკითხვაზე მოხვდა სწორი შედეგი პირველ k-ში MRR (Mean Reciprocal Rank) — სწორი შედეგის 1/რიგის საშუალო; რამდენად მაღლაა სწორი ```
### The golden set and two numbers: hit@k and MRR A **golden set** — a set of questions for which **we know** what should be found. We put it together by hand, once, and run it after every change. A good golden set resembles real questions: ordinary ones, with a synonym, with an exact number/name, with the answer in two places, and also something that isn't in the document. Lecture 11's homework table is its first version. For each question we write a **phrase that must appear in the right part** (“24 hours before”, “B-2”). Why a phrase and not the chunk's Id? When we change the chunking, the parts are cut again and the Ids change — but the golden set must stay. A phrase works with any chunking strategy. **hit@k** — on what share of the questions the right part was in the first k. In the table: on 4 out of 6 it's in the top three → **hit@3 = 0.67**. For RAG this is the main number: if the right part didn't get into the context, the model can't answer. **MRR (Mean Reciprocal Rank)** — the average of `1 / rank` (0 if not found). In first place — 1, second — ½, third — ⅓. It measures how **high** the right part is: (1 + 1 + ½ + 0 + ⅓ + ⅕) / 6 = 3.03 / 6 ≈ **0.51** Your number depends on your data. Two systems can have the same hit@3 but a different MRR: in one the right part is always first, in the other — third. ```terms Golden set — a set of questions with a known right answer; for measuring quality hit@k — on what share of the questions the right result landed in the first k MRR (Mean Reciprocal Rank) — the average of 1/rank of the right result; how high the right one is ```

### Hybrid search: vector + full-text The **vector** finds meaning: “without meat” → lobio. But exact words — codes, numbers, names (“B-2”, “12%”, “SKU-1234”) — “dissolve” in a vector: an embedding stores the idea, not the exact letters. **Search by words** works the other way round: it finds “B-2” exactly, but not “without meat”. In lecture 9 we said: “we don't throw LIKE away — we complement it”. **Hybrid search** runs both searches together and merges the results. **PostgreSQL's full-text search** — much stronger than LIKE: - **`tsvector`** — the text, split into words (lexemes): `to_tsvector('english', 'Hall B-2 seats 20+ guests')` → `'hall' 'b-2' 'b' '2' 'seat' '20' 'guest'`. - **`tsquery`** — the query: `'b-2' | 'hall'` (`|` — or, `&` — and). - **`@@`** — whether it matches; **`ts_rank`** — how well (how many words, how many times). - **The GIN index** — a fast search by words. **The configuration: `'english'`.** Our documents are in English, and PostgreSQL has a dictionary and a stemmer for English: `'english'` turns “guests” into “guest”, “rooms” into “room”, and throws away stop words (is, the, where…). The query must be processed with the **same** configuration (`ToTsQuery("english", …)`), otherwise “guests” ≠ “guest”. **For Georgian** there's no such dictionary — Georgian text uses `'simple'`: a word is stored as it is, and the vector covers the grammatical forms (“დარბაზი” / “დარბაზში” — hall / in the hall). **RRF (Reciprocal Rank Fusion)** — merging two lists **by rank**: `score(chunk) = Σ 1 / (60 + rank)` — in each list where the part was found. A part that's high in **both** lists comes first. Why the rank and not the scores? The vector's score (0.3–0.8) and `ts_rank` (0.01–0.1) are in different “units” — adding them up makes no sense. The rank is the same everywhere: 1, 2, 3. 60 is the standard constant (from the original RRF study): it softens the difference between the top places. ```terms Hybrid search — searching by meaning (vector) and by words (full-text) together, merging the results tsvector / tsquery — PostgreSQL's full-text: the text as words / a query with words 'english' / 'simple' — a full-text configuration: with the English dictionary and stemmer / without a dictionary (a word as it is) RRF (Reciprocal Rank Fusion) — merging several lists by rank: Σ 1/(60 + rank) ```

### Hybrid search in code **1. The full-text column.** `DocumentChunk` gets a `tsvector` column that PostgreSQL calculates **by itself** from `Content` (a generated column), and a GIN index: ```csharp Data/DocumentChunk.cs using NpgsqlTypes; // ... public NpgsqlTsVector SearchVector { get; set; } = null!; ``` ```csharp Data/AppDbContext.cs · OnModelCreating modelBuilder.Entity() .HasGeneratedTsVectorColumn(c => c.SearchVector, "english", c => new { c.Content }) .HasIndex(c => c.SearchVector) .HasMethod("GIN"); ``` After the migration the old parts get a `SearchVector` too — a generated column is calculated on every row. We don't need to upload again. **2. The query with words.** `plainto_tsquery` joins the words with **“and”**: “Where is hall B-2” would only find the part that has all the words — on a natural question often 0 results. We join them with “or”, and `ts_rank` puts the one with more matches higher: ```csharp Controllers/AiLabController.cs · OrQuery private static string OrQuery(string q) { var words = Regex.Matches(q, @"[\p{L}\p{N}]+(?:-[\p{L}\p{N}]+)*").Select(m => m.Value); return string.Join(" | ", words); // "Where is hall B-2?" → "Where | is | hall | B-2" } ``` The regex takes words and numbers, keeps hyphenated ones together (“B-2”), and throws away punctuation (otherwise `to_tsquery` would return a syntax error). **3. Two lists and RRF:** ```csharp Controllers/AiLabController.cs · HybridSearchAsync private async Task> HybridSearchAsync(string q, CancellationToken ct) { float minScore = _config.GetValue("Rag:MinScore"); var query = new Vector(await _embeddings.GenerateVectorAsync( EmbeddingText.Query(q), cancellationToken: ct)); var words = EF.Functions.ToTsQuery("english", OrQuery(q)); List byMeaning = await _db.DocumentChunks // by vector, with a threshold .Where(c => 1 - c.Embedding!.CosineDistance(query) >= minScore) .OrderBy(c => c.Embedding!.CosineDistance(query)) .Select(c => c.Id).Take(20).ToListAsync(ct); List byWords = await _db.DocumentChunks // by words .Where(c => c.SearchVector.Matches(words)) .OrderByDescending(c => c.SearchVector.Rank(words)) .Select(c => c.Id).Take(20).ToListAsync(ct); List top = Rrf(byMeaning, byWords).Take(5).ToList(); var chunks = await _db.DocumentChunks .Where(c => top.Contains(c.Id)) .Select(c => new { c.Id, c.Document.FileName, c.Page, c.Content }) .ToDictionaryAsync(c => c.Id, ct); return top.Select((id, i) => new FoundChunk(chunks[id].FileName, chunks[id].Page, chunks[id].Content, Score: 1.0 / (i + 1))).ToList(); // Score — here simply by rank } private static IEnumerable Rrf(params List[] lists) => lists .SelectMany(l => l.Select((id, i) => (id, s: 1.0 / (60 + i + 1)))) .GroupBy(x => x.id) .OrderByDescending(g => g.Sum(x => x.s)) .Select(g => g.Key); ``` - **The threshold** is only on the vector list: a full-text match is “evidence” in itself (the word really is written there). Both empty → 0 parts → “I don't have information”, as in lecture 11. - **20 + 20 → 5.** We take more candidates from each list, and after RRF — 5 for the context. - **The last query** loads the parts by Id; we keep `top`'s order (`WHERE IN` doesn't preserve order). - In `/chat` and `/rag/eval`, `HybridSearchAsync` instead of `SearchChunksAsync`. **Measure again.** **The result (sample):** hit@3 0.67 → **0.83**, MRR 0.51 → **0.72**. “B-2” got fixed. “Service charge for 6 people?” — still a miss: the document says “for 5+ people — 12%”. Neither the word (“6”) nor the meaning matches exactly — this is the limit of search. For a question like this, reranking or a tool that calculates the rule in code is better. ```terms Generated column — a column that PostgreSQL calculates by itself from other columns GIN index — PostgreSQL's index for words (and for arrays, jsonb) ```

### Chunking strategies | Strategy | How | Plus | Minus | |---|---|---|---| | **By size** (fixed) | every N characters/tokens, with an overlap | the simplest | cuts a sentence and an idea in the middle | | **By sentences / recursive** | first by paragraph, then by sentence, then by word — until it fits the size | natural boundaries; our lecture 11 version | doesn't see the boundary of a topic | | **By headings** (heading-aware / structure-aware) | a part = a section; the heading is attached to the part | topics don't get mixed; the heading is strong context | needs structure (Word styles, Markdown); recognizing a heading in a PDF is hard | | **By meaning** (semantic) | compares the vectors of consecutive sentences and cuts where the similarity drops | finds the topic boundary by itself | an embedding for every sentence — expensive; studies show it isn't always better than the simple one | **The heading in the prefix.** Lecture 9's document format: `title: … | text: …`. In lecture 11 we wrote the file name as the title. When cutting by headings — the **section's heading**: `title: Cancelling a booking | text: …`. The part's vector now “knows” the topic too, even if the word “booking” isn't written in the text. This is one of the cheapest and most effective improvements. **How to choose — only by measuring.** A change → upload the documents again (vectors on the new parts) → `/rag/eval`. On the sample: by headings 0.92; 300-character parts — **worse** (0.75): the parts are too small and lose context. “Smaller = more precise” doesn't always work — that's why we measure. **The golden set survives a change in chunking**, because it checks by a phrase (“24 hours before”), not by Id — part 1's decision pays off here. ```terms Recursive chunking — first by a big boundary (paragraph), then a smaller one (sentence, word), until the part fits the size Heading-aware chunking — cutting by the document's sections; the heading is attached to the part Semantic chunking — cutting where the meaning of consecutive sentences changes ```

### Reranking: ძებნის მეორე, ზუსტი ფენა ჩვენი ძებნა (ვექტორი და full-text) **სწრაფია**, მაგრამ „უხეში“: embedding მოდელი შეკითხვას და ნაწილს **ცალ-ცალკე** ხედავს. ნაწილის ვექტორი ingestion-ისას დაითვალა — შეკითხვის შესახებ არაფერი იცოდა. ასეთ მოდელს **bi-encoder** ჰქვია. **Reranker** (ჩვეულებრივ **cross-encoder**) შეკითხვას და ნაწილს **ერთად** კითხულობს და ერთ ციფრს აბრუნებს: რამდენად პასუხობს ეს ნაწილი ამ შეკითხვას. ეს ბევრად ზუსტია — "Service charge for 6 people?" ↔ "5+ people — 12%" reranker-ისთვის აშკარა წყვილია. მაგრამ წინასწარ ვერაფერს დაითვლი: ყოველ შეკითხვაზე ყოველ წყვილს ცალკე გამოთვლა სჭირდება. **ამიტომ ორი ფენა:** სწრაფი ძებნა ირჩევს 20–50 კანდიდატს → reranker ზუსტად ალაგებს და 5 მიდის კონტექსტში. მილიონ ნაწილზე reranker-ს ვერ გაუშვებ — 20-ზე კი შეგიძლია. **რა ვარიანტებია:** | | როგორ | ფასი | |---|---|---| | **Rerank API** — Cohere Rerank, Voyage, Jina | HTTP: შეკითხვა + 20 ტექსტი → 20 score | ცალკე key და ანგარიში; ფასი მოთხოვნაზე; +100–300 მწ | | **LLM როგორც reranker** | Gemini-ს ვთხოვთ: "Sort these 20 parts by relevance" — structured output (ლექცია 2) | ჩატის მოდელის ფასი — ძვირი; ნელი (წამები) | | **ლოკალური cross-encoder** | ღია მოდელი (მაგ. bge-reranker) საკუთარ სერვერზე | GPU/CPU, ინფრასტრუქტურა | Gemini API-ს ცალკე rerank მოდელი არ აქვს. ჩვენ Gemini-ზე ვართ, ამიტომ reranking-ს ლექციაზე ვხსნით, კოდი კი ⭐-შია (LLM-rerank). რეალურ სისტემებში reranking ხშირად ყველაზე დიდ ნახტომს იძლევა hit@3-ში — ფასის და დაყოვნების ფასად. და ისევ: **გაზომე**, ღირს თუ არა. ```terms Bi-encoder — მოდელი, რომელიც შეკითხვას და დოკუმენტს ცალ-ცალკე აქცევს ვექტორად (embedding) Cross-encoder (reranker) — მოდელი, რომელიც შეკითხვას და დოკუმენტს ერთად კითხულობს და რელევანტურობის ციფრს აბრუნებს Reranking — ძებნის კანდიდატების ხელახალი, ზუსტი დალაგება ```
### Reranking: a second, precise layer of the search Our search (vector and full-text) is **fast** but “rough”: the embedding model sees the question and the part **separately**. The part's vector was calculated at ingestion — it knew nothing about the question. A model like this is called a **bi-encoder**. A **reranker** (usually a **cross-encoder**) reads the question and the part **together** and returns one number: how well this part answers this question. This is much more precise — “service charge for 6 people?” ↔ “for 5+ people — 12%” is an obvious pair for a reranker. But you can't calculate anything in advance: on every question every pair needs a separate computation. **So, two layers:** the fast search picks 20–50 candidates → the reranker sorts them precisely and 5 go into the context. You can't run a reranker on a million parts — but you can on 20. **What options there are:** | | How | Cost | |---|---|---| | **A rerank API** — Cohere Rerank, Voyage, Jina | HTTP: a question + 20 texts → 20 scores | a separate key and account; a price per request; +100–300 ms | | **An LLM as the reranker** | we ask Gemini: “sort these 20 parts by relevance” — structured output (lecture 2) | the chat model's price — expensive; slow (seconds) | | **A local cross-encoder** | an open model (e.g. bge-reranker) on your own server | GPU/CPU, infrastructure | The Gemini API has no separate rerank model. We're on Gemini, so in the lecture we explain reranking, and the code is in the ⭐ (LLM-rerank). In real systems reranking often gives the biggest jump in hit@3 — at the price of cost and latency. And again: **measure** whether it's worth it. ```terms Bi-encoder — a model that turns the question and the document into vectors separately (embedding) Cross-encoder (reranker) — a model that reads the question and the document together and returns a relevance number Reranking — re-sorting the search candidates precisely ```

### Groundedness: does the answer rely on the sources? In part 1 we measured the search. The second place where RAG fails is the **answer**: the part is right, but the model added something. **Groundedness** — how much the answer relies **only** on the given sources. You can't measure this with `Contains`: “15 GEL” could also be “fifteen lari”. So — **LLM-as-judge**: we give another (or the same) model the question, the sources and the answer, and ask: “is everything written in the answer from the sources?” **`Microsoft.Extensions.AI.Evaluation.Quality`** — ready-made evaluators on Microsoft.Extensions.AI: `GroundednessEvaluator`, `RelevanceEvaluator`, `CompletenessEvaluator`, `RetrievalEvaluator` and others. ## შეჯამება - RAG **ორ ადგილას** ცდება: **ძებნაში** (სწორი ნაწილი ვერ მოიძებნა — ყველაზე ხშირი) და **პასუხში** (მოდელმა დაამატა). „თვალით“ ვერ ვიტყვით, გაუმჯობესდა თუ არა — ვზომავთ. - **Golden set** — შეკითხვები ფრაზით, რომელიც სწორ ნაწილში უნდა წერდეს (არა Id-ით — chunking-ს უძლებს). **hit@3** — რა წილზე იყო სწორი პირველ სამში; **MRR** — საშუალო 1/რიგი; **misses** — რა გამოვასწოროთ. `/rag/eval` LLM-ს არ იძახებს — იაფია. - **Hybrid search:** ვექტორი (მნიშვნელობა) + PostgreSQL full-text (`tsvector`, `'english'` — stemmer და stop-word-ები; ზუსტი სიტყვები, კოდები, რიცხვები), შერწყმა **RRF**-ით: Σ 1/(60 + რიგი). - **Metadata filtering:** კატეგორია, tenant, ენა, თარიღი, უფლებები — **SQL-ში, მოდელამდე**. ხარისხიც და უსაფრთხოებაც. - **Chunking:** ზომით / წინადადებით / სათაურებით / მნიშვნელობით. სათაური prefix-ში — იაფი და ეფექტური. პატარა ნაწილი ყოველთვის არ სჯობს — **გაზომე**. - **Reranking:** სწრაფი ძებნა 20 კანდიდატს ირჩევს, cross-encoder ზუსტად ალაგებს და 5 მიდის კონტექსტში. ფასი და დაყოვნება — გაზომე, ღირს თუ არა. - **Groundedness:** `GroundednessEvaluator` (`Microsoft.Extensions.AI.Evaluation.Quality`) — LLM-as-judge, 1–5 და ახსნა. მსაჯსაც ვამოწმებთ. ### ნაწილი 1 დასრულდა 12 ლექციაში: LLM და prompt engineering, `IChatClient` და DI, structured output, tools, pipeline და middleware, streaming, context engineering, resilience და ხარჯი, embeddings, pgvector და **RAG** — გაზომვით. ეს ყველაფერი ერთ RestaurantApi-ში მუშაობს. ### შემდეგ ლექციაზე ჩვენი ჩატი ძებნას **ყოველ** შეკითხვაზე აკეთებს და tool-ებს მოდელი იძახებს — მაგრამ ციკლს ჩვენ ვმართავთ. რა მოხდება, თუ მოდელი თვითონ გადაწყვეტს, რა მოძებნოს, რომელი tool გამოიძახოს და რამდენჯერ? ლექცია 13-ზე: **Agentic Systems** — chatbot vs RAG vs workflow vs აგენტი, ReAct, და როდის **არ** გვჭირდება აგენტი.
## Summary - RAG fails in **two places**: in the **search** (the right part wasn't found — the most common) and in the **answer** (the model added something). We can't tell “by eye” whether it improved — we measure. - **Golden set** — questions with a phrase that must appear in the right part (not by Id — it survives the chunking). **hit@3** — on what share the right one was in the top three; **MRR** — the average 1/rank; **misses** — what to fix. `/rag/eval` doesn't call the LLM — it's cheap. - **Hybrid search:** the vector (meaning) + PostgreSQL full-text (`tsvector`, `'english'` — a stemmer and stop words; exact words, codes, numbers), merged with **RRF**: Σ 1/(60 + rank). - **Metadata filtering:** the category, tenant, language, date, permissions — **in SQL, before the model**. Both quality and security. - **Chunking:** by size / by sentences / by headings / by meaning. The heading in the prefix — cheap and effective. A smaller part isn't always better — **measure**. - **Reranking:** a fast search picks 20 candidates, a cross-encoder sorts them precisely and 5 go into the context. The cost and the latency — measure whether it's worth it. - **Groundedness:** `GroundednessEvaluator` (`Microsoft.Extensions.AI.Evaluation.Quality`) — LLM-as-judge, 1–5 and an explanation.
