## 🎯 მიმოხილვა

ლექცია ლექცია 11-ის ბოლო კითხვით იწყება: „RAG ზოგჯერ არასწორ ნაწილს პოულობს. ‚ზოგჯერ‘ — რამდენჯერ?“ სამი ნაწილია.

**ნაწილი 1 — გაზომვა (ლექციის საფუძველი).** retrieval vs generation; golden set (ფრაზით, არა Id-ით); hit@3, MRR, misses; `/rag/eval` — ცოცხლად, პირველი ციფრი.

**ნაწილი 2 — უკეთესი ძებნა (ლექციის მთავარი კოდი).** რატომ „ვერ ხედავს“ ვექტორი „B-2“-ს; PostgreSQL full-text (`tsvector`, `'simple'`, ქართულს ლექსიკონი არ აქვს); RRF; `HybridSearchAsync` → **ისევ `/rag/eval`** — ციფრი იზრდება. metadata filtering — ხარისხი და უსაფრთხოება.

**ნაწილი 3 — დაჭრა და პასუხი (თეორია + ერთი კოდი).** chunking-ის ოთხი სტრატეგია და „სათაური prefix-ში“; reranking (bi-encoder vs cross-encoder) — თეორია; groundedness — `GroundednessEvaluator`.

**ეს ლექცია ნაწილი 1-ს ხურავს.** მთავარი სათქმელი არა რომელიმე ტექნიკაა, არამედ **მეთოდი**: გაზომე → შეცვალე → ისევ გაზომე. ეს მთელ მოდულს გასდევს (ლექცია 20, 22) და პროფესიაში AI Engineer-ს „AI-ს მომხმარებლისგან“ განასხვავებს. ბოლოს 2 წუთი — ნაწილი 1-ის მიმოხილვა და ხიდი აგენტებზე.

| **recall@k** (ბევრი სწორი) | სწორი ნაწილების რა წილი მოხვდა k-ში | პასუხი რამდენიმე ნაწილშია |
| **precision@k** | k-დან რამდენია სწორი | „ხმაური“ კონტექსტში |
| **nDCG** | რიგი + რელევანტურობის ხარისხი (0–3) | ძებნის სისტემები, რთული golden set |

ჩვენი ორი (hit@3, MRR) — RAG-ისთვის საკმარისი საწყისი წერტილია. სტუდენტებს მხოლოდ ესენი.

#### golden set — როგორ შევადგინოთ

- **ზომა:** 20–50 შეკითხვა საწყისისთვის; production-ში — ასობით, რეალური ლოგებიდან.
- **ტიპები:** ჩვეულებრივი; სინონიმი/პერიფრაზი; ზუსტი კოდი/რიცხვი/სახელი; ორ ადგილას პასუხი; „არარსებული“ (სწორი შედეგი — 0 ნაწილი; ჩვენს eval-ში ასეთს `MustContain` არ აქვს — ⭐-ში მისი დამატება: hit = „ცარიელი დაბრუნდა“).
- **ფრაზა vs Id:** Id chunking-ზეა მიბმული; ფრაზა — დოკუმენტზე. ფრაზა მოკლე და უნიკალური უნდა იყოს ("24 hours before", არა „ჯავშანი“).
- **ვინ წერს:** საუკეთესოა — დომენის ექსპერტი (რესტორნის მენეჯერი), არა დეველოპერი. ან რეალური მომხმარებლების შეკითხვები.
- **სინთეზური golden set:** LLM-ს ვთხოვთ თითოეული ნაწილიდან შეკითხვა „მოიგონოს“ — სწრაფია, მაგრამ შეკითხვები ტექსტის სიტყვებს ზედმეტად იმეორებს (ძებნისთვის ზედმეტად „ადვილია“). ხელით გადახედვა აუცილებელია.

#### რატომ არ იძახებს `/rag/eval` LLM-ს

retrieval-ის შეფასება დეტერმინისტულია: ერთი და იგივე მონაცემი და კოდი — ერთი და იგივე ციფრი (embedding ერთნაირ ტექსტზე ერთნაირ ვექტორს აბრუნებს). ეს ნიშნავს, რომ ციფრის ცვლილება **ჩვენი ცვლილებით** არის გამოწვეული, არა შემთხვევით. generation-ის შეფასება (groundedness) კი LLM-ზეა და ოდნავ „ხმაურიანია“.

### 📖 ისწავლე: full-text search, RRF და ფილტრი

#### PostgreSQL full-text — მოკლედ

- `to_tsvector(config, text)` — ტექსტი → lexeme-ების სია პოზიციებით. config (`'english'`, `'simple'`…) განსაზღვრავს parser-ს, stop-word-ებს და stemmer-ს.
- `to_tsquery(config, 'a | b & c')` — ოპერატორებით; `plainto_tsquery` — ჩვეულებრივი ტექსტი, სიტყვები `&`-ით; `websearch_to_tsquery` — Google-ის სინტაქსი („…“, or, -).
- `tsvector @@ tsquery` — ემთხვევა; `ts_rank` / `ts_rank_cd` — რელევანტურობა (სიხშირე, სიახლოვე).
- **GIN** ინდექსი `tsvector`-ზე — სიტყვა → ხაზები (inverted index).
- **Generated column** (`GENERATED ALWAYS AS (to_tsvector('english', "Content")) STORED`) — ყოველ INSERT/UPDATE-ზე თვითონ ითვლება. Npgsql: `HasGeneratedTsVectorColumn`.

#### 'english' და ქართული

ჩვენი დოკუმენტები ინგლისურადაა — `'english'`: stemmer ("guests" → 'guest', "cancelled" → 'cancel') და stop-word-ები. ყურადღება: `to_tsvector` და `to_tsquery` **ერთი** კონფიგით, თორემ lexeme-ები არ დაემთხვევა. სტუდენტს თუ დოკუმენტები ქართულადაა:

PostgreSQL-ში ქართულის text search configuration (dictionary + stemmer) არ არის. `'simple'` — lower-case + split, stemming-ის გარეშე. შედეგად „დარბაზი“, „დარბაზში“, „დარბაზის“ — სამი სხვადასხვა lexeme. ვარიანტები:

- **მივანდოთ ბრუნვები ვექტორს** — hybrid ზუსტად ამიტომ: full-text ზუსტ ტოკენებზე (კოდი, რიცხვი, სახელი, ტერმინი), ვექტორი — მნიშვნელობაზე. ჩვენი არჩევანი.
- **`pg_trgm`** — სამ-ასოიანი მსგავსება: `similarity('დარბაზი', 'დარბაზში')` მაღალია. ფაზი ძებნა, ბეჭდვის შეცდომებზეც მუშაობს. ⭐.
- **prefix-ძებნა** — `დარბაზ:*` — სიტყვის ფუძით. ფუძის ავტომატური პოვნა ქართულზე რთულია.
- **ICU / hunspell ლექსიკონი** — PostgreSQL-ში შეიძლება ispell/hunspell ლექსიკონის მიერთება; ქართულისთვის მზა ხარისხიანი ლექსიკონი იშვიათია.

#### RRF

Cormack, Clarke, Buettcher (2009) — `RRF(d) = Σ 1/(k + rank_i(d))`, k = 60. ძლიერი მხარე — score-ების ნორმალიზაცია არ სჭირდება და პარამეტრი პრაქტიკულად არ საჭიროებს მორგებას. ალტერნატივა — **weighted sum** ნორმალიზებული score-ებით (`α·vector + (1−α)·text`) — ზუსტად მორგებადია, მაგრამ α-ს შერჩევა golden set-ზე სჭირდება. Azure AI Search, Elasticsearch, OpenSearch hybrid-ში ნაგულისხმევად RRF-ს იყენებენ.

#### `HybridSearchAsync`-ის დეტალები

- **ზღვარი მხოლოდ ვექტორზე**: full-text-ის დამთხვევა თავისთავად მტკიცებულებაა. მაგრამ „ან“-ით შეკითხვა ხშირ სიტყვაზეც (მაგ. „რა“, „არის“) ემთხვევა — სუსტ დამთხვევას RRF ქვემოთ აგდებს, მაგრამ თუ ვექტორის სია ცარიელია, ერთი სუსტი full-text-ის ნაწილი კონტექსტში მოხვდება. ამას prompt-ის წესი („თუ წყაროებში არ არის — თქვი“) აზღვევს. დახვეწა: მინიმალური `ts_rank` ან stop-word-ების სია.
- **20 + 20 → 5.** რაც მეტი კანდიდატი, მით უკეთესი RRF (და reranker), მაგრამ ნელი. 20–50 — ტიპური.
- **ერთ SQL-ში** (CTE + FULL OUTER JOIN + RRF) — pgvector-ის README-ში მაგალითია; ერთი round-trip. ჩვენი ორი მოთხოვნა — უფრო წაკითხვადი.

#### Metadata filtering და უსაფრთხოება

- **pre-filter** (ჩვენი): `WHERE` ძებნამდე — სწორი, მაგრამ HNSW-ზე overfiltering შესაძლებელია (iterative scan).
- **post-filter**: ძებნის შემდეგ ფილტრი — ნაკლებ შედეგს აბრუნებს; უსაფრთხოებისთვის **არ** გამოდგება, თუ ფილტრამდე რამე ლოგში/კეშში ხვდება.
- **tenant isolation:** `TenantId` ყველა ნაწილზე + ყოველ მოთხოვნაში. EF Core-ის **global query filter** (`HasQueryFilter(c => c.TenantId == _tenant.Id)`) — დავიწყება შეუძლებელია. PostgreSQL-ის Row-Level Security — კიდევ ერთი ფენა.
- **უფლებები (ACL):** დოკუმენტზე როლები/ჯგუფები; ფილტრი მომხმარებლის როლებით. „HR-ის დოკუმენტი“ — კლასიკური მაგალითი.

### 📖 ისწავლე: chunking, reranking და groundedness

#### chunking — პრაქტიკული რჩევები

- **სათაური prefix-ში** (contextual chunk headers) — ყველაზე იაფი მოგება. Word-ში სათაურები სტილებითაა (Heading 1/2) — `DocumentFormat.OpenXml`-ით ზუსტად; Markdown-ში `#`; PDF-ში — ევრისტიკა (მოკლე ხაზი, დიდი შრიფტი — PdfPig-ის `Letter.PointSize`).
- **Contextual Retrieval** (Anthropic, 2024) — ყოველ ნაწილს LLM-ით მოკლე „კონტექსტი“ ეწერება („ეს ნაწილი რესტორნის წესების ‚ჯავშნის‘ სექციიდანაა, ეხება გაუქმებას…“) და ის embedding-შიც და full-text-შიც შედის. ძვირი ingestion-ზე (LLM ყოველ ნაწილზე), მაგრამ მნიშვნელოვნად ამცირებს retrieval-ის შეცდომებს.
- **Parent-child / small-to-big** — ეძებ პატარა ნაწილით (ზუსტი ვექტორი), კონტექსტში აგზავნი მის „მშობელს“ (მთელ სექციას). ორივე სამყაროს უპირატესობა.
- **Semantic chunking** — კვლევებში (მაგ. Chroma-ს 2024 წლის ანალიზი) ყოველთვის არ სჯობს კარგად მორგებულ recursive-ს, ფასი კი მაღალია. ამიტომ — გაზომვით.

#### reranking — დეტალები

- **cross-encoder** — transformer, რომელიც `[question] [SEP] [chunk]`-ს ერთად კითხულობს და ერთ logit-ს აბრუნებს. სიზუსტე bi-encoder-ზე მაღალია, რადგან შეკითხვისა და ნაწილის სიტყვები ერთმანეთს „ხედავს“ (attention).
- **Rerank API-ები:** Cohere Rerank (v3.5+), Voyage rerank, Jina reranker — ყველა მრავალენოვანია (ქართულის ხარისხი — შეამოწმე!). ფასი — მოთხოვნაზე/დოკუმენტზე.
- **LLM-rerank** (⭐) — მოქნილი, მაგრამ ძვირი და არადეტერმინისტული; listwise (ყველა ერთად დაალაგე) vs pointwise (თითოეულს ქულა 0–10).
- **როდის ღირს:** როცა hit@20 მაღალია, hit@3 — დაბალი (სწორი მოიძებნა, მაგრამ დაბლაა). თუ hit@20-იც დაბალია — reranker ვერ უშველის, ჯერ ძებნა.

#### groundedness და `Microsoft.Extensions.AI.Evaluation`

- **პაკეტები:** `Microsoft.Extensions.AI.Evaluation` (ბირთვი: `IEvaluator`, `EvaluationResult`, `ChatConfiguration`, metric-ები), `.Quality` (LLM-based evaluator-ები), `.NLP` (BLEU/F1 — LLM-ის გარეშე), `.Safety` (Azure AI Foundry-ის სერვისით), `.Reporting` (შედეგების შენახვა, ქეში, HTML რეპორტი; `dotnet aieval` tool) — ლექცია 20.
- **`GroundednessEvaluator`** — 1–5 ქულა `NumericMetric`-ში; `Interpretation` (`Rating`, `Failed`) — ნაგულისხმევად 4-ზე დაბალი „ცუდია“. `Reason` — მსაჯის ახსნა (ძალიან სასარგებლოა).
- **სხვა Quality evaluator-ები RAG-ისთვის:** `RelevanceEvaluator` (პასუხი შეკითხვას პასუხობს?), `CompletenessEvaluator` (ყველაფერი თქვა, რაც ground truth-შია? — `CompletenessEvaluatorContext`), `RetrievalEvaluator` (ნაპოვნი ნაწილები რელევანტურია?), `EquivalenceEvaluator`.
- **მსაჯის client:** `ChatConfiguration(IChatClient)`. ჩატის pipeline-ის client-ი tool-ებით (`UseFunctionInvocation`), `InputGuard`-ით და `TokenCounter`-ით მსაჯისთვის ზედმეტია და შეიძლება შეფასებაც შეცვალოს. ცალკე client — `AddKeyedChatClient("judge", …)` (ლექცია 8-ის ⭐).
- **ქეში:** `.Reporting`-ის `ResponseCachingChatClient` — ერთნაირ შეფასებაზე LLM-ს თავიდან არ იძახებს (ლექცია 20).

#### LLM-as-judge-ის ცნობილი პრობლემები

- **self-preference bias** — მოდელი საკუთარ (ან იმავე ოჯახის) პასუხებს უკეთ აფასებს;
- **position bias** — წყვილის შედარებისას პირველს ან მეორეს „ანიჭებს უპირატესობას“;
- **verbosity bias** — გრძელ პასუხს უკეთ აფასებს;
- **არადეტერმინიზმი** — ერთსა და იმავეზე სხვადასხვა ქულა; temperature 0 და რამდენიმე გაშვების საშუალო ამცირებს.

ამიტომ: ბევრ მაგალითზე, `Reason`-ის კითხვით, და პერიოდულად ადამიანის შეფასებასთან შედარებით.

### 🥇 LLM-rerank · 10 წთ

```csharp Controllers/AiLabController.cs · RerankAsync
public record RankResult(List<int> Best);

private async Task<List<FoundChunk>> RerankAsync(string q, List<FoundChunk> candidates, CancellationToken ct)
{
    string list = string.Join("\n\n", candidates.Select((c, i) => $"[{i}] {c.Content}"));
    ChatResponse<RankResult> r = await _judge.GetResponseAsync<RankResult>($"""
        Question: {q}

        Below are the chunks. Return the numbers of the 5 chunks that answer
        this question best, in decreasing order of relevance.

        {list}
        """, cancellationToken: ct);

    return r.Result.Best.Where(i => i >= 0 && i < candidates.Count)
        .Distinct().Take(5).Select(i => candidates[i]).ToList();
}
```

2. `/rag/eval` — hit@3 და **დრო** (`Stopwatch`) — ორივე დაფაზე.

### 🔤 pg_trgm და ბეჭდვის შეცდომები · 6 წთ

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
SELECT similarity('cancellation', 'cancelation'), similarity('cancellation', 'booking');
SELECT "Page", left("Content", 60) FROM "DocumentChunks"
WHERE "Content" % 'cancelation' ORDER BY similarity("Content", 'cancelation') DESC LIMIT 3;
```

🙋 „შეცდომით დაწერილი სიტყვა დაიჭირა?“ — სიტყვა-სიტყვაზე — კი (stemmer ამას ვერ შველის: "cancelation" სხვა lexeme-ა); გრძელ ტექსტზე `similarity` მთელ ტექსტს ადარებს და დაბალია — `word_similarity` / `%>` სჯობს. ქართულ დოკუმენტებზე იგივე ხერხი ბრუნვებსაც („დარბაზი“ / „დარბაზში“) იჭერს. დასკვნა: ინსტრუმენტი არსებობს, მაგრამ hybrid-ში ბევრს უკვე ვექტორი ფარავს.
