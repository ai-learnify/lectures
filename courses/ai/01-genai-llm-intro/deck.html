### მოდულის ბოლოს — ასეთი იქნება RestaurantApi კლიენტი ჩვეულებრივი ენით წერს: „რამე მსუბუქი, ხორცის გარეშე, ორისთვის. და ხვალ 8-ზე მაგიდა“. AI აგენტი: 1. **ეძებს მენიუში** — ჩვენი ბაზიდან (PostgreSQL), და არა „მეხსიერებიდან“; ამიტომ ფასი რეალურია. 2. **ჯავშნის მაგიდას** — ჩვენი C# მეთოდით (`BookTable`), რომელსაც თვითონ იძახებს. 3. **სთავაზობს კალათაში დამატებას** — და მოქმედებამდე თანხმობას ეკითხება. 4. **იცავს თავს** — როცა ვინმე ცდილობს მოატყუოს („დაივიწყე ინსტრუქციები…“), უარს ამბობს. 5. **იზომება** — რამდენი ტოკენი დაიხარჯა, რა ღირდა, რამდენ ხანს გაგრძელდა. მარჯვენა ნაწილი — „აგენტი შიგნიდან“ — მთავარი იდეაა: **მოდელი წყვეტს, რა გააკეთოს; აკეთებს ჩვენი კოდი.** ეს ყველაფერი 24 ლექციაში ნაბიჯ-ნაბიჯ შენდება.
### By the end of the module — this is RestaurantApi The customer writes in plain language: “Something light, no meat, for two. And a table tomorrow at 8”. The AI agent: 1. **Searches the menu** — in our database (PostgreSQL), not “from memory”, so the price is real. 2. **Books a table** — with our C# method (`BookTable`), which it calls itself. 3. **Offers to add to the cart** — and asks for consent before acting. 4. **Protects itself** — when someone tries to trick it (“forget your instructions…”), it refuses. 5. **Is measured** — how many tokens were spent, what it cost, how long it took. The right-hand part — “inside the agent” — is the key idea: **the model decides what to do; our code does it.** All of this is built step by step over 24 lectures.

### Regular code vs a language model | | C# code | LLM | |---|---|---| | Input | exact, structured (`dishId`, `date`) | any text | | Rules | we write them | the model “learned” them from text | | Result | **deterministic**: one input → always the same result | **probabilistic**: one question can get different answers | | Error | a bug — we find and fix it | a convincingly stated falsehood (we'll name it in part 2) | The key idea: **an LLM doesn't replace regular code.** Adding to the cart, calculating the price, saving a reservation stay in C# — that's where we need precision. We use an LLM where human language has to be “understood” or produced. This whole module is about connecting these two worlds. ```terms deterministic — the same input always produces the same result probabilistic — the result contains randomness; one input can produce different results ``` ### AI → ML → Deep Learning → GenAI → LLM These terms are often used as synonyms, but they are actually **circles nested inside each other**: each one is part of the previous. | Term | What it is | Example | |---|---|---| | **AI** — artificial intelligence | The broadest concept: any program that performs a “smart” task. ### The big picture: what happens after “Send”? Before we go into the details, here's how a language model works in simple terms. **Once, in advance — training.** The model “read” trillions of words (books, web pages, code) and learned which word follows which. Companies do this (Google, OpenAI…). We use a ready model. **On every request — 4 steps:** 1. **The text is cut into pieces** — “Book a table for” → `Book` · ` a` · ` table` · ` for`. These pieces are called **tokens**. 2. **The model calculates which piece comes next** — it gives every possible piece a probability: ` two` 62%, ` four` 21%, ` pizza` 0.1%… 3. **It picks one and appends it to the text** — “Book a table for **two**”. How “boldly” it picks is decided by **Temperature** (part 3). 4. **It repeats** — what comes after “Book a table for two”? And so on, piece by piece, until it finishes the answer. That's why you see the answer in a chat appear gradually, word by word. **Analogy:** a phone keyboard that suggests the next word — only one that has read almost the entire internet. On the next slides we break down each step: what a **token** is, how the **next token** is chosen, **why the model makes mistakes** and **what it sees** in one request.

GPT-4o-ს ლექსიკონში ~200 000 ნაჭერია; ` table` = **3293**. 4. **მოდელში შედის მხოლოდ რიცხვები** — `[6904, 261, 3293, 395, 1920]`. პასუხსაც მოდელი რიცხვებად აბრუნებს, tokenizer კი მათ ისევ ტექსტად აქცევს. **როგორ „იცის“ მოდელმა, რას ნიშნავს 3293?** მოდელის შიგნით თითო ნომერს შეესაბამება **ვექტორი** — ასობით რიცხვი, რომელიც წვრთნისას ისე „დალაგდა“, რომ მსგავსი მნიშვნელობის ტოკენები ახლოს არიან. ამ იდეას ლექცია 9-ზე (embeddings) დავუბრუნდებით — RAG სწორედ მასზე დგას. ```terms tokenizer — პროგრამა, რომელიც ტექსტს ტოკენებად ჭრის და ნომრებად აქცევს (და პირიქით) vocabulary (ლექსიკონი) — tokenizer-ის ცხრილი: ნაჭერი → ნომერი (ID) ```
### One idea in two languages — real tokens Below is the **real** split by the GPT-4o tokenizer (`o200k_base`), with real IDs: | Text | Tokens | Count | |---|---|---| | Book a table for two | `Book` · ` a` · ` table` · ` for` · ` two` | **5** | | დაჯავშნე მაგიდა ორისთვის (Georgian) | `დ` · `აჯ` · `ავშ` · `ნ` · `ე` · ` მაგ` · `იდა` · ` ო` · `რის` · `თვის` | **10** | Notice: a token often includes the **leading space** (` table`). The English word is a single token, while Georgian splits into parts — the tokenizer “learned” on the text that is most common on the internet, and there is little Georgian there. **What it means for us:** Georgian text is more tokens → more expensive, slower, and less of it fits into the context. ```note Different models have different tokenizers (Gemini has its own), so the numbers vary from model to model — but the trend is the same. You'll see this yourself in Tiktokenizer. ``` ### The model sees only numbers This is how text reaches the model: 1. **Text** — e.g. `Book a table for two`. 2. **Pieces** — the tokenizer cuts the text into tokens: `Book` · ` a` · ` table` · ` for` · ` two`. A token often includes the leading space. 3. **Vocabulary** — the tokenizer has a table where each piece has its own number (ID). GPT-4o's vocabulary has ~200 000 pieces; ` table` = **3293**. 4. **Only numbers go into the model** — `[6904, 261, 3293, 395, 1920]`. The model also returns its answer as numbers, and the tokenizer turns them back into text. **How does the model “know” what 3293 means?** Inside the model each number maps to a **vector** — hundreds of numbers that, during training, “arranged themselves” so that tokens with similar meanings are close together. We'll come back to this idea in lecture 9 (embeddings) — RAG is built on it. ```terms tokenizer — a program that cuts text into tokens and turns them into numbers (and back) vocabulary — the tokenizer's table: piece → number (ID) ```

### Next-token prediction — LLM-ის მთელი საიდუმლო LLM ერთ საქმეს აკეთებს: **იცის, რა ტოკენი მოდის შემდეგ.** უფრო ზუსტად, ტექსტის საფუძველზე თითოეული შესაძლო ტოკენისთვის ითვლის **ალბათობას**. ციკლი ასეთია: 1. **შეყვანა** — მოდელი იღებს ტოკენების მიმდევრობას: `Book a table for` 2. **ალბათობები** — ითვლის, რომელი ტოკენი მოვა შემდეგ: `two` — 62%, `four` — 21%, `tonight` — 9%, `pizza` — 0.1%… (რიცხვები საილუსტრაციოა) 3. **არჩევა** — ირჩევს ერთს (როგორ — ამას **Temperature** წყვეტს, მე-3 ნაწილი) 4. **გამეორება** — არჩეულს უმატებს ტექსტს და მთელ ციკლს თავიდან უშვებს: `Book a table for two` → შემდეგი ტოკენი → … 5. **დასასრული** — როცა მოდელი სპეციალურ „დასრულების“ ტოკენს აირჩევს, ან ლიმიტს მიაღწევს (`max_tokens`) ესაა ყველაფერი. ჩატი, კოდის წერა, თარგმანი — ყველაფერი ამ ერთი ციკლით ხდება. მოდელს „ფიქრი“ და „ცოდნა“ ამ ალბათობებში აქვს „ჩაწერილი“: გიგანტურ ტექსტზე ვარჯიშისას ისწავლა, რა მოსდევს რას. **backend-ის დასკვნა:** ყოველი ტოკენი მოდელის ერთი სრული გაშვებაა. ამიტომ 500-ტოკენიანი პასუხი 50-ტოკენიანზე შესამჩნევად ნელია და ძვირი. ამიტომაც ჩანს ChatGPT-ში პასუხი „ნელ-ნელა იწერება“ — ეს **streaming**-ია (მე-6 ლექცია). ```terms next-token prediction — შემდეგი ტოკენის წინასწარმეტყველება: LLM-ის ძირითადი მექანიზმი ალბათობების განაწილება (distribution) — ყველა შესაძლო ტოკენის სია თავისი ალბათობით; ჯამი 100% ```
### Next-token prediction — the whole secret of an LLM An LLM does one thing: **it knows which token comes next.** More precisely, based on the text it calculates a **probability** for every possible token. The loop looks like this: 1. **Input** — the model receives a sequence of tokens: `Book a table for` 2. **Probabilities** — it calculates which token comes next: `two` — 62%, `four` — 21%, `tonight` — 9%, `pizza` — 0.1%… (illustrative numbers) 3. **Choice** — it picks one (how — that's decided by **Temperature**, part 3) 4. **Repeat** — it appends the chosen token to the text and runs the whole loop again: `Book a table for two` → next token → … 5. **End** — when the model picks a special “end” token, or hits the limit (`max_tokens`) That's all. Chat, writing code, translation — everything happens through this one loop. The model's “thinking” and “knowledge” are “written” into these probabilities: while training on an enormous text it learned what follows what. **Backend takeaway:** every token is one full run of the model. That's why a 500-token answer is noticeably slower and more expensive than a 50-token one. It's also why the answer in ChatGPT “appears gradually” — that's **streaming** (lecture 6). ```terms next-token prediction — predicting the next token: the core mechanism of an LLM probability distribution — the list of all possible tokens with their probabilities; they add up to 100% ```

### Where the model “knows” things from — and when it lies A model is created in two stages: 1. **Pre-training** — on an enormous text (internet, books, code) it learns to guess the next token. The result: a model that “convincingly continues” any text, but isn't an assistant yet — it might “continue” a question with ten more questions. 2. **Fine-tuning** (and RLHF) — extra training on dialogues and human ratings: it learns to follow instructions and behave like an assistant. That's how it becomes a “chat” model. **Knowledge cutoff** — the training data goes up to a certain date. The model doesn't know what happened after it. And most importantly: **our restaurant's menu, prices and free tables** it has never seen. **Hallucination** — when the model doesn't know the answer, it still writes the most “likely” text. “Khinkali 1.20 ₾” sounds convincing because there are many such sentences on the internet — but it's not our price. The model isn't lying on purpose: its goal is **likely** text, not **true** text. **The fix** (the main theme of the course): we don't make the model answer from memory, we **give it our data** — with a tool (lecture 4: the model calls our `GetMenu()` method) or with RAG (lecture 11: we find the relevant document and put it in the prompt). ```warn A rule that applies throughout the course: **prices, stock, reservations, money — never from the model's memory.** Such data always comes from our database. ``` ```terms pre-training — the main training on a large text: guessing the next token fine-tuning — additional training for a specific behaviour (e.g. assistant dialogue) knowledge cutoff — the date up to which the model's training data reaches hallucination — convincingly stated but wrong or made-up information ```

### Context window — what the model “sees” in one request The **context window** is the maximum number of tokens the model processes in one request — **input and output** together. ### Max Tokens — where to stop **Max Tokens** (`max_tokens`, `max_output_tokens`, in C# `MaxOutputTokens`) limits how many tokens the model may write **in the answer**. When it reaches the limit, writing simply stops — even mid-word or mid-sentence. **Why we need it:** - 💸 **Cost limit** — output tokens are the most expensive; the limit guarantees one request won't “grow out of control”. - ⏱️ **Time limit** — a short answer arrives quickly. - 🐛 **Protection from odd behaviour** — sometimes a model repeats the same thing endlessly; the limit stops it. **How do we know whether it was cut off?** The response has `finish_reason`: | Value | Means | |---|---| | `stop` | the model finished by itself — the normal case | | `length` | it hit Max Tokens — **the answer is cut off** | ```warn If the limit is too low, the user gets a cut-off sentence. That's why the backend should always check `finish_reason == length` (log it, or raise the limit). We'll see this in code in lecture 2. ```
