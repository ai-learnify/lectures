## ლექცია 8: Error Handling, Resilience და ხარჯის კონტროლი ჩვენი ჩატი ისტორიას ინახავს, tool-ებს იძახებს და სტრიმავს. მაგრამ ყოველი შეკითხვა Gemini-ს ერთი ან რამდენიმე HTTP გამოძახებაა, და Gemini ზოგჯერ ცდება: **429** (ძალიან ბევრი მოთხოვნა), **503** (მოდელი გადატვირთულია), ან უბრალოდ დიდხანს არ პასუხობს. ახლა ასეთ დროს მომხმარებელი 500-ს ხედავს. დღეს ვარჩევთ, რომელი შეცდომა „გაივლის“ და რომელი არა, ვამატებთ **retry**-ს და **timeout**-ს, **სარეზერვო მოდელს**, და ვიწყებთ **ხარჯის აღრიცხვას** ბაზაში.
## Lecture 8: Error Handling, Resilience and Cost Control Our chat stores the history, calls tools and streams. But every question is one or more HTTP calls to Gemini, and Gemini sometimes fails: **429** (too many requests), **503** (the model is overloaded), or it just takes too long to answer. Right now the user sees a 500 when that happens. Today we sort out which errors “pass” and which don't, add **retry** and **timeout**, a **fallback model**, and start **recording the cost** in the database.

### ლექციის გეგმა: 3 ნაბიჯი 1. 🧯 **რა ფუჭდება.** AI გამოძახების შეცდომები სამ ჯგუფად: **დროებითი** (429, 503, timeout — თავიდან ცდა შველის), **მუდმივი** (400, 401, 404 — თავიდან ცდა არ შველის, კოდი ან კონფიგურაცია უნდა გასწორდეს) და **შინაარსის** (პასუხი მოვიდა, მაგრამ მოჭრილია ან JSON არასწორია). 2. 🔁 **retry და timeout.** დროებით შეცდომაზე ვცდით თავიდან, მზარდი პაუზით. `Microsoft.Extensions.Http.Resilience` ამას ერთი ხაზით აკეთებს HttpClient-ის დონეზე. ცოცხლად ვნახავთ, როგორ „გადაურჩება“ მოთხოვნა ორ 503-ს. 3. 🛟 **fallback და ხარჯი.** თუ retry არ შველის, სარეზერვო მოდელზე გადავდივართ. და ყოველი გამოძახების ტოკენებს ბაზაში ვწერთ, რომ ვიცოდეთ, რა დაჯდა დღეს. ბოლოს კლასის დავალებაა: ფენა, რომელიც დღიურ ლიმიტზე ჩატს აჩერებს.
### Lecture plan: 3 steps 1. 🧯 **What breaks.** The errors of an AI call in three groups: **transient** (429, 503, timeout — trying again helps), **permanent** (400, 401, 404 — trying again doesn't help, the code or configuration has to be fixed) and **content** errors (an answer arrived, but it's cut off or the JSON is wrong). 2. 🔁 **Retry and timeout.** On a transient error we try again, with a growing pause. `Microsoft.Extensions.Http.Resilience` does this in one line at the HttpClient level. We'll see live how a request “survives” two 503s. 3. 🛟 **Fallback and cost.** If retry doesn't help, we switch to a fallback model. And we write the tokens of every call to the database, so we know what today cost. At the end there's classwork: a layer that stops the chat at a daily limit.

### The problem: Gemini sometimes fails Two typical responses that Gemini will return on any given day: | Code | Status | What it means | |---|---|---| | **503** | `UNAVAILABLE` | “The model is overloaded, please try again later” — too many requests on Google's side | | **429** | `RESOURCE_EXHAUSTED` | **our** limit ran out: the number of requests or tokens per minute (the limit is small on a free key) | On such a response Google.GenAI throws an exception: **`ServerError`** (5xx) or **`ClientError`** (4xx). Both are **`ApiException`**s, with a `StatusCode` property. We don't catch it, so ASP.NET Core returns a **500** to the user. On top of that, in lecture 7's `/chat` the `AppendAsync` comes **after** the answer, so the question is lost too. **This isn't our bug**: an external service sometimes fails, the network drops. It will definitely happen. But **the reaction is ours**. A person would wait a few seconds and try again: that's exactly what we teach the code.

### The error map: three groups | What happened | What it means | Group | What we do | |---|---|---|---| | **429** | A limit: too many requests or tokens per minute | transient | we wait (if the response says `Retry-After` — exactly that long) and try again | | **500 · 503** | Gemini is overloaded or has an internal error | transient | retry; if it doesn't work — a fallback model | | **timeout** | The answer takes too long, the network drops | transient | a time limit and retry | | **400 · 401 · 403 · 404** | A wrong request, key, permission or model name | permanent | **no** retry: the same request brings the same error. Log it and fix it | | **FinishReason = length · bad JSON** | An answer arrived, but it's cut off or doesn't match the schema | content | in code: headroom in `MaxOutputTokens` (lecture 2), `TryGetResult` (lecture 3) | | **tool exception** | Our C# method failed | content | `FunctionInvokingChatClient` returns the error to the model, and the model writes the answer anyway | **The main rule: retry only on a transient error.** On a 401 (wrong key), trying again five times gives five 401s and wastes the user's time. Same with a 400: the request is wrong and will stay wrong. **Content errors don't show at the HTTP level:** the status is 200, an answer arrived. Our code checks them: lecture 3's `TryGetResult` (if the JSON doesn't match the schema, `false` instead of an exception), checking the `FinishReason`. ```terms Transient error — an error that may not repeat on another try: 429, 5xx, timeout, the network Permanent error — trying again doesn't help: a wrong request, key, permission, model name (4xx, except 429) ApiException — a Google.GenAI error with a StatusCode: ClientError (4xx) and ServerError (5xx) ```

### retry სწორად: backoff, jitter, Retry-After, circuit breaker გულუბრყვილო retry — „ჩავარდა? მაშინვე თავიდან, 10-ჯერ“ — პრობლემას **აუარესებს**: Gemini გადატვირთულია, ჩვენ კი მას კიდევ უფრო მეტ მოთხოვნას ვუგზავნით, და ათასი კლიენტი ერთსა და იმავე წამში აკეთებს იგივეს. სწორი retry-ს ოთხი ნაწილი აქვს: | ნაწილი | რას აკეთებს | |---|---| | 📈 **exponential backoff** | ყოველ ცდამდე მეტს ვიცდით: ~2 → ~4 → ~8 წამი. სერვისს „ამოსუნთქვის“ დრო ეძლევა | | 🎲 **jitter** | პაუზას შემთხვევითი ნაწილი ემატება (2.3 წმ, 1.8 წმ…). ათასი კლიენტი ერთსა და იმავე მომენტში აღარ ცდის თავიდან | | ⏰ **Retry-After · timeout** | 429-ზე სერვერი ხშირად გვეუბნება, რამდენი ვიცადოთ (`Retry-After` header). და თითო ცდას დროის ლიმიტი აქვს: თუ პასუხი 40 წამში არ მოვიდა, ცდა ჩავარდნილად ითვლება | | 🔌 **circuit breaker** | თუ ბოლო პერიოდში ცდების დიდი ნაწილი ჩავარდა, „ჩამრთველი“ ითიშება: რამდენიმე წამი Gemini-ს საერთოდ არ ვიძახებთ და მაშინვე შეცდომას ვაბრუნებთ. სერვისი ისვენებს, მომხმარებელი ტყუილად არ ელოდება | ```terms Retry — ჩავარდნილი მოთხოვნის თავიდან გაგზავნა დროებით შეცდომაზე Exponential backoff — retry-ებს შორის მზარდი პაუზა (2, 4, 8… წამი) Jitter — პაუზის შემთხვევითი ნაწილი, რომ ბევრმა კლიენტმა ერთდროულად არ სცადოს Circuit breaker — „ჩამრთველი“: ბევრი ჩავარდნის შემდეგ გამოძახებებს დროებით წყვეტს ```
### Retry done right: backoff, jitter, Retry-After, circuit breaker A naive retry — “it failed? try again immediately, 10 times” — makes the problem **worse**: Gemini is overloaded, and we send it even more requests, while a thousand clients do the same in the same second. A proper retry has four parts: | Part | What it does | |---|---| | 📈 **exponential backoff** | we wait longer before every attempt: ~2 → ~4 → ~8 seconds. The service gets time to “catch its breath” | | 🎲 **jitter** | a random part is added to the pause (2.3 s, 1.8 s…). A thousand clients no longer retry at the same moment | | ⏰ **Retry-After · timeout** | on a 429 the server often tells us how long to wait (the `Retry-After` header). And each attempt has a time limit: if the answer doesn't arrive in 40 seconds, the attempt counts as failed | | 🔌 **circuit breaker** | if a large share of recent attempts failed, the “breaker” trips: for a few seconds we don't call Gemini at all and return an error right away. The service rests, the user doesn't wait for nothing | ```terms Retry — sending a failed request again on a transient error Exponential backoff — a growing pause between retries (2, 4, 8… seconds) Jitter — a random part of the pause, so many clients don't retry at the same time Circuit breaker — a “breaker”: after many failures it temporarily stops the calls ```

### `FallbackChatClient`: retry doesn't help → another model Lecture 5's `DelegatingChatClient` — now a layer that **catches an error**: ```csharp Ai/FallbackChatClient.cs public class FallbackChatClient : DelegatingChatClient { private readonly IChatClient _fallback; private readonly ILogger _logger; public FallbackChatClient(IChatClient inner, IChatClient fallback, ILogger logger) : base(inner) { _fallback = fallback; _logger = logger; } public override async Task GetResponseAsync( IEnumerable messages, ChatOptions? options = null, CancellationToken cancellationToken = default) { try { return await base.GetResponseAsync(messages, options, cancellationToken); } catch (Exception ex) when (IsTransient(ex)) { _logger.LogWarning("🛟 {Error} — fallback model", ex.Message); return await _fallback.GetResponseAsync(messages, options, cancellationToken); } } private static bool IsTransient(Exception ex) => ex switch { ApiException api => api.StatusCode is 429 or >= 500, HttpRequestException or TimeoutRejectedException => true, _ => false }; } ``` - **`catch … when (IsTransient(ex))`** — an exception filter: we catch **only** a transient error. A permanent one (400, 401, 404) goes up: the fallback uses the same key and the same request and would bring the same error. - **`IsTransient`** — an `ApiException` (Google.GenAI, 429 or 5xx), an `HttpRequestException` (the network) or a `TimeoutRejectedException` (the resilience timeout, `using Polly.Timeout;`). The order matters: `ApiException` is itself an `HttpRequestException`, so it has to come first. An `OperationCanceledException` (the user left) doesn't land here — that's right. **Registration:** the fallback is the **innermost** layer, closest to Gemini. This way every request of the tool loop has its own fallback: ```csharp Program.cs IChatClient fallback = new Client(apiKey: apiKey) .AsIChatClient(builder.Configuration["Gemini:FallbackModel"]!); builder.Services.AddChatClient(sp => /* gemini — as on slide 11 */) .Use(inner => new InputGuardChatClient(inner)) .UseFunctionInvocation() .Use((inner, sp) => new TokenCounterChatClient(inner, /* ... */)) .UseLogging() .Use((inner, sp) => new FallbackChatClient(inner, fallback, sp.GetRequiredService>())); ``` In `appsettings.json`: `"Gemini": { "Model": "...", "FallbackModel": "..." }` — another, usually lighter model (the current names: Gemini's list of models). **What if Gemini is down entirely?** The fallback can be **another provider** too (OpenAI, Groq…): it's an `IChatClient` as well (lecture 3: switching the provider = one line). In production this is often how it's done. ```terms Fallback — a backup option: if the main service doesn't answer, the request goes to another one Exception filter (catch … when) — a catch that only catches the exception when a condition holds ```

### Recording the cost: tokens in the database Lecture 5's `TokenCounterChatClient` wrote the tokens to the log. The log is lost in a few days and is hard to sum up. Now we write to the **database**: one row = one Gemini call. ```csharp Data/AiUsageRecord.cs public class AiUsageRecord { public Guid Id { get; set; } public DateTime At { get; set; } public string Model { get; set; } = ""; public long InputTokens { get; set; } public long OutputTokens { get; set; } } ``` ```csharp Ai/TokenCounterChatClient.cs public class TokenCounterChatClient : DelegatingChatClient { private readonly IServiceScopeFactory _scopes; public TokenCounterChatClient(IChatClient inner, IServiceScopeFactory scopes) : base(inner) { _scopes = scopes; } public override async Task GetResponseAsync( IEnumerable messages, ChatOptions? options = null, CancellationToken cancellationToken = default) { ChatResponse response = await base.GetResponseAsync(messages, options, cancellationToken); // a Scoped DbContext in a Singleton layer → its own scope using IServiceScope scope = _scopes.CreateScope(); AppDbContext db = scope.ServiceProvider.GetRequiredService(); db.AiUsage.Add(new AiUsageRecord { Id = Guid.NewGuid(), At = DateTime.UtcNow, Model = response.ModelId ?? "?", InputTokens = response.Usage?.InputTokenCount ?? 0, OutputTokens = (response.Usage?.OutputTokenCount ?? 0) + (response.Usage?.ReasoningTokenCount ?? 0) }); await db.SaveChangesAsync(cancellationToken); return response; } } // Program.cs: .Use((inner, sp) => new TokenCounterChatClient(inner, // sp.GetRequiredService())) ``` **Why `IServiceScopeFactory`?** `AddChatClient` registers the client as a **Singleton**: the pipeline is created once and serves every request. But `AppDbContext` is **Scoped**: a new one for every HTTP request. Putting a Scoped service directly into a Singleton is a mistake (a “captive dependency” — one DbContext for every user). So the layer creates **its own scope** every time and takes the `AppDbContext` from it. **We add `ReasoningTokenCount` to the output:** Gemini's thinking tokens are counted separately but charged at the output price (lecture 2). **`response.ModelId`** — which model answered. After a fallback this shows the fallback model's name, so the database shows how many times the fallback kicked in. **Today's cost with SQL:** ```sql SELECT "Model", SUM("InputTokens") AS input, SUM("OutputTokens") AS output FROM "AiUsage" WHERE "At" >= CURRENT_DATE GROUP BY "Model"; ``` The cost with lecture 1's formula: **input × the input price + output × the output price** (the price per 1 million tokens, from Gemini's pricing page). ```terms IServiceScopeFactory — a DI service with which we create our own scope inside a Singleton and take a Scoped service (DbContext) from it Captive dependency — a mistake: a Scoped service is “captured” inside a Singleton and every request shares it ```

## Summary - The errors of an AI call come in three groups: **transient** (429, 500/503, timeout — retry helps), **permanent** (400, 401, 403, 404 — retry doesn't help) and **content** errors (a cut-off answer, bad JSON, a tool error — we check them in code). - A proper **retry**: exponential **backoff**, **jitter**, respecting `Retry-After`, a **timeout** per attempt and a **circuit breaker** on many failures. - **`AddStandardResilienceHandler`** (`Microsoft.Extensions.Http.Resilience`) adds this to an HttpClient. For an LLM we raise the timeouts. We give Google.GenAI our HttpClient (`ClientOptions.HttpClientFactory`) and turn off its own retry: retry in **one** place. - **`FallbackChatClient`** — a `DelegatingChatClient` that calls a fallback model on a transient error. It's the innermost layer of the pipeline. - Tokens **in the database**: `TokenCounterChatClient` writes every call to `AiUsage` (`IServiceScopeFactory`, because the pipeline is a Singleton). `ReasoningTokenCount` is added to the output. ### Next lecture In lecture 7 we said: only what's needed goes into the context.
