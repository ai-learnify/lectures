## Lecture 10: pgvector and EF Core In lecture 9 we wrote a semantic search for the menu, but the vectors were kept in memory: they disappeared when the app restarted, and the search compared every dish one by one. Today we move the vectors to **PostgreSQL**. For this PostgreSQL has an extension, **pgvector**: a new column type `vector` and distance operators. We store the vectors with EF Core, do the search in SQL, and with an **HNSW** index we make the search fast on large data too.

### The problem: vectors in memory In lecture 9 the vectors were kept in the `MenuIndex` Singleton. This has three problems: 1. **It disappears on restart.** On every deploy the whole menu has to be sent to the embedding model again — money and time. 2. **We compare everything one by one.** On 200 dishes this is milliseconds. On a million documents every question takes seconds, and every vector has to fit in memory. 3. **Two places, one piece of data.** The dish is in the database, its vector is in memory. If the description changes, the vector stays old, and nobody notices. A **vector database** stores vectors and quickly finds the ones closest to a given vector. There are dedicated vector databases (Qdrant, Pinecone, Weaviate, Milvus), but we already have PostgreSQL. Its extension **pgvector** adds a vector column to an ordinary table: the dish and its vector on one row, in one transaction, with one backup. **In Docker** the change is one line: instead of the PostgreSQL image we take the image of the same version that already has pgvector installed: ```yaml docker-compose.yml services: db: image: pgvector/pgvector:pg17 # before: postgres:17 — keep the same version! ``` ```warn The version (`pg17`, `pg16`…) must match your old image. An image of a different major version can't read the old volume's data. ``` ```terms Vector database — a database that stores vectors and quickly finds the ones closest to each other pgvector — a PostgreSQL extension: the vector type, distance operators and vector indexes ```

### pgvector: vector ტიპი და მანძილის ოპერატორები pgvector PostgreSQL-ს ორ რამეს უმატებს: **1. სვეტის ტიპი `vector(n)`** — n რიცხვის (`float4`) მასივი. ჩვენი ვექტორი 768 რიცხვია, ამიტომ `vector(768)`. ზომა სვეტშივე იწერება: 3072-იან ვექტორს ბაზა არ ჩაწერს — შეცდომას დააბრუნებს. ეს კარგია: ლექცია 9-ის „ერთი მოდელი, ერთი რუკა“ ბაზის დონეზე მოწმდება. ```sql CREATE EXTENSION IF NOT EXISTS vector; ALTER TABLE "Products" ADD COLUMN "Embedding" vector(768); ``` **2. მანძილის ოპერატორები:** | ოპერატორი | რას ზომავს | როდის | |---|---|---| | `<=>` | **cosine distance** = 1 − cosine similarity | ტექსტის embedding-ები — ჩვენი | | `<->` | L2 (ევკლიდური) — „სწორი ხაზით“ მანძილი | ნორმალიზებულ ვექტორებზე იგივე რიგს იძლევა | | `<#>` | უარყოფითი dot product | ნორმალიზებულ ვექტორებზე ყველაზე სწრაფი | **ყურადღება: distance, არა similarity.** ლექცია 9-ში ვზომავდით **მსგავსებას** (1 — ძალიან მსგავსი). pgvector ზომავს **მანძილს** (0 — ერთი და იგივე). კავშირი მარტივია: `distance = 1 − similarity`. score 0.71 → distance 0.29. ამიტომ ძებნაში `ORDER BY distance` **ზრდადობით** — პატარა მანძილი პირველია. **ძებნა SQL-ში** — უბრალოდ დალაგება მანძილით და პირველი სამი: ```sql SELECT "Name", "Embedding" <=> @q AS distance FROM "Products" ORDER BY distance LIMIT 3; ``` `@q` — შეკითხვის ვექტორი, რომელსაც C#-ში ვითვლით (ლექცია 9-ის `EmbeddingText.Query`) და პარამეტრად ვაგზავნით. ```terms vector(n) — pgvector-ის სვეტის ტიპი: n რიცხვის ვექტორი Cosine distance — 1 − cosine similarity; 0 — ერთი მიმართულება. pgvector-ში <=> L2 distance — ევკლიდური მანძილი, „სწორი ხაზით“. pgvector-ში <-> ```
### pgvector: the vector type and the distance operators pgvector adds two things to PostgreSQL: **1. The column type `vector(n)`** — an array of n numbers (`float4`). Our vector is 768 numbers, so `vector(768)`. The size is written in the column itself: the database won't store a 3072-long vector — it returns an error. That's good: lecture 9's “one model, one map” is checked at the database level. ```sql CREATE EXTENSION IF NOT EXISTS vector; ALTER TABLE "Products" ADD COLUMN "Embedding" vector(768); ``` **2. The distance operators:** | Operator | What it measures | When | |---|---|---| | `<=>` | **cosine distance** = 1 − cosine similarity | text embeddings — ours | | `<->` | L2 (Euclidean) — the “straight line” distance | gives the same order on normalized vectors | | `<#>` | negative dot product | the fastest on normalized vectors | **Careful: distance, not similarity.** In lecture 9 we measured **similarity** (1 — very similar). pgvector measures **distance** (0 — the same thing). The link is simple: `distance = 1 − similarity`. Score 0.71 → distance 0.29. So in the search `ORDER BY distance` is **ascending** — the smallest distance comes first. **A search in SQL** — just sorting by distance and taking the first three: ```sql SELECT "Name", "Embedding" <=> @q AS distance FROM "Products" ORDER BY distance LIMIT 3; ``` `@q` — the question's vector, which we calculate in C# (lecture 9's `EmbeddingText.Query`) and send as a parameter. ```terms vector(n) — pgvector's column type: a vector of n numbers Cosine distance — 1 − cosine similarity; 0 — the same direction. In pgvector: <=> L2 distance — the Euclidean, “straight line” distance. In pgvector: <-> ```

⚡ ზუსტი vs მიახლოებითი ძებნა

HNSW: სართულიანი გზა უახლოესამდე

📖
ინდექსის გარეშეყველა ხაზი, ყველა ვექტორი — ზუსტი, მაგრამ O(n)
🛗
HNSW = გრაფი სართულებითზემოთ — ცოტა წერტილი, შორი ნახტომები. ქვემოთ — ყველა, მოკლე ნაბიჯები
🎯
მიახლოებითი (ANN)ძალიან სწრაფი, მაგრამ იშვიათად შეიძლება გამოტოვოს ერთი სწორი
🙋 რესტორნის მენიუში 1% შეცდომა მისაღებია? ბანკის ტრანზაქციებში?
💡 რესტორანში — კი: მეორე საუკეთესო კერძიც კარგი პასუხია. ბანკში — არა: იქ ANN არ გამოიყენება
### ზუსტი vs მიახლოებითი ძებნა: HNSW **ინდექსის გარეშე** ბაზა `ORDER BY distance`-ზე ყველა ხაზს კითხულობს და ყველა ვექტორთან მანძილს ითვლის (sequential scan). შედეგი **ზუსტია**, მაგრამ დრო ხაზების რაოდენობის პროპორციულია: O(n). B-tree ინდექსი აქ ვერ შველის — ის „ტოლობას“ და „მეტ/ნაკლებს“ ეძებს, არა „ყველაზე ახლოს მყოფს“ 768-განზომილებიან სივრცეში. **ვექტორული ინდექსი** ამიტომ **მიახლოებითია** — ANN (approximate nearest neighbor): ძალიან სწრაფად პოულობს „თითქმის ყოველთვის“ სწორ მეზობლებს. pgvector-ს ორი ასეთი ინდექსი აქვს: **HNSW** და **IVFFlat**. ჩვენ HNSW-ს ვიყენებთ — უფრო ზუსტი და სწრაფია, და ცარიელ ცხრილზეც შეიძლება შეიქმნას. **HNSW (Hierarchical Navigable Small World) — „სართულიანი გრაფი“:** - ყველა ვექტორი **სართულ 0-ზეა**, დაკავშირებული უახლოეს მეზობლებთან (გრაფი). - ზედა სართულებზე **ცოტა** ვექტორია, შორი კავშირებით — „ექსპრეს ხაზი“. - ძებნა იწყება ზემოდან: დიდი ნახტომებით სწორ „უბანში“ მივდივართ, მერე ქვედა სართულზე ვეშვებით და მოკლე ნაბიჯებით უახლოესს ვპოულობთ. ანალოგია: ქალაქის მისამართის ძებნა — ჯერ მაგისტრალი (სწორი რაიონი), მერე ქუჩა, მერე სახლი. ყველა სახლის შემოვლა არ გვჭირდება. **ფასი — recall.** ANN-მა იშვიათად შეიძლება ერთი სწორი მეზობელი გამოტოვოს. **recall** — რა წილი იპოვა ზუსტი ძებნის შედეგებიდან (მაგ. 0.98 = 100-დან 98). ძებნის ხარისხს `hnsw.ef_search` პარამეტრი არეგულირებს (ნაგულისხმევად 40): მეტი — ზუსტი, მაგრამ ნელი. ტექსტის ძებნაში და RAG-ში ეს ნორმალურია: „მეორე საუკეთესო“ კერძიც კარგი პასუხია. სადაც ზუსტი შედეგია აუცილებელი (ფინანსები, აუდიტი), ANN არ გამოიყენება. ```terms Sequential scan — ცხრილის ყველა ხაზის წაკითხვა; ზუსტია, მაგრამ O(n) ANN (approximate nearest neighbor) — მიახლოებითი უახლოესი მეზობლის ძებნა: სწრაფი, იშვიათად გამოტოვებს HNSW — მრავალსართულიანი გრაფის ინდექსი ვექტორებისთვის; pgvector-ის ძირითადი ინდექსი Recall — რა წილი იპოვა ინდექსმა ზუსტი ძებნის შედეგებიდან ```
### Exact vs approximate search: HNSW **Without an index**, for `ORDER BY distance` the database reads every row and calculates the distance to every vector (a sequential scan). The result is **exact**, but the time is proportional to the number of rows: O(n). A B-tree index doesn't help here — it looks for “equal” and “greater/less”, not for “the closest one” in a 768-dimensional space. That's why a **vector index** is **approximate** — ANN (approximate nearest neighbor): it finds the “almost always” correct neighbours very fast. pgvector has two such indexes: **HNSW** and **IVFFlat**. We use HNSW — it's more accurate and faster, and it can be created on an empty table too. **HNSW (Hierarchical Navigable Small World) — a “graph with floors”:** - Every vector is on **floor 0**, linked to its closest neighbours (a graph). - The upper floors hold **few** vectors, with long links — an “express line”. - The search starts at the top: with big jumps we get to the right “neighbourhood”, then go down a floor and find the closest one with short steps. An analogy: finding an address in a city — first the highway (the right district), then the street, then the house. We don't need to walk past every house. **The price — recall.** ANN can occasionally miss one correct neighbour. **Recall** — what share of the exact search results it found (e.g. 0.98 = 98 out of 100). The search quality is controlled by the `hnsw.ef_search` parameter (40 by default): more — more accurate, but slower. In text search and RAG this is normal: the “second best” dish is a good answer too. Where an exact result is required (finance, auditing), ANN isn't used. ```terms Sequential scan — reading every row of a table; exact, but O(n) ANN (approximate nearest neighbor) — an approximate nearest-neighbour search: fast, occasionally misses HNSW — a multi-floor graph index for vectors; pgvector's main index Recall — what share of the exact search results the index found ```

### The HNSW index with EF Core and `EXPLAIN` The index is written in `OnModelCreating` and created by a migration: ```csharp Data/AppDbContext.cs · OnModelCreating modelBuilder.Entity() .HasIndex(p => p.Embedding) .HasMethod("hnsw") // the index type .HasOperators("vector_cosine_ops"); // for which distance ``` ```bash dotnet ef migrations add ProductEmbeddingIndex dotnet ef database update ``` In SQL this is: `CREATE INDEX ... ON "Products" USING hnsw ("Embedding" vector_cosine_ops);` **The most common mistake: the operator.** An index is created for one specific distance: | Index operator | Search function (EF) | SQL | |---|---|---| | `vector_cosine_ops` | `CosineDistance` | `<=>` | | `vector_l2_ops` | `L2Distance` | `<->` | | `vector_ip_ops` | `MaxInnerProduct` | `<#>` | If the index uses `vector_l2_ops` and the search uses `CosineDistance` — the index is **not** used, and there's no error either: it's just slow. **How to check — `EXPLAIN`.** In psql or pgAdmin: ```sql SET enable_seqscan = off; -- only for the test: we forbid the planner a seq scan EXPLAIN SELECT "Name" FROM "Products" ORDER BY "Embedding" <=> (SELECT "Embedding" FROM "Products" WHERE "Name" = 'Lobio in a clay pot') LIMIT 3; -- Limit -> Index Scan using "IX_Products_Embedding" on "Products" ``` **Why doesn't it use it on 20 dishes?** PostgreSQL's planner calculates what's cheaper. Reading 20 rows is cheaper than walking through an index — so it picks a `Seq Scan`. That's the correct behaviour. The index starts to pay off on thousands of rows and more. `enable_seqscan = off` is only for seeing that the index can be used — it isn't turned on in production. ```terms EXPLAIN — a PostgreSQL command that shows how the database will run a query (seq scan or index) vector_cosine_ops — the HNSW index operator class for cosine distance ```

### A decision: EF Core directly or `Microsoft.Extensions.VectorData` In lecture 9 we said: “in lecture 10 we'll see whether we need `Microsoft.Extensions.VectorData`”. The answer: | | EF Core + pgvector | `Microsoft.Extensions.VectorData` | |---|---|---| | What it is | a vector column in an ordinary table | an abstraction over vector stores (like `IChatClient` for models) | | Where it's stored | in the same table, next to the dish | in a separate “collection”: PostgreSQL, Qdrant, Azure AI Search, in-memory… | | Filters, JOINs, transactions | ordinary SQL / LINQ | with the store's capabilities | | When | the database is PostgreSQL and stays that way | the vectors are in a separate store, or the store may change | **Our choice — EF Core directly.** The reason: the data is already in PostgreSQL. The vector stands next to the dish, and “without meat, up to 20 lari” is one query: `WHERE "Price" <= 20 ORDER BY "Embedding" <=> @q`. One `AppDbContext`, one migration, one transaction. If the vectors were in a separate database (Qdrant), the same question would need a “join” between two systems: either we copy the price into Qdrant too, or two queries and merging the results in C#. Exactly in a case like that VectorData gives one API for every store. The idea of `Microsoft.Extensions.VectorData` (to try in the ⭐): ```csharp public class MenuRecord { [VectorStoreKey] public int Id { get; set; } [VectorStoreData] public string Name { get; set; } = ""; [VectorStoreVector(768, DistanceFunction = DistanceFunction.CosineDistance)] public ReadOnlyMemory Embedding { get; set; } } // collection.SearchAsync(queryVector, top: 3) — the same way on any store ``` ```terms Microsoft.Extensions.VectorData — an abstraction over vector stores in .NET: one API for PostgreSQL, Qdrant, Azure AI Search and others Vector store — the place where vectors are stored and searched ```

Embedding` (`vector(768)`) და `EmbeddingModel`. - **ინდექსაცია** მხოლოდ გადასათვლელს ითვლის (`Embedding == null` ან სხვა მოდელი), `Chunk(100)`-ით. **ძებნა:** `OrderBy(p => p.Embedding!.CosineDistance(query)).Take(3)` — SQL-ში `ORDER BY <=> LIMIT 3`. - **HNSW** — მიახლოებითი (ANN) ინდექსი: სართულიანი გრაფი, ძალიან სწრაფი, recall ~100%-ზე ოდნავ ნაკლები. ინდექსის ოპერატორი (`vector_cosine_ops`) ძებნის ფუნქციას უნდა ემთხვეოდეს. მცირე ცხრილზე პლანერი seq scan-ს ირჩევს — ეს ნორმალურია. - **EF Core vs VectorData:** მონაცემი PostgreSQL-შია — EF Core პირდაპირ. ვექტორები ცალკე store-შია ან შეიძლება შეიცვალოს — `Microsoft.Extensions.VectorData`. ### შემდეგ ლექციაზე მენიუს ძებნა მუშაობს. მაგრამ "How do I cancel a booking?" ან "I'm allergic to nuts, what can I eat?" — ამის პასუხი მენიუში კი არა, რესტორნის **დოკუმენტებშია** (PDF-ები). ლექცია 11-ზე: **Simple RAG** — PDF-ს ნაწილებად ვჭრით, ვექტორებს ბაზაში ვინახავთ და მოდელი პასუხობს დოკუმენტიდან, წყაროს მითითებით.
## Summary - **pgvector** — a PostgreSQL extension: the column type `vector(768)` and distance operators. In Docker, `pgvector/pgvector` of the same version instead of `postgres`. - **`<=>` — cosine distance** = 1 − similarity. A small distance = close, so `ORDER BY distance` is ascending. `<->` — L2, `<#>` — negative dot product. - **EF Core:** `Pgvector.EntityFrameworkCore`, `UseNpgsql(..., o => o.UseVector())`, `HasPostgresExtension("vector")`, `Vector? Embedding` (`vector(768)`) and `EmbeddingModel`. - **Indexing** calculates only what needs recalculating (`Embedding == null` or another model), with `Chunk(100)`. **Search:** `OrderBy(p => p.Embedding!.CosineDistance(query)).Take(3)` — in SQL `ORDER BY <=> LIMIT 3`. - **HNSW** — an approximate (ANN) index: a graph with floors, very fast, recall slightly below 100%. The index operator (`vector_cosine_ops`) must match the search function. On a small table the planner picks a seq scan — that's normal. - **EF Core vs VectorData:** the data is in PostgreSQL — EF Core directly.
