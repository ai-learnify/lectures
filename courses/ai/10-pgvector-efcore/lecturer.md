## 🎯 მიმოხილვა

ლექცია ლექცია 9-ის ბოლო კითხვით იწყება: „აპი გადაიტვირთა — ვექტორებს რა დაემართა? მილიონ დოკუმენტზე?“ სამი ნაწილია.

**ნაწილი 1 — ვექტორი ბაზაში (თეორია + SQL).** მეხსიერების სამი პრობლემა. ვექტორული ბაზა vs PostgreSQL + pgvector. Docker image-ის შეცვლა. `vector(768)`, ოპერატორები, **distance = 1 − similarity**.

**ნაწილი 3 — ინდექსი.** ზუსტი vs ANN, HNSW „სართულები“, recall. ინდექსი EF Core-ით, ოპერატორის ხაფანგი, `EXPLAIN` და „რატომ არ იყენებს 20 კერძზე“. გადაწყვეტილება: EF Core vs `Microsoft.Extensions.VectorData` (ლექცია 9-ის დაპირება).

**ეს ლექცია RAG-ის საცავია:** ლექცია 11-ში იგივე ცხრილი-სვეტი-ძებნა დოკუმენტის ნაწილებზე (`DocumentChunk`) გამეორდება, 12-ში — ფილტრი და full-text იმავე ბაზაში. ამიტომ მთავარია, სტუდენტმა `CosineDistance`-იანი LINQ თავისით დაწეროს.

### 📖 ისწავლე: ვექტორული ბაზები და pgvector

#### რატომ არის ვექტორული ძებნა ცალკე პრობლემა

ჩვეულებრივი ინდექსი (B-tree) მონაცემს **ალაგებს** ერთი მნიშვნელობით: ფასი, სახელი, თარიღი. „ფასი 20-მდე“ — ინდექსში ერთი ადგილიდან ბოლომდე. „ყველაზე ახლოს 768-განზომილებიან სივრცეში“ ერთ რიგად ვერ დალაგდება: ორი ვექტორი, რომლებიც ერთმანეთთან ახლოსაა, შეიძლება რომელიმე ერთი რიცხვით შორს იყოს. ამიტომ ვექტორებს სხვა ტიპის ინდექსი სჭირდება — გრაფი (HNSW) ან კლასტერები (IVFFlat), — და ის **მიახლოებითია** (ნაწილი 3).

#### ვექტორული ბაზების ბაზარი (სტუდენტები ეკითხებიან)

| ტიპი | მაგალითები | როდის |
|---|---|---|
| ცალკე ვექტორული ბაზა | Qdrant, Pinecone (cloud), Weaviate, Milvus | ასეულობით მილიონი ვექტორი, სპეციალური ფუნქციები, ცალკე გუნდი |
| გაფართოება არსებულ ბაზაში | **pgvector** (PostgreSQL), SQL Server 2025 `VECTOR`, MongoDB Atlas Vector Search | მონაცემი უკვე ამ ბაზაშია — ვექტორი გვერდით |
| ძებნის სისტემა | Elasticsearch / OpenSearch, Azure AI Search | full-text + ვექტორი ერთად, დიდი ძებნის სისტემები |

pgvector რეალურ production-ში ფართოდ გამოიყენება (Supabase, Neon, AWS RDS/Aurora, Azure Database for PostgreSQL — ყველა სთავაზობს). მილიონობით ვექტორამდე კომფორტულად მუშაობს.

#### pgvector-ის ტიპები

- **`vector(n)`** — `float4` (4 ბაიტი) × n. 768 → ~3 KB ხაზზე. შენახვა 16 000 განზომილებამდე, **HNSW ინდექსი — 2 000-მდე** (ამიტომ ავირჩიეთ 768 ლექცია 9-ში).
- **`halfvec(n)`** — 2 ბაიტი რიცხვზე, ინდექსი 4 000-მდე. ზომა ორჯერ მცირდება, ხარისხი თითქმის იგივე. 3072-იანი ვექტორისთვის — ერთადერთი გზა ინდექსამდე.
- **`bit(n)`, `sparsevec`** — binary quantization და sparse ვექტორები. ჩვენთვის არ გვჭირდება.

#### ოპერატორები

| ოპერატორი | ფუნქცია | EF Core | ინდექსის ოპერატორი |
|---|---|---|---|
| `<=>` | cosine distance (1 − cos) | `CosineDistance` | `vector_cosine_ops` |
| `<->` | L2 (ევკლიდური) | `L2Distance` | `vector_l2_ops` |
| `<#>` | უარყოფითი inner product | `MaxInnerProduct` | `vector_ip_ops` |
| `<+>` | L1 (მანჰეტენი) | `L1Distance` | `vector_l1_ops` |

`<#>` **უარყოფითს** აბრუნებს, რადგან PostgreSQL ინდექსით მხოლოდ ზრდადობით ალაგებს — ასე „უდიდესი ნამრავლი“ პირველი ხდება. ტექსტისთვის `<=>` ყველაზე უსაფრთხოა: ლექცია 9-ში ვთქვით, რომ 768-იანი ვექტორები შეიძლება ნორმალიზებული არ იყოს, cosine კი სიგრძეს არ უყურებს.

#### Docker და ვერსიები

`pgvector/pgvector:pg17` — ოფიციალური PostgreSQL 17 image + pgvector. Tag-ები ყველა მხარდაჭერილი ვერსიისთვისაა (`pg16`, `pg17`, `pg18`). **მთავარი ვერსიის შეცვლა volume-ს ვერ კითხულობს** (PostgreSQL-ის მონაცემის ფორმატი ვერსიაზეა მიბმული) — ამიტომ ზუსტად იგივე ნომერი.

### 📖 ისწავლე: Pgvector.EntityFrameworkCore

#### რეგისტრაცია და ტიპები

- **`Pgvector.EntityFrameworkCore`** (NuGet) — დამოკიდებულია `Pgvector`-სა და Npgsql-ის EF provider-ზე. `Pgvector` namespace-ში — `Vector`, `HalfVector`, `SparseVector`; `Pgvector.EntityFrameworkCore`-ში — `CosineDistance`, `L2Distance`, `MaxInnerProduct`, `L1Distance` extension-ები.
- **`npgsql.UseVector()`** — Npgsql-ს ტიპის mapping-ს ურთავს (`Vector` ↔ `vector`). მის გარეშე: „The property ... could not be mapped“.
- **`HasPostgresExtension("vector")`** — migration-ში `CREATE EXTENSION IF NOT EXISTS vector;`. გაფართოების შექმნას superuser-ის ან ბაზის მფლობელის უფლება სჭირდება — Docker-ის `postgres` მომხმარებელს აქვს; managed ბაზებზე (Azure, AWS) ზოგჯერ ჯერ პანელიდან ირთვება.
- **`[Column(TypeName = "vector(768)")]`** — ან Fluent: `.Property(p => p.Embedding).HasColumnType("vector(768)")`.

#### `Vector` ტიპი

`new Vector(float[])` ან `new Vector(ReadOnlyMemory<float>)`; `.ToArray()` / `.Memory` უკან. Immutable-ია.

#### ინდექსაციის ლოგიკა

`Where(p => p.Embedding == null || p.EmbeddingModel != model)` — ორი შემთხვევა: ახალი/შეცვლილი (null) და მოდელის შეცვლა. ეს რეალური სისტემების მარტივი ვერსიაა: production-ში ხშირად ინახავენ **content hash**-ს (აღწერის ჰეში) — ვექტორი მხოლოდ მაშინ ითვლება, თუ ტექსტი შეიცვალა, და `null`-ის დაყენება აღარ გვჭირდება. ⭐ იდეა ძლიერი სტუდენტისთვის.

`Chunk(100)` + ერთი `SaveChangesAsync` ბოლოს: 20 კერძზე კარგია. ათასობით ჩანაწერზე — `SaveChangesAsync` ყოველი batch-ის შემდეგ (თორემ შეცდომა ბოლოს ყველაფერს დაკარგავს და change tracker გაიზრდება).

#### ძებნის SQL

```sql
SELECT p."Name", p."Embedding" <=> @query AS "Distance"
FROM "Products" AS p
WHERE p."Embedding" IS NOT NULL
ORDER BY p."Embedding" <=> @query
LIMIT @p;
```

`Select`-ში და `OrderBy`-ში `CosineDistance` ორჯერ წერია — SQL-შიც ორჯერ ითვლება, მაგრამ PostgreSQL-ისთვის ეს უმნიშვნელოა, და ინდექსისთვის `ORDER BY`-ში სწორედ ეს გამოსახულება უნდა იყოს. ზღვარს C#-ში ვადებთ (3 ხაზზე) — ასე ინდექსი გარანტირებულად გამოიყენება. SQL-ში `WHERE distance < x`-ით ფილტრიც შეიძლება, მაგრამ `ORDER BY ... LIMIT`-თან ერთად (pgvector-ის README: „combine with ORDER BY and LIMIT to use an index“).
